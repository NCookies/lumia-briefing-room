## 1. 목적

이터널 리턴 플레이의 **스팀 자동 녹화본에서 교전 장면만 자동으로 잘라내어 보관**한다.

주 용도는 두 가지다.

1. **복기 / 피드백** — 내 교전을 다시 보며 판단과 포지셔닝을 점검한다.
2. **감상** — 잘 나온 교전을 다시 보며 즐긴다.
3. **잘하는 사람의 교전 모으기 / 라벨 자료** — 스트리머 방송 다시보기 영상에서도 같은 방식으로 교전을 뽑아 별도 탭에서 본다(§2.14). 사용자가 찍는 교전/사냥 라벨이 PvP 판별 튜닝의 정답이 되므로 표본을 늘리는 수단이기도 하다.

개인용 도구이며, 공유나 편집 기능은 목표가 아니다.

### ★ 추출 대상 — 사람과의 교전 전부

**v1의 목표는 내가 참여한 모든 "사람과의" 교전을 빠짐없이 추출하는 것이다.** 이기든 지든, 킬을 냈든 못 냈든 전부 뽑는다.

#### ⚠ 배지만으로는 안 된다 — 실사용으로 드러난 사실

원래 SPEC은 §2.7의 초상화 배지(교전 중 표시)를 주 신호로 삼아 "교전 그 자체가 신호다"라고 적었다. **실제로 20매치를 돌려보니 틀렸다.**

이터널 리턴은 크레딧과 경험치를 벌기 위해 섬을 돌며 **야생동물을 사냥하는 시간이 대부분**인데, **야생동물과 싸울 때도 사람과 싸울 때와 똑같은 교전 배지가 뜬다.** 배지에는 둘을 가르는 차이가 없다(실측 확인). 그래서 뽑힌 클립의 대부분이 사냥 장면이었다.

**배지는 "전투 상태"일 뿐 "교전"이 아니다.** 배지는 여전히 필요하다 — 무슨 일이 일어나는 시점을 찍어주는 앵커다. 다만 그것만으로 클립을 만들면 안 된다. **PvP인지 PvE인지를 가르는 별도 증거가 필요하다** (§2.12).

#### 필터를 어디에 둘 것인가 — 생성이 아니라 열람에

**오판의 대가가 양쪽이 다르다.**

- **잘못 버리면 영구 손실이다.** 원본은 링버퍼가 2시간이면 지운다(§2.6). 생성 단계에서 PvE로 오판해 버린 교전은 되찾을 방법이 없다.
- **잘못 남기면 디스크만 쓴다.** 그건 보관 정책(§7.6)이 알아서 정리한다.

그래서 **초기 기본값은 느슨하게 생성하고, 엄격한 판단은 열람 단계에서 한다.** 점수를 메타데이터에 남겨 UI에서 정렬·필터하면, 생각이 바뀌어도 재추출이 필요 없다. 라벨이 쌓여 가중치가 검증된 뒤에 생성 단계 임계를 올린다.

#### ★ 이 원칙은 점수 임계뿐 아니라 **모든 제외 규칙**에 적용된다 (2026-09-21 추가)

`minPvpScore` 만 0으로 두면 되는 줄 알았는데 아니었다. **구간 경계를 정하는 규칙도 결국 필터다** — 어떤 프레임을 "교전 아님"으로 판정하면 그 구간은 클립이 되지 않고, 링버퍼가 원본을 지우면 끝이다.

실제로 그렇게 잃었다. "팀원 전투 링만 있고 내 배지가 한 번도 안 켜진 구간은 버린다"는 규칙(사용자가 지적한 *이미 끝난 교전* 클립을 막으려던 것)을 라벨 57개에 대고 재보니:

| 그 규칙이 버리는 클립 | 사용자 라벨 |
|---|---|
| `122301_04` 6일차 낮 학교 · `130245_06` 3일차 낮 경찰서 · `131701_01` · `134809_07` 4일차 낮 연구소 | **전부 교전** |
| — | 사냥 0개 |

**막으려던 오탐은 1개(라벨 없음), 같이 버린 진짜 교전은 4개다.** 내가 원거리에서 지켜보거나 도망치는 동안 배지가 안 켜지는 교전이 그만큼 많다(§2.7의 배지 한계가 그대로 드러난다).

그래서 규칙으로 정한다.

1. **교전을 "아님"으로 판정하는 새 규칙은 라벨된 교전을 몇 개 버리는지부터 잰다.** 1개라도 버리면 그 규칙은 채택하지 않는다.
2. 버리는 대신 **점수를 깎거나 신호로 기록한다.** 열람 단계에서 사용자가 정렬·필터로 판단한다.
3. 예외는 **그 상황에서 교전이 물리적으로 불가능할 때**뿐이다 (예: 본게임 시작 전 대기방 — §2.10 `브리핑 룸`). 이 경우에도 오독으로 진짜 교전이 잘리지 않는지 실측한다.

> "교전이 아닌 장면 몇 개를 빼겠다고 핵심인 교전 장면을 빠뜨리면 안 된다" — 사용자, 2026-09-21. 이 프로젝트의 목적 함수는 **정확도가 아니라 재현율**이다.

### 교전에 붙이는 태그

추출은 전부 하되, **각 교전에 태그를 달아 나중에 걸러볼 수 있게 한다.**

| 태그 | 판정 |
|---|---|
| `kill` | 교전 중 `K` 증가 |
| `assist` | 교전 중 `A` 증가 |
| `death` | 교전 중 내가 사망 (§2.7 회색 검출) |
| `teammate_death` | 교전 앞뒤 8초 안에 팀원이 죽음 (팀 슬롯 체력바 주황) — §2.12 |
| `team_wipe` | 교전 중 전멸 배너(BREAK/TERMINATE/CLUTCH/CHECKMATE) — §2.12 (**미구현, 후순위**) |
| `no_result` | 위 다섯 다 없음 — 전투는 했으나 성과도 사망도 없음 |

`kill` 과 `death` 는 **동시에 붙을 수 있다** (킬 내고 죽는 경우). 태그는 서로 배타적이지 않다.

⚠ `no_result` 는 이제 두 가지가 섞인 자리다 — **야생동물 사냥**과 **아무도 안 죽고 끝난 진짜 교전**. 이 둘을 가르는 것이 §2.12의 과제이고, 결과는 태그가 아니라 **PvP 점수**(`pvpScore`)로 남긴다.

### ★ 일단 전부 만들고, 정리는 나중에

**기본 동작은 "모든 교전을 클립으로 만든다"이다.** 거르는 건 그다음 문제다.

| 단계 | 동작 |
|---|---|
| 검출 | **항상 전부.** 어떤 설정이든 교전은 빠짐없이 찾는다 |
| 생성 | **기본은 전부 클립으로.** 필터를 걸면 그때만 줄어든다 (§7) |
| 정리 | 사용자가 UI에서 **삭제 · 복구 · 원하는 경로로 내보내기** |

정리 단계가 이 설계의 핵심이다.

- **삭제는 즉시 지우지 않는다.** 휴지통으로 옮기고 유예 기간(기본 30일) 뒤에 실제 삭제한다. **복구가 항상 가능해야 한다.**
- **고정(pin)** 한 클립은 자동 정리 대상에서 빠진다.
- **내보내기**는 사용자가 지정한 경로로 복사 또는 이동한다. 메타데이터 JSON과 썸네일을 같이 보낼지 고를 수 있다.
- 태그가 메타데이터에 남으므로 **나중에 생각이 바뀌어도 재추출이 필요 없다.** UI에서 다시 필터링하면 된다.

> 원래 목표였던 "팟지(하이라이트 자동 선별)"는 이 파이프라인 위에 스코어링 레이어를 얹는 형태로 v3 이후 검토한다. 태그가 이미 그 밑그림이다.

## 2. 사전 조사 결과 (확정 사실)

구현 전에 확인된 제약들. 이 결론을 뒤집지 말 것. 측정 절차는 [research.md](research.md) 참조.

### 2.0 게임 구조 — 검출 설계의 전제

- **3인 1팀 배틀로얄.**
- 나나 팀원이 죽어도 **조건을 만족하면 다시 살아날 수 있다.**
  - **2일차 밤까지**는 시간만 지나면 **무료 부활**.
  - **3일차 낮부터**는 **크레딧**(인게임 재화)을 써야 부활한다.
- **3명이 전부 죽어야 게임이 끝난다.** 내가 죽어도 팀원이 살아있으면 매치는 계속된다.

이 부활 규칙은 **사망의 무게가 게임 시점에 따라 다르다**는 뜻이다. 2일차 밤까지의 죽음은 가볍고, 그 이후는 팀에 실제 비용을 지운다. 복기 가치도 다르다.

→ 클립 필터에 **게임 시점(일차·낮/밤)** 기준을 넣는다 (§7). 페이즈에 순번을 매겨 다루면 깔끔하다.

```
phaseIndex = (일차 - 1) × 2 + (낮이면 0, 밤이면 1)
  1일차 낮=0   1일차 밤=1   2일차 낮=2   2일차 밤=3   3일차 낮=4 ...

무료 부활 구간 = phaseIndex ≤ 3
크레딧 구간    = phaseIndex ≥ 4
```

여기서 나오는 중요한 결론 둘:

1. **`K` 는 항상 내 값이다.** 팀원 것으로 바뀌지 않는다. "관전 중에 남의 카운터를 내 것으로 오판한다"는 걱정은 **존재하지 않는다.**
2. 내가 죽고 팀원이 살아있는 상황이 곧 예전 SPEC이 말한 "관전"이었다. 별도의 리플레이 관전이 아니다. 그리고 **본 게임 플레이 화면과 관전 화면은 UI 자체가 다르다.**

→ 사망 구간을 다루는 이유가 바뀐다. **카운터 오판 방지가 아니라, UI가 다른 화면을 판독 대상에서 빼기 위해서다** (§3 사망·관전 구간 처리).

### 2.1 ★ 공식 API는 쓰지 않는다

> **재확인 (2026-09-21)**: 순위표 스크롤로 팀원이 안 보이는 경우 등에 게임ID→공식 API 조회를 검토했으나, 배포·키 관리 부담 때문에 **계속 쓰지 않기로 했다.** 화면 인식만으로 가고, 못 읽으면 비워 둔다.

BSER 오픈 API(`developer.eternalreturn.io`)는 전부 매치 단위 집계값이라 "몇 분 몇 초에 킬"이 없다. 그에 더해 **지원이 열악해 의존하지 않기로 했다.**

**API 없이 전부 대체된다.**

| 원래 API로 하려던 것 | 대체 수단 | 상태 |
|---|---|---|
| 매치 시작/종료 감지 | `Player.log` 매치 경계 이벤트 (§2.3) | ✅ 확정 |
| `playerKill` = 검출기 정답지 | **매치 마지막 인게임 프레임의 `K` 최종값** | ✅ 자체 정답지 |
| `playTime` = 관전 구간 제외 | 사망 회색 오버레이 검출 (§2.7) | ✅ 확정 |
| 낮/밤·일차 | **HUD 상단** 판독 (§2.10). 로그는 누락이 심해 못 쓴다 | ✅ 확정 |
| `gameRank` | 결과 화면 판독 (`5/8 실험 종료`) | ✅ 구현 (§2.13) |
| `characterNum` | 초상화 템플릿 매칭 (§2.10) | 구현 필요 |

**`K` 카운터가 자기 자신의 정답지다.** 매치 마지막 인게임 프레임의 `K` 값이 곧 그 매치의 총 킬 수이고, 검출기가 센 `K` 증가 횟수와 대조하면 외부 의존 없이 회귀 테스트가 된다. 네트워크도, 키 발급도, 레이트 리밋도 없다.

### 2.2 Steam 타임라인 마커는 쓸 수 없다 (재확인)

게임이 `ISteamTimeline`을 직접 호출해야 하는데 ER은 미지원. 외부 주입은 프로세스 인젝션이라 안티치트 문제로 선택지에서 제외.

`timelines\*.json`을 실제로 열어 확인했다. `entries[]`에 들어있는 것은 **`"type": "screenshot"` 뿐**이다. 킬/전투 마커는 없다.

### 2.3 ★ 클라이언트 킬 로그는 없다 — 대신 매치 경계가 있다 (확정)

`%USERPROFILE%\AppData\LocalLow\NimbleNeuron\Eternal Return\Player.log`

**킬 이벤트는 없다.** `grep -i kill` 이 잡는 32건은 전부 `Skill`의 부분일치고, 단어 경계로 검색하면 0건이다. `death`/`damage`/`combat`/`assist`/`respawn` 도 전부 0건.

**대신 매치 경계가 정확히, 실시간으로 남는다.** 이게 파이프라인의 트리거다.

라인 포맷:

```
[LEVEL][HOSTNAME][YYYY-MM-DD HH:mm:ss,SSS][thread][Class:Method:Line] message
```

| 이벤트 | 라인 |
|---|---|
| **매치 로딩 시작** | `[LoadingView:Show:194] [PROFILE TIME][LOADING][GAME]` |
| 서버 접속 | `[GameClient:Init:223] [GameClient] battleTokenKey: , host: <ip>, userId: <userNum>` |
| 게임 시작 | `[ClientService:StartGame:712] [StartGame] FrameUpdateRate: 0.01666667` |
| 페이즈 전이 | `[ClientService:OnUpdateGamePlayPhase:3473] OnUpdateGamePlayPhase : Briefing\|StartCountdown\|PlayGame, <a> <b>` |
| ~~낮/밤 전이~~ | `[WeatherDayNightMaterialColorControl:SetDayNight:139] ... input=Day\|Night` — ⚠ **누락이 심해 쓸 수 없다.** §2.10 |
| **로비 복귀 (매치 종료)** | `[LoadingView:Show:135] [PROFILE TIME][LOADING][LOBBY]` |

- 8경기 연속에서 `[LOADING][GAME]` ↔ `[LOADING][LOBBY]` 가 **완벽한 1:1 교대, 누락 0**. 직전 세션 로그도 11/11.
- 로그는 실시간 flush된다. tail 감시로 매치 종료 즉시 트리거 가능.
- `GameResultTeamPlayerSlot` 라인은 **프리메이드 팀원이 있을 때만** 찍힌다. 종료 마커로 쓰지 말 것.
- **시각은 로컬 타임존**이다. 녹화 폴더/mpd의 UTC와 다르다 (§2.5).

> **화면 기반 폴백**: 클라이언트가 튕기면 `[LOADING][LOBBY]` 가 안 찍힐 수 있다. 그 경우를 위해 화면 판독 폴백을 둔다 — 본게임 전에는 항상 캐릭터 선택창과 로딩창이, 종료 후에는 항상 결과표가 뜬다. 로그가 1차, 화면이 2차다.

### 2.4 ★ Steam 녹화본 포맷 (확정)

```
<BackgroundRecordPath>\video\bg_<appid>_<YYYYMMDD>_<HHMMSS>\     ← 시각은 UTC
    session.mpd
    init-stream0.m4s          892 B   ftyp + moov (영상 트랙 정의)
    init-stream1.m4s          765 B   ftyp + moov (음성 트랙 정의)
    chunk-stream0-NNNNN.m4s   ~8.9 MB 영상, moof/mdat 180쌍 = 프레임당 1프래그먼트
    chunk-stream1-NNNNN.m4s   ~75 KB  음성
    chunk-stream0-NNNNN.m4s.tmp       기록 중. 완료 시 rename
```

- 녹화 경로는 `Steam\userdata\<id>\config\localconfig.vdf` 의 `GameRecording.BackgroundRecordPath`. **계정이 여러 개일 수 있으니 `userdata` 아래를 전부 훑을 것.** 미설정이면 기본값 `userdata\<id>\gamerecordings`.
- 조각 번호는 **세션마다 1부터** 5자리 zero-pad.
- **세그먼트 길이는 정확히 3.000초.**
- 병합: `cat init-stream0.m4s chunk-stream0-*.m4s > out.mp4` — 그대로 ffmpeg로 디코딩된다.
- **init 없이 chunk만으로는 실패한다** (`could not find corresponding trex`). 트랙 정의가 init에만 있다.
- **★ 단일 chunk + init 만으로도 독립 디코딩된다.** 모든 세그먼트가 키프레임으로 시작하기 때문. 프레임 샘플링 비용이 여기서 결정된다 (§3).
- 녹화 진행 중에도 완료된 조각은 읽을 수 있다 (파일 잠금 없음). `.tmp` 만 제외.
- **원본은 절대 수정하지 않는다.** 항상 복사해서 작업.

측정된 영상 규격 (이 PC 기준):

| 항목 | 값 |
|---|---|
| 코덱 | HEVC Main (`hev1`), B프레임 없음 |
| 해상도 | 2560x1440 |
| fps | 60.02 |
| 픽셀 포맷 | yuv420p, bt709 |
| 비트레이트 | 15,660 kb/s 실측 |
| **키프레임 간격** | **정확히 3.000초 = 세그먼트당 1개** |
| 디스크 사용량 | 약 8.5 GB/시간 |

> ⚠ **해상도는 고정값이 아니다.** 2560x1440은 이 PC의 디스플레이 설정에서 나온 값이고, 스팀 녹화 설정·모니터·게임 해상도에 따라 달라진다. **런타임에 `session.mpd`의 `width`/`height`에서 읽어야 한다.** 좌표를 하드코딩하지 말 것 (§3 해상도 프로필).

> ⚠ **코덱이 HEVC라는 점은 UI 재생에 영향을 준다.** §4 참조.

> ffprobe가 헤더에서 읽는 `Duration`은 틀리게 나온다. init의 `mvhd`가 세션 전체 길이를 들고 있어서다. 실제 길이는 디코딩해서 재야 한다.

### 2.5 ★ 시간 매핑 — 로그·영상을 잇는 축

**이게 파이프라인의 중심이다. 타임존을 섞으면 9시간 어긋난다.**

```
세그먼트 N의 시작 시각(UTC) = 세션시작(UTC) + (N - 1) × 3.000초

세션시작(UTC)
  = session.mpd 의 availabilityStartTime      (녹화 중 세션, type="dynamic")
  = 폴더명 bg_<appid>_<YYYYMMDD>_<HHMMSS>     (항상 유효. 종료된 세션은 이걸 쓴다)

폴더명 · session.mpd  →  UTC
Player.log            →  로컬 타임존
```

검증 결과:

- `Player.log` 첫 라인 `2026-09-19 22:07:47,579` ↔ `availabilityStartTime="2026-09-19T13:07:47Z"` — **초 단위 일치.** 게임 클라이언트가 뜨는 순간 스팀이 녹화를 시작한다.
- 종료된 세션의 `Period@start` = `(startNumber-1) × 3초` 로 정확히 일치.
- 병합한 파일의 ffprobe `start_time` 도 `(N-1) × 3` 과 일치 (포맷 레벨 확인).
- 로그의 `PlayGame` 시각 → 세그먼트 180 → 그 세그먼트 실제 프레임에 인게임 HUD 있음. 로비 시각 → 세그먼트 140 → HUD 없음. **매핑 정합 확인.**

세션이 끝나면 `session.mpd`가 `type="static"` 으로 바뀌고 `availabilityStartTime`이 사라진다. **폴더명을 1차 소스로 쓰는 게 안전하다.**

### 2.6 ★ 링버퍼가 실시간으로 지운다

스팀 백그라운드 녹화는 **전역 설정 하나**로 버퍼 길이가 정해진다. 게임별이 아니다.

- 조사 PC의 설정값은 **120분**. `session.mpd`의 `timeShiftBufferDepth="PT2H0M0.0S"` 와 일치했다.
- 실측: 5분(=100 세그먼트) 동안 가장 오래된 조각 번호가 105 전진. **새 세션이 쓰는 만큼 옛 세션이 앞에서 깎인다.**
- 보존량을 두 번 재봤고 각각 2,406 / 2,401 세그먼트 = **약 2시간 00분**. 설정값과 정확히 일치.

**버퍼 길이는 자동 인식한다.**

1. `session.mpd`의 `timeShiftBufferDepth` (녹화 중 세션에서 읽힘) — 1차
2. `localconfig.vdf` 의 `GameRecording` 설정 — 2차
3. 둘 다 실패하면 **기본값 120분**
4. 설정 UI에서 사용자가 직접 덮어쓸 수 있게 노출

매치가 9~20분이고 버퍼가 2시간이면 추출 여유는 충분하다. 하지만:

> **"세션 폴더가 있으니 조각도 있다"는 가정은 틀린다.** 번호로 접근하기 전에 항상 존재를 확인할 것. 조사 중 실제로 이것 때문에 첫 병합 시도가 실패했다.

### 2.7 ★ 좌하단 초상화가 상태를 다 말해준다 (확정)

화면 좌하단 캐릭터 초상화가 **교전 중 / 사망** 을 둘 다 알려준다. **이 프로젝트의 핵심 신호다.**

2560x1440 기준 좌표:

| 요소 | ROI |
|---|---|
| 초상화 전체 | `x 640..870, y 1240..1440` |
| 얼굴(원형 중심부) | `x 690..860, y 1250..1400` |
| **좌하단 배지** | **`x 680..732, y 1395..1440`** |

#### 교전 중 — 배지가 주황색 교차 칼로 바뀐다

- **평상시**: 원형 배지에 레벨 숫자
- **교전 중**: 같은 배지가 **주황색 + 교차된 칼 아이콘** (애니메이션 있음)

배지 ROI에서 선명한 픽셀(`V≥90 AND S≥60`)만 색상별로 센 실측:

| 상태 | 주황 px | 파랑 px |
|---|---|---|
| 평상시 (26프레임) | **0 ~ 21** | 398 ~ 546 |
| 교전 중 (5프레임) | **138 ~ 522** | 97 ~ 225 |

**주황 픽셀 수만으로 6배 이상 마진으로 갈린다.** 템플릿 매칭이 필요 없다.

```
주황 = V≥90 AND S≥60 AND R > B+60 AND R ≥ G AND G < R×0.80
노랑 = V≥90 AND S≥60 AND R > B+60 AND G ≥ R×0.80
파랑 = V≥90 AND S≥60 AND B > R+40
교전 판정 = 주황 px ≥ 100
```

주의할 점:

- **평상시 배지 색이 매치마다 다르다.** 파랑인 매치도, 노랑인 매치도 있었다(레벨 티어로 추정, 규칙은 미확인). 위 식처럼 **녹색 채널로 주황/노랑을 갈라야** 한다. 노랑 배지 매치에서도 교전 프레임은 주황 773으로 확실히 떴다.
- **판정 전에 배지가 보이는지 먼저 확인할 것.** 로비에서 주황 58 / 파랑 0 / 노랑 0 이 나온 사례가 있다. `주황+파랑+노랑 ≥ 250` 정도를 "배지 있음" 조건으로 둘 것.
- 완전히 어두운 프레임에서는 전부 0이 나온다. **"판독 불가"를 "교전 아님"과 구분할 것.**
- 칼 아이콘 애니메이션 때문에 주황 픽셀이 138~773으로 크게 변동한다. 임계는 낮게(100).

#### 사망 — 초상화가 회색이 되고 부활 카운트다운이 뜬다

사망 세그먼트 전후 실측 (얼굴 ROI):

| 세그먼트 | 얼굴 채도 | 얼굴 밝기 |
|---|---|---|
| 정상 | 25.9 | 111.4 |
| **사망** | **13.3** | **33.9** |
| 전환 | 11.7 | 15.4 |

채도 절반, 밝기 1/3. 그리고 **초상화 중앙에 부활까지 남은 시간 카운트다운 숫자**가 뜬다.

#### 사망 — 화면 전체도 회색으로 덮인다

월드 레이어가 점진적으로 탈채도 + 암전된다. 화면 중앙 월드 영역(가로 20~80%, 세로 15~72%) 기준 60fps 실측:

| 사망 후 경과 | 중앙 채도 | 중앙 밝기 |
|---|---|---|
| 0.0s (정상) | 45.0 | 130.9 |
| 2.0s | 19.5 | 90.2 |
| 3.5s | 15.2 | 71.3 |
| 5.2s | 12.6 | 54.1 |
| 5.3s | 0.7 | 암전 |

- 램프는 약 **3.5~5초에 걸쳐 단조 감소**한다. 계단식이 아니다.
- **HUD는 회색화되지 않는다.** 미니맵·킬피드·상단 카운터는 색을 유지한다.
- 따라서 **화면 전체 평균으로 재면 HUD에 희석돼 신호가 죽는다.** 실제로 전역 평균으로는 사망 구간을 집어내지 못했다.
- 스킬바가 회색으로 비활성화되고 `"일원이 사망하였습니다"` 텍스트가 뜬다.

**단일 절대 임계는 위험하다.** 밤 맵·실내에서는 평상시 중앙 밝기도 40~80까지 떨어진다. **수 초에 걸친 단조 하강(ramp)** 자체를 신호로 삼을 것. 초상화 ROI 쪽이 더 작고 신호가 세니 1차로 쓰고, 화면 전체 램프는 교차검증용으로 쓴다.

> ★ **추가 실측 (§2.12)**: 암전 직전에 **초상화가 빨갛게 변한다** — 빨강 픽셀 비율 0.0% → 71.5%. 계단형이라 램프 분석보다 훨씬 다루기 쉽다. 그리고 **사망 후에는 캐릭터 UI가 통째로 사라져** 관전 화면이 된다. 즉 사망은 세 국면이다: **빨강 → 암전 램프 → UI 소멸(관전)**. 셋을 다 보되 가장 싼 빨강부터 본다.

#### ★ 사망은 "끝"이 아니다

§2.0 대로 부활이 있고(2일차 밤까지 무료, 이후 크레딧), 팀원이 살아있으면 매치는 계속된다.

→ **사망은 시점이 아니라 구간이다.** 시작은 회색 램프, 끝은 부활이다.

### 2.8 상단 HUD 카운터 — `TK` / `K` / `A`

| 카운터 | 의미 |
|---|---|
| `TK` | 팀 전체 킬 |
| **`K`** | **내 킬 — §2.0 대로 항상 내 값이다** |
| `A` | 내가 관여한 팀 킬 (어시스트) |

좌표와 판독 방식은 §3 참조. **교전 앵커는 배지(§2.7)가 잡고, `K`/`A` 는 그 교전에 태그를 다는 데 쓴다.** 예전 SPEC처럼 `K` 증가를 앵커로 삼지 않는다.

- **`K`/`A` 가 올랐는데 그 시각에 배지가 꺼져 있으면(킬 직후 배지가 빨리 꺼진다) 그 이벤트가 스스로 교전 구간을 만든다**(이벤트 12초 전~이벤트, 가까우면 앞뒤 구간과 합침). 예전엔 배지 구간 밖의 킬을 조용히 버려서 킬이 클립에 안 들어갔다(2등판 6일차 밤: K 6→7→8 이 클립 사이 빈 구간에서 일어남).
- **`TK` 는 여전히 새 구간의 앵커가 아니다.** 팀 전체 킬이라 내가 없는 곳의 팀원 킬(코발트에서는 초당 수준)까지 올라 가짜 클립이 쏟아진다.
  - ★ **다만 2026-09-23 부터 "이미 있는 구간의 끝을 늘리는 데"는 쓴다.** 실사용 보고(다시보기 1일차 낮 교전 · 마르티나): 내 배지가 꺼지고 2초 뒤 팀원이 막타를 넣었는데 클립이 그 직전에 끊겼다. `finalize_match` 가 배지 기반 구간의 끝 근처(`TRAILING_KILL_EXTEND_SEC=12초`)에서 K/A/TK 델타를 보면 그 구간의 끝만 그 시점까지 늘린다 — **새 구간은 만들지 않으므로** 위 경고(가짜 클립 폭주)에 해당하지 않는다. `detect/match.py::resolve_tk_templates()` 가 K 템플릿을 `tk_value` 칸 크기로 리사이즈해 재사용한다(같은 폰트·같은 검정 배경, §3 K/A 판독과 동일 원리).
  - ⚠ **정규화 프로필 함정**: `tk_value` 처럼 K/A 와 폭이 다른 칸은 템플릿 크기를 `profile.rois`(이 프로필 자체의 실측값)가 아니라 `profile.crop()`이 실제로 내놓는 크기(정규화 프로필은 기준 해상도로 자동 확대됨)에 맞춰야 한다 — 안 맞추면 `read_field`가 크기 불일치로 조용히 `None`만 낸다. 2026-09-23 VOD(1920x1080) 실측으로 발견.
- **숫자 7·8 본보기가 없으면 K/A 가 7 에서 `None` 으로 끊겨 위 이벤트가 통째로 사라진다.** 새 숫자가 처음 나오면 결과 화면/HUD 로 정답을 확인해 `2560x1440_samples` 에 넣고 다시 빌드한다. 9 는 TK 칸(같은 글꼴, 한 자리일 때 K 칸보다 1픽셀 왼쪽)에서 뽑아 넣었다. 두 자리 값은 판독하지 않는다.

### 2.9 ★ 게임 모드가 둘이다 — 둘 다 추출 대상

| | 배틀로얄 | 코발트 프로토콜 (캐주얼) |
|---|---|---|
| `TK` 증가 속도 | 느림 | **빠름** (20분에 31까지) |

- **두 모드 모두 추출 범위에 넣는다.** HUD가 같으므로 검출기는 그대로 쓴다.

- 모드 자동 식별은 아직 안정적인 규칙이 없다. 결과 화면 문구가 후보다. 검출기는 공유되므로 메타데이터 라벨링에만 영향이 있다.
- 코발트 프로토콜에는 **한글 킬피드**가 좌하단에 나온다 (`[07:51] A님이 B님을 처치했습니다.`). v1에서는 쓰지 않는다.

| **팀원 캐릭터 2명** | 우측 초상화 (`x 2097..2180`, `y 1165..1250` / `y 1302..1387`) | ✅ 위치 확인 |

#### 지역명 — 지도를 분석하지 말고 글자를 읽는다

미니맵 **헤더에 현재 지역명이 상시 표시된다**(스크린샷상 `묘지`). 지도 안쪽에도 지역 라벨이 있지만 그쪽은 캐릭터 아이콘에 가려진다.

그래서 **미니맵 픽셀 → 지역 좌표 매핑도, 지역 모양 학습도 필요 없다.** 고정 ROI의 글자를 읽으면 된다. K/A 숫자 판독과 같은 기법(글자다움 맵 × 알파 템플릿)을 지역명 템플릿 ~20개로 확장하면 된다.

- ⚠ **헤더 텍스트 색도 같이 바뀐다** (실측: 평상시 흰색, 금지구역 예정이면 주황). 처음엔 배경색과 무관한 줄 알았으나 틀렸다. **색으로 판정하지 말고 밝기 대비로 읽을 것.** K/A 숫자에 쓴 "글자다움 맵"의 무채도 항은 여기선 빼야 한다 — 주황 글자를 걸러내버린다.
- ⚠ **헤더 바가 반투명이라 배경이 비친다** (§2.10의 낮/밤 아이콘과 같은 문제). 밝은 지형 위에서는 대비가 줄어든다.
- 가려지거나 전이 중일 수 있으므로 **교전 구간 전체에서 최빈값**을 쓴다.
- 교전 중 지역이 바뀌면 **교전 시작 시점의 지역**을 제목에 쓴다.
- 헤더 우측의 **아이콘 4개(원그래프·핀·카메라·톱니)는 항상 같은 자리**라 ROI 정렬 확인용 앵커로 쓸 수 있다.

낮/밤은 아이콘 색으로 갈린다 — **해는 노랑, 달은 보라.**

```
노랑 = V≥90 AND S≥55 AND R > B+50 AND G > B+30      (해)
보라 = V≥90 AND S≥55 AND B > G+40 AND R > G+20      (달)
판정 = 노랑과 보라 중 큰 쪽
```

| 상태 | 노랑 px | 보라 px |
|---|---|---|
| 낮 | 305 ~ 1115 | 0 |
| 밤 | 0 | 198 ~ 204 |

- ⚠ **상단 바가 반투명이라 배경이 섞인다.** 배경이 밝은 주황(사막/석양)일 때 낮 프레임에서 보라 148~184가 잡혔다. 그래서 **단순 임계가 아니라 "큰 쪽 비교"** 로 판정할 것. 그 규칙으로는 16프레임 전부 정답이었다.
- 한 페이즈(낮 또는 밤)는 대략 **2.5~3분**이다. 20분 매치면 4~5일차까지 간다.

> ⚠ **`Player.log` 의 낮/밤은 쓰지 말 것.** 로그에도 `input=Day` / `input=Night` 가 남지만, **화면과 대조해보니 틀렸다.** `Duplicate set` 경고가 났을 때만 기록돼서 정상 전이가 대부분 누락된다. 로그상 한 매치에 전이가 3번인데 실제로는 8~10번이다. **HUD 판독이 유일하게 믿을 수 있는 소스다.**

- 캐릭터 이름은 **초상화 템플릿 매칭**이 필요하다. 캐릭터 수만큼 템플릿을 모아야 하는데, 게임 리소스에서 뽑거나 실사용하며 누적하는 두 방법이 있다. **v1 범위 밖이다** (§6).

### 2.12 ★ PvP 인지 PvE 인지 — v2의 핵심 과제

§1에 적은 대로 배지는 둘을 못 가른다. 대신 **여러 약한 증거를 모아 점수로 판단한다.** 단일 신호로 확정하려 들면 어느 쪽으로든 크게 틀린다.

#### 증거 목록

|---|---|---|---|---|

**킬/어시(1번)만 확실하다.** 사망(2·4번)은 강한 증거지만 **야생동물이나 금지구역에도 죽으므로** PvP 가 확정은 아니다 — 처음엔 1~4번 전부 확정으로 적었으나 첫 실전 결과에서 1.0 이 과다해 이렇게 고쳤다.
이겼으면 1번, 졌으면 2번이 걸린다. 그래서 5~7번이 담당할 몫은 **"양쪽 다 안 죽고 끝난 교전"** 하나뿐이다. 부담이 그만큼 작다.

> 이 구조가 "무성과 클립을 빼면 패배한 교전도 빠진다"는 문제를 푼다. 패배한 교전은 무성과가 아니라 **사망 증거가 걸리기** 때문이다.

#### 3. 전멸 배너 — 가장 읽기 쉬운 확정 증거

적 팀을 전멸시키면 **화면 상단 중앙에 큰 배너**가 뜬다.

| 배너 | 뜻 |
|---|---|
| `BREAK` | 1일차(낮·밤) 안에 적 팀 전멸 |
| `TERMINATE` | 적 팀 전멸 |
| `CLUTCH` | 나 혼자 살아남은 채로 적 팀 전멸 |
| `CHECKMATE` | 최종 우승 |

배너는 **고정 위치 · 큰 글자 · 높은 대비**라 판독 난이도가 K/A 숫자보다 낮다. 배너 좌측에 처치자 이름과 킬 수, 우측에 전멸당한 팀의 초상화가 같이 뜬다.

- ⚠ **확인 필요**: 이 배너가 내 팀의 전과일 때만 뜨는지, 다른 팀끼리의 전멸도 뜨는지 실측 안 됨. 모든 팀에 뜬다면 배너 단독으로는 못 쓴다.
- **그래서 배너 단독이 아니라 `배너 ∧ 내가 교전 중` 으로 본다.** 남의 싸움이면 나는 그 시점에 교전 중이 아닐 가능성이 높다. 이 조합이면 위 불확실성과 무관하게 안전하다.

#### 5. 미니맵 — 애매한 교전을 건지는 유일한 수단

우하단 미니맵은 **내 주변만** 보여준다(전체 지도는 M/Tab). 그래서 **"미니맵에 적이 보인다" 자체가 이미 어느 정도 가깝다는 뜻**이라 신호가 세다.

다만 한계가 분명하다.

- ⚠ **가까이 붙으면 아군 아이콘과 구분이 안 된다** (아이콘이 겹침). → 한 프레임으로 판정하지 말고 **교전 구간 전체에서 집계**한다. 몇 초의 교전 동안 모든 프레임에서 겹쳐 있을 가능성은 낮다.
- ⚠ **거리 임계를 추측으로 정하지 않는다.** 1~4번으로 **확정된 PvP 구간**과 아무 일도 없던 긴 전투 구간을 각각 정답으로 놓고, 두 집단의 "내 아이콘 ↔ 가장 가까운 적 아이콘" 거리 분포를 실측해서 정한다. 분포가 겹치면 이 신호는 못 쓴다는 결론이 바로 나온다. **라벨은 공짜로 이미 쌓여 있다.**
- ⚠ **지역 배경색은 계속 바뀐다** — 기본 / 노랑(금지 예정) / 빨강(금지) / 흰 테두리 빨강(해제 예정). **배경색 기반 판정은 금지.** 아이콘만 본다.

#### 8. 네임플레이트 — 색이 **사용자 설정**이라 고정 RGB 로 못 쓴다 (2026-09-21 실측)

화면 안 캐릭터 머리 위 체력바의 색은 게임 내 `설정 → 색약 간단 설정` 에서 역할별로 바꿀 수 있다. 기본값:

| 역할 | 기본 색 | 비고 |
|---|---|---|
| 자신 | 초록 | |
| 아군(내 팀원) | 파랑 | |
| 환경 오브젝트 | 베이지 | |
| 몬스터 | 진홍 | ⓘ 표시 — **팀1과 같은 색** |
| 팀1 ~ 팀8 (적 팀) | 진홍 / 주황 / 황금 / 베이지 / 분홍 / 자홍 / 짙은 장미 / 연보라 | 팀1은 몬스터와, 팀4는 환경 오브젝트와 겹친다 |

여기서 따라오는 제약이 셋이다.

- **적 플레이어는 단일 색이 아니라 8색 집합이다.** "적 = 빨강" 식으로 못 짠다.
- **기본값에서도 몬스터 = 팀1(진홍), 환경 오브젝트 = 팀4(베이지)가 겹친다.** 게임이 그 두 항목에만 ⓘ 를 붙여 경고하는 이유다. 색만으로는 적 플레이어와 야생동물을 못 가른다 — 체력바 눈금·레벨 상자 같은 **모양** 단서가 같이 필요하다.
- **색은 사용자가 바꾼다.** 코드에 RGB 를 박으면 색약 설정을 바꾼 순간 검출기가 조용히 고장 난다.

실측한 것: 프로토타입이 잡아낸 "파란 눈금 바"는 적이 아니라 **내 팀원**이었다(기본 아군 색). 즉 이 신호는 적 탐지가 아니라 **"팀원이 화면에 있다"** 를 재는 것이고, 그 값만으로는 교전/사냥이 잘 안 갈렸다(AUC 0.62 — [plan-pvp.md §5-3](plan-pvp.md)).

> **추후 구현 옵션 — 설정 화면 스크린샷으로 색 자동 인식.**
> `색약 간단 설정` 화면 **오른쪽 미리보기 패널(12행: 자신 ~ 팀8, [plan-ui §5](plan-ui.md) 에 범위 정의)만 잘라** 첨부하는 것으로 통일한다. 이름과 색 견본이 고정 배치라 사용자가 UI 옵션에서 이 스크린샷을 첨부하면 각 행의 견본 색을 뽑아 프로필에 저장하는 방식이면, 기본값이든 색약 설정이든 똑같이 동작한다. **지금은 만들지 않는다** — 네임플레이트 신호 자체가 아직 쓸 만한지 증명되지 않았다. 신호를 채택하기로 결정하면 그때 같이 만든다. 구현 항목은 [plan-ui.md §5](plan-ui.md).

#### 9. 궁극기(R) 사용 — 제안, 미검증 (2026-09-22)

> 사용자 관찰: "대부분 캐릭터는 궁 쿨타임이 20초 내외거나 더 짧지 않은 이상, 보통 사람과 교전할 때에만 궁극기를 쓴다."

스킬바의 `R` 칸은 캐릭터가 바뀌어도 위치가 고정이라, **캐릭터 식별 없이 쓸 수 있는 몇 안 되는 후보다** (8번·11번과 결정적으로 다른 점).

- **검출 대상은 "궁 발동 순간"이지 궁의 종류가 아니다.** 아이콘이 활성(선명) → 쿨타임(회색조 + 숫자 오버레이)으로 바뀌는 전환만 잡으면 된다. 쿨타임 숫자 판독은 K/A·일차 숫자에 쓴 글자 매칭 기법을 그대로 재사용할 수 있다.
- **조건부 신호다.** 쿨타임이 짧은 캐릭터는 사냥 중에도 궁을 돌릴 수 있어 신호가 흐려진다. 그래서 **"궁을 썼다" 자체보다 "쿨타임 진입 시점에 읽힌 쿨타임 값"으로 가중치를 조절하는 안**을 검토한다 — 예: 쿨타임이 길게(예: ≥15초) 잡히면 가중치를 높게, 짧으면 낮게. 캐릭터별 실제 쿨타임 표 없이도 "이번엔 얼마나 걸렸는지"만으로 대략적 구분이 될 수 있다는 가설이며, **라벨로 검증 전까지는 가정이다.**
- ROI 미측정 — 스킬바 전체 ROI(`plan-pvp.md` §3 실측 표의 `880,1290,1300,1365`)는 있으나 `R` 칸만 자른 좌표는 아직 없다. 실제 녹화 프레임에서 실측해야 한다.
- 검증 절차는 미니맵·네임플레이트와 동일: 라벨된 교전/사냥 클립에서 "구간 내 R 발동 여부"와 "발동 시점 쿨타임 값"의 분포를 각각 재고 AUC 로 판단한다.

> **1차 육안 확인 (2026-09-22, 라벨된 클립 프레임으로).** `20260920_134809_01.mp4`(pvp, kill)에서 대략 `x 1110..1170, y 1290..1360` 부근이 `R` 칸이었다. **준비 상태는 원래 색 그대로, 쿨타임 상태는 파르스름한 반투명 오버레이 + 흰 숫자**로 뚜렷이 갈렸다 — 5초 시점엔 준비 상태, 60초 시점(교전 진행 중)엔 `37`(쿨타임 진입, 궁을 썼다는 뜻). 같은 방식으로 확인한 사냥 클립(`20260920_134809_03.mp4`, 멧돼지와 전투)에서는 8초 시점까지 `R` 이 계속 준비 상태(안 씀)였다.
>
> **★ 라벨 110개 전체로 검증 완료 (2026-09-22, `scripts/probe/eval_ultimate_signal.py`).** 처음엔 "파란기 비율 ≥ 고정 임계"로 재서 AUC 0.894 가 나왔는데, **가짜 신호였다** — 캐릭터마다 `R` 아이콘 원화 자체의 파란기 베이스라인이 달라서 궁을 안 써도 항상 ~0.25 근방이 나오는 캐릭터가 있었다(같은 세션의 사냥 클립 여러 개가 거의 똑같은 값을 반복해서 낸 게 단서). **클립 자체의 최솟값을 그 클립의 "준비" 기준선으로 잡고 최댓값과의 차이(delta)로 재계산하니** 훨씬 신뢰할 만한 결과가 나왔다:
>
> | | pvp (73개) | pve (37개) |
> |---|---|---|
> | delta ≥ 0.15 로 "궁 사용" 검출 | 66개 (90%) | 10개 (27%) |
>

#### 11. 캐릭터별 발동 특성(적 대상에만 트리거) — 보조 후보, 후순위

> 사용자 관찰: "액셀러레이터"(마르티나 특성)처럼 **상대 캐릭터를 직접 타격했을 때만** 발동하는 특성이 여럿 있다. 다만 캐릭터·특성마다 발동 조건이 달라 **메인 판별 기준으로 쓰기엔 애매하다는 점을 사용자도 동의.**

- 이 신호를 쓰려면 (1) 초상화로 캐릭터를 식별하고 (2) 그 캐릭터가 든 특성을 알고 (3) 그 특성 아이콘이 버프 줄의 어느 자리에 뜨는지까지 알아야 한다 — §2.10 이 "v1 범위 밖"으로 미뤄둔 캐릭터 식별에 얹히는 작업이라 **비용이 10번보다 훨씬 크다.**
- 대신 **사용자가 자주 쓰는 캐릭터(마르티나 등) 한둘에 한해 보조 신호로 얹는 것**은 비용 대비 효과가 있을 수 있다. 전체 캐릭터를 커버하려 들지 않는다.
- **후순위.** 10번(활성 효과 개수)이 범용 신호로 채택된 뒤, 그 위에 "이 캐릭터를 플레이 중이면 이 아이콘의 발동도 본다" 정도로 얹는 방식을 검토한다.

체력바 색 실측: 생존 클립 24샘플 × 2슬롯에서 주황 0건. 눈으로 사망을 확인한 슬롯 4개(사망 클립·리스폰 카운트 `23` 표시·주황 바)에서 전부 주황 검출(2~4샘플).

**3. 사망 후엔 캐릭터 UI가 통째로 사라진다.** 초상화·스킬바·팀 패널·미니맵 헤더가 전부 0이 된다. 관전 화면은 **"신호가 약해지는" 게 아니라 "ROI가 비는"** 상태다. 이건 오히려 좋다 — 관전 구간을 판독 대상에서 제외하기 쉽다(§3). **관전 중 화면은 팀원 시점이므로, 그 구간의 미니맵·지역명·배지를 내 것으로 읽으면 전부 오판이 된다.** 반드시 제외해야 한다.

**4. 지역명은 읽힌다.** 5개 클립에서 `학교` `경찰서` `묘지` 를 모두 같은 ROI에서 잡았다. 글자 픽셀 비율이 HUD가 있으면 5.8~6.6%, 없으면 0.0% 로 명확히 갈린다.

**5-0. ⚠ 회색화는 "내 사망"이 아니라 "팀 전멸"일 가능성이 높다.** 사용자 제보: 회색 화면은 **우리 팀이 전멸했을 때**(BREAK 당했거나 게임이 끝났을 때) 뜬다. research.md 가 관찰한 회색 램프도 그 상황이었을 수 있다.

이게 맞다면 **의미가 완전히 달라진다.**

| | 빈도 | 지금 검출되나 |
|---|---|---|
| 팀 전멸 (회색화) | 매치당 최대 1회 | ✅ 되고 있다 |
| **내 개인 사망** (부활 가능, 200 크레딧) | 매치당 여러 번 | ❌ **안 되고 있다** |

즉 지금의 `death` 태그는 개인 사망이 아니라 팀 전멸을 잡고 있을 수 있다. **개인 사망의 진짜 신호는 "관전 UI로의 전환"(위 3번)이다.** 개인 사망은 확정 PvP 증거이므로 이 구멍은 꼭 메워야 한다. 🔲 회색화가 정말 팀 전멸에서만 뜨는지 실측 필요.

**5. 미니맵 — 단순 색 카운팅은 실패했다.** ROI 전체의 색상 히스토그램은 **금지구역 빨강 배경과 시야·안전지대 원(초록·하늘)이 압도**해서 캐릭터 아이콘이 묻힌다. 아이콘은 너무 작다.

대신 **원형 링 검출(`HoughCircles`)은 된다.** 프레임당 원 9~13개를 찾았고 그중 유채색 링이 7~10개였다. 링 테두리만 샘플링해 색을 재면 **빨강·주황·노랑·초록·하늘**로 갈린다 — 팀마다 색이 다른 것으로 보인다.

**색 → 진영 매핑이 풀렸다.** 사용자 제보 + 캐릭터 선택 화면으로 확인:

- **빨강 = 적**
- **노랑 · 초록 · 파랑 = 아군** — 캐릭터 선택 화면에서 팀원 3명이 각각 파랑/초록/노랑 바를 갖는 것과 일치한다.
- ⚠ **내 아이콘 색은 고정이 아니다** (매치마다 노랑이기도 파랑이기도 하다). 내가 팀의 몇 번째 슬롯이냐에 따라 달라지는 것으로 보인다. → **내 아이콘을 특정하려 들지 않는다.** 필요하면 아군 아이콘 무리의 중심을 내 위치 대용으로 쓴다.

**★ 실제로 갈리는지 검증했다.** 확정 PvP 클립 3개와 사냥 후보 5개에서 3초 간격 프레임의 빨강 링 개수를 셌다.

| 집단 | 프레임당 적 링 평균 | 적 링이 보인 프레임 비율 |
|---|---|---|
| **확정 PvP** (사망 클립 3개) | **0.8 / 1.1 / 1.3** | 50% / 60% / 69% |
| **사냥 후보** (5개) | **0.1 / 0.5 / 0.6 / 0.2 / 0.1** | 11% / 32% / 63% / 15% / 14% |

**"프레임당 적 링 평균"이 겹치지 않고 갈린다** — PvP는 최소 0.8, 사냥은 최대 0.6. 반면 "최대값"이나 "한 번이라도 보였나"는 겹친다. **구간 전체의 평균으로 봐야 한다**는 뜻이고, 이는 §2.12에서 아이콘 겹침 때문에 프레임 단위 판정을 피하라고 한 것과도 맞는다.

> ⚠ **표본이 너무 작다** (PvP 3, 사냥 5). 게다가 PvP 3개가 전부 사망 클립이다 — 킬 클립이 하나도 없다(아래 참조). 이 수치를 임계로 굳히지 말고 **라벨을 더 모아 다시 잴 것.** 사냥 후보 중 0.6짜리(`20260920_124925_03`)는 오히려 **아무도 안 죽은 진짜 교전**일 수 있다. 우리가 찾던 바로 그 경우다.

#### 🔲 BREAK 회색 화면 — 찾지 못했다 (보류)

제보: 1일차에 전멸당하면(BREAK) **회색 화면 + 중앙에 흰 숫자로 부활 카운트다운**이 뜨고, 이건 매치당 여러 번 가능하다.

**클립 60개를 전부 훑었으나 0건이다** (채도 < 16 이면서 암전은 아닌 프레임). 추정 원인 둘:

1. 클립이 교전 구간 ±preroll/postroll 만 잘라내므로 **BREAK 화면이 클립 범위 밖**일 수 있다.
2. 회색 화면에도 색 있는 UI(카운트다운 숫자 등)가 남아 채도 임계에 안 걸렸을 수 있다.

언제 당했는지 기록이 없어 원본에서 찾기도 어렵다. **보류한다.** 팀 전멸 자체는 회색화·전멸 배너로도 잡히므로 막히는 항목은 아니다.

#### 튜닝 루프

가중치와 임계는 **실사용 라벨로 정한다.** UI에서 클립을 보며 "이건 교전 / 이건 사냥"을 찍을 수 있게 하고(§6 3단계), 그 라벨로 임계를 다시 맞춘다. 초기에는 임계를 낮게 두어 **놓치는 쪽보다 남기는 쪽으로 기운다** (§1의 근거).

### 2.11 원본이 스팀 export보다 고화질이다

스팀 UI로 클립을 export하면 **1080p로 다운스케일된다** (`clip.pb`의 해상도 필드에서 확인). 우리는 export를 거치지 않고 원본 `.m4s`를 직접 읽으므로 **녹화 원본 해상도를 그대로 얻는다.**

### 2.13 결과 화면 판독 (구현, 실측)

> ⚠ **기존 클립 보강(`tools/backfill_result.py`)의 함정 (2026-09-21 실제 사고)**: 스팀 링버퍼는 새 녹화가 시작되면 옛 세그먼트를 지운다. 원본이 이미 지워진 경기를 `--force` 로 다시 돌리면, 마지막 클립 뒤가 비어 있어 훑기가 **뒤쪽에 남은 다른 경기의 결과 화면**까지 넘어가 그걸 이 경기 것으로 붙였다(13:36·13:48 경기가 14:12 경기의 `1/8` 로 덮어써짐). 이제 훑기는 마지막 클립 바로 뒤에서 **끊김 없이 이어진 세그먼트**만, 그리고 **다음 경기 시작 전까지만** 본다(`contiguous_segments`). 이어져 있지 않으면 "못 찾음" 이다.

경기가 끝나면 **`나가기` 를 누르기 전 결과 화면**이 항상 뜬다(`4/7 랭크 대전 실험 종료`, 승리는 `1/8 … 최종 생존`). 좌측 패널에 순위(`N/M`), 모드 칩, 결과 문구, 내 닉네임이 모여 있다(2560x1440 기준 `result_panel` `[300,450,1000,1080]`, `result_chip` `[335,625,600,675]`). 랭크 게임만 그 뒤에 `RANK POINT` 정산 화면이 더 뜨고, 순위표·통계·그래프 화면은 일반/랭크가 같다.

- **OCR**: RapidOCR(ONNX, PP-OCRv5 한국어/중국어 모델). 글자 모양 템플릿을 모으는 방식은 순위 숫자·문구 샘플이 부족해 접었다. 프레임당 ~1초라 경기 끝에서 거슬러 올라가며 인게임 프레임(일차 판독 성공)은 건너뛰고 처음 판독되는 프레임에서 멈춘다(최대 40프레임).
- **글자 위치가 아니라 순서로 읽는다**: 순위(`N/M`) → 그 뒤 신뢰도 0.8 이상·한글 2자 이상인 줄이 결과 문구 → 그 뒤 막대(`|`)로 시작하는 줄이 닉네임. 칩 잡음(`이`)이 결과 문구로 읽히던 버그를 이렇게 막았다.
- **랭크 여부**: 파란 알약 칩은 그대로는 OCR 이 못 읽는다. 밝기 200 이하를 지우고 3배 키우면 `랭크` 가 읽힌다. `랭크` 가 있으면 rank, 아니면 normal(일반 칩은 아직 실측 못 함 — 칩 원문은 `matchLabel` 에 남긴다).
- **닉네임**: 줄만 잘라 3배 키운 뒤 한국어·중국어 모델을 둘 다 돌려 점수가 높은 쪽을 쓴다. 한글·영문은 실측으로 정확했고 **일본어·한자는 아직 실측 못 했다.** 결과 화면은 항상 내 화면이라 닉네임은 "내 행 찾기"에는 필요 없지만, 순위표 화면을 읽을 때 내 행을 찾는 열쇠다. 설정 `player.nickname` 이 비어 있으면 워처가 첫 판독값을 저장하고, 사용자가 옵션에서 고칠 수 있다.
- **스탯**: 패널의 `TK K D A` 라벨 아래 같은 열의 숫자를 읽는다(`tk`, `kills`, `deaths`, `assists`). 실측: `4위 13/3/1/6`, `7위 2/0/4/0`(dak.gg 와 K·A 일치). **결과 화면의 TK 와 순위표/dak.gg 의 TK 는 다를 수 있다**(1위 경기 결과 화면 16, 순위표 17 — OCR 오류가 아니라 게임이 그렇게 보여준다).
- **결과표 이미지**: 결과 화면 프레임을 경기당 1장 1280px JPEG 로 `<clips>/.thumbs/<경기시작>_result.jpg` 에 저장하고 `matchResult.imagePath` 에 남긴다. 열람 UI 의 게임 섹션 첫 칸에 썸네일처럼 보인다(경기 구분용).
- **저장**: 클립 메타데이터 `matchResult` (`matchType` rank/normal, `matchLabel`, `placement`, `total`, `outcome`, `nickname`). 같은 게임의 클립이 다 같은 값을 갖는다. 판독 실패는 클립 생성을 막지 않는다.
- **캐릭터**: 순위표 부제는 작고 흐려 OCR 이 못 읽는다. 대신 오른쪽의 **세로 영문 이름**(`MARKUS`)을 대비를 늘려 눕힌 뒤 읽는다(`result_character` ROI). 일러스트에 가려 잘려 나오므로(`MARKU`, `MARTIN`) `data/characters.json`(영문→한글, 기억으로 채운 표라 사용자가 고칠 수 있다)에서 **유일한 접두어**로 찾고, 모호하면 `characterRaw` 만 남긴다. 성공하면 클립 `myCharacter` 를 채운다.
- **기존 클립**: `tools/backfill_result.py` 가 원본이 남은 경기만 채운다(게임별 마지막 클립 뒤에서 앞으로 훑는다).
- **팀원 캐릭터 (순위표 탭)**: 게임이 끝나면 결과 화면 뒤에 `순위표 / 통계 / 그래프` 탭이 나오고, `순위표` 탭에는 플레이어마다 **순위 · 닉네임 · 캐릭터 이름(닉네임 아래 작은 글자)** 이 나온다. 내 닉네임 행을 찾고 **같은 순위의 다른 행이 팀원**이다(`detect/scoreboard.py`). 캐릭터 이름 글자는 작고 어두워서 그냥은 못 읽는다 — 밝은 글자만 강조(`min(R,G,B)` 에서 90 을 빼 2~3배)해 여러 배율로 읽고 같은 줄끼리 합치며, `data/characters.json` 이름표에 맞는 읽기를 우선한다(표에 없는 글자는 버린다). 닉네임 옆 레벨 숫자는 건너뛴다. 실측(14:12 경기): 10행 중 9행의 캐릭터를 읽었고 내 팀 `팀원가=루치아`, `TeamMateB=(엘레나 놓침)`. **캐릭터 이름 재시도**: 그래도 못 읽은 행은 닉네임 아래 띠를 위치·폭을 바꿔(3×2×3) R/max/G 채널로 다시 읽고 같은 이름이 2번 나오면 채택한다(`recover_character`). 푸른 행의 `엘레나` 는 min 채널에서 사라지고 R/max 채널에서만 남아 이 재시도로 읽는다 — 14:12 경기 10행 모두 판독. **순위표 탭은 기본 탭이 아니다** — 녹화에서 결과 뒤 처음 뜨는 탭은 `그래프` 이고, 사용자가 `순위표` 를 눌러야 나온다(13:48 경기는 그래프만 보고 나가서 순위표 프레임이 없다). 그 경기는 팀원을 못 읽는다. 순위표가 보이면 결과 화면에서 못 읽은 내 캐릭터도 표에서 채운다.
- **자동 제목**: `5일차 낮 경찰서 교전 · 마커스` (내 캐릭터만 — 팀원 캐릭터는 게임 행에만 표시하고, 모르는 팀원은 `미확인`, 닉네임은 쓰지 않는다). 자동 제목만 다시 만들고 사용자가 직접 바꾼 제목은 건드리지 않는다(`pipeline/titles.py`).
- **미완**: 탈출·일반 게임 결과 화면(샘플이 없어 문구·칩을 실측하지 못했다. 칩을 못 읽으면 `matchType=unknown`, 문구는 원문 저장), 팀원 캐릭터(제목 규칙 `{teamChars}` 는 아직 비어 있다).

#### 수동 보정 (설계 결정, **미구현**)

**자동 판독이 틀리거나 못 읽었을 때 사용자가 손으로 고치는 것을 정식 경로로 삼는다.** 이 프로그램의 핵심은 클립 추출이고 캐릭터·팀원·순위는 클립을 찾고 분류하는 부가 정보다. 판독 정확도를 끝없이 올리기보다 틀렸을 때 고칠 수단을 주는 편이 싸고, 배포한 뒤 코드를 바로 못 고치는 환경에서도 통한다.

- **판독 실패의 실제 사례**: 결과 순위표는 10행쯤만 보이고 나머지는 스크롤해야 한다. 사용자가 스크롤하지 않으면 **내 행이 화면에 없어** 닉네임으로 내 행을 못 찾고, 순위표 탭을 아예 안 누르면 팀원도 못 읽는다(§2.13). 이런 경기는 영상에 정보 자체가 없으므로 더 나은 OCR 로 풀 수 없다.
- **고칠 수 있는 항목**: 내 캐릭터(`myCharacter`), 팀원 캐릭터(게임 행의 팀원 목록), 순위·결과(`matchResult.placement`/`outcome`). 캐릭터는 `data/characters.json` 목록에서 고르게 한다(자유 입력 X).
- **UI**: 게임 행에서 값이 `미확인` 이거나 사용자가 틀렸다고 보면 그 자리에서 눌러 고른다. 클립 제목 수정 버튼과 같은 방식이다.
- **잠금**: 사용자가 고친 값은 `manual` 로 표시해 **자동 판독·`tools/backfill_result.py`·자동 제목 재생성이 절대 덮어쓰지 않는다**(자동 제목에서 이미 쓰는 원칙, `pipeline/titles.py`). 고친 뒤에는 그 게임의 자동 제목을 새 값으로 다시 만든다(제목을 사용자가 직접 바꾸지 않은 경우만).
- **되돌리기**: 수동 값을 지우면 잠금이 풀리고 다음 판독이 다시 채울 수 있다.
- **저장 위치**: 같은 게임의 클립이 같은 값을 갖는 기존 구조(`matchResult`, `myCharacter`)를 따라 그 게임의 모든 클립에 함께 기록한다. 메타데이터 스키마는 `manual` 표시와 판독 로직 버전을 담을 자리를 마련한다.
- **못 읽었을 때의 원칙**: 틀린 값을 쓰느니 `미확인` 으로 둔다. 순위가 같은 행이 후보이므로 내 행을 못 정하면 억지로 고르지 않는다.
- **공식 API 는 쓰지 않는다**(§2.1 유지). 스크롤로 가려진 정보를 API 로 채우는 안은 약관·배포 문제(개인 이용자 범위, 키 공유, 타인 식별 금지, 콘텐츠 저장·제공 제한) 때문에 접었다. 나중에 재검토하면 사용자가 각자 발급한 키를 쓰는 선택 기능 + 실패한 경기의 게임ID 조회에 한정한다. 결과 화면 좌측 패널의 `게임ID` 가 조회 키가 될 수 있다.

### 2.14 ★ 다시보기(VOD) 소스 — 별도 탭 (설계 결정, **미구현**)

> 상세 설계·작업 순서·확인 필요는 [plan-vod.md](plan-vod.md). 아래는 이 문서 다른 절에 영향을 주는 결정만 옮긴 것이다.

스트리머 방송 다시보기 영상(치지직 등)에서 교전 클립을 뽑는다. **내 스팀 녹화와 저장소·목록·탭을 전부 분리한다.**

- **앱은 다운로드하지 않는다.** 사용자가 받아 둔 영상의 **로컬 경로를 설정에서 지정**하면 읽기만 한다. §7.8 의 "네트워크 호출을 하지 않는다"와 "원본은 수정하지 않는다"가 그대로 유지된다. 분석·컷은 파일의 원래 해상도에서 한다.
- **저장소 분리**: 클립은 `paths.vodClips` 에 따로 둔다. `scan_clips` 가 폴더의 `*.json` 을 통째로 읽으므로 섞으면 스팀 쪽 목록·자동 정리·평가에 남의 방송이 끼기 때문이다.
- **계층**: 다시보기 영상 → 게임(화면으로 나눈 1판) → 교전 클립. UI 는 영상 단위 섹션 안에 게임별 행이 들어가는 구조이고, 게임 행·클립 카드·플레이어·라벨·자르기·저장은 기존 컴포넌트를 재사용한다(plan-vod.md §3).
- **트리거는 수동**이다. `Player.log` 도 벽시계 시각도 없으므로 매치 종료 감시가 성립하지 않는다. 사용자가 영상마다 "분석"을 누르고, 진행률·취소·이어하기가 있다(7~8시간 영상).
- **경기 경계는 화면으로 찾는다.** 일차 판독 성공 구간 = 인게임, 일차 감소 = 새 판, 결과 화면 OCR = 판의 끝(§2.13). 못 나누면 클립을 버리지 않고 확신도만 낮춘다 — §1 의 재현율 우선 원칙 그대로.
- **검출 코드를 프레임 공급자(`FrameSource`)로 분리한다.** 지금 검출은 스팀 세션·세그먼트 번호에 묶여 있다(`t = (세그먼트-1)×3초`). §3 의 "녹화 소스는 인터페이스로 추상화한다"를 실현하는 것이며, 스팀 경로의 출력은 리팩터링 전후 동일해야 한다.
- **해상도 프로필**: 방송은 보통 1080p 라 `1920x1080` 프로필과 본보기(숫자·지역·일차)를 **다시보기 프레임에서 다시 만든다**(§3 "해상도 프로필" — 모르는 해상도는 신뢰도 낮춤 + 경고). 스트리머의 UI 스케일이 기본인지는 미확인이다.
- **닉네임 자동 학습 금지**: 결과 화면에서 읽은 닉네임을 `player.nickname` 에 저장하는 동작을 다시보기 경로는 호출하지 않는다(스트리머 이름이 내 닉네임 자리에 들어가므로). 그 VOD 의 `streamerNickname` 으로만 저장한다.
- **메타데이터**: 스팀 클립 스키마(§3)에 `source: "vod"`, `vodId`, `vodFile`, `streamer`, `vodGameIndex`, `vodOffsetSec`, `gameStartOffsetSec`/`gameEndOffsetSec` 를 더한다. `sessionDir`/`segmentStart`/`matchStartUtc` 는 없다. `source` 가 없는 기존 클립은 `steam` 이다.
- **라벨은 같은 `userLabel`** 이지만 평가 도구는 기본이 스팀 표본만이다(`--source steam|vod|all`). 해상도·화질이 달라 섞으면 정해 둔 가중치의 평가가 흔들리므로 따로 평가해 비교한다.
- **자동 정리는 v1 에 적용하지 않는다.** 원본이 사용자 파일로 남아 지워도 다시 뽑을 수 있다(스팀은 링버퍼 때문에 영구 손실이라 필요했다).

### 핵심 설계 원칙

**녹화 소스는 인터페이스로 추상화한다.** Steam 녹화 포맷은 문서화되지 않은 내부 포맷이라 밸브 업데이트로 언제든 깨질 수 있다. `RecordingSource` 인터페이스를 두고 `SteamRecordingSource`를 구현하되, 최악의 경우 `ObsReplayBufferSource`로 갈아끼울 수 있는 구조를 유지한다. **이게 이 프로젝트 최대 리스크에 대한 유일한 방어선이다.**

**외부 서비스에 의존하지 않는다.** 로그·영상·스팀 설정 파일만 읽는다. 네트워크 호출이 없으므로 API 장애·키 만료·레이트 리밋·스펙 변경이 전부 사라진다 (§2.1).

**실시간 화면 캡처를 하지 않는다.** 스팀이 이미 녹화 중이므로 그 결과물을 사후 분석한다. 인게임 오버헤드 0, 검출 시각이 곧 영상 타임코드라 매핑도 공짜.

**검출은 전부 하고, 필터는 나중에 건다.** 보관 정책을 바꿔도 재추출이 필요 없도록 태그를 메타데이터에 남긴다 (§1).

**LLM을 핫패스에 넣지 않는다.** 20분 매치를 2fps로 샘플링하면 2400프레임이고, 1080p 한 장이 약 1.8k 토큰이라 매치당 400만 토큰(대략 $10) 수준이다. 고정 UI 영역 픽셀 매칭은 OpenCV가 공짜로 더 빠르고 정확하다. LLM은 클립 제목 다듬기 정도에만 선택적으로 쓴다.

### 프레임 샘플링 전략

**세그먼트 단위로 샘플링한다.** 구간 전체를 하나로 병합할 이유가 없다 (§2.4).

```
검출:  init-stream0.m4s + chunk-stream0-NNNNN.m4s  →  N번 세그먼트 3초를 독립 디코딩
컷:    실제로 자를 구간의 세그먼트만 병합  →  ffmpeg -c copy
```

조사에서 2시간 세션 전체에 걸쳐 56개 세그먼트를 이렇게 샘플링했고 전부 성공했다. 수십 초 걸렸다.

#### ★ 키프레임만 디코딩한다

검출 비용의 거의 전부가 HEVC 디코딩이다. 실측했다(영상 60초 = 세그먼트 20개 기준).

| 방식 | 60초 처리 | 배속 | 20분 매치 환산 |
|---|---|---|---|
| 전체 디코딩 (소프트웨어) | 12.6초 | 4.8x | 4분 10초 |
| 전체 디코딩 + `-hwaccel d3d11va` | 9.4초 | 6.4x | 3분 8초 |
| **키프레임만 (`-skip_frame nokey`)** | **1.1초** | **55x** | **22초** |
| **키프레임만 + `-hwaccel d3d11va`** | **0.59초** | **102x** | **12초** |

**16배 차이인데 정밀도는 거의 잃지 않는다.** 키프레임은 세그먼트당 1개, 3.000초 간격이고(§2.4), `-c copy` 컷도 같은 3초 격자에만 붙는다. **검출 정밀도와 컷 정밀도가 정확히 일치한다.**

포기하는 것은 3초 미만의 짧은 교전인데, 최소 길이 필터가 어차피 버릴 대상이다. 정밀도가 모자라다고 판명되면 **키프레임 전체 스캔 → 경계 부근만 전체 디코딩**하는 2패스로 간다. 상세는 [plan.md §5.1](plan.md).

### 전투 구간 검출 — 앵커 신호

> ⚠ 이 신호는 **전투 상태**만 알려준다. 야생동물 사냥도 똑같이 켜진다 (§1, §2.12).
> 여기서 나온 구간은 후보일 뿐이고, PvP 여부는 §2.12의 점수로 따로 판단한다.

**초상화 배지(§2.7)의 주황 픽셀 수만 센다.** 제일 싸고 제일 확실하다. 이것부터 만들 것.

- 배지 on/off 로 교전 구간 `[t_start, t_end]` 를 뽑는다.
- 짧은 off 구간(1~2 샘플)은 애니메이션/판독 실패일 수 있으니 갭 메우기(hysteresis)를 넣는다.
- 마찬가지로 아주 짧은 on 구간(몬스터 한 대 때리고 끝난 경우 등)은 **최소 길이 필터**로 걸러낸다. 임계는 설정값.
- "판독 불가" 프레임은 직전 상태를 유지한다. 교전 종료로 치지 말 것.

### 사망·관전 구간 처리

§2.0 대로 **`K`는 항상 내 값이라 카운터 오판 걱정은 없다.** 그래도 이 구간을 따로 다뤄야 하는 이유는 둘이다.

1. **관전 화면은 UI가 다르다.** 좌표가 안 맞으므로 판독 결과를 믿으면 안 된다. **"판독 불가"로 처리할 것.**
2. 내가 죽어있는 동안 팀원이 싸우는 건 내 교전이 아니다. 추출 대상에서 뺀다.

구현:

- **1차: 초상화 ROI** (`x 690..860, y 1250..1400`)의 채도·밝기 램프.
- **2차(교차검증): 화면 중앙 월드 영역** (가로 20~80%, 세로 15~72%).
- **수 초에 걸친 단조 하강**을 신호로 삼는다. 절대 임계는 밤 맵/실내에서 오탐한다.
- 사망 구간의 **끝**은 초상화가 정상 채도로 복귀하는 시점으로 잡는다. 부활 순간 샘플이 아직 없어 잠정이다 (§6 0.5단계).
- **사망한 교전 자체는 버리지 않는다.** `death` 태그를 달아 남긴다 — 복기 가치가 제일 높은 구간이다. 제외하는 건 *사망 이후 부활까지의 구간*이다.
- 보조 신호: 초상화 중앙의 부활 카운트다운 숫자, 스킬바 회색 비활성화, `"일원이 사망하였습니다"` 텍스트.

- 조사에서 HUD가 보이는 **49프레임 전부 판독됐다** — 어두운 실내, 초록 수풀, 붉은 피격 이펙트, 밝은 하늘 모두.

|---|---|---|
| 휘도 > 110 | 49 | **49** (전부 다름) |
| 휘도 ≥ 210 AND 채도 ≤ 40 | 41 | 34 |

안티에일리어싱 경계가 배경과 블렌딩되므로 같은 숫자도 프레임마다 비트마스크가 다르다.

→ **해시/정확 매칭은 쓸 수 없다. `cv2.matchTemplate` 상관 기반으로 갈 것.**

#### 값 전환 타이밍

`K 5 → 6` 전이를 60fps로 측정했다.

- **자형 전환은 한 프레임에 끝난다.** 크로스페이드 없음.
- 다만 새 숫자에 **알파 페이드인**이 붙어 약 0.15초에 걸쳐 불투명해진다 (밝기 113 → 169 → 220 → 255).
- **`V ≥ 210` 같은 높은 휘도 임계는 전환 직후 5~8프레임을 "HUD 없음"으로 오판한다.** 조사 중 실제로 이 오탐이 났다. 임계를 낮추거나 상관 매칭을 쓸 것.

#### 로비 화면 배제

로비도 같은 영역에 흰 아이콘(지구본/메일/톱니, `x 2391..2525`, `y 30..54`)을 그린다. 흰 픽셀 수가 255~259로 숫자(56~96)와 크게 달라 쉽게 배제된다.

### 해상도 프로필

**좌표를 하드코딩하지 말 것.** 해상도는 환경에 따라 바뀐다 (§2.4).

- 런타임에 `session.mpd`의 `width`/`height`를 읽어 프로필을 고른다.
- 설정 파일에 `{ "2560x1440": { "badge_roi": [...], "k_roi": [...], ... } }` 형태로 분리한다.
- **측정된 프로필은 2560x1440 하나뿐이다.** 모르는 해상도를 만나면 비례 스케일로 추정하되 **신뢰도를 낮추고 경고를 남긴다.** 조용히 틀리는 것보다 낫다.

### 클립 구간

- **교전 구간 기반이 기본이다.** `교전 시작 -5초 ~ 교전 종료 +8초`. 앞뒤 여유는 설정값.
  - 교전 구간 판독에 실패하면 **앵커(K/A 증가 시점) -30초 ~ +8초** 로 폴백한다.
  - 교전이 지나치게 길면(장기 난전) 상한을 둔다. 기본 90초, 설정값.
- 겹치는 구간은 병합.
- 컷은 `-c copy` + 키프레임 스냅. 재인코딩 없이 거의 즉시 끝난다.
- **★ 키프레임 간격이 정확히 3.000초다.** 즉 `-c copy` 컷은 3초 격자에만 붙는다.
  - 지정한 경계보다 앞뒤로 최대 3초씩 늘어난다.
  - **복기 목적에는 앞이 길어지는 게 손해가 아니므로 그대로 둔다.** 메타데이터에는 실제 경계를 기록한다. 정확한 경계가 필요한 경우에만 재인코딩 옵션을 켠다.

- 캐릭터 이름이 아직 안 나오는 단계에서는 `myCharacter`/`teamCharacters` 를 비우고 제목을 `3일차 낮` 까지만 만든다.

### ★ UI 스택 선택 근거

"세련되면서 RAM을 적게 먹는 것"이 요구사항이다. 후보를 비교했다.

| 방식 | 추가 RAM(대략) | 배포 크기 | 평가 |
|---|---|---|---|
| **pywebview + WebView2** | **40~80 MB** | +0 MB | **추천.** Windows 10/11에 WebView2가 기본 탑재라 런타임을 안 싣는다. 파이썬 프로세스에 자연스럽게 붙는다 |
| 브라우저로 열기 | 0 (기존 브라우저 재사용) | +0 MB | 제일 가볍다. 다만 "앱 같지 않다". **폴백으로 지원할 것** |
| Tauri | 30~80 MB | +5~10 MB | 가볍지만 Rust 툴체인이 필요하고 파이썬 백엔드와 조합이 어색하다 |
| Electron | 150~300 MB | +120 MB 이상 | **쓰지 말 것.** 크로뮴 런타임을 통째로 싣는다 |

**결론: React + Vite 로 정적 빌드 → FastAPI가 서빙 → pywebview 창으로 띄운다.** `--browser` 플래그로 기본 브라우저에서 열 수 있게 폴백도 같이 둔다.

프론트엔드 세부:

- **Vite + React + TypeScript.** 빌드 산출물은 정적 파일이라 서버 부담이 없다.
- **Tailwind CSS.** MUI 같은 무거운 컴포넌트 라이브러리는 피한다. 필요하면 shadcn/ui 처럼 **소스를 복사해 쓰는** 방식이 번들 크기에 유리하다.
- 클립 수가 수천 개가 되면 목록은 **가상 스크롤**(`@tanstack/react-virtual`)을 쓴다. 썸네일은 lazy-load.
- 상태 관리는 별도 라이브러리 없이 시작한다. 필요해지면 그때 넣는다.

### HEVC가 뭐고 왜 신경 쓰는가

**HEVC(= H.265)는 영상 압축 방식의 이름이다.** 영상을 파일에 담을 때 어떻게 줄일지를 정한 규격으로, 이전 세대인 **H.264(AVC)** 보다 같은 화질에서 파일이 대략 절반이다. 스팀이 HEVC로 녹화하는 이유도 이것이다 — 2시간치를 디스크에 계속 들고 있어야 하니까.

문제는 **HEVC에 특허료가 걸려 있어서 Windows나 브라우저에 기본 내장되지 않는다**는 점이다. 재생하려면 별도의 디코더(코덱)가 있어야 한다.

**이 PC는 이미 갖고 있다.** 설치된 코덱을 확인했다.

```
Microsoft.HEVCVideoExtension   2.5.33.0   Status: Ok
```

- 이건 **PC·GPU 제조사가 무료로 끼워 넣는 판**이다. MS Store에서 개인이 따로 사는 `Microsoft.HEVCVideoExtensions`(복수형, 유료)와는 다른 패키지다.
- 그래서 **"설치한 기억이 없는데 스팀 녹화가 잘 재생된다"** 가 성립한다. 제조사가 넣어둔 것이다.
- GPU(RX 6600 XT)도 HEVC 하드웨어 디코딩을 지원한다.

**결론: 이 PC에서 HEVC 재생은 문제없을 가능성이 높다.** WebView2는 OS 디코더를 쓰므로 그대로 재생될 것이다.

그래도 대비는 해둔다.

- **H.264 프록시 생성을 옵션으로 둔다. 기본값은 끔.** 개인용 도구이고 이 PC는 재생되니까.
- 재생이 안 되면 UI가 감지해서 **프록시 생성을 켜라고 안내**하거나 시스템 기본 플레이어로 연다.
- 다른 PC에 배포할 일이 생기면 그때 기본값을 바꾸면 된다.
- 썸네일은 JPEG이라 영향 없다.

실제 재생 테스트는 UI 초기 단계에서 한다 (§6 0.5단계).

### 배포 시 주의

- **★ ffmpeg 번들은 선택이 아니라 필수다.** 조사 PC의 PATH에 ffmpeg가 없었다. 시스템 곳곳에 다른 앱이 끼워둔 빌드가 있었지만(2014~2015년판 포함) 버전이 제각각이라 의존할 수 없다. LGPL 빌드를 번들하거나 첫 실행 시 다운로드할 것. GPL 빌드를 함께 배포하면 라이선스 의무가 생긴다.
- **백신 오탐**: PyInstaller + 파일 감시 조합은 Defender 오탐이 잦고, 코드 서명이 없으면 SmartScreen 경고가 뜬다. README에 명시.
- `--onefile`은 첫 실행이 느리고 오탐이 더 심하므로 `--onedir` 사용.
- **안티치트 안전**: 게임 프로세스를 건드리지 않고 내 파일만 읽는다. 네트워크 호출도 없다. README에 명시.

## 5. 개발 방식

**검출기는 테스트 하네스를 먼저 만든다.**

1. 샘플 프레임을 폴더에 모으고 **교전 구간 / 킬·어시 / 사망**을 수동 라벨링한다(최소 30개).
2. 검출기를 이 라벨셋에 대해 정밀도/재현율로 평가한다.
3. 튜닝은 이 루프 안에서만 돈다.

> **라벨셋 구축은 예상보다 싸다.** `init + 단일 세그먼트` 디코딩(§2.4) 덕분에 2시간 세션의 임의 시점 프레임을 초 단위로 뽑을 수 있다. 조사에서 56프레임 뽑는 데 수십 초 걸렸다. [scripts/probe/](../scripts/probe/) 의 `sample_segments.sh` 를 그대로 쓰면 된다.

**★ `K` 카운터를 자동 정답지로 쓴다.** 매치 마지막 인게임 프레임의 `K` 최종값이 그 매치의 총 킬 수다. 검출기가 센 증가 횟수와 대조하고, 불일치하면 로그를 남겨 튜닝 대상으로 쌓는다. 실사용이 곧 회귀 테스트가 되는 구조다. **외부 API 없이 성립한다.**

#### 실사용 피드백으로 바뀐 UI (2026-09-21, 구현 완료)

첫 실사용 뒤 "체감을 해보며 다듬자"는 방침으로 아래를 고쳤다. 상세는 [plan-ui.md](plan-ui.md).

- **게임 단위 목록(접이식)** — 각 게임은 dak.gg 전적처럼 접힌 한 줄(순위·모드·시각·캐릭터·TK/K/A·클립 수)이고 ▾ 로 영상을 펼친다(결과 배지 문구는 순위·모드만, 탈출은 명시). 원래 설명: 클립을 `sessionDir + matchStartUtc` 로 묶어 게임 섹션으로 보여준다. 섹션은 게임마다 5색을 돌려 쓰는 색 테두리 + 헤더 띠로 구분하고, 헤더에 `게임 N`, 시작 시각, 클립 수, **경기 결과 배지**(`랭크 · 4위 / 7팀 · 실험 종료`, 1위는 금색)가 붙는다. 번호는 화면에 로드된 게임 기준이다.
- **정렬** — **게임 순서**만 정렬 기준을 따른다: 최신 순(기본) / 오래된 순 / 교전 가능성순(게임의 최고 점수 순). **게임 안의 클립은 항상 오름차순**이다. 정렬은 프론트에서 하고 API `sort` 는 쓰지 않는다.
- **플레이어** — 좌우 큰 이전/다음 버튼(끝에서 비활성), 삭제 버튼(삭제 후 다음 영상으로 이동), 저장 버튼. 볼륨·음소거는 localStorage 에 저장해 다음 영상·재접속에서도 유지한다(영상마다 `<video>` 가 다시 만들어져 초기화되던 문제). 저장 창이 떠 있는 동안엔 단축키를 멈춘다. 라벨 기능은 그대로다.
- **영상 자르기** — 플레이어에서 남길 구간을 고르면 나머지는 삭제된다(불필요한 사냥·대치 제거용). `ffmpeg -ss S -to E -i clip.mp4 -map 0 -c copy` 로 임시 파일에 잘라 `os.replace` 로 원본을 바꾼다(실패하면 원본 유지). MP4 편집 리스트 덕에 시작이 키프레임이 아니어도 프레임이 정확하다(5.5초 지점과 픽셀 차이 0.0). 메타데이터는 `durationSec`/`videoOffsetSec` 를 갱신하고 `trimmed`·`originalDurationSec` 를 남긴다. `combatStart/EndOffsetSec` 는 세션 시각이라 그대로다. 보이지 않는 프리롤(최대 3초)이 파일에 남는 것이 재인코딩 없는 방식의 대가다.
- **게임 단위 삭제·용량** — 게임 행에서 클립을 한꺼번에 휴지통으로/복구/완전 삭제하고, 접힌 행에 클립 총 용량(`sizeBytes` 합)을 표시한다.
- **카드** — 이미 라벨한 클립은 선택된 라벨 버튼만 보인다(안 한 클립은 둘 다).
- **영상 저장(내보내기)** — 브라우저는 로컬 절대경로를 못 다루므로 서버가 `GET /api/fs/dirs`·`POST /api/fs/mkdir` 로 폴더를 탐색·생성하고 `POST /api/clips/{id}/export` 로 mp4 를 복사한다. 같은 이름이면 `(2)` 를 붙여 덮어쓰지 않는다. 저장할 때마다 그 폴더가 `paths.exportDefault` 로 기억돼 다음 저장 창의 시작 위치가 된다. 사용자는 `S:
eplay\<캐릭터>` 처럼 폴더를 나눠 보관한다.
- **옵션 모달** — 헤더 `⚙ 옵션`. 내 닉네임과 영상 저장 기본 폴더를 관리한다. 설정 API 는 매번 설정 파일을 다시 읽는다(워처가 학습한 닉네임을 메모리 사본이 덮어쓰지 않게).
- **디스코드 10MB 제한 대응 — 클립 재인코딩은 접었다.** 목표 용량에서 비트레이트를 역산해 `libx264` 2-pass 로 굽는 실험 버튼(`GET /api/clips/{id}/discord-download`)을 한 번 만들어 실측했지만, 45초 안팎 클립을 10MB 에 우겨넣으면 720p 이하로 내려가면서 닉네임 등 작은 텍스트가 못 읽을 정도로 뭉개져 실용성이 없었다(2026-09-23). **되살릴 거면 인코딩으로 용량을 줄이는 방식이 아니라 다른 접근을 먼저 검토할 것**:
  - **외부 클립 호스팅 사이트(Medal.tv, Streamable 등)에 자동 업로드하고 공유 링크를 받아오는 기능** — 기술적으로는 가능하지만 §7.8/§2.1 "외부 서비스에 의존하지 않는다·네트워크 호출이 없다"(안티치트 안전 근거, §1009) 원칙과 정면으로 부딪힌다. 이 원칙을 깨면서까지 넣을지는 별도 논의가 필요하다.
  - **자체 호스팅 공유 사이트를 별도 프로젝트로 만들기** — 이 앱과는 분리된 서비스라 위 원칙과 안 부딪힌다. 후보지로 OCI(Oracle Cloud Infrastructure) Always Free 인스턴스를 검토함: ARM Ampere A1 기준 컴퓨팅 4코어·24GB RAM, 아웃바운드 트래픽 월 10TB 로 이 용도엔 넉넉하지만 블록 스토리지는 총 200GB 라 클립을 무한정 쌓아두긴 어렵고 보관 기간 만료 정책이 필요하다. 압축 없이 원본 화질을 그대로 서빙할 수 있다는 게 핵심 장점.

### ★ 4단계 — PvP 판별 (§2.12) ✅ 구현 완료, **다음은 사용자 라벨링**

1~3단계는 끝났지만, 실사용에서 **뽑힌 클립의 대부분이 야생동물 사냥**이라 목적을 못 채운다 (§1). 이 단계가 v1을 실제로 쓸 만하게 만든다.

#### ⚠ 그 전에 — K/A 검출이 꺼진 채로 돌고 있었다

실사용으로 만들어진 클립 60개를 열어보니 **전부 `killDelta=0`, `assistDelta=0`, `matchKills=null`** 이었다. HUD 에는 `TK 13 K 4 A 2` 가 멀쩡히 찍혀 있는데도 그렇다.

원인은 간단하다. `cli/watch.py` 가 `--k-templates` 를 **명시적으로 줘야만** 숫자 템플릿을 싣는다. `run.bat` 도 트레이 앱도 그걸 안 넘긴다. 템플릿은 `data/templates/digits/2560x1440.npz` 에 이미 있는데 안 쓰이고 있었다.

**즉 가장 강력한 확정 증거가 통째로 꺼져 있었다.** "뽑힌 클립이 죄다 `no_result` 더라" 의 상당 부분이 PvE 문제가 아니라 이 설정 구멍이다. 4단계의 어떤 작업보다 먼저 고쳐야 하고, **고치는 즉시 라벨 품질이 올라가 나머지 단계가 쉬워진다.**

- 해상도에 맞는 템플릿을 **기본으로 자동 탐색**하게 바꿀 것 (ffmpeg·녹화 경로 자동 탐지와 같은 방식).
- 템플릿을 못 찾으면 **조용히 넘어가지 말고 경고를 남길 것.** 지금은 아무 말 없이 꺼진다.

#### 순서

실측이 먼저다. 순서를 지킬 것 — **앞 단계가 뒤 단계의 정답 라벨을 만들어준다.**

1. ~~**ROI 실측**~~ — ✅ **대부분 완료** (§2.12 실측표). 미니맵 · 지역명 · 팀 패널 · 초상화 좌표를 실제 녹화본에서 쟀다. **남은 것 둘**: ① 전멸 배너 ROI(배너가 찍힌 프레임을 아직 못 찾음) ② 배너가 내 팀 전과일 때만 뜨는지.
2. **개인 사망 검출 (관전 UI 전환)** — 지금 `death` 태그는 팀 전멸만 잡고 있을 가능성이 높다(§2.12 5-0). 개인 사망은 확정 PvP 증거인데 비어 있다. **관전 구간 제외도 같이 해결된다** — 그 화면은 팀원 시점이라 미니맵·지역명을 내 것으로 읽으면 전부 오판이다.
3. **팀원 사망** — ✅ 검출 가능 확인 (팀 슬롯 빨강 0% → 7~12%).
3-1. **전멸 배너** — 후순위. 위 신호들과 상당 부분 겹치고 ROI 도 아직 못 쟀다.
4. **지역명 판독** — 헤더 텍스트 템플릿 ~20개. K/A 판독과 같은 기법이라 재사용이 쉽다 (§2.10).
5. **정답 라벨 수집** — 1~4번 확정 증거로 판정된 구간 = PvP 정답, 아무 일 없던 긴 전투 구간 = PvE 후보.
6. **미니맵 적 링 — 표본을 늘려 다시 잰다.** 색 매핑(빨강=적)과 초기 분리(PvP 0.8+ vs 사냥 0.6-)는 확인했다(§2.12). 다만 표본이 8개뿐이고 PvP 쪽이 전부 사망 클립이다. **K/A 를 켠 뒤 킬 클립까지 포함해 다시 재고**, 그때도 갈리면 채택한다. 거리 임계는 그다음이다 — 개수만으로 갈린다면 거리는 필요 없을 수도 있다.
7. **점수·가중치 배선** — `pvpScore` / `pvpSignals` 를 메타데이터에 쓰고, UI에서 정렬·필터·라벨링.

목표: **사냥 클립을 상위 목록에서 몰아내되, 진짜 교전은 하나도 안 버린다.** 재현율을 정밀도보다 우선한다 (§1).

### 7.2.1 ★ 시간 여유와 백로그 — 링버퍼를 이기는 법

**추출은 매치 종료 직후에 돈다.** 하지만 링버퍼가 계속 앞에서 깎기 때문에(§2.6), "언제까지 안전한가"를 숫자로 알고 있어야 한다.

#### 남은 여유 계산

```
세그먼트는 120분이 지나면 지워진다.

매치의 첫 세그먼트 나이 = (매치 종료 후 경과 시간) + (매치 길이)
남은 여유              = 버퍼길이 - 매치의 첫 세그먼트 나이
```

| 상황 | 매치 길이 | 종료 후 경과 | 남은 여유 |
|---|---|---|---|
| **정상** (앱이 떠 있음) | 20분 | 0분 | **100분** |
| 앱이 30분 꺼져 있었음 | 20분 | 30분 | 70분 |
| 앱이 1시간 30분 꺼져 있었음 | 20분 | 90분 | **10분** — 위험 |
| 앱이 2시간 넘게 꺼져 있었음 | 20분 | 120분+ | **소실** |

**정상 동작에서는 100분 여유가 있다.** 매치(9~20분)와 버퍼(120분)의 차이가 워낙 커서 여유가 부족할 일이 없다. 실시간성 자체는 문제가 아니다.

#### 백로그 복구 (`watch.processBacklog`)

앱이 꺼져 있었거나 죽어 있던 동안 끝난 매치는 **시작할 때 한 번 훑어서 복구한다.**

1. `Player.log` + `Player-prev.log` 를 거슬러 읽어 매치 경계 목록을 만든다 (§2.3)
2. 이미 처리한 매치는 건너뛴다 (처리 이력을 상태 파일에 남긴다)
3. 남은 매치를 **오래된 것부터** 처리한다 — 지워지기 직전인 것이 먼저다
4. 각 매치마다 남은 여유를 계산해 §아래의 구출 정책을 적용한다

> **순서가 중요하다.** 최신 매치부터 처리하면 오래된 매치가 처리를 기다리는 동안 지워진다.

#### 구출 정책 (`watch.rescueThresholdMin`)

분석(프레임 샘플링 → 검출)에는 시간이 걸린다. 그 사이에 원본이 깎이면 늦는다.

| 남은 여유 | 동작 | 이유 |
|---|---|---|
| **> 임계(기본 20분)** | 평소대로. 샘플링해서 분석하고, 실제로 자를 세그먼트만 복사 | 디스크를 아낀다 |
| **≤ 임계** | **원본 세그먼트를 통째로 임시 폴더에 먼저 복사한 뒤 분석** | 분석 도중 원본이 사라져도 된다 |

구출 복사의 비용:

- 20분 매치 = 영상 세그먼트 약 400개 × 8.9 MB ≈ **3.5 GB** (+ 음성 30 MB)
- 복사만 하면 되니 수십 초
- 복사 전에 `paths.temp` 의 여유 공간을 확인하고, 부족하면 **구출을 포기하는 대신 샘플링 간격을 넓혀 분석을 서두른다**

> 평상시에 이 경로를 타지 않는 게 정상이다. 여유가 100분인데 20분 임계에 걸릴 일은 없다.

#### 부분 소실

링버퍼는 매치를 통째로 지우지 않고 **앞에서부터 깎는다.** 그래서 "매치의 앞부분만 사라진" 상태가 생긴다.

- 세그먼트 번호로 접근하기 전에 **항상 존재를 확인한다** (§2.6).
- 남아있는 구간만 분석하고, **없는 구간은 조용히 건너뛰지 않고 기록한다.**
- 클립 메타데이터에 `sourceIncomplete: true` 와 실제로 확보한 세그먼트 범위를 남긴다.
- UI에서 그런 클립에 표시를 달아, "교전이 더 있었는데 못 뽑은 건지" 알 수 있게 한다.

#### 영구 소실은 영구 소실이다

**앱이 2시간 넘게 꺼져 있었으면 그 매치는 복구할 방법이 없다.** 스팀이 이미 지웠고 우리가 할 수 있는 게 없다.

그래서:

- **자동 시작을 기본으로 켠다** (`ui.autoStart`). 이게 실질적인 방어책이다.
- 백로그 복구 중 **소실된 매치를 발견하면 로그와 UI에 남긴다.** 조용히 넘어가면 사용자는 클립이 왜 없는지 모른다.
- 트레이 아이콘에 "감시 중" 상태를 표시해, 꺼져 있는 걸 눈치챌 수 있게 한다.

#### 실패 재시도

추출이 실패하면(디스크 부족, ffmpeg 오류 등) `watch.retryCount` 만큼 재시도한다. 끝내 실패하면 **매치를 "미처리"로 남겨두고** 다음 시작 때 백로그가 다시 집어가게 한다 — 그때까지 버퍼에 남아있다면.

**필터는 생성 단계에만 적용된다.** 검출은 항상 전부 하므로, 나중에 필터를 풀면 그 시점부터의 매치에 반영된다. 이미 지나간 매치는 버퍼에 남아있는 한 수동 재처리가 가능하다.

**라벨 보관소.** 영구 삭제(수동 완전 삭제·휴지통 비우기·유예 만료·`permanent` 자동 삭제) 직전에 `userLabel` 이 pvp/pve 인 클립은 메타데이터에서 `thumbnailPath`·`deletedAt`·결과 이미지 경로를 뺀 사본을 `clips/.labels/<클립ID>.json` 에 남긴다(`pipeline/label_archive.py`). 라벨 없는 클립은 남기지 않는다. 영상이 아니라 근거·라벨이 평가(§2.12, `tools/eval_pvp.py`)의 자료이기 때문이다. 목록·복구 대상이 아니다(`scan_clips` 는 서브폴더를 보지 않는다).

**게임 기록 보관.** 영상 정리와 전적 기록은 분리한다. 용량을 차지하는 건 영상(클립당 60~80MB)이고 경기 요약은 몇 KB 라, 자동 정리로 클립이 다 사라져도 요약을 `clips/.games/<경기키>.json` 에 남기고 결과표 이미지(약 100~200KB)도 유지한다(`retention.keepGameRecords`, 기본 켬). 적용 지점은 라벨 보관소와 같은 네 삭제 경로다. 게임 단위 삭제는 기록까지 지운다. 구현은 `pipeline/game_records.py` — 결과표를 못 읽은 경기는 요약할 게 없어 기록하지 않는다. 상세는 [plan-ui.md §0](plan-ui.md).

UI에서 제공할 동작:

- **삭제 / 복구** — 다중 선택, 되돌리기(undo) 지원
- **고정(pin)** — 자동 정리에서 보호
- **내보내기** — 경로를 골라 복사 또는 이동. 자주 쓰는 경로는 즐겨찾기로 저장
- **휴지통 비우기** — 유예 기간 전이라도 수동으로
- **일괄 작업** — 필터로 고른 전체에 한 번에 적용

> **구현 (2026-09-21)**: 위 표의 `autoCleanEnabled`·`maxAgeDays`·`maxTotalGB`·`maxCount`·`trashDays`·`deleteMode`·`protect*` 가 실제로 동작한다(`pipeline/cleanup.py`). 이전에는 선택/삭제 함수만 있고 호출하는 곳이 없어 클립도 휴지통도 영원히 남았다. 앱이 1시간마다 설정 파일을 다시 읽어 실행하고, `POST /api/cleanup {dryRun}` 로 미리보기·즉시 실행한다. 클립 나이는 **경기 시각(`matchStartUtc`)** 기준이다(메타데이터 파일 수정 시각은 라벨링 때마다 바뀐다). 휴지통 이동은 같은 드라이브 안의 이동이라 디스크가 바로 비지는 않고 `trashDays` 뒤에 실제로 줄어든다. 클립이 다 사라진 경기의 결과표 이미지도 함께 지운다. 옵션 모달의 "자동 정리" 탭에서 설정한다.

### 7.8 불변 사항

설정으로 바꿀 수 없는 것들이다.

- **원본 녹화본은 절대 수정하지 않는다.** 읽기만 한다. **다시보기 원본 파일도 같다** — 앱은 그 파일을 수정·삭제·이동하지 않는다(클립만 지운다).
- 네트워크 호출을 하지 않는다 (자동 업데이트 확인은 예외, v2). 다시보기도 사용자가 받아 둔 로컬 파일만 읽는다.
- 게임 프로세스를 건드리지 않는다.

### 7.9 디스크 사용량 감각

- 스팀 버퍼: 1440p60에서 약 **8.5 GB/시간**. 2시간이면 17 GB (우리가 쓰는 게 아니라 스팀이 점유)
- 클립: 교전 30~40초 × 15.7 Mbps ≈ **60~80 MB/개**. 매치당 5~10개면 **0.4~0.8 GB/매치**
- 프록시(켤 경우): 1080p CRF 23이면 원본의 대략 1/4~1/5
- → **`retention.maxTotalGB` 를 걸어두는 걸 권한다.** 하루 5매치면 주당 15~25 GB다.

### 7.10 다시보기 (§2.14, 미구현)

| 키 | 기본값 | 설명 |
|---|---|---|
| `vod.sources` | `[]` | 다시보기 영상 **파일 또는 폴더 경로** 목록. 폴더면 안의 `mp4` `mkv` `ts` `webm` 을 찾는다 |
| `vod.recursive` | `false` | 폴더 경로를 하위 폴더까지 훑을지 |
| `vod.autoAnalyze` | `false` | 새로 발견한 영상을 자동으로 분석. 7~8시간짜리가 저절로 돌지 않게 기본 꺼짐 |
| `vod.sampleIntervalSec` | 3 | 키프레임만 쓸 수 없는 영상에서 프레임을 뽑는 간격 (V0 실측 후 확정) |
| `vod.gameGapSec` | 미정 | 인게임 프레임이 이 시간 이내로 끊기면 같은 게임으로 잇는다 (V0 실측 후 확정) |
| `vod.hwaccel` | `null` | 디코딩 하드웨어 가속 (`d3d11va` 등) |
| `vod.streamers` | `{}` | 영상 ID → 스트리머 표시명. UI 에서 편집 |

- 클립 구간(`clip.*`)과 필터(`filter.*`, §7.3)는 **스팀과 같은 설정을 공유한다.** 다르게 쓰고 싶은 사례가 실사용으로 확인되면 그때 분리한다.
- `retention.*` 자동 정리는 다시보기 클립에 적용되지 않는다(v1). 사용자가 UI 에서 직접 삭제·휴지통 관리를 한다.
