# 과거 녹화 전체 분석 (로그에 없는 경기 복구)

> 목적: 게임 로그(`Player.log`)에 남지 않은 과거 경기도 스팀 녹화 영상만으로 찾아 클립을 만든다.
> 계기: 친구 PC 에서 어제·엊그제 녹화가 분석되지 않았다. 앱이 경기 목록을 `Player.log`/`Player-prev.log`(최근 게임 실행 2번 분량)에서만
> 얻기 때문이다. 앱을 늦게 설치한 사용자는 스팀에 녹화가 남아 있어도 그 경기가 있었다는 사실을 알 수 없다.
> 진행 상태를 이 문서 §0 에 적는다([CLAUDE.md](../CLAUDE.md)).

## 1. 설계

**핵심 아이디어**: 로그 기반 경로는 "경기 시작·종료 시각"만 넘겨받으면 나머지(검출·컷·썸네일·결과 화면 OCR)를 다 한다
(`process_match(session, start, end, …)`). 그래서 새로 만들 것은 **경계를 화면에서 찾는 부분**뿐이다.
다시보기(VOD) 분석이 이미 프레임 판독(`analyze_frame`)과 게임 분할(`split_games`)을 갖고 있다.

```
세션 폴더(bg_1049590_…) ─▶ 세그먼트 키프레임(3초 간격) ─▶ FrameState 판독(캐시) ─▶ split_games ─▶ 게임 구간
   ─▶ 로그·기존 클립과 겹치는 것 제외 ─▶ 오래된 것부터 process_match(스테이징) ─▶ 클립 폴더로 이동
```

- **이터널 리턴 세션만** 본다(폴더 이름의 앱 ID 1049590). 다른 게임 세션은 건너뛴다.
- **경계 보정**: 화면 기준 시작은 로딩이 끝나 HUD 가 뜬 시점이라 로그 시작보다 늦고, 끝은 마지막 인게임 프레임이라 로그 종료(로비 복귀)보다 이르다.
  결과 화면은 경기 끝 뒤에 나오므로 끝에 여유(`POST_GAME_SEC`)를 주되 다음 경기 시작을 넘지 않게 한다.
- **취소 시 "복원"** = 롤백이 아니라 **이어하기 + 경기 단위 스테이징**이다. 이 분석은 원본을 읽기만 하고 완성된 클립은 취소해도 유효하다.
  경기 하나는 임시 폴더에 다 만든 뒤 mp4 → 썸네일 → json 순서로 옮기므로, 중간에 멈추거나 컴퓨터가 꺼져도 깨진 클립이 목록에 뜨지 않는다.
  프레임 판독은 캐시에 이어 쓰므로 다시 누르면 저장된 지점부터 계속한다.
- **링버퍼**: 스팀이 새 녹화를 쌓으면 옛 세그먼트를 지운다. 오래된 것부터 처리하고, 처리 중 사라진 구간은 건너뛰며 알린다.
  (실측: 분석 도중 세그먼트가 801 → 616 개로 줄었다.)
- **게임 중 부하**: CPU 를 많이 쓴다. 확인 창에서 게임을 끄고 실행하라고 안내한다(앱은 이미 낮은 우선순위로 돈다).

## 5. 알아 둘 함정

- **결과 화면 탐색은 구간 끝이 로비 복귀라는 전제였다.** 화면 기반 경계는 끝이 마지막 인게임 프레임이라 처음엔 순위가 전부 비었다. `find_result_after`(끝 뒤에서 앞으로) 로 바꿔 해결.
- **프레임 추출이 구간 전체를 임시 파일로 이어붙여 통째로 메모리에 올렸다**(40분 = 9GB). 파이프 스트리밍으로 바꿔 메모리가 일정해졌다. 이 함수는 평소 매치 분석도 쓴다.
- **아는 경기 판별에 로그도 써야 한다.** 클립 폴더만 보면 "로그엔 있지만 아직 처리 전"인 경기를 여기서 또 만들어 감시와 중복된다.
- **링버퍼가 분석 중에도 앞을 지운다**(실측: 세그먼트 801→616). 지워진 구간의 캐시된 판독은 버리고, 앞부분이 잘린 경기는 클립을 부분적으로만 만들 수 있어 건너뛴다. 잘린 경기는 시작 시각이 계속 밀려 같은 경기가 다른 키로 중복 처리될 위험도 있다.
- **소요 시간 예측은 이 PC 기준**이다(25배속). 친구 PC 는 디스크·CPU 에 따라 다르다.

## 6. 남은 확인 필요

1. **친구 PC** — 로그에 없는 어제·엊그제 녹화가 실제로 복구되는지. 진단 zip 으로 결과를 받는다.
2. **4시간 규모** — 약 40GB 세션의 소요 시간과 메모리(스캔은 프레임 한 장 분량이라 문제없을 것으로 보지만 실측 아님).
3. **앞부분이 잘린 경기** — 지금은 건너뛴다. 부분이라도 클립으로 만들지는 사용자 의견을 듣고 정한다.
4. **다른 해상도·다른 UI 크기**에서 게임 분할 정확도.
5. **게임 중 실행** — CPU 를 많이 쓴다. 확인 창이 게임을 끄라고 안내하지만, 실제 프레임 저하는 재 보지 않았다.

## 7. 확인 필요 — 진행률 (B8) — 구현하며 답을 찾음 (2026-09-28)

- **게임당 평균 처리 시간(60~100초)은 이 PC 의 실측 일부다. 이동 평균으로 보정하는가** → **한다.** `AdaptiveGameDuration`(`pipeline/backfill_progress.py`)이 기본값(중앙값 80초)에서 시작해, `run_backfill` 이 게임을 하나 처리할 때마다(성공·실패 모두, 취소는 제외) 실제 걸린 시간(`time.monotonic()` 차이)을 기록하고 최근 5개의 평균으로 다음 게임들의 남은 작업량 추정에 쓴다. 그래서 느린 PC 든 빠른 PC 든 같은 실행 안에서 스스로 맞춰진다(다른 PC 마다 상수를 따로 관리할 필요가 없다). `tests/test_backfill.py::test_adaptive_average_updates_after_each_game_and_is_used_for_the_next_ones_progress` 로 확인.
- **스캔 중 게임 수 추정 방법** → **세션 길이 ÷ 평균 경기 길이(20분, 로비 포함)로 거칠게 추정한다**(`estimate_game_count`). `known_starts`·이전 스캔 캐시로 추정하는 방법은 **채택하지 않았다** — 이 값은 스캔이 끝나기 전 잠깐 쓰이고 스캔이 끝나면 바로 실제 게임 수(`len(todo)`)로 재계산되므로(§0 B8 결정 (1)), 정교하게 만들 실익이 적다고 판단했다. 다만 추정이 실제와 크게 다르면(예: 게임이 훨씬 많이 나옴) 재계산 시 계산값이 순간적으로 내려갈 수 있는데, `MonotonicProgress` 가 화면 표시값을 그대로 지켜준다 — 이게 설계 (2)의 존재 이유다.
- **게임 내부 진행률을 `process_window` 에서 얻을 수 있는가 — 검출 vs 결과 화면 vs 컷 비중** → **얻을 수 있고, 실측했다.** `H:\steam video\video` 실제 세션(3시간 47분 녹화, 이터널 리턴)의 21분짜리 경기 하나(`bg_1049590_20260926_162109`, 18:27:24~18:50:06, 클립 12개)를 그대로 돌려 쟀다: **검출(`detect_match`) 24.8초, 결과 화면 판독(`find_result_after`) 8.8초, 클립 컷·썸네일·메타데이터(클립 12개) 21.6초, 전체 55.2초.** 비중은 45% / 16% / 39%. 이 비율을 `orchestrator.py`의 `DETECTION_PROGRESS_FRACTION=0.45`·`RESULT_SCAN_PROGRESS_FRACTION=0.61(=0.45+0.16)` 로 코드에 반영했다 — 검출은 프레임마다(`detect_source` 의 `on_progress(i, total)`, `SteamSegmentSource.expected_frame_count()`), 결과 화면 판독은 통짜 구간(OCR 은 세부 진행을 못 쪼갠다), 클립 컷은 클립마다 진행률이 올라간다. **경기 길이·클립 수가 다르면 이 비율도 달라질 수 있어 고정 상수의 한계는 있지만**, 60~100초 동안 완전히 멈춰 보이던 이전보다는 낫다. 다른 경기·다른 PC 로 더 재보정할지는 실사용 피드백을 보고 정한다.
- **영상 파일(VOD) 분석 진행률도 같은 문제가 있는가** → **부분적으로.** `pipeline/vod_analyze.py` 는 이미 3단계 고정 비중(`DECODE_SHARE=0.70`·`GAMES_SHARE=0.10`·나머지 0.20)을 쓰고 있어 backfill 의 옛 "고정 반반"보다는 낫다 — 디코딩(70%) 은 실제 디코딩한 초/전체 길이 비율이라 시간에 비례해 정확하게 움직인다. 그러나 **결과 화면 판독(`games`, 10%)과 클립 컷(`cut`, 나머지 20%) 은 여전히 "게임 개수 균등 배분"이다** — 특히 클립 컷 단계는 `report("cut", base + (1-base)*i/n, ...)` 의 `i` 가 **게임 인덱스**라서, 한 게임에 클립이 여러 개면(다시보기는 한 경기에 클립이 몰릴 수 있다, plan-vod §2.9) 그 게임을 처리하는 동안 진행률이 안 움직이다가 다음 게임으로 넘어갈 때만 뛴다 — backfill 이 B8 (3)에서 고친 것과 같은 증상이 결과 화면·클립 컷 단계에 남아 있다. **이번 작업 범위에는 포함하지 않았다** — VOD 분석은 몇 시간짜리라 사용자가 이미 다른 일을 하며 기다리는 경우가 많고(plan-vod §2.7), backfill 처럼 "몇 분 안에 끝나길 기대하며 계속 쳐다보는" 시나리오와 체감 우선순위가 다르다고 판단했다. 고치려면 `pipeline/backfill_progress.py` 의 `Workload`/`MonotonicProgress`/`AdaptiveGameDuration` 을 그대로 재사용할 수 있다(로드맵 후보로 남긴다).
