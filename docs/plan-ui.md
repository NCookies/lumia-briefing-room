- [ ] **클립 유니크 ID(`clipUid`)** (설계만, 미구현 — [SPEC 클립 메타데이터](SPEC.md), [plan-deploy §5](plan-deploy.md), 아래 §4-6 확인 필요) — 지금 클립 ID 는 파일 이름이고(`20260920_134809_03` = 경기 시작 시각 + 번호, 다시보기는 `vod_<영상>_g01_000123`) 한 PC 안에서는 유일하지만 **여러 사용자의 라벨을 서버에서 합치면 겹칠 수 있다**(같은 초에 시작한 경기·같은 번호). 결정: (1) **메타데이터에 `clipUid` 를 새로 둔다.** 클립을 만들 때 한 번 생성하고 그 뒤로 바뀌지 않는다(단일 구간 자르기처럼 같은 클립을 고치는 동작은 유지, 다시 분석으로 새로 만든 클립은 새 `clipUid`). **형식**: 새 클립의 기본 값은 하이픈 없는 무작위 hex(`uuid4().hex`, 예: `b1f6c7e2…`)이고, **구간 분할 조각은 원본 `clipUid` 뒤에 `-<번호>` 를 붙인다**(`b1f6c7e2…-1`, `b1f6c7e2…-2`). 조각을 다시 분할하면 번호를 한 단계 더 붙인다(`b1f6c7e2…-1-3` = 원본의 1번 조각의 3번 조각). 기본 값에 하이픈이 없으므로 `-` 로 잘라 계보를 그대로 읽을 수 있고, **그래서 원본 `clipUid` 를 별도 필드로 남기지 않는다**(`splitFrom` 은 기존대로 원본 파일 ID). 번호는 1부터 조각 시각 순서로 매기되, 같은 부모 밑에 이미 있는 조각(살아 있는 클립·휴지통·보관소 포함)이 있으면 그 최댓값 다음 번호부터 매겨 겹치지 않게 한다. (2) **파일 이름은 바꾸지 않는다** — 라벨 보관소(`clips/.labels/`)·게임 기록(`clips/.games/`)·휴지통·API URL 이 모두 파일 이름을 키로 쓰고 사람이 읽기 쉬운 시각 형식이라, 이름을 바꾸면 이미 쌓인 라벨·기록이 끊긴다. (3) **이미 있는 클립은 한 번 채워 넣는다** — 파일 이름은 그대로 두고 메타데이터에 `clipUid` 만 추가한다. **방식·시점(결정)**: 앱이 시작할 때 백그라운드 스레드로 스팀 클립 폴더와 영상 파일 클립 폴더를 한 번 스캔해 `clipUid` 가 없는 클립에만 채운다. 이미 있으면 건너뛰므로 여러 번 돌려도 같고, 채우는 도중 앱이 꺼지거나 개발용 자동 재시작(`dev.bat`)이 돌아도 이어서 된다. 메타데이터 파일은 임시 파일에 쓴 뒤 교체(`os.replace`)해 반쯤 쓰인 파일이 남지 않게 하고, 서버의 클립 수정·삭제와 같은 락을 쓴다. 새로 만드는 클립은 만들 때 바로 부여한다. 안전망으로 라벨 전송·`GET /api/clips` 가 `clipUid` 없는 클립을 만나면 그 자리에서 채운다. 별도 `tools/` 스크립트는 만들지 않는다. (4) 라벨 보관소 항목에도 `clipUid` 를 함께 남긴다. (5) **서버 전송의 키는 `(installId, clipUid)`** 이며 서버는 파일 ID 를 키로 쓰지 않는다([plan-deploy §5](plan-deploy.md)). (6) 화면의 클립 ID 표시(카드·모달, 개발 모드)는 사람이 읽는 파일 ID 그대로이고 `clipUid` 는 화면에 보이지 않는다(대화에서 클립을 가리킬 때는 파일 ID + 표시용 설치 ID, [plan-deploy D14](plan-deploy.md)). 순수 로직(생성·채워 넣기·보관소 기록)과 API 는 TDD

고정(pin)→휴지통 이동(trash)→복구(restore) 라운드트립은 실제 API(curl)로 직접

**범위 판단**: SPEC §3 3단계가 요구하는 전체(타임라인 뷰 + 그리드 뷰 + 모든 필터 +
정리 도구 + 재생)를 한 번에 다 만들지 않는다. **백엔드 API를 먼저 완결하고
(TDD로, 이미 검증된 파이프라인처럼), 프론트는 동작하는 최소 버전(그리드 뷰 +

타임라인 뷰·고급 필터·내보내기는 v1.1 후보로 미룬다 — SPEC 자체도 "타임라인
중심"이라고 못박았지만, 그리드 뷰가 먼저 있어야 API를 검증하며 반복할 수 있다.

## 1. 왜 이 순서인가

| 후보 | 장점 | 단점 |
|---|---|---|
| **백엔드 API 먼저** | 지금까지와 같은 파이썬 TDD로 계속 검증 가능. pipeline/retention.py 를 그대로 노출하면 됨 | 눈에 보이는 화면이 늦게 나옴 |
| 프론트 먼저(목업 데이터) | 화면을 빨리 봄 | API 계약이 나중에 바뀌면 다시 작업. 실제 클립 데이터 검증이 늦어짐 |

**백엔드 먼저로 정한다.** 이 프로젝트 전체가 "실제 데이터로 검증"을 반복해온 방식과
일치하고, API가 먼저 안정되면 프론트는 그 위에서 빠르게 만들 수 있다.

### 2.1 파일 구조

실제로는 계획했던 routes_*.py 분할 대신 `app.py` 하나에 모든 라우트를 모았다
(라우트 수가 적어 분할할 이유가 없었다) — 최종 구조:

│   ├── filters.py          저장된 메타데이터 위에서 도는 UI 필터

│                           (find_frontend_dist/mount_static)

                             (build_app/run_server_in_thread/wait_until_started/open_ui)

frontend/                    Vite + React + TypeScript + Tailwind, `npm run build`
                             결과가 frontend/dist 에 생기면 static.py 가 자동으로 찾는다

### 2.2 클립 스캔 — `api/clips.py`

`clips_dir` 아래 `*.json` 을 전부 읽어 `ClipSummary` 목록을 만든다. 매번 디스크를
훑는 게 단순하고, 클립이 수천 개 수준이면(§7.9: 매치당 0.4~0.8GB, 하루 5매치) 파일
I/O 도 수 ms~수십 ms 라 캐싱 없이 시작한다 — 느려지면 그때 mtime 기반 캐시를 더한다.

```python
@dataclass(frozen=True)
class ClipSummary:
    id: str                 # 파일명(확장자 제외) — meta_path.stem
    meta_path: Path
    meta: dict               # 메타데이터 JSON 그대로
    size_bytes: int          # mp4 파일 크기
    created_at: datetime     # meta_path 의 mtime (매치 시각이 아니라 "생성된 시각" —
                              # retention 정렬 기준은 이거다)


def scan_clips(clips_dir: Path) -> list[ClipSummary]: ...
def find_clip(clips_dir: Path, clip_id: str) -> ClipSummary | None: ...
```

`select_for_auto_clean()` 이 요구하는 `_created_at`/`_size_bytes` 키는 여기서
`ClipSummary` 를 dict 로 펼 때 채운다 (`{**meta, "_created_at": ..., "_size_bytes": ...}`).

### 2.3 필터 재사용

`pipeline/filters.py::apply_filter()` 는 `CombatInterval` 리스트에 대해 동작한다.
UI 필터는 **이미 저장된 메타데이터 dict** 위에서 동작해야 하므로 별도의 얇은
`filter_clip_summaries(clips, query) -> list[ClipSummary]` 를 만든다 — 태그/낮밤/
일차범위/기간/캐릭터를 메타데이터 필드 그대로 비교하는 수준이라 apply_filter 보다
단순하다. 로직 중복처럼 보이지만 **입력 타입이 다르다**(CombatInterval vs 저장된 dict)
는 걸 명확히 하기 위해 이름과 파일을 분리한다.

### 2.4 REST API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/clips` | 목록. 쿼리파라미터로 필터(`tags`, `dayNight`, `gameMode`, `pinned`, `trashed`, `minPvpScore`, `label`=pvp/pve/unlabeled) 와 정렬(`sort`=pvp/recent — 웹 UI 는 이걸 안 쓰고 받은 목록을 게임 단위로 묶어 프론트에서 정렬한다) |
| GET | `/api/clips/{id}` | 메타데이터 하나 |
| PATCH | `/api/clips/{id}` | 제목 수정, pin 토글, 교전/사냥 라벨(`userLabel`: pvp/pve/null, 그 외 400) |
| POST | `/api/clips/{id}/export` | 영상을 `dir` 폴더에 `filename`(기본 제목)으로 복사(중복 시 `(2)`), 그 폴더를 `paths.exportDefault` 에 저장. 폴더 없음 404 |

| POST | `/api/clips/{id}/trash` | 휴지통으로 |
| POST | `/api/clips/{id}/restore` | 복구 |
| DELETE | `/api/clips/{id}` | 휴지통에서 완전 삭제 (유예기간 무시하고 수동) |
| GET | `/api/clips/{id}/video` | 클립 mp4 스트리밍 (Range 헤더 지원 — 탐색바 이동에 필수) |
| GET | `/api/clips/{id}/thumbnail` | 썸네일 |
| GET | `/api/config` / PUT `/api/config` | 설정 조회/저장 (config.py 재사용) |

전부 `127.0.0.1` 에만 바인드한다 (SPEC §7.7 `ui.port`, 이미 로컬 전용 원칙 §3).

### 2.5 비디오 스트리밍은 Range 를 지원해야 한다

브라우저의 `<video>` 탐색바(seek)가 동작하려면 `Accept-Ranges`/`Content-Range` 를
직접 구현해야 한다 — FastAPI 의 기본 `FileResponse` 는 Range 를 지원하지 않는다.
`starlette.responses` 의 저수준 스트리밍으로 직접 구현하거나, 검증된 서드파티
(`fastapi-range` 류)를 쓴다. 이건 실제 재생 UX 를 좌우하는 지점이라 **테스트에
Range 요청(`Range: bytes=100-199`)을 반드시 포함시킨다.**

## 4. 확인 필요

### 4-1. pywebview 와 FastAPI(uvicorn)를 한 프로세스에서 같이 띄우는 법 — ✅ 해결됨

`cli/serve.py` 로 구현: uvicorn 을 백그라운드 스레드(`run_server_in_thread`)로
띄우고, 메인 스레드에서 `open_ui()` 가 pywebview 를 시도한다(없거나 실패하면
`webbrowser.open()` 으로 대체). 실제로 만들어 `npm run build` 산출물(`frontend/
dist`)을 `api/static.py::mount_static()` 으로 같은 FastAPI 앱에 얹고, 실제
uvicorn 서버를 띄워 curl 로 확인: `GET /` 가 프론트 `index.html`(정적 자산 포함)을
정상 서빙하면서 `GET /api/clips` 도 그대로 실제 클립 메타데이터를 반환함 — 정적
마운트가 API 라우트를 가리지 않는다(FastAPI 라우트를 먼저 등록하고 `Mount("/")`
를 나중에 추가하면 Starlette 가 등록 순서대로 매칭하기 때문).

트레이 상주 프로세스(`cli/app.py`)의 "열기" 메뉴는 pystray 의 `icon.run()` 이 이미
메인 스레드를 점유하고 있어 같은 스레드에서 `webview.start()` 를 또 요구하는
pywebview 와 충돌한다 — 그래서 트레이 경로(`make_on_open`)는 **항상 기본
브라우저**를 연다(서버는 최초 1회만 기동, 이후엔 재사용). 전용 창이 필요하면
`python -m lumia_briefing_room.cli.serve` 를 독립 실행하면 되고, 그 경로에서는
pywebview 창을 그대로 시도한다.

### 4-2. 대용량 HEVC 클립의 브라우저 재생 (research §4.10 의 연장) — ✅ 해결됨

**실측 완료.** Playwright 로 두 가지를 비교했다:
- Playwright 번들 `chromium-headless-shell`: `<video>` 가 `readyState:4`/길이/
  `currentTime` 진행은 정상이지만 `videoWidth`/`videoHeight` 가 계속 0 — HEVC
  디코더가 없어 화면은 검은색(오디오/탐색바만 동작).
- **실제 설치된 Microsoft Edge**(`executablePath: 'C:/Program Files (x86)/Microsoft/
  Edge/Application/msedge.exe'`, Playwright 로 직접 실행): `videoWidth: 2560,
  videoHeight: 1440` 로 재생 전/후 모두 정상, 스크린샷에 실제 게임 화면이 보임.

pywebview 의 Windows 백엔드가 Edge WebView2(=이 Edge 와 같은 엔진)이므로 **프록시
생성(`encode.proxy.enabled`) 없이 원본 HEVC mp4 를 그대로 재생해도 된다** —
Chromium 번들(headless-shell)에서만 안 되는 것이지, 실제 배포 환경(WebView2)에서는
문제 없음을 확인했다. H.264 프록시는 계획대로 v1.1 이후 "필요해지면" 검토.

### 4-3. `lumia-briefingroom.localhost` 주소 — 실측 (일부 완료)

위 §0 "접속 주소" 항목의 전제. 이 PC(Windows 11)에서 실측한 것은 ✅, 아직 못 한 것은 남겨 둔다.

- ✅ **80번 바인드**: 일반 권한(관리자 아님)으로 `cli.serve --port 80` 이 `127.0.0.1:80` 에 바인드됐다.
- ✅ **Chrome(Playwright MCP)에서 `http://lumia-briefingroom.localhost/` 접속**: 페이지가 뜨고 origin 이 `http://lumia-briefingroom.localhost` 로 잡혔다. 콘솔 오류는 `favicon.ico` 404 한 건뿐. `canPlayType` 은 HEVC(`hvc1`)·H.264 모두 `probably`(이 PC 기준).
- ✅ **IPv6**: `[::1]:80` 은 연결이 거부되고(서버는 IPv4 만 바인드), 이름 주소는 IPv4 로 접속돼 지연·실패가 없었다(curl·Chrome).

- ⬜ **pywebview(Edge WebView2)가 `*.localhost` 를 루프백으로 여는가.** (미실측 — 지금 트레이 경로는 pywebview 를 쓰지 않고 기본 브라우저를 연다) Chromium 은 그렇게 동작하는 것으로 알려져 있으나 이 프로젝트의 WebView2 로 직접 열어본 적은 없다. 안 열리면 `ui.shell=webview` 만 `127.0.0.1` 을 쓰는 예외를 둔다.
- ⬜(위 IPv6 실측으로 대체) **`127.0.0.1` 에만 바인드한 서버에 `::1`(IPv6) 로 접속을 시도하는 문제.** `*.localhost` 는 IPv4·IPv6 루프백 둘 다로 풀릴 수 있다. 브라우저가 다른 쪽으로 넘어가 접속하는지, 지연이 없는지 확인한다.
- ⬜(위 실측으로 이 PC 는 확인, 다른 PC 의 IIS·백신·VPN 점유는 폴백 동작으로 대응) **80번 바인드가 일반 권한으로 되는가.** Windows 에서는 보통 되지만 IIS·`http.sys`·백신·VPN 등이 이미 잡고 있으면 실패한다. 이 PC 에서의 실측과 실패 시 폴백 동작(포트가 붙은 주소로 열기)을 확인한다.
- ⬜ **저장 폴더 선택 등 서버 쪽 기능이 새 주소에서도 동작하는가** (`api/export.py` 는 요청 출처가 아니라 서버 프로세스가 파일을 다룬다 — 회귀 확인용).

### 4-4. 일자 타임라인 보기 모드 — 확인 필요 (아직 실측 안 함)

위 §0 "보기 모드: 일자 타임라인" 의 전제 중 확인하지 못한 것. 구현 전에 확인하고 결과를 이 절에 적는다.

- **페이즈 시작·끝 시각이 메타데이터에 있는가.** 클립에는 `phaseIndex`(일차·낮/밤)만 확인했고 페이즈가 게임 안에서 몇 초에 시작하는지는 확인하지 못했다. 그래서 1차 구현은 칸 안에 클립을 **시각 순서대로 나열**하고 시간축 비례 배치는 하지 않는다. 페이즈 경계 시각을 알 수 있으면(HUD 일차 판독이 바뀐 프레임) 블록 위치를 비례로 바꿀 수 있는지 검토한다.
- **`phaseIndex` 가 `null` 인 클립의 비율.** "시점 미상" 칸이 실사용 데이터에서 얼마나 큰지 본다(다시보기·구 클립에 많으면 이 칸이 주 화면이 된다).
- **페이즈 칸 수가 많은 게임(8일차 이상)의 가로 폭.** 가로 스크롤로 갈지 줄바꿈할지 실제 화면에서 정한다.

### 4-6. 클립 유니크 ID · 영상 파일 확장자 — 확인 필요 (아직 실측 안 함)

위 §0 "클립 유니크 ID(`clipUid`)" 와 "지원 확장자 도움말" 의 전제 중 확인하지 못한 것.

- ~~기존 클립에 `clipUid` 를 채워 넣는 방식·시점~~ → **결정함**(§0: 앱 시작 시 백그라운드 1회 스캔, 이미 있으면 건너뜀). 남은 것: 이 PC 의 클립 수백 개에서 걸리는 시간을 실측한다.
- **이미 삭제돼 보관소(`clips/.labels/`)에만 남은 항목, 그리고 이미 파일 ID 로 서버에 보낸 라벨 — 결정 대기.** 클립 영상·메타데이터를 지우면 라벨·근거 사본만 `clips/.labels/<파일ID>.json` 에 남는데(`label_archive.py`), 이 사본은 삭제 시점의 메타데이터를 복사한 것이라 그때 `clipUid` 가 없었으면 사본에도 없다. 살아 있는 클립은 위 백필로 채우지만 이미 지워진 클립은 채울 원본이 없다. 게다가 라벨 전송(`telemetry/collect.py`)은 이미 구현돼 있고 **지금은 파일 ID 를 클립 키로 서버에 보낸다** — `clipUid` 를 도입하면 이미 보낸 라벨도 새 키로 다시 나가 서버에 중복이 생길 수 있다(살아 있는 클립도 마찬가지). 선택지는 아래 대화에서 사용자에게 다시 물었고 답을 받으면 이 절을 갱신한다: (가) 보관소 사본에도 새 `clipUid` 를 발급하고 전송 항목에 옛 파일 ID(`legacyClipId`)를 함께 실어 서버가 기존 행을 승격, (나) 보관소 항목은 전송에서 제외, (다) 그 밖.
- ~~자르기 분할 조각의 원본 참조~~ → **결정함**: 조각의 `clipUid` 를 `<원본 clipUid>-<번호>` 로 붙여 계보가 ID 에 들어 있게 한다(§0). 원본 `clipUid` 별도 필드는 두지 않는다.
- **파일 ID 의 실제 충돌 가능성.** 시각(초 단위)+번호라 다른 PC 에서 같은 값이 나올 수 있다는 것은 이론이고 실제 사용자 수에서 얼마나 되는지는 보지 않았다. `clipUid` 로 해결되므로 파일 이름 규칙은 바꾸지 않는다.
- **`(?)` 도움말에 적을 확장자(`.mp4` `.mkv` `.ts` `.webm` `.mov`) 중 분석해 본 것은 `.mp4` 뿐이다**(사용자 실사용 확인). 나머지 4개는 코드가 받아들이는 형식일 뿐 실제 영상으로 확인하지 못했다. 확인되면 도움말 문구에서 "확인된 형식"으로 옮기고, 안 되는 형식이 있으면 목록에서 뺀다.

### 4-5. 자르기 다중 구간 분할 — 확인 필요 (아직 실측 안 함)

위 §0 "자르기: 구간 여러 개" 의 전제 중 확인하지 못한 것.

- **새 클립 ID 규칙.** 클립 ID 는 파일 이름(`<id>.json`/`<id>.mp4`)이라 조각마다 새 이름이 필요하다. 원본 ID 에 접미사(`-p1`, `-p2`…)를 붙이는 안을 기본으로 하되 기존 ID 규칙·정렬·중복과 부딪히지 않는지 구현 때 확인한다.
- **`userLabel`·`pvpScore` 를 조각에 어떻게 넘기나.** 라벨은 원본 전체에 대한 판단이라 조각마다 맞는지 알 수 없다. 기본은 **라벨은 복사하지 않고 비운다**(`pvpScore`·`pvpSignals` 같은 자동 근거는 그대로 복사). 원본이 휴지통에 남아 있으므로 근거는 잃지 않는다. 시간이 겹치는 조각으로 라벨을 옮기는 `pipeline/label_migrate.py` 를 재사용할지는 사용해 보고 정한다.
- **`-c copy` 조각의 프리롤.** 조각 시작 앞의 키프레임까지(최대 3초)가 화면에 안 보이는 채로 파일에 남는 기존 자르기의 대가가 조각마다 생긴다. 조각이 매우 많으면 총 용량이 원본보다 늘 수 있다 — 실측한다.
- **조각 수 상한.** 지금은 두지 않는다. 실사용에서 지나치게 많이 만드는 일이 생기면 정한다.

## 5. 추후 구현 옵션 — 설정 화면 스크린샷으로 네임플레이트 색 읽기

**아직 만들지 않는다.** 근거: 네임플레이트 신호 자체가 쓸 만한지 아직 증명되지 않았다([plan-pvp.md §5-3](plan-pvp.md)). 신호를 채택하기로 결정하면 그때 같이 만든다.

**왜 필요한가.** 머리 위 체력바 색(자신/아군/몬스터/팀1~8)은 게임 내 `설정 → 색약 간단 설정` 에서 사용자가 바꿀 수 있다([SPEC §2.12-8](SPEC.md)). 코드에 기본 RGB 를 박으면 색약 설정을 쓰는 사용자에게는 검출기가 조용히 고장 난다.

**스크린샷 범위는 하나로 통일한다.** `색약 간단 설정` 화면의 **오른쪽 미리보기 패널만** 잘라서 첨부한다 — 왼쪽 드롭다운 목록은 넣지 않는다. 범위: `자신 색상` 행부터 `팀8 색상` 행까지 **12행**(이름 + 레벨 상자 + 체력바 견본), 위 4행(자신/아군/환경 오브젝트/몬스터)과 아래 8행(팀1~8) 사이에 빈 간격이 있는 그대로.
왜 오른쪽인가: 견본이 실제 게임 속 체력바 모양(눈금·레벨 상자) 그대로라 색을 뽑는 곳이 곧 검출할 모양이다. 왼쪽 막대는 색만 있고 모양이 없다.
(예시 이미지 `docs/img/` 는 미디어라 커밋하지 않는다 — CLAUDE.md.)

**형태.** UI 에 설정 화면을 만들고 거기에 위 범위의 스크린샷을 드래그해 넣으면:

1. 업로드 → `POST /api/profile/nameplate-colors` (이미지 바이트)
2. 서버가 12개 행을 찾아 각 체력바 견본의 대표 RGB 를 뽑는다. 행 순서는 고정이므로 세로 위치(4행 + 간격 + 8행)로 역할을 안다 — 이름 글자를 읽을 필요가 없다. 이미지 크기가 달라도 비율로 잡는다.
3. 결과를 역할→RGB 표로 화면에 보여주고(사용자가 눈으로 확인), 저장하면 해상도 프로필 옆에 사용자 오버라이드로 기록한다.
4. 저장된 색이 없으면 기본값 표를 쓴다.

**주의.** 스크린샷 해상도가 녹화 해상도와 다를 수 있으므로 좌표는 비율로 잡는다. 행 개수가 안 맞으면(게임 업데이트로 항목 추가) 조용히 틀린 색을 저장하지 말고 **거부하고 알린다.**

- **설치·배포 간편화.** 사용자 환경에 프로그램·코덱을 따로 설치하지 않아도 되게 배포 파일에 전부 포함한다(ffmpeg 등 — SPEC §4 "배포 시 주의" 와 같이 볼 것). 스팀 리플레이 폴더를 자동 인식하거나 첫 실행 때 설정하게 하고, 클립 저장 위치도 그때 함께 묻는다.
  - **HEVC 재생(배포 시 결정 사항).** 디코더는 배포 파일에 넣을 수 없다 — Windows 의 HEVC 는 Microsoft Store "HEVC 비디오 확장"이고 재배포가 안 되며 특허 라이선스 문제도 있다. `winget` 등으로 설치기가 그 확장을 자동 설치할 수 있는지는 미확인(유료 여부·무인 설치 가능 여부). Chrome·웨일은 GPU 가 HEVC 하드웨어 디코딩을 지원하면 확장 없이 재생하지만 PC 마다 다르다. **채택안: ffmpeg 를 배포 파일에 포함하고, 프론트가 `canPlayType`/MediaCapabilities 로 HEVC 재생 가능 여부를 확인해 안 되는 PC 에서는 H.264 프록시(`encode.proxy`)로 자동 폴백한다.** 사용자는 아무것도 설치하지 않는다. 폴백 판별·프록시 자동 생성 시점은 구현 때 정한다.
- **호스팅 공유 시 자체 추출 클립과 외부 파일 구분.** 클립을 호스팅해 공유할 때 이 앱이 만든 클립(메타데이터·서명 등으로 식별)과 그냥 올린 파일을 구분한다. 식별 방식은 미정.
- **개발/배포 모드 분리.** 개발용 기능(클립 ID 표시, 클라이언트 로그 전송(§6), 라벨링 등)은 배포 모드에서 자동 비활성화한다. 모드 판별 방식(설정 키·빌드 플래그)은 미정.
