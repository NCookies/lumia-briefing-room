## 1. 왜 만드는가

1. **잘하는 사람의 교전을 모아 본다.** 내 판만 보면 표본이 적고 내 플레이에 갇힌다.
2. **라벨링 자료를 늘린다.** 교전/사냥 라벨이 곧 PvP 점수 가중치 튜닝의 정답이다([plan-pvp.md §4](plan-pvp.md)). 방송 한 편(7~8시간)에 게임이 여러 판 들어 있어 표본이 빨리 쌓인다.
3. 스팀 링버퍼는 2시간이면 원본을 지우지만(SPEC §2.6) **다시보기 파일은 사용자가 지우기 전까지 남는다.** 시간 압박이 없어 검출을 다시 돌려도 된다.

개인 분석용이다. 클립을 서비스에 올려 재배포하지 않는다(§8-1).

## 2. 설계 결정

### 2.1 앱은 다운로드를 하지 않는다 — 사용자가 받은 파일의 경로만 안다

영상은 사용자가 따로 받아 둔다(yt-dlp 등). 앱은 **로컬 파일 경로를 설정에서 지정**받아 읽기만 한다.

- SPEC §7.8 의 "네트워크 호출을 하지 않는다"가 그대로 유지된다. 치지직 API 도 약관도 앱이 건드리지 않는다.
- 원본 다시보기 파일은 **수정·삭제하지 않는다**(§7.8 "원본 녹화본은 절대 수정하지 않는다"의 연장). 클립 삭제·자동 정리도 클립만 지운다.
- 화질은 사용자가 받을 때 정한다. **분석과 클립 컷은 파일 그대로의 해상도**에서 한다(저해상도 프록시를 따로 만들지 않는다).

### 2.2 스팀 클립과 저장소·목록·탭을 전부 분리한다

| | 내 녹화 (기존) | 다시보기 (신규) |
|---|---|---|
| 클립 폴더 | `paths.clips` | `paths.vodClips` (기본 `%USERPROFILE%\Videos\LumiaBriefingRoom\vod`) |
| 썸네일/휴지통 | `<clips>\.thumbs` `.trash` | `<vodClips>\.thumbs` `.trash` |
| 감시·자동 추출 | `Player.log` 감시, 매치 끝날 때 | **없음. 사용자가 "분석" 버튼으로 시작** |
| 자동 정리(SPEC §7.6) | 적용 | **v1 은 적용 안 함** (§8-6) |
| UI | 첫 번째 탭 | 두 번째 탭 |
| 평가·라벨 도구 | 기본 대상 | 기본 제외, `--source vod` 로 명시 (§2.9) |

폴더를 나누는 이유: `scan_clips` 가 `clips_dir/*.json` 을 통째로 읽으므로, 섞어 두면 **스팀 쪽 목록·정리·평가에 남의 방송이 끼어든다.** 폴더가 다르면 기존 코드는 한 줄도 안 바꿔도 그대로 돈다.

클립 ID(파일명)는 두 폴더에서 겹치지 않게 `vod_<vodId>_g<게임>_<시작초>` 로 짓는다. `find_clip` 은 두 폴더를 모두 찾는다.

### 2.3 데이터 모델 — 다시보기 → 게임 → 클립

```
다시보기 영상 (VOD)        ← 설정에 지정한 파일 하나. 7~8시간
 └─ 게임 (1판)             ← 화면으로 나눈다. 한 영상에 여러 판
     └─ 교전 클립          ← 기존과 같은 교전 구간 → 클립
```

- **VOD 색인** `<vodClips>\.vods\<vodId>.json`: 파일 경로, 크기, 길이, 해상도, fps, 분석 상태, 게임 목록(시작·끝 초, 결과 화면 판독값), 스트리머 표시명(사용자 입력).
- **VOD 상태 캐시** `<vodClips>\.vods\<vodId>.states.json`: 프레임별 판독값(`FrameState`). **디코딩·판독이 비용의 거의 전부**이므로, 필터·클립 구간 설정을 바꿔도 캐시에서 다시 계산한다(재디코딩 없음).
- `vodId` = 파일 크기 + 앞·뒤 1MiB 해시의 앞 12자. **경로가 아니라 내용으로 식별**해 파일을 옮겨도 색인·클립이 이어진다(경로만 갱신).
- **클립 메타데이터**는 기존 스키마([SPEC §3](SPEC.md))를 그대로 쓰되 세션 필드 대신 VOD 필드를 채운다:

```json
{
  "source": "vod",
  "vodId": "3fa91c02b7de",
  "vodFile": "D:\\vod\\방송_2026-09-20.mp4",
  "streamer": "○○○",
  "vodGameIndex": 3,
  "vodOffsetSec": 15234.0,
  "durationSec": 41.0,
  "gameStartOffsetSec": 14820.0,
  "gameEndOffsetSec": 16391.0,
  "combatStartOffsetSec": 15242.0,
  "combatEndOffsetSec": 15268.5,
  "sourceWidth": 1920, "sourceHeight": 1080,
  "tags": ["kill"], "pvpScore": 1.0, "pvpSignals": ["kill_delta"],
  "matchResult": null
}
```

  - `sessionDir`/`segmentStart`/`matchStartUtc` 는 **없다.** 다시보기 파일에는 벽시계 시각이 없다. 게임의 위치는 `gameStartOffsetSec`(영상 안의 초)로만 안다. `source` 가 없는 기존 클립은 `steam` 으로 취급한다.
  - `vodOffsetSec` 만 있으면 영상에서 다시 자를 수 있다(`vodFile` 은 경로가 바뀌면 색인에서 갱신).
  - 태그·`pvpScore`·`pvpSignals`·`userLabel`·`trimmed` 등은 스팀 클립과 같은 의미다. **UI 의 라벨·필터·플레이어·자르기·저장 코드가 그대로 재사용된다.**

### 2.4 프레임 소스 추상화 — 검출 코드는 세그먼트에 묶여 있다

지금 `detect_match()` 는 스팀 세션과 세그먼트 번호를 전제로 한다(`extract_keyframe_frames(session, segment_numbers…)`, 시각 `t = (세그먼트 번호-1) × 3초`, 세그먼트 존재 확인과 gap 처리). **다시보기는 하나의 mp4 파일**이라 이 전제가 통째로 없다.

- 판독 단위인 `analyze_frame(frame, profile, t=…)` 과 시계열 처리(`finalize_match`, 구간 산출, 태그, PvP 점수)는 **프레임 배열과 시각만 받으므로 그대로 쓴다.** 갈아끼울 곳은 "프레임을 어디서 어떻게 뽑아 `(t, frame)` 로 내주느냐"뿐이다.
- 그래서 **`FrameSource` (프레임 공급자)** 를 둔다: `(t초, 프레임)` 을 순서대로 내주고, 끊긴 구간(gap)과 해상도를 알려준다. `SteamRecordingSource`(기존 동작을 옮긴 것)와 `VodFileSource` 두 구현. SPEC §3 의 "녹화 소스는 인터페이스로 추상화한다" 원칙의 실현이다.
- 기존 스팀 경로의 **동작·출력은 그대로**여야 한다. 추상화 리팩터링 전후로 기존 테스트가 전부 통과하고, 실제 녹화 1경기의 검출 결과가 동일한지 비교한다(리팩터링만 하는 커밋을 따로 둔다).
- `VodFileSource`: ffprobe 로 해상도·fps·길이·키프레임 간격을 알아내고, 키프레임 간격이 충분히 촘촘하면 `-skip_frame nokey`(SPEC §3 "키프레임만 디코딩한다"), 아니면 고정 간격(`vod.sampleIntervalSec`)으로 뽑는다. **어느 쪽이 맞는지는 V0 에서 잰다**(§4, §8-2).

### 2.5 해상도 프로필 — 다시보기는 1440p 가 아닐 가능성이 높다

현재 측정된 프로필은 `2560x1440` 하나뿐이고 숫자·지역·일차 본보기(`data/templates/*/2560x1440.npz`)도 그 해상도의 글자 모양이다. 방송 다시보기는 보통 1080p(1920x1080)라 **좌표도 글자 모양도 다르다.**

- 프로필은 **영상의 실제 해상도**로 고른다(SPEC §3 "해상도 프로필"). 모르는 해상도는 비례 스케일 + **신뢰도 낮춤 + 경고**가 원칙이다.
- **`1920x1080` 프로필**(`profiles/builtin/1920x1080.json`)은 2560x1440 ROI 에 0.75 를 곱해 만들었고 `normalizedTo: [2560, 1440]` 을 가진다(구현됨, V1).
- **정규화 방식으로 정했다 — 본보기를 새로 만들지 않는다.** 검출기는 픽셀 개수 임계(배지 250/100, 낮밤 100, 링 반지름 7~16 등)와 글자 본보기가 전부 2560x1440 픽셀 기준이다. 그래서 검출기를 하나씩 고치는 대신 `ResolutionProfile.crop()` 이 **ROI 조각만 기준 ROI 크기로 키워**(큐빅, 조각만이라 싸다) 기존 코드·본보기·임계를 그대로 쓴다. 기준 해상도 프로필(2560x1440)은 배율이 1 이라 조각을 그대로 돌려주므로 **스팀 경로는 동작이 바뀌지 않는다**(실제 녹화 20분 구간 출력이 바이트 단위로 동일함을 확인).
- 실측(H:\vod 방송 2편, 인게임 프레임 2,360장): **K 99%·A 99.5% 이상 판독, 리셋이 아닌 감소 0건**(오독이 있으면 숫자가 줄어드는 것으로 드러난다). 일차는 인게임 프레임의 80% 에서 읽힌다(분포 1~8일차) — 못 읽는 20% 는 화면은 선명한데 확대 이미지가 엄격한 점수 임계(0.9)에 못 미치는 경우다. 게임 분할(V2)은 구간 전체를 쓰므로 V1 에서는 그대로 둔다. 필요하면 나중에 **1080p 네이티브 본보기**(`data/templates/days/1920x1080.npz` 등)를 만들어 그 ROI 만 정규화에서 뺀다.
- 지역명은 아직 못 읽는다(스팀 본보기가 확대 이미지에 안 맞거나 ROI 가 어긋남). 제목에만 쓰이므로 V3 이후로 미룬다.
- 스트리머의 **UI 스케일·HUD 배치**가 기본값이 아닐 수 있다(§8-4). 이것도 V0 확인 사항이다.

### 2.6 게임 분할 — `Player.log` 가 없으니 화면으로 경계를 찾는다

스팀 쪽은 로그의 `[LOADING][GAME]`/`[LOADING][LOBBY]` 로 매치 경계를 정확히 안다(SPEC §2.3). 다시보기에는 **로그가 없다.** 이미 있는 화면 판독을 조합한다.

| 신호 | 출처 | 쓰임 |
|---|---|---|
| 인게임 프레임 | 일차 판독(`detect/day.py`) 성공 · K/A 카운터 영역 판독 성공 | 게임 안의 프레임 |
| 일차 감소 | 5일차 → 1일차 같은 되돌아감 | 새 게임의 시작(연속된 두 판 사이 로비가 짧을 때도 잡는다) |
| 로비/대기방 | 인게임 신호 없음이 길게 이어짐, 지역명 `브리핑 룸`(SPEC §2.10) | 게임 사이 |
| 결과 화면 | `detect/result.py` OCR (`N/M 실험 종료`) | 게임의 끝 · 순위/스탯(SPEC §2.13) |

- **게임 = 인게임 프레임이 이어진 구간.** 짧은 끊김(로딩·컷 전환·방송 화면 전환)은 메운다(`vod.gameGapSec`). 이 값은 V0 에서 실제 방송으로 정한다.
- 결과 화면은 경기 끝에서 **앞으로** 거슬러 훑는 기존 방식(`pipeline/result_scan.py`)과 달리, 다시보기는 분석 중 이미 모든 프레임을 지나므로 **게임 끝 근처 프레임만 OCR** 한다(전 프레임 OCR 은 8시간 × 비용이 너무 크다).
- **못 나눈 경우도 버리지 않는다.** 경계가 모호하면 가장 긴 하나의 구간으로 두고 `gameSplitConfidence` 를 낮게 남긴다. 클립은 어떤 경우에도 만든다 — **재현율 우선 원칙(SPEC §1)이 여기서도 그대로**다. 다만 이 경우 원본이 사라질 걱정은 없으므로(사용자 파일) 나중에 다시 분석하면 된다.
- 스트리머가 방송 도중 **관전 화면**(죽고 나서 팀원 시점)을 오래 보는 경우는 기존 관전 검출(`detect/spectator.py`)이 판독 제외로 다룬다. 그러나 **게임 안에 있는 프레임으로 간주**해 게임을 끊지 않는다.

### 2.7 분석 작업 — 오래 걸리니 이어하기·진행률·취소가 있어야 한다

7~8시간 영상은 스팀 경기(20분) 하나와 규모가 다르다. 참고로 1440p HEVC 를 키프레임만 디코딩했을 때 55x 실시간이었으니(SPEC §3) 같은 배속이면 8시간은 10분 안팎이지만, **다시보기 코덱·키프레임 간격에서 다시 잰 뒤에 믿는다**(§4).

- **백그라운드 작업 1개**, 한 번에 한 영상. 이미 있는 `POST /api/games/reprocess` 와 같은 방식(스레드 + 상태 폴링, [plan-ui.md §0](plan-ui.md)).
- **진행률**: `분석한 초 / 전체 초`, 지금 게임 번호, 찾은 클립 수. 화면이 3초마다 조회한다.
- **취소**와 **이어하기**: 프레임 판독은 일정 구간마다 상태 캐시에 저장한다. 취소·앱 종료·오류 뒤 다시 누르면 **마지막으로 저장된 구간부터** 이어간다.
- **단계 분리**: (1) 프레임 판독 → 캐시 (2) 캐시로 게임 분할 + 교전 구간 + 태그 + PvP 점수 (3) 클립 컷 + 썸네일 + 메타데이터. 2·3 은 캐시만 있으면 빠르게 다시 돌 수 있다(필터·클립 여유를 바꾼 뒤 "클립 다시 만들기").
- **스팀 감시와의 동시 실행**: 트레이 앱이 스팀 경기를 감시하는 동안 다시보기 분석이 CPU 를 다 먹으면 안 된다. 낮은 우선순위로 돌리고 스팀 매치 처리가 시작되면 잠시 양보할지는 §8-5 에서 정한다. **스팀 쪽 처리가 항상 우선**이다(링버퍼는 기다려 주지 않는다).
- 분석 대상은 **사용자가 명시적으로 누른 영상만**이다(`vod.autoAnalyze` 기본 `false`). 설정에 경로를 넣었다고 8시간짜리가 저절로 돌지 않는다.

### 2.8 스팀 쪽에는 없는 다시보기 특유의 주의

- **닉네임 자동 학습을 끈다.** `pipeline/nickname.py::learn_nickname` 은 결과 화면에서 읽은 닉네임을 `player.nickname` 에 저장한다(비어 있을 때). **다시보기의 결과 화면은 스트리머의 닉네임이다.** 그대로 두면 사용자 본인 닉네임 자리에 남의 이름이 들어간다. 다시보기 경로는 이 학습을 호출하지 않고, 읽은 닉네임은 **그 VOD 의 `streamerNickname`** 으로만 저장한다(순위표에서 스트리머 행을 찾는 열쇠로 쓴다).
- **자동 제목**은 `pipeline/titles.py` 규칙을 쓰되 내 캐릭터 자리에 **스트리머의 캐릭터**가 온다. 앞에 스트리머 표시명을 붙일지는 UI 에서 게임 행 머리로 충분하므로 제목에는 넣지 않는다(§8-7).
- **방송 화면 간섭.** 오버레이·캠·채팅·알림이 HUD 를 가릴 수 있다. 판독 실패는 `None` 으로 남는 기존 규칙(SPEC §3 "판독 불가는 직전 상태 유지")으로 견딘다. 특정 영역이 계속 가려지는 방송은 V0 에서 확인한다.
- **시작·끝 컷의 정밀도.** 다시보기 키프레임 간격이 스팀의 3초와 다를 수 있다. `-c copy` 컷은 그 격자에 붙으므로 실제 경계를 메타데이터에 남기는 원칙(SPEC §3 "클립 구간")은 그대로다.
- **광고·방송 끊김·이어 붙임**으로 영상 타임스탬프가 어긋나는 다시보기가 있을 수 있다(§8-2).

### 2.9 라벨과 평가 — 스팀 기준선을 흔들지 않는다

- 다시보기 클립도 **같은 `userLabel`(교전/사냥)** 을 쓴다. 사용자가 다시보기 클립을 훑으며 찍는 라벨이 이 기능의 큰 목적이다.
- 그러나 `tools/eval_pvp.py`·`rescore_clips.py`·`migrate_labels.py` 는 **기본이 스팀 클립만**이다. 다시보기 표본은 해상도·HUD·화질이 달라 섞으면 지금 정해 둔 가중치의 평가 수치가 바뀐다. `--source steam|vod|all` 옵션을 추가하고, 기본은 `steam`.
- 두 표본을 **따로 평가해 서로 비교**한다. 다시보기 표본에서 미니맵 적 링 같은 신호의 분리력이 스팀과 다르다면 그 자체로 발견이다([plan-pvp.md §2.4-b](plan-pvp.md) 의 표본 부족 문제도 완화된다).
- **"잘하는 사람" 판정**은 자동화하지 않는다. 스트리머 표시명은 사용자가 정하고, 결과 화면에서 읽은 순위·킬 수는 게임 행에 표시만 한다. 정렬·필터로 사용자가 판단한다(SPEC §1 "열람 단계에서 거른다").

## 3. UI 설계

### 3.1 탭 — 최상위 분리

```
[ 내 녹화 ]  [ 다시보기 ]                       ⚙ 옵션
```

- 헤더에 탭 두 개. **기존 화면은 "내 녹화" 탭으로 그대로 들어간다**(동작 변화 없음). 선택한 탭은 `localStorage` 에 저장해 다음 실행에 유지한다.
- 탭마다 **필터·정렬·펼침 상태·클립/휴지통 서브탭이 독립**이다. 한쪽 필터가 다른 쪽에 안 새게 한다.
- 플레이어의 이전/다음은 **지금 탭에 보이는 목록 안에서만** 움직인다.

### 3.2 "다시보기" 탭의 레이아웃 — 영상 단위로 나누고, 그 안에서 게임별

```
▼ 방송_2026-09-20.mp4  ○○○   7:42:10   1080p   분석 완료 · 게임 9 · 클립 63 · 2.4 GB   [다시 분석] [영상 삭제…]
  ▶ 게임 1   0:12:40 ~ 0:31:05   #3 랭크   12/3/4   클립 6
  ▼ 게임 2   0:38:22 ~ 0:58:47   #1 랭크   15/1/6   클립 8
      [결과표] [클립] [클립] [클립] ...
  ▶ 게임 3   ...
▶ 다른영상.mp4  △△△   5:10:03   분석 안 함      [분석 시작]
▶ 세번째.mp4    분석 중 41%  (게임 4 · 클립 22)   [취소]
```

- **바깥 단위 = 다시보기 영상**(`VodSection`, 접이식). 접힌 한 줄에 파일명·스트리머·길이·해상도·분석 상태·게임 수·클립 수·용량과 버튼이 나온다. 영상 사이는 굵은 구분선·색으로 확실히 나눈다.
- **안쪽 단위 = 게임**. **기존 `GameSection` 을 재사용**한다. 다른 점은 시각 표시뿐이다 — 벽시계 시작 시각 대신 **영상 안의 위치**(`0:38:22 ~ 0:58:47`). 접힌 행의 순위·모드·캐릭터·TK/K/A·클립 수·용량, 결과표 썸네일은 같다.
- 게임 안 클립은 항상 오름차순, 게임 순서 정렬은 그 VOD 안에서만 적용한다(기존 규칙).
- **분석 전 상태**의 영상은 클립이 없으므로 게임 목록 대신 `[분석 시작]` 과 안내를 보인다. **분석 중**에는 진행률과 지금까지 나온 게임/클립이 실시간으로 늘어난다.
- 영상이 여러 개면 영상 정렬(파일명 / 분석 시각 / 스트리머)과 "모두 접기/펼치기". 스트리머 표시명은 접힌 행에서 그 자리에서 고친다.
- **영상 삭제**는 두 가지를 분명히 구분한다: (a) 이 영상에서 만든 클립만 지우기(휴지통), (b) 목록에서 빼기(설정 경로 제거). **다시보기 원본 파일은 앱이 절대 지우지 않는다**(§2.1). 이 문구를 확인창에 명시한다.
- 필터 바는 태그·낮밤·PvP 점수·라벨 없음 등을 그대로 쓰되, **스트리머 / 영상 필터**가 추가된다.

### 3.3 옵션 모달 — "다시보기" 탭

일반 / 영상 저장 / 자동 정리 옆에 **다시보기** 탭을 추가한다.

- **영상 경로 목록**: 파일 또는 폴더 추가(기존 `FolderPicker` 확장 — 파일 선택 필요). 폴더를 지정하면 그 안의 `mp4`·`mkv`·`ts`·`webm` 을 찾는다(재귀 여부는 옵션). 각 항목에 존재 여부 표시(파일이 없으면 경고 배지 — 옮겼거나 지웠을 수 있다).
- **클립 저장 폴더**(`paths.vodClips`).
- **분석 옵션**: 샘플 간격(키프레임을 못 쓸 때), 하드웨어 디코딩, 자동 분석 켜기(기본 꺼짐), 게임 사이 끊김 허용 시간.
- 클립 구간·필터(`clip.*`, `filter.*`)는 **스팀과 같은 설정을 공유**한다. 다시보기만 따로 두면 설정이 두 벌이 되어 헷갈린다. 다르게 하고 싶어지는 게 실사용으로 확인되면 그때 분리한다.

## 4. V0 — 코드 전에 실측할 것

**다시보기 1편(2~3시간)을 받아 재본다.** 스팀 때도 0단계 조사([research.md](research.md))가 설계를 여러 번 뒤집었다. 여기서도 같다.

| 확인 | 방법 | 결과가 바꾸는 것 |
|---|---|---|
| 해상도·fps·코덱·비트레이트 | `ffprobe` | 프로필 (§2.5), 디스크·분석 시간 추정 |
| **키프레임 간격** | `ffprobe -skip_frame nokey -show_entries frame=pts_time` | 키프레임 샘플링 가능 여부 (§2.4). 간격이 크면 고정 간격 샘플링 + 분석 시간 급증 |
| 타임스탬프 연속성(광고·이어 붙임) | pts 점프 탐지 | 영상 시각 ↔ 클립 컷 신뢰 (§8-2) |
| **HUD 좌표·크기** | 인게임 프레임을 뽑아 2560x1440 프로필에 0.75 곱한 ROI 를 겹쳐 본다 | 1080p 프로필이 비례 스케일로 되는지 (§8-3) |
| **스트리머 UI 스케일·배치** | 같은 방송 여러 시점의 프레임 비교 | HUD 위치가 고정인지 (§8-4) |
| 오버레이·캠 간섭 | 프레임 육안 확인 | 가려지는 ROI 가 있는지 |
| **기존 검출기 그대로 돌렸을 때** | 라벨한 프레임 20~30장에 배지·K/A·일차·사망 판독 | 본보기를 다시 만들어야 하는 정도 |
| 경기 경계 | 방송 한 편의 인게임/로비/결과 프레임 구성 | `vod.gameGapSec`, 게임 분할 규칙 (§2.6) |
| 디코딩 속도 | 키프레임만 vs 고정 간격 vs 하드웨어 | 분석 시간 (§2.7) |

**결과는 이 문서의 "V0 실측 결과" 절(아직 없음)과 필요하면 [research.md](research.md) 에 남기고, 설계 결정이 바뀌면 SPEC 도 같이 고친다**([CLAUDE.md](../CLAUDE.md)). 프레임 뽑기는 기존 `scripts/probe/` 방식을 참고한다. 영상·프레임 이미지는 커밋하지 않는다(`.gitignore`).

| 방송 오버레이 | 오른쪽 채팅창, 오른쪽 아래 VTuber 아바타(y<840), 왼쪽 아래 채팅 로그. 핵심 ROI(TK/K/A, 일차, 초상화)는 가리지 않는다. 미니맵 헤더(지역명)와 아바타가 x 방향으로 가깝다 |
| 화면 종류 | 팀 로비(`매칭 중`), 루미아 섬 이동 로딩, 하이퍼루프 지도 오버레이, 인게임이 다 나온다 → 경기 경계를 화면으로 나눌 재료가 있다 |

**기존 검출기 시험** — 1080p 프레임을 1440p 로 키워 기존 스팀 본보기·프로필로 돌렸다(8프레임, 육안 대조 가능한 6프레임 기준). 대략적인 시험이다.

| 신호 | 결과 |
|---|---|
| 일차(`game_day`) | 6/6 정확 |
| 낮/밤 | 정확 |
| K | 5/5 정확 |
| A | 4/5 (`5` 를 못 읽고 `None`) |
| 로비·로딩 | K·일차가 `None` → 인게임과 구분된다 |
| 교전 배지 `combat` | 4/8 프레임이 `None`(판독 불가). **원인 미확인** |
| 지역명 | 인게임 전부 `None` (스팀 본보기가 안 맞거나 ROI 가 어긋남) |
| 관전 `spectating` | **로비·로딩·하이퍼루프 지도 화면에서 오탐(True)** |

**결론**
- 파일 성질·HUD 배치는 걱정했던 것보다 좋다. **V1 진행 가능.**
- 일차·K·낮밤은 지금 본보기로도 읽힌다(키운 프레임 기준). 1080p 네이티브 본보기를 만들면 더 나아질 것이다.
- **미해결**: 교전 배지 판독 불가 원인, 지역명, 관전 오탐(게임 분할에서 `game_day is None` 을 인게임 판정에 함께 쓰면 피할 수 있다), A 숫자 오독.

**추가로 확인한 것 (V1 작업 중)**
- **교전 배지 `None` 의 원인**: 평상시 배지가 **초록 원(레벨 숫자)** 인데 검출기는 주황·노랑·파랑만 세서 "배지 없음"으로 봤다. 교전 중(주황 교차 칼)만 잡히고 끝을 못 잡는 상태. 초록 계열을 추가해 해결(H:\vod 20분 구간 인게임 800프레임: `None` 595 → 0, `True` 158 유지, 스팀 출력 동일).
- **팀원 전투 신호가 오탐한다**: 팀원 초상화 링 ROI 에 **빨간 머리 캐릭터**가 들어와 "전투 중"으로 잡힌다(한 게임에서 인게임의 76%). 스팀에도 있는 약점이다. 기존 안전장치(`_team_combat_saturated`: 전체의 60% 초과면 신호 폐기)가 **경기 단위로 돌아야 작동**한다.
- **⇒ V2·V3 필수 사항: `finalize_match` 는 영상 전체가 아니라 게임 하나씩 돌린다.** 영상 한 편에 여러 판이 있으므로 K/A 단조 규칙(값은 줄지 않는다)·최종값·팀원 신호 포화 판정·사망 구간이 모두 게임 경계에서 초기화돼야 한다.

**게임 분할 실측 (V2a)** — 인게임 = 낮밤 아이콘·일차가 읽히거나 관전 아닌 채 K 가 읽히는 프레임. 인게임이 30초 이내로 이어지면 한 게임, 일차가 2 이상에서 1 로 5프레임 연속 돌아가면 새 게임, 60초 미만은 게임이 아니다. 방송 A(3시간 47분) 9판, B(3시간 18분) 8판이 나왔고 판 사이 로비 공백은 183~470초, 판 안의 인게임 비율은 99.5% 이상이라 30초 허용이 넉넉하다. 눈으로 본 프레임(6000초 팀 로비, 9000초 섬 이동 로딩)과 일치한다. 일차 감소 규칙은 이 2편에서는 로비가 항상 있어 발동하지 않았다(합성 테스트로만 검증).

**결과 화면 판독 실측 (V2b)** — 1080p 프레임에서 기존 `read_result_screen` 이 그대로 동작한다(순위 `N/M`, 랭크 여부, 결과 문구, 닉네임, 캐릭터, TK/K/D/A). 17판 중 15판에서 읽었고 판독 시간은 게임당 11~19초(결과 화면이 없는 판은 탐색 창 전체를 훑어 52~55초). 못 읽은 2판(A 게임 3·6)은 **스트리머가 탈락 화면(`ELIMINATED`) 뒤 `결과를 불러오는 중` 에서 결과 화면을 안 보고 로비로 넘어간 경우**라 화면 자체가 없다(A 게임 3 을 눈으로 확인). 이 경우 탈락 여부는 알 수 없으므로 순위를 비워 둔다. 팀원 캐릭터는 순위표 탭을 눌러 본 판에서만 읽힌다(6판에서 읽음). B 게임 3 은 결과 화면은 읽었지만 TK/K/D/A 숫자는 못 읽었다(미확인). 일반 게임은 칩을 못 읽어 `matchType=unknown` 이 많다(스팀과 같은 미해결 항목).

**게임 단위 검출 실측 (V2c)** — 게임별로 돌린 K/A 최종값이 결과 화면의 K/A 와 **결과 화면이 있는 14판 중 13판에서 정확히 일치**한다(영상 전체를 한 번에 돌리면 K 가 판마다 0 으로 돌아가 틀린다). 교전 구간은 게임 시간의 18~33%, 최장 66초. 불일치 1판(A 게임 8: 화면 K=12, 검출 K=9)은 **두 자릿수 K(10~12)를 못 읽는 스팀 공통의 알려진 한계**(plan-pvp §2.0)가 원인이었고 눈으로 확인했다(11830초 K 10 → 11908초 K 12, 그동안 검출은 `None`). **한 자리 본보기를 좌우 6픽셀씩 밀어 겹친 10~99 조합 본보기**(`with_two_digit_templates`)로 고쳤다: 그 게임이 K=12·A=6 으로 결과 화면과 일치, 한 자리 판독은 4,720건에서 하나도 안 바뀌었고 스팀 출력도 동일. 이제 결과 화면이 있는 14판 **모두** 일치. 게임 4 의 `death` 8건은 실제 사망(부활 카운트다운 화면 확인).

**실제 방송 전체 분석 실측 (V3, 명령줄)** — 방송 B(3시간 18분, 12.2GB)를 `analyze_vod` 로 끝까지 돌렸다: **8판, 클립 110개(4.7GB), 총 약 12분**(테스트 실행 등 다른 작업과 겹친 시간). 게임별 결과가 화면과 맞는다(순위·K/A: 2/8위 K6A4, 1/8위 K7A6, 1/7위 K5A3, 6/8위 K2A1, 2/7위 K6A6, 7/7위 K3A1, 1/8위 K7A8, 2/8위 K6A6). 클립은 평균 44초(최장 161초, 병합된 연속 교전), 태그는 `no_result` 61·`kill` 30·`teammate_death` 28·`assist` 25·`death` 20, PvP 점수 0.8 이상이 48개. 썸네일은 실제 교전 장면(1080p)이다. 이 실행에서는 앞선 결과 탐색에서 못 읽었던 게임 3 의 결과 화면(1/7위)도 읽혔다(순위표 탭·탈락 여부에 따라 판독이 갈린다). 판독 캐시(`.vods/<id>.states.jsonl.gz`)는 400KB 정도라 8시간 영상도 부담이 없다.

**남은 V0 확인**
- [ ] 1080p 네이티브 프레임에서 ROI·본보기 적합도(키우지 않은 상태)
- [ ] 교전 배지가 `None` 이 되는 원인
- [ ] 판독 시간(프레임당) 실측
- [ ] 다른 스트리머 방송 1편 이상
- [ ] 방송 한 편의 경기 경계를 손으로 표시해 자동 분할과 비교(§8-8)

## 5. V1~V6 작업 세부

각 단계는 **테스트를 먼저 쓴다**([CLAUDE.md](../CLAUDE.md)). 실제 다시보기 영상은 커밋하지 않으므로, 테스트는 **합성 영상**(ffmpeg 로 만든 작은 mp4 + 인위 HUD)과 합성 `FrameState` 시계열을 쓰고, 실제 방송으로는 수동 검증한다(기존 검출기 테스트와 같은 방식, [plan.md §7](plan.md)).

### V1 — 프레임 소스 추상화 · 프로필
- `FrameSource` 프로토콜, `SteamRecordingSource`(기존 동작 이관), `VodFileSource`.
- **첫 커밋은 스팀 경로 리팩터링만**: 기존 테스트 전부 통과 + 실제 녹화 1경기 검출 결과 동일 확인.
- `profiles/builtin/1920x1080.json`, 1080p 본보기(`data/templates/*/1920x1080.npz`). 프로필이 없거나 본보기가 없으면 경고.

### V2 — 게임 분할
- `pipeline/vod_games.py`: `FrameState` 시계열 → 게임 목록(시작·끝·확신도). 합성 시계열로 TDD: 판 사이 로비, 일차 감소로 붙은 두 판, 방송 화면 전환으로 잠깐 끊김, 게임 하나뿐, 인게임이 전혀 없음.
- 게임 끝 근처 프레임만 결과 화면 OCR.

### V3 — 분석 작업 · 클립 · 메타데이터
- `pipeline/vod_analyze.py`: 판독→캐시→(게임별) 구간·태그·점수→컷. 이어하기·취소·진행률.
- 게임별로 기존 `process_match` 의 구간/태그/PvP/컷 로직을 재사용한다(입력만 `VodFileSource` 프레임으로 다르다). 컷은 `ffmpeg -ss/-to -i <vod> -c copy`.
- 메타데이터 `source: "vod"`(§2.3), 닉네임 학습 비활성(§2.8).
- **영상 하나가 실패해도 다른 영상에 영향이 없어야 한다.** 실패한 게임은 색인에 실패 사유를 남기고 다음 게임으로 넘어간다.

## 8. 확인 필요 (추측으로 메우지 않은 것)

### 8-1. 저작권·약관
개인 분석·소장용으로만 쓴다는 전제다. **앱이 받지도 올리지도 않으므로** 코드에는 영향이 없다. 클립을 공유·배포하려면 방송 콘텐츠와 스트리머 권리 문제가 따로 생기니 이 도구의 범위 밖이다. 스트리머 표시명을 메타데이터에 남기는 것은 출처 표시 용도다.

### 8-2. 다시보기 파일의 성질 — **V0 최우선**
치지직 다시보기를 yt-dlp 로 받으면 무엇이 나오는지(컨테이너·코덱·키프레임 간격·타임스탬프 연속성)를 실제로 봐야 안다. 키프레임 간격이 스팀의 3초보다 훨씬 길면 키프레임 샘플링이 성립하지 않고, 분석 시간이 크게 늘어난다. 광고·재접속으로 영상이 이어 붙은 경우 시각이 어긋날 수 있다.

### 8-3. 1080p 에서 기존 ROI·본보기가 얼마나 맞는가
2560x1440 좌표 × 0.75 가 1080p 에서 픽셀 단위로 맞는지, 압축 화질에서 K/A 숫자 상관 매칭이 성립하는지 모른다. 스팀 쪽에서 "K/A 가 꺼진 채 돌고 있었다"는 사고가 있었으므로([SPEC §6 4단계](SPEC.md)) **본보기를 못 찾으면 반드시 경고**한다.

### 8-4. 스트리머의 UI 스케일·HUD 배치가 기본인가
스팀 프로필은 UI 스케일 기본값에서 쟀다([research §7-4](research.md) 미확인 항목과 같은 문제). 스트리머마다 다르면 ROI 가 어긋난다. 스트리머별 프로필 보정이 필요할 수 있다.

### 8-5. 스팀 감시와 분석의 동시 실행
분석이 CPU/디스크를 점유할 때 스팀 매치 처리가 밀리지 않는가. 우선순위 조절만으로 충분한지, 스팀 처리 시작 시 분석을 일시정지해야 하는지는 실측 후 정한다. **링버퍼가 스팀 쪽 시한이므로 스팀이 우선이다.**

### 8-6. 다시보기 클립의 정리 정책
스팀 클립은 링버퍼 때문에 "지금 못 뽑으면 영구 손실"이라 자동 정리가 필요했다. 다시보기는 원본이 남아 있어 **지워도 다시 뽑을 수 있다.** 그래서 v1 은 자동 정리 없이 사용자가 직접 삭제한다. 쌓이는 양이 문제가 되면 그때 정한다(§7.9 에 용량 감각 추가 필요).

### 8-7. 제목 규칙
`{day}일차 {dayNight} {myChar}, {teamChars}` 의 `myChar` 를 스트리머 캐릭터로 채우는 것으로 충분한지. 여러 스트리머 클립을 섞어 볼 때 제목만으로 누구인지 모호하면 스트리머 표시명을 제목에 넣는다.

### 8-8. 게임 분할의 실제 정확도
이미 있는 판독만으로 판 경계가 충분히 나뉘는지는 방송 종류(솔로 랭크·일반·듀오, 스트리머가 대기방에서 오래 노는 경우 등)에 따라 다를 수 있다. V0 에서 방송 몇 편의 경계를 손으로 표시해 자동 분할과 비교한다.

### 8-9. 파일 선택 UI
브라우저는 로컬 절대경로를 못 다루므로 기존 폴더 탐색 API(`/api/fs/dirs`)를 확장해 **파일 목록**도 돌려줘야 한다. 확장자 필터와 용량·길이 미리보기가 필요한지는 만들면서 정한다.
