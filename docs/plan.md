> 대상: SPEC [§6 1단계](SPEC.md) — 녹화본에서 **전투 구간**을 찾아내고, 각 구간에 태그를 다는 검출 레이어.
> 근거 수치는 [research.md](research.md)와 이 문서 §5.1의 실측에서 왔다. 확인되지 않은 것은 §8에 **확인 필요**로 표시했고, 추측으로 메우지 않았다.
>
> ⚠ **이 문서가 만든 검출기는 완성됐지만, 그것만으로는 목적을 못 채운다.** 아래 §0-2 참조.
> PvP/PvE 판별은 [plan-pvp.md](plan-pvp.md)(SPEC 4단계)에서 이어서 다룬다.

## 0-2. ★ 실사용으로 드러난 정정 (2026-09-21)

**이 계획의 전제가 틀렸다.** 아래 §0에서 "SPEC은 고칠 필요가 없다"고 적었는데, 고쳐야 했던 건 SPEC 쪽이었다.

배지는 **야생동물 사냥에도 똑같이 켜진다.** 이터널 리턴은 섬을 돌며 야생동물을 잡는 시간이 대부분이라, 실사용 20매치에서 뽑힌 클립 60개의 대부분이 사냥 장면이었다. 배지에는 PvP와 PvE를 가를 차이가 없다(실측 확인).

| 이 문서가 적은 것 | 실제 |
|---|---|
| "교전 배지 — 교전 구간을 정한다, **주 신호**" | 배지는 **전투 상태**만 알려준다. 교전의 **앵커**일 뿐이다 |
| "1번만 있어도 클립이 나온다" | 나오긴 하는데 **대부분 사냥 클립**이다 |

또 하나, **`K`/`A` 검출이 설정 구멍으로 꺼진 채 돌고 있었다.** `cli/watch.py` 가 `--k-templates` 를 명시적으로 줘야만 템플릿을 싣는데 `run.bat` 도 트레이 앱도 안 넘긴다. 클립 60개 전부 `killDelta=0` 이었고, 정작 매치 결과 화면에는 `K 1 · A 4` 가 찍혀 있었다. **가장 강한 확정 증거가 통째로 비활성이었다.**

→ 이 문서의 검출기들은 그대로 쓴다. 그 위에 PvP 판별 레이어를 얹는 것이 [plan-pvp.md](plan-pvp.md) 다.

## 0. 이전 판에 대한 정정 (첫 판 → 이 판)

이 문서의 첫 판은 **킬 검출기** 계획이었다. 요청을 글자 그대로 받아 카운터 판독만 다뤘는데, 그건 이 프로젝트의 주 신호가 아니다.

SPEC은 이미 올바르게 적혀 있다.

> **§1** — "v1의 목표는 내가 참여한 **모든 교전**을 빠짐없이 추출하는 것이다. 이기든 지든, 킬을 냈든 못 냈든 전부 뽑는다."
>
> **§2.8** — "**교전 앵커는 배지가 잡고, `K`/`A` 는 그 교전에 태그를 다는 데 쓴다.** 예전 SPEC처럼 `K` 증가를 앵커로 삼지 않는다."

**SPEC은 고칠 필요가 없다.** 어긋난 건 계획서 쪽이었고, 이 판에서 교전 검출을 중심으로 다시 썼다. 카운터 판독은 §5.5로 내려가 제자리를 찾았다.

### 검출기 셋과 우선순위

SPEC §6이 정한 순서를 그대로 따른다.

| # | 검출기 | 역할 | 난이도 | 상태 |
|---|---|---|---|---|
| **1** | **교전 배지** | 전투 구간의 **앵커** (PvP/PvE 구분 못함 — §0-2) | 낮음 (색 픽셀 세기) | ✅ |
| 2 | 사망 | 사망 구간 제외 + `death` 태그 | 낮음~중간 (램프 판정) | ⚠ 팀 전멸만 잡는 듯 |
| 3 | `K`/`A` 카운터 | `kill`/`assist` 태그, 자체 검증 | **높음** (글자 판독) | ⚠ 코드는 됨, **꺼져 있었음** |
| 4 | 일차·낮/밤 | 제목·필터용 | 낮음 (색 비교) | ✅ |

이 순서면 매 단계 끝에 돌아가는 물건이 남는다 — 그 판단 자체는 맞았다. 다만 **1번만으로는 사냥 클립이 대부분**이라, 2·3번이 태그가 아니라 **PvP 판별의 핵심 증거**라는 것이 뒤늦게 드러났다 (§0-2).

## 4. 공통 타입

```python
@dataclass(frozen=True)
class FrameState:
    t: float                    # 세션 시작 기준 오프셋(초)
    combat: bool | None         # None = 판독 불가
    dead: bool | None
    k: int | None
    a: int | None
    day: int | None
    day_night: str | None       # "day" | "night"
    confidence: float


@dataclass(frozen=True)
class CombatInterval:
    start: float
    end: float
    tags: frozenset[str]        # kill / assist / death / no_result
    k_delta: int
    a_delta: int
    died: bool
    day: int | None
    day_night: str | None
    confidence: float
```

**`None` 을 `False` 와 엄격히 구분한다.** SPEC §2.7이 반복해서 경고하는 지점이다 — "판독 불가를 교전 아님과 구분할 것". 어두운 프레임에서 배지 색 카운트는 전부 0이 되는데, 이걸 "교전 아님"으로 처리하면 교전이 끊겨 보인다.

## 5. 핵심 설계 결정과 트레이드오프

### 5.1 ★ 디코딩 전략 — 키프레임만 읽는다

**이게 이 계획에서 제일 큰 결정이다.** 검출 비용의 거의 전부가 HEVC 디코딩이다.

실측했다 (영상 60초 = 세그먼트 20개, 2560x1440 60fps HEVC, RX 6600 XT):

| 방식 | 60초 처리 시간 | 배속 | 20분 매치 환산 | 얻는 프레임 |
|---|---|---|---|---|
| 전체 디코딩 (소프트웨어) | 12.6초 | 4.8x | **4분 10초** | 원하는 만큼 |
| 전체 디코딩 + `-hwaccel d3d11va` | 9.4초 | 6.4x | 3분 8초 | 〃 |
| 전체 디코딩 + `-hwaccel dxva2` | 13.0초 | 4.6x | 4분 20초 | 〃 |
| **키프레임만 (`-skip_frame nokey`)** | **1.1초** | **55x** | **22초** | 세그먼트당 1장 |
| **키프레임만 + `-hwaccel d3d11va`** | **0.59초** | **102x** | **12초** | 〃 |

**16배 차이다.** 그런데 정밀도는 거의 잃지 않는다.

- 키프레임은 **세그먼트당 정확히 1개, 3.000초 간격**이다 (research §2.2).
- 그리고 SPEC §3의 컷은 **`-c copy` + 키프레임 스냅이라 어차피 3초 격자에만 붙는다**.
- 즉 **검출 정밀도와 컷 정밀도가 정확히 일치한다.** 3초보다 정밀하게 검출해봐야 컷 단계에서 버려진다.

```bash
ffmpeg -hwaccel d3d11va -skip_frame nokey -i <seg.mp4> -vsync 0 \
       -vf "crop=..." -f rawvideo -pix_fmt rgb24 -
```

#### 이 선택이 포기하는 것

| 잃는 것 | 영향 | 대응 |
|---|---|---|
| 3초보다 짧은 교전 | 샘플이 0개일 수 있어 통째로 놓친다 | SPEC §3의 **최소 길이 필터**가 어차피 버릴 대상이다 |
| 사망 램프의 형태 | 램프가 3.5~5초라 샘플이 1~2개뿐 (research §4.7) | 램프 "모양" 대신 **전후 값 차이**로 판정 (§5.4). ⚠ §8-3 |
| 카운터 증가 시각 정밀도 | ±1.5초 | 앵커가 배지라 카운터 시각은 태그용일 뿐. 영향 없음 |
| 배지 애니메이션의 저점 | 3초에 1장이라 저점을 밟을 수 있다 | 임계를 낮게(100) 두고 히스테리시스로 흡수. ⚠ §8-2 |

#### 폴백: 정밀 디코딩

필요하다고 판명되면 **2패스**로 간다.

```
1패스  키프레임만 전 구간 스캔 (12초)  → 교전 후보 구간
2패스  후보 구간 경계 ±6초만 전체 디코딩 → 경계 다듬기
```

교전이 매치당 5~10개면 2패스 대상은 매치 전체의 5~10%다. 전체 디코딩 4분이 20~25초로 줄어든다.

**단, 1패스만으로 목표 정확도가 나오면 2패스는 만들지 않는다.** 먼저 재고 결정한다 (§8-2, §8-3).

#### `hwaccel` 을 기본으로 켤 것인가

| | 켜기 | 끄기 |
|---|---|---|
| 속도 | 2배 빠름 (0.59 vs 1.1초) | — |
| 위험 | GPU 드라이버·기기에 따라 실패하거나 픽셀이 미세하게 달라질 수 있다 | 어디서나 동일 |

**기본은 켜되, 실패하면 조용히 소프트웨어로 떨어진다.** 22초도 충분히 빠르므로 hwaccel 은 있으면 좋은 정도지 필수가 아니다. 설정 키 `detect.hwaccel`(기본 `auto`).

> ⚠ **하드웨어 디코딩 결과가 소프트웨어와 픽셀 단위로 같은지는 확인하지 않았다** (§8-6). 색 임계를 쓰는 검출기라 미세한 차이가 판정을 뒤집을 수 있다. 라벨셋 평가를 두 경로로 각각 돌려 비교할 것.

### 5.2 ★ 교전 배지 검출기 — 주 신호

research §4.6이 이미 규칙을 확정해뒀다. 구현은 그대로 옮기면 된다.

```python
# detect/color.py — 배지·낮밤이 공용으로 쓴다
def count_colors(rgb: np.ndarray, v_min: int = 90, s_min: int = 60) -> ColorCounts:
    """ROI에서 '선명한' 픽셀만 골라 색 계열별로 센다."""
    a = rgb.astype(np.int16)
    r, g, b = a[..., 0], a[..., 1], a[..., 2]
    v = a.max(axis=2)
    s = v - a.min(axis=2)
    vivid = (v >= v_min) & (s >= s_min)

    warm = vivid & (r > b + 60)
    return ColorCounts(
        orange=int((warm & (r >= g) & (g < r * 0.80)).sum()),
        yellow=int((warm & (g >= r * 0.80)).sum()),
        blue=int((vivid & (b > r + 40)).sum()),
    )
```

```python
# detect/badge.py
ORANGE_MIN = 100      # 교전 판정. 실측 평상시 0~21 vs 교전 138~773
PRESENT_MIN = 250     # 배지가 화면에 있는가 (로비·암전 배제)

def read_badge(rgb: np.ndarray) -> bool | None:
    """교전 중이면 True, 평상시면 False, 판독 불가면 None."""
    c = count_colors(rgb)
    if c.orange + c.yellow + c.blue < PRESENT_MIN:
        return None                      # 배지가 안 보인다 — 로비/암전/관전
    return c.orange >= ORANGE_MIN
```

**왜 색 세기만으로 되는가**: 평상시 배지는 레벨 숫자(파랑 또는 노랑 원), 교전 중에는 주황 교차 칼이다. 주황 픽셀 수가 평상시 **0~21**, 교전 중 **138~773** 으로 6배 이상 벌어진다 (research §4.6). 템플릿 매칭이 필요 없다.

**주의 셋** (전부 research §4.6에서 실제로 부딪힌 것):

1. **평상시 배지 색이 매치마다 다르다** — 파랑인 판도, 노랑인 판도 있었다. 그래서 주황과 노랑을 **녹색 채널로 가른다**(`g < r * 0.80`). 노랑 배지 판에서도 교전 프레임은 주황 773으로 확실히 떴다.
2. **로비에서 주황 58이 잡힌 적이 있다** — 그래서 `PRESENT_MIN` 가드가 먼저 온다.
3. **완전히 어두운 프레임은 전부 0** — `None` 이지 `False` 가 아니다.

### 5.3 교전 구간 산출 — 상태 기계 + 히스테리시스

프레임 상태 시계열을 구간으로 바꾼다. 키프레임 샘플링이라 **한 샘플 = 3초**다.

```python
GAP_FILL_SAMPLES = 2      # 이 이하의 off 는 메운다 (= 6초)
MIN_COMBAT_SAMPLES = 2    # 이 미만의 on 은 버린다 (= 6초)

def to_intervals(states: list[FrameState]) -> list[tuple[float, float]]:
    """배지 on 구간을 교전 구간으로 만든다.

    규칙:
      1) None(판독 불가)은 직전 상태를 유지한다 — 교전 종료로 치지 않는다
      2) 짧은 off 는 메운다 (애니메이션 저점 / 순간 가림)
      3) 짧은 on 은 버린다 (야생동물 한 대 때린 것 등)
      4) 구간 경계는 샘플 시각 그대로 — 3초 격자에 이미 맞아 있다
    """
```

파라미터의 트레이드오프:

| | 크게 잡으면 | 작게 잡으면 |
|---|---|---|
| `GAP_FILL` | 별개 교전 둘이 하나로 붙는다 | 한 교전이 여러 조각으로 쪼개진다 |
| `MIN_COMBAT` | 짧지만 진짜인 교전을 놓친다 | 야생동물 사냥이 클립이 된다 |

**어느 쪽으로 틀릴지 미리 정해둔다.** SPEC §6은 *"오탐은 클립 하나 더 생기는 정도라 관대하게"* 라고 했다. 따라서 **놓치는 쪽보다 더 잡는 쪽으로 기울인다** — `GAP_FILL` 은 넉넉히, `MIN_COMBAT` 은 빠듯하게. 실제 값은 라벨셋으로 정한다 (§8-2).

> SPEC §3의 클립 구간은 `교전 시작 -5초 ~ 교전 종료 +8초` 이고 `-c copy` 가 3초 격자로 스냅한다. 즉 구간 경계의 오차 3초는 프리롤에 흡수된다.

### 5.4 사망 검출기

research §4.7이 두 신호를 줬다.

| 신호 | ROI | 정상 → 사망 |
|---|---|---|
| **초상화 얼굴** (1차) | `x 690..860, y 1250..1400` | 채도 25.9 → **13.3**, 밝기 111.4 → **33.9** |
| 화면 중앙 월드 (2차) | 가로 20~80%, 세로 15~72% | 채도 45 → 12.6, 밝기 131 → 54 |

초상화 쪽이 ROI가 작고 신호가 세다(채도 절반, 밝기 1/3). 1차로 쓴다.

**절대 임계를 쓰지 않는다.** research §4.7이 명시한 대로, 밤 맵·실내에서는 평상시 밝기도 40~80까지 떨어진다. 대신 **매치 내 기준선 대비 상대 하락**을 본다.

```python
def detect_death(states: list[FaceStat]) -> list[tuple[float, float]]:
    """얼굴 ROI의 채도·밝기가 '그 매치의 평소'보다 크게 떨어진 구간을 찾는다.

    기준선은 매치 전체의 중앙값으로 잡는다 — 사망 구간은 소수라 중앙값을 거의 안 흔든다.
    """
    base_v = np.median([s.value for s in states])
    base_s = np.median([s.sat for s in states])
    # 사망 = 밝기가 기준선의 REL_V 이하 AND 채도가 REL_S 이하
```

> ⚠ **키프레임 샘플링(3초)에서는 램프의 "모양"을 볼 수 없다.** research §4.7은 3.5~5초에 걸친 단조 하강을 신호로 쓰라고 했는데, 3초에 1장이면 램프 중 1~2장만 잡힌다. 그래서 **모양 대신 전후 값 차이**로 판정한다. 이게 충분한지는 재봐야 한다 (§8-3).

**사망 구간의 끝(부활)은 아직 정할 수 없다** — 샘플이 없다 (§8-4). 잠정적으로 "얼굴 지표가 기준선으로 복귀하는 시점"으로 두고, 그 잠정성을 코드 주석과 로그에 남긴다.

### 5.5 `K`/`A` 카운터 판독 — 태그용

**여기서만 글자를 읽어야 해서 셋 중 제일 어렵다.** 다만 **앵커가 아니라 태그용**이라, 실패해도 교전 구간 자체는 나온다. 우선순위를 3번에 둔 이유다.

#### 왜 단순 비교로 안 되는가

research §4.4의 결론이다. HUD 텍스트에 **불투명 배경판이 없어** 글자가 게임 화면 위에 직접 그려지고, 글자 테두리가 배경과 섞인다. **같은 숫자인데도 프레임마다 픽셀 배치가 달라서**(49프레임 → 49가지) 모양을 그대로 대조하는 방식은 못 쓴다.

#### 쓰려는 방법 — 쉬운 말로

이전 판에서 "흰 글자다움 맵 × 알파 템플릿 상관"이라고 적었는데, **그건 제가 만든 말이고 한국어로 읽히지 않는다.** 풀어 쓰면 이렇다.

> **1단계 — 화면에서 "글자일 만한 곳"에 점수를 매긴다.**
> 픽셀 하나하나에 대해 *밝은가* + *색기가 없는가(흰색인가)* 를 따져 **0에서 1 사이 점수**를 준다. 글자는 흰색이니 점수가 높고, 배경은 대개 색이 있거나 어두우니 낮다.
> 여기서 **"점수" 그대로 두고 이진(글자/배경)으로 자르지 않는 게 요점이다.** 값이 막 바뀐 직후에는 새 숫자가 흐리게 나타났다가 0.15초에 걸쳐 진해지는데(research §4.5), 잘라버리면 그 구간이 통째로 "글자 없음"이 된다.
>
> **2단계 — 숫자마다 "본보기"를 만들어 둔다.**
> 0부터 9까지 각각, **어느 위치에 글자가 얼마나 진하게 찍히는지**를 담은 기준 이미지다. 실제 게임 화면에서 같은 숫자를 여러 배경에서 모아 만든다.
>
> **3단계 — 화면 점수와 본보기를 겹쳐 모양이 얼마나 닮았는지 잰다.**
> 가장 닮은 숫자를 답으로 고른다. 1등과 2등의 점수 차이가 작으면 **답을 내지 않는다** — 억지로 고르면 틀린 값이 조용히 들어간다.

이름을 다음과 같이 정한다.

| 이전 표현 | 이 판에서 쓰는 이름 | 뜻 |
|---|---|---|
| 흰 글자다움 맵 | **글자 점수 맵** | 픽셀마다 "흰 글자일 가능성" 0~1 |
| 알파 템플릿 | **숫자 본보기** | 숫자별 기준 이미지. 값은 글자의 진하기(0~1) |
| 상관 | **모양 비교** | 두 이미지의 패턴이 얼마나 닮았는지 (평균 제거 정규화 상관) |

#### 글자 점수 맵

```python
# detect/glyph.py
def text_score(rgb: np.ndarray, v_lo: int = 120, s_hi: int = 70) -> np.ndarray:
    """픽셀마다 '흰 글자일 가능성'을 0~1로 매긴다.

    이진화하지 않는 것이 핵심이다. 값이 바뀐 직후 새 숫자가 흐리게 나타났다가
    0.15초에 걸쳐 진해지는데(research §4.5, 밝기 113→169→220→255),
    임계로 자르면 그 구간이 통째로 '글자 없음'이 된다.
    """
    a = rgb.astype(np.int16)
    v = a.max(axis=2)              # 밝기
    s = v - a.min(axis=2)          # 색기 (글자는 흰색이라 0에 가깝다)
    bright = np.clip((v - v_lo) / (255 - v_lo), 0.0, 1.0)
    achroma = np.clip(1.0 - s / s_hi, 0.0, 1.0)
    return (bright * achroma).astype(np.float32)
```

#### 숫자 본보기 만들기

글자는 흰색(≈255)이 배경 위에 겹쳐진 것이다. 픽셀별로

```
보이는 값 = 진하기 × 255 + (1 - 진하기) × 배경
```

배경만 프레임마다 바뀌고 진하기는 글꼴이 정한 고정값이다. 따라서 **같은 숫자를 여러 배경에서 모아 픽셀별 하위값을 취하면 진하기를 역산할 수 있다.** 어두운 배경 샘플이 섞여 있으면 `배경 ≈ 0` 이므로:

```python
def build_template(samples: np.ndarray) -> np.ndarray:
    """같은 숫자 크롭 N장 (N,H,W,3) → 숫자 본보기 (H,W) 0~1.

    최솟값 대신 하위 10 퍼센타일을 쓰는 것은, 압축 아티팩트 같은
    이상치 한 장이 진하기를 통째로 깎지 않게 하기 위해서다.
    """
    v = samples.astype(np.int16).max(axis=3)
    return np.clip(np.percentile(v, 10, axis=0) / 255.0, 0, 1).astype(np.float32)
```

#### 모양 비교

```python
def _similarity(a: np.ndarray, b: np.ndarray) -> float:
    """평균을 뺀 뒤 정규화해 비교한다.

    평균을 빼므로 '글자 모양 안쪽은 점수가 높고 바깥쪽은 낮다'를 동시에 요구하게 된다.
    이게 없으면 흰 덩어리가 아무 숫자에나 높은 점수를 받는다.
    """
    a = a - a.mean(); b = b - b.mean()
    d = float(np.sqrt((a * a).sum() * (b * b).sum()))
    return float((a * b).sum() / d) if d > 1e-6 else 0.0
```

**1등과 2등의 차이를 신뢰도로 쓴다.** 절대 점수보다 오판을 훨씬 잘 걸러낸다. 차이가 작으면 `None` 을 반환한다.

#### 자릿수

research §4.2: **자릿수가 늘면 필드 중심을 기준으로 좌우로 확장된다.** 우측 정렬이 아니고, 한 필드가 늘어도 다른 필드는 안 밀린다.

자릿수를 먼저 판정하지 않고 **ROI 전체에 훑어서 매칭한 뒤 피크를 묶는다.** 1자리·2자리를 한 코드로 처리할 수 있다. ROI가 36x24, 본보기가 12x17이라 후보 위치가 수십 개뿐이고, 키프레임 샘플링이면 20분 매치가 400프레임이라 **최적화할 이유가 없다.**

#### 본보기를 어디서 구하나 ⚠

`K`는 보통 한 자리다. **7·8·9는 좀처럼 안 나온다.**

| 방법 | 장점 | 단점 | 판정 |
|---|---|---|---|
| `TK`/`K`/`A` 세 필드에서 수집 | 같은 글꼴·크기가 확실 | 높은 숫자는 판을 많이 쌓아야 모인다 | **1차** |
| 매치 타이머(`00:25`)에서 수집 | 매 판 0~9가 전부 돌아 데이터 무한 | **⚠ 글자 크기가 같은지 미확인** (§8-5) | 확인 후 결정 |
| 게임 리소스에서 글꼴 추출 | 즉시 전부 확보 | Unity 에셋 파싱. 인게임 렌더와 일치 보장 없음 | 위가 다 막히면 |

없는 숫자는 본보기가 없으므로 **판독기가 `None` 을 반환한다.** 조용히 틀린 값을 내지 않는다.

> **✅ 1차 방법으로 실제 구축 완료** (§9-8). `K` 필드에서 0~4 본보기를 실제 녹화본으로 만들어 `data/templates/digits/2560x1440.npz` 에 담았다. 같은 라벨셋 기준 정확도 29/30, 오답 0건. 5~9는 아직 비어 있다.

### 5.8 결과 화면 판독 — OCR (2026-09-21 추가)

경기가 끝나면 `나가기` 전에 **결과 화면**(`4/7 랭크 대전 실험 종료`)이 항상 뜬다. 순위·랭크 여부·결과 문구·내 닉네임을 읽어 클립 메타데이터 `matchResult` 에 남긴다. 상세 규칙과 실측은 [SPEC §2.13](SPEC.md).

- **왜 OCR 인가.** 숫자·문구 템플릿을 만들려 했지만 녹화본에 남은 결과 화면이 1과 4, `실험 종료`/`최종 생존` 뿐이라 샘플이 부족했다. 닉네임은 한글·영문·일본어·한자가 섞여 템플릿으로는 불가능하다. RapidOCR(ONNX, PP-OCRv5) 한국어 모델은 화면 한 장에 ~1~2초, 순위·문구·한글/영문 닉네임을 정확히 읽었다.
- **파일.** `detect/ocr.py`(엔진 래퍼, 언어별 지연 로딩) · `detect/result.py`(파싱 + `read_result_screen`) · `pipeline/result_scan.py`(경기 끝에서 거슬러 올라가며 탐색) · `pipeline/nickname.py`(첫 닉네임 학습). ROI 는 프로필의 `result_panel`, `result_chip`.
- **탐색.** 경기 끝 최대 40 세그먼트를 뒤에서부터 본다. 인게임 프레임은 일차 판독으로 건너뛰어 OCR 을 아낀다. 실패는 클립 생성을 막지 않는다.
- **파싱은 위치가 아니라 순서.** 순위 `N/M` → 신뢰도 0.8+ · 한글 2자+ 줄 = 결과 문구 → `|` 로 시작하는 줄 = 닉네임. (칩 잡음 `이` 가 문구로 읽히던 버그를 회귀 테스트로 고정.)
- **랭크 여부.** 파란 알약 칩은 원본 그대로는 안 읽힌다. 밝기 200 초과만 남겨 흑백 반전·3배 확대하면 `랭크` 가 읽힌다.
- **검증.** 실제 경기 하나(13:48 시작)를 `process_match` 로 끝까지 돌려 11개 클립 모두에 `랭크 · 4/7 · 실험 종료` 가 들어갔다(2분 33초).

## 6. 구멍 난 시계열을 견딜 것

링버퍼는 매치를 통째로 지우지 않고 **앞에서부터 깎는다**(SPEC §7.2.1). 백로그로 늦게 처리하는 매치는 앞부분 세그먼트가 이미 없을 수 있다.

- 없는 세그먼트는 **`None` 구간으로 기록한다.** 프레임이 없었던 것과 판독 실패를 같게 다룬다.
- **구멍을 사이에 둔 값 변화로 태그를 만들지 않는다.** `K: 2 → [구멍 5분] → 6` 은 킬 4회가 아니라 "그 사이를 모름"이다.
- 구멍 옆에서 시작하거나 끝나는 교전 구간은 **경계가 잘렸을 수 있다**고 표시한다.
- 구멍이 있으면 자체 검증(증가 횟수 == 최종값)이 당연히 안 맞는다. **검출기 실패로 집계하지 말 것.**

> **구현 확인**: `video/frames.py` 는 요청받은 세그먼트 번호 중 존재하는 것만 골라 **번호가 연속인 구간별로 나눠 각각 별도 ffmpeg 호출로 디코딩한다.** 구멍을 사이에 두고 통째로 이어붙이면 fMP4 프래그먼트의 바이트 오프셋 참조가 깨져 디코딩이 중단된다(실측: NAL 유닛 크기가 쓰레기값으로 깨짐). 연속 구간별 분리 디코딩이 이 문제를 원천적으로 피한다.

```python
@dataclass(frozen=True)
class MatchDetection:
    intervals: list[CombatInterval]
    k_final: int | None
    a_final: int | None
    gaps: list[tuple[float, float]]
    source_incomplete: bool
```

## 7. 테스트와 평가

SPEC §5: **"검출기는 테스트 하네스를 먼저 만든다."**

### 라벨셋

교전 구간 라벨링이 주다. **프레임 단위가 아니라 구간 단위로 라벨링한다.**

```json
{"match": "20260919_130747_m3", "combats": [[412.0, 447.0], [610.0, 638.0]],
 "deaths": [[1180.0, 1215.0]], "k_final": 4, "a_final": 9}
```

| 항목 | 목표 |
|---|---|
| 라벨링된 매치 | 최소 5판 (배틀로얄 3 + 코발트 2) |
| 교전 구간 | 합계 40개 이상 |
| 배경 다양성 | 낮/밤, 실내/실외가 고루 (research §4.3의 조건) |
| 사망 구간 | 5개 이상 — **팀원 생존 상태의 사망을 반드시 포함** (§8-4) |
| 숫자 0~9 각각 | 최소 20 샘플 (카운터용, §5.5) |

### 지표

교전 검출은 **구간 단위 지표**를 쓴다. 프레임 정확도는 의미가 없다.

```
교전 재현율     라벨 구간 중 검출된 비율      ← SPEC 목표 90% 이상
교전 정밀도     검출 구간 중 진짜인 비율      ← 낮아도 관대 (클립 하나 더)
경계 오차       시작·끝의 평균 절대 오차(초)
분할/병합 횟수  라벨 1개가 검출 N개로 쪼개짐 / 라벨 N개가 1개로 붙음
```

```
카운터 오답률   틀린 값을 자신 있게 낸 비율   ← ★ 제일 중요
카운터 미지율   판독을 포기한 비율            ← 오답보다는 낫다
```

> **오답률을 미지율보다 우선한다.** 판독을 포기하면 그 프레임만 버려지지만, 틀린 값을 내면 없는 킬 태그가 붙는다.

### 시계열 테스트는 합성 데이터로

구간 산출 로직은 실제 영상 없이 테스트한다.

```python
def test_판독불가는_교전을_끊지_않는다():
    states = [s(0, True), s(3, True), s(6, None), s(9, True), s(12, True)]
    assert to_intervals(states) == [(0.0, 12.0)]


def test_짧은_교전은_버린다():
    states = [s(0, False), s(3, True), s(6, False), s(9, False)]
    assert to_intervals(states) == []


def test_구멍을_사이에_둔_카운터_변화는_태그가_아니다():
    ...
```

## 8. 확인 필요

계획에 영향을 주는데 확인되지 않은 것들이다. **추측으로 메우지 않았다.**

### 8-1. 멀티킬 시 카운터 거동 (research §7-6)

`+2`가 한 번인지 `+1`이 두 번인지 모른다.

- **영향**: §5.5의 태그 부여. `k_delta` 해석.
- **현재 처리**: 관측된 그대로 기록하고 `delta > 1` 이면 경고. 어느 쪽으로도 가정하지 않는다.
- **막는가**: 아니다.

### 8-2. 키프레임 샘플링(3초)으로 교전 경계가 충분한가 (신규 · **제일 먼저 확인**)

§5.1의 디코딩 전략 전체가 여기 걸려 있다.

- **모르는 것**: ① 배지 애니메이션의 주황 픽셀 저점이 3초 간격 샘플에서 임계 100 아래로 내려가는가 ② 3초 격자로 잡은 교전 경계가 라벨과 얼마나 어긋나는가 ③ 3초 미만 교전이 실제로 얼마나 있는가
- **확인 방법**: 교전 한 구간을 **전체 디코딩**해 60fps 전 프레임의 주황 픽셀 수를 그린다. 그 위에 3초 간격 샘플을 겹쳐 본다. `scripts/probe/` 도구를 조금 고치면 된다.
- **막는가**: 아니다. 다만 결과에 따라 2패스 폴백(§5.1)을 만들지 말지가 갈린다. **작업 순서 2번에 둔 이유다.**
- **✅ 실제 녹화본으로 스모크 검증됨**: 구현 완료 후 실제 2560x1440 세션(`bg_1049590_20260919_130747`)에 `detect_match()`를 그대로 돌려봤다. 세그먼트 3600~3660(180초) 구간에서 교전 4개(`day`, conf 1.00)가 정확히 잡혔고, 61개 키프레임 디코딩에 5.8초 걸렸다(하드웨어 가속). 완전한 라벨셋 통계는 아니지만 **키프레임 샘플링만으로 실제 교전을 놓치지 않고 잡는다는 최소 증거는 확보됐다.**

### 8-3. 3초 샘플링으로 사망 램프를 잡을 수 있는가 (신규)

- **모르는 것**: research §4.7은 3.5~5초 램프를 봤다. 3초에 1장이면 1~2장만 잡히는데, "전후 값 차이"만으로 밤 맵의 어두운 구간과 구분되는가.
- **현재 처리**: 매치 중앙값 기준 상대 하락으로 판정하되, 임계는 비워뒀다.
- **확인 방법**: §8-2와 같은 프레임 데이터로 동시에 잰다.
- **막는가**: 아니다. 사망 검출기는 2순위다.
- **✅ 실제 녹화본으로 스모크 검증됨**: research §4.7이 실측한 그 사망 시퀀스(세그먼트 3800~3830, 실제 시각 t=11457~11487)를 `detect_match()`로 다시 돌리니 **`tags=['death'], died=True` 로 정확히 잡혔다.** 같은 세션의 밤 구간(세그먼트 3500~3520)도 `day_night="night"` 로 정확히 판독됐다(research가 "1일차 밤"으로 확인한 바로 그 구간). 3초 샘플링으로 충분하다는 실증이다.

### 8-4. 팀원 생존 상태의 사망·관전 화면 (research §7-1, §7-2)

**이 계획에서 가장 큰 미지수다.**

- **모르는 것**: 내가 죽고 팀원이 살아있을 때 화면이 어떻게 생겼는지. SPEC §3은 "관전 화면은 UI가 다르니 판독 불가로 처리"하라는데, **그 화면을 아직 아무도 못 봤다.** 부활 순간도 마찬가지.
- **영향**: §5.4의 사망 구간 끝 판정, §5.2 배지의 `PRESENT_MIN` 가드가 관전 화면에서 통하는지.
- **현재 처리**: 사망 구간 끝을 "얼굴 지표 복귀"로 **잠정** 정의하고, 잠정임을 코드와 로그에 남긴다.
- **확인 방법**: 팀원이 살아있는 상태로 죽은 매치가 필요하다. 조사한 3판은 전부 "사망 = 매치 종료"였다. **라벨셋 수집 때 이 조건을 의도적으로 만들 것.**
- **막는가**: 교전 검출은 막지 않는다. 사망 태그의 정확도를 보증할 수 없을 뿐이다.
- **부분 진행 (plan-pvp.md §2.1)**: `detect/spectator.py` 를 구현해 관전 화면 판독을 완료 처리했고, 사용자가 보내온 스크린샷 1장 + 사망 직후 4프레임으로 부분 검증했다. 다만 plan-pvp.md 스스로도 "관전 화면의 실제 영상 표본이 없다"고 인정하므로, 위 "모르는 것"의 핵심(관전 화면이 실제로 어떻게 생겼는지 영상으로 확인)은 여전히 해소되지 않았다.

### 8-5. 타이머·일차 숫자가 카운터와 같은 글꼴·크기인가 (신규)

- **영향**: §5.5의 본보기 조달, §5.6의 일차 판독.
- **현재 처리**: 같다고 가정하지 않는다. 확인 전까지 일차는 비워둔다.
- **확인 방법**: 같은 프레임에서 글리프 높이를 비교한다. 카운터는 **높이 17px, 폭 11~13px**로 이미 재뒀다(research §4.2). 30분이면 끝난다.
- **막는가**: 아니다. 같다면 라벨링 부담이 크게 준다.
- **우회됨(§9-5)**: 일차 판독은 결국 카운터 본보기 재사용이 아니라 `detect/day.py` 의 별도 템플릿(`data/templates/days`, 지역명과 같은 방식)으로 구현했다. 이 질문(타이머·카운터 글꼴 일치 여부) 자체는 여전히 미확인이지만, 일차 판독을 막고 있지는 않다.

### 8-6. 하드웨어 디코딩 결과가 소프트웨어와 같은 픽셀인가 (신규)

- **영향**: §5.1. 색 임계를 쓰는 검출기라 미세한 차이가 판정을 뒤집을 수 있다.
- **현재 처리**: 기본 `auto`, 실패 시 소프트웨어 폴백.
- **확인 방법**: 같은 세그먼트를 두 경로로 디코딩해 ROI 픽셀을 직접 비교. 라벨셋 평가도 양쪽으로 돌린다.
- **막는가**: 아니다. 소프트웨어만 써도 20분 매치가 22초다.
- **부분 확인됨**: `hwaccel="d3d11va"` 로 실제 HEVC 녹화본을 디코딩해 배지/사망/낮밤 판정이 전부 올바르게 나온 것은 확인했다(§8-2, §8-3 스모크 검증). 다만 소프트웨어 디코딩과의 **픽셀 단위 직접 비교**는 아직 안 했다.

### 8-7. 다른 해상도에서 UI가 비례 스케일되는가 (research §7-4)

- **영향**: §5.7 전체.
- **현재 처리**: 추정하되 `measured=False` 로 표시하고 경고.
- **막는가**: 아니다. 2560x1440 하나로 개발·평가가 가능하다.

### 8-9. 결과 화면 — 아직 못 본 것 (신규)

- **일반 게임 칩·탈출 결과 문구.** 샘플이 없다. 칩에 `랭크` 가 없고 다른 글자가 읽히면 normal, 칩을 못 읽으면 unknown, 문구는 화면 원문 그대로 저장한다. 탈출 화면에 `N/M` 순위가 없으면 지금 코드는 결과 화면으로 인식하지 못한다.
- **일본어·한자 닉네임.** 한국어/중국어 모델 중 높은 점수를 쓰게 했지만 실측하지 못했다.
- **캐릭터 이름 표.** `data/characters.json` 은 기억에서 채운 영문→한글 표라 틀린 항목이 있을 수 있다. 표에 없거나 모호한 이름은 `characterRaw` 로만 남으니, 그걸 보고 표를 고친다. 순위표 행 OCR 로는 못 읽는다.
- **다른 해상도.** `result_panel`/`result_chip` 은 2560x1440 실측값이고 다른 해상도는 비례 스케일 추정이다.

### 8-8. 색 임계값들 (신규)

`text_score()` 의 `v_lo=120 / s_hi=70`, `GAP_FILL=2`, `MIN_COMBAT=2`, 사망 상대 임계 — **전부 research 수치에서 역산한 출발점이지 검증된 값이 아니다.** 라벨셋을 만든 뒤 §7의 평가 하네스로 정한다.

### 10-3. 신규 발견 — 이 다시보기의 방송 오버레이가 `spectating`/`K`/`A` 판독을 막는다 (2026-09-27)

C2 작업 중 `pipeline/vod_games.py::is_ingame` 이 기존 조건(`k`/`spectating`)만으로는 실제 인게임 구간을 거의 못 잡는 것을 발견해 원인을 팠다. **코발트 프로토콜의 문제가 아니라 이 특정 다시보기(스트리머)의 방송 레이아웃 문제였다** — plan-vod.md §8-4 가 이미 우려했던 "스트리머의 UI 스케일·오버레이가 기본값이 아닐 수 있다"가 실제로 나온 사례다.

- **미니맵 헤더 자리가 스트리머의 프로필/설정 위젯으로 덮여 있다.** `minimap_icons` ROI(`[1808,795,1909,844]`, 1920x1080)를 실제로 크롭해 보면 배틀로얄의 4개 아이콘이 아니라 **스트리머 자신의 캐릭터 초상화(레벨 숫자 포함) + 아이콘 3개(파이차트·음소거·톱니)** 가 있다. `minimap_visible()` 이 기대하는 패턴과 달라 계속 `False` → `read_spectating` 이 계속 `None` → `combat`/`day_night`/`face_value`(사망 검출 입력) 가 전부 판독 시도조차 안 된다(§2.12 규칙: `spectating` 이 확실할 때만 그 아래 신호를 읽는다).
- **`K`/`A` 값 자리도 어긋나 있다.** 실제 프레임의 밝은 열(column)만 골라 정밀 측정(`region_score` 로 눈대중 대신 픽셀 분석)한 결과, `TK` 값은 기존 ROI(`[1792,20,1815,38]`)와 거의 일치했지만 **`K` 값은 실제로 `x 1867~1876`, `A` 값은 `x 1909~1917`** 로 기존 ROI(`k_value=[1839,1866]`, `a_value=[1885,1912]`)와 20~30px 어긋나 있었다. `TK` 만 우연히(라벨 글자 획을 숫자로 오인해) 가끔 읽히고 `K`/`A` 는 실측 구간(190~300초) 내내 전부 `None` 이었다.
- **왜 고치지 않았는가**: `k_value`/`a_value` ROI 는 `read_field` 가 "ROI 폭 == 본보기 폭"(탐색 여유 없음, `test_counter_rois_are_as_wide_as_the_digit_templates` 로 고정된 계약)이라 폭을 넓히면 기존 배틀로얄 경로가 깨질 위험이 있고, 이 20~30px 어긋남이 "코발트라서"인지 "이 스트리머의 UI 스케일이 달라서"인지 이 한 편만으로는 구분이 안 된다(다른 코발트 녹화나 이 스트리머의 배틀로얄 녹화로 교차 확인해야 한다). 섣불리 코발트 전용 ROI 를 박으면 실제로는 "이 스트리머 전용" 값을 코발트 전체인 것처럼 커밋하는 위험이 있다.
- **영향**: 이 실측 파일에서는 `combat`/`kill`/`assist`/`death` 태그가 거의 안 나온다 — Phase 판독 기반 모드 판별(C1-b)·게임 경계(C2)는 이 문제와 무관해 정상 동작하지만, **클립 생성 자체(교전 검출)는 이 영상으로는 검증이 안 된다.** 다른 코발트 다시보기(오버레이가 HUD 를 안 가리는 방송)가 있어야 C4 의 나머지 항목(부활 상시화의 사망 처리 영향)도 확인할 수 있다.
- **다음에 이 문제를 만나면**: (1) 여러 스트리머의 다시보기로 `minimap_icons`/`k_value`/`a_value` 를 교차 검증해 "코발트 자체의 차이"와 "이 방송 특유의 오버레이/스케일"을 가른다. (2) 후자라면 ROI 재조정이 아니라 스트리머별 UI 스케일 보정(§8-4 가 이미 예견한 더 큰 작업)이 맞는 해법이다.

### 10-4. C3 코발트 결과 화면 판독 구현 기록 (2026-09-27)

C0(§10-1) 에서는 이 실측 파일에 결과 화면이 안 뜨는 것처럼 보였는데, 사용자가 **같은 파일을 다시 보라고 지시**해 다른 매치 종료 지점(약 806초·1638초·4799초)을 더 찾아보니 실제로는 **여러 판 중 일부에서** 상세 결과 패널이 뜬다는 걸 확인했다(패배 예시: 1638초, 승리 예시: 4799초 — 이 4799초 장면이 사용자가 대화 맨 처음에 준 스크린샷의 실제 출처였다). 화면 흐름은 `PROTOCOL COMPLETE` 배너(인게임 화면 위에 겹침) → `VICTORY`/`DEFEAT` 전체화면 배너 → `결과를 불러오는 중` 로딩 → **(뜰 때도, 안 뜰 때도 있음)** 상세 패널(코발트/승리|패배, 본인 TK/K/D/A, 팀원 카드 3장) → 팀 로비. 상세 패널이 항상 뜨는 건 아니다(관측 3판 중 2판만) — 배틀로얄의 "결과 화면 없는 판"과 같은 급으로 다룬다.

- **구현**: `detect/cobalt_result.py`. `CobaltResultScreen`(outcome·nickname·stats·teammates)을 읽어 `to_result_screen()` 으로 기존 `ResultScreen` 모양으로 바꾼다 — `placement=1(승리)/2(패배)`, `total=2` 를 UI 호환용 자리표시자로 쓰고, 나머지 파이프라인(`match_result_dict`, `build_vod_metadata`, 프론트 `MatchResult`)은 한 글자도 안 고쳤다.
- **ROI**(1920x1080 전용, 정규화 없음 — Phase 본보기와 같은 이유): `cobalt_outcome`(승/패 글자, `[195,500,309,554]`), `cobalt_result_panel`(코발트 라벨·닉네임·TK/K/D/A, `[140,440,720,710]`), `cobalt_teammate1~3`(팀원 카드 3장). 카드 경계는 처음에 눈대중으로 재서 2·3번 카드가 왼쪽이 잘렸다(닉네임 앞글자 소실) — 밝은 열(column) 분석으로 다시 재서 고쳤다.
- **`승리`/`패배` 글자는 OCR 로 못 읽는다**: 이 스타일화된 글꼴을 RapidOCR 이 `패배` → `HAHⅡ`(점수 0.75, 자신 있게 틀림)로 읽는다. `Phase N` 과 같은 이유로 **일반 OCR 대신 본보기 대조**(`read_cobalt_outcome`, `region_score`+`read_region`)로 바꿨다 — 실측 2건(승리·패배 각 1장) 교차 검증에서 정답 상관계수 1.0, 오답 0.39 로 마진이 아주 크다(Phase 숫자보다 쉬운 문제 — 단어 모양 차이가 큼).
- **닉네임은 재판독하지 않는다**: 배틀로얄의 `read_nickname`(닉네임 줄만 다시 잘라 3배로 키워 재 OCR)을 그대로 가져다 썼더니 오히려 나빠졌다 — 첫 판독 `|우퓨`(0.86, 정답 `우쮸`에 근접) → 재판독 `1早`(완전히 틀림). 첫 판독 줄을 그대로 정리해 쓰는 것으로 바꿨다.
- **팀원 카드 닉네임이 추천 배지(`5/6`)로 오인됐다**: 카드 위쪽의 추천 버튼 배지가 닉네임보다 먼저(더 위) 나올 때가 있어, "라벨도 숫자도 아닌 첫 줄"로 고르면 배지가 걸렸다. `TK/K/D/A` 라벨 줄보다 **위에 있는 후보 중 가장 아래**(닉네임 자리)로 바꿔 해결.
- **배틀로얄과 공유하는 `parse_stats` 의 잠재 버그도 발견해 고쳤다**: 같은 행 안 숫자를 라벨과 짝지을 때 정렬 우선순위가 (행 간격, 열 거리) 순이었는데, 실제로는 열(x)이 먼저여야 한다(함수 자체의 docstring 도 그렇게 적혀 있었다). 코발트 팀원 카드는 열 간격이 좁아 이 버그가 실제로 드러났다(예: K 열 값이 엉뚱하게 TK 열 값으로 채워짐 — 세 팀원 모두 `kills` 가 TK 값과 똑같이 나왔었다). `(abs(x 거리), y 거리)` 순으로 바꿔 해결(`detect/result.py::parse_stats`) — 배틀로얄 쪽은 열 간격이 넓어 이 버그가 안 드러났을 뿐이라 회귀 위험은 낮다고 판단했다(관련 테스트 전부 통과).
- **남은 오차**: 팀원 카드의 작은 숫자가 이따금 OCR 로 오독된다(`9`→`6`, `8`→`B`). 2배 확대해도 안 고쳐졌다 — 폰트 자체 문제로 보인다. 본인 TK/K/D/A(더 큰 글자)는 두 실측 모두 100% 정확했다. 팀원 통계는 부가 정보라 그대로 뒀다(닉네임은 항상 정확).
- **실측 검증**: `find_vod_result()` 전체 파이프라인(진짜 ffmpeg 프레임 스캔)을 **학습에 안 쓴 세 번째 매치**(약 200~790초 구간)에 돌려 승/패·팀원 3명 닉네임·팀원 스탯을 정확히 찾아냈다 — 학습 표본 2개를 넘어서는 일반화를 확인했다(본인 스탯은 이 프레임에서는 못 읽었는데, 스캔이 패널 전환 애니메이션 도중의 프레임을 잡았을 가능성이 있다 — 한 프레임 안에서 일부 필드만 비는 것은 정상 범위로 본다).
- **UI 반영**: 배틀로얄은 `#N위` 를 보여주지만 코발트는 순위가 없어(2팀 승/패) 사용자가 "승리/패배 글자로 표시"를 선택했다(대화 중 결정). `grouping.ts::formatMatchResult` 가 `result.outcome` 이 `승리`/`패배` 면 순위 대신 그 글자를 쓰고, `GameSection.tsx` 의 큰 표시도 같은 조건으로 분기한다.
- **테스트**: `tests/test_cobalt_result.py`(11건, 합성 데이터) + `tests/test_result.py`(`parse_stats` 우선순위 변경 회귀 확인) + 프론트 `grouping.test.ts`(승패 표시 2건). 전체 1658개 백엔드·145개 프론트 테스트 통과, `npm run build` 완료.

### 10-5. 실사용 사고 — `ANALYSIS_VERSION` 을 안 올려서 코발트 다시보기가 "분석 완료, 게임 0개"로 사라짐 (2026-09-27)

사용자가 실제 앱(`run.bat`)에서 `코발트.mp4` 를 분석했는데 **영상 파일 탭 목록에서 아예 안 보이는** 문제를 보고했다. 원인 조사:

1. 사용자가 이 세션 초반(C0 작업 전, `2026-09-27T05:46 UTC`)에 앱에서 `코발트.mp4` 를 분석했다 — 그때는 아직 `cobalt_phase` 판독(C1-a)도 `is_ingame()` 의 코발트 대응(C2)도 없었다. 그 결과 게임 0개·클립 0개로 "분석 완료"가 저장됐다(`.vods/3df9b3313b4e.json`: `"status":"done","games":[],"clips":[]`).
2. **프론트엔드는 "분석 끝났는데 클립 0개"인 영상을 목록에서 숨긴다**(`vodGrouping.ts::groupByVod` 의 `keptEmpty` 필터, 의도된 동작 — 진짜로 빈 영상이 계속 목록을 차지하지 않게 하려는 것). 그래서 화면에서 사라졌다.
3. **진짜 원인**: `pipeline/vod_analyze.py::ANALYSIS_VERSION` 을 이번 세션에서 `FrameState` 에 `cobalt_phase` 를 추가했을 때 올렸어야 했는데(§0 "3: TK 판독 추가..." 항목이 이미 이 규칙을 문서화해 뒀었다) 빠뜨렸다. 그래서 **판독 캐시(`.states.jsonl.gz`)에 `cobalt_phase` 가 전부 `None` 인 채로 남아**, "다시 분석"을 눌러도 재디코딩 없이 그 캐시를 그대로 써서 여전히 게임 0개가 나올 뻔했다.
4. **수정**: `ANALYSIS_VERSION` 을 3→4 로 올렸다(주석에 이유 기록). 이제 옛 캐시는 버전 불일치로 무효화되어 "다시 분석"을 누르면 처음부터 다시 판독한다.
5. **또 하나의 원인 — 서버 재시작 필요**: 파이썬은 코드를 바꿔도 이미 떠 있는 프로세스에 반영되지 않는다. 이 세션에서 바꾼 검출 코드(C1~C4)는 **앱을 껐다 다시 켜야** 실제로 적용된다(`run.bat` 은 자동 재시작 기능이 없다, 그건 개발용 `dev.bat` 만 있다 — plan-ui.md §0).
6. **사용자가 할 일**: 앱을 껐다 다시 켠 뒤, `코발트.mp4` 에서 "다시 분석"을 누른다. `ANALYSIS_VERSION` 불일치로 캐시가 무효화돼 있어 처음부터(약 80분 분량, 키프레임만 디코딩하므로 실측상 수 분 내) 다시 판독하고, 이번엔 `Phase N` 기반 게임 경계·모드 자동 판별·결과 화면 판독이 전부 적용된 채로 게임이 나뉜다.
7. **교훈**: `FrameState` 에 새 필드를 추가하는 작업은 `ANALYSIS_VERSION` 을 올리는 것과 항상 짝을 이뤄야 한다 — 이미 §0 에 이 규칙이 한 번 적혀 있었는데도 이번에 놓쳤다. 앞으로 `FrameState`/`CombatInterval` 필드 추가 PR 은 이 체크리스트 항목을 먼저 본다.

**후속 — ②를 다시 보니 그 자체가 별도 버그였다.** 사용자가 릴리스 빌드가 아니라 실제로 소스에서 뜬 서버로 재시작한 뒤(포트 80 을 잡은 프로세스가 `python.exe` 로 바뀐 것으로 확인) 다시 물었는데도 `코발트.mp4` 가 여전히 안 보였다 — `/api/vods/{id}/analyze` 가 `idle` 이라 **"다시 분석"을 누른 적조차 없었다**. 이유: 목록에서 안 보이니 누를 버튼 자체가 없다 — **②의 `keptEmpty` 필터가 "분석 끝, 게임 0개(애초에 못 찾음)"와 "게임은 찾았는데 그 클립을 나중에 다 지움"을 똑같이 `status==='done' && clipCount===0` 으로만 구분해 둘 다 숨겼다.** 이게 진짜 카탈로그 22 — 못 찾은 영상은 다시 시도할 방법이 UI 에 없었다.
- **1차 수정(폐기)**: 처음엔 클립을 지워도 인덱스의 `games` 배열은 안 건드린다는 점(클립 파일만 지운다)을 이용해 `keptEmpty` 조건에 `v.games.length > 0` 을 추가해 두 경우를 구분하려 했다.
- **사용자 판단으로 더 단순하게 바꿈(2026-09-27)**: "그런 복잡한 조건 달지 말고 새로고침 버튼을 달자 — 삭제된 건 삭제된 채로 두고, 보기 싫으면 사용자가 알아서 지우면 된다." **`keptEmpty` 자체를 없앴다** — `includeEmpty` 면 조건 없이 모든 vod 를 보여준다(`vodGrouping.ts::groupByVod`, `keptEmpty = vods.map((v) => v.id)`). 대신 "영상 파일" 탭에 **새로고침 버튼**(`FilterBar.tsx` 의 `onRefresh` prop, `ClipBrowser.tsx` 에서 `reload()`+`reloadVods()` 호출)을 추가해 언제든 목록을 다시 읽을 수 있게 했다. 테스트 단순화(`vodGrouping.test.ts`), 프론트 145개 테스트 통과, `npm run build` 완료.
- **교훈**: "숨길지 말지"를 데이터로 정교하게 구분하려는 시도보다, 아예 숨기지 않고 사용자에게 새로고침·삭제 같은 명시적 도구를 주는 쪽이 더 단순하고 견고할 때가 있다 — 조건을 정교하게 다듬기 전에 "정말 자동으로 숨겨야 하는가"부터 되묻는다.

### 10-6. 실제 앱으로 `코발트.mp4` 재분석 — C0~C4 전체 종단 검증 (2026-09-27)

§10-5 의 UI 단순화(§10-6 관련 있음, 아래는 별도 변경)를 마친 뒤, Playwright 로 사용자의 실제 실행 중인 서버(`http://127.0.0.1`, 소스에서 뜬 개발 서버)에서 `코발트.mp4` 의 "다시 분석 → 처음부터 다시 → 확인" 을 실제로 눌러 전체 파이프라인을 종단 검증했다 — 이 세션의 모든 코발트 작업(C1-a·C1-b·C2·C3)이 **내 손으로 짠 검증 스크립트가 아니라 실제 앱 코드로** 처음부터 끝까지 돈 첫 사례다.

- **결과 화면 6판 전부 판독 성공**: 패배 3판·승리 3판, 승패 글자·본인 TK/K/D/A·팀원 3명 닉네임 대부분 정확(예: 게임 6 은 §10-4 에서 손으로 확인했던 "TK29 K8 D6 A16, 승리"와 완전히 일치). 팀원 카드 일부 닉네임 오독(게임 3: `kellino8`→OCR 이 `kellin08`을 다르게 읽음 등)은 §10-4 에서 이미 기록한 한계 그대로.

### 10-7. 클립 0개 게임 행이 앱 전체를 죽인 사고와 수정 (2026-09-27)

§10-6 검증 직후 사용자가 실제로 화면을 열어보니 "게임 6개·클립 0개"인데 행이 하나도 안 보이다가, 원인 조사 중 완전히 새로 고쳐도 **앱 전체가 빈 화면**이 되는 사고로 번졌다. Chrome 콘솔에 `Uncaught TypeError: Cannot read properties of undefined (reading 'id')`.

- **원인**: `groupByVod`(§10-5 에서 클립 0개 게임도 `vod.games[]` 요약으로 행을 만들도록 고침, `clips: []`)가 만든 그룹을, `ClipBrowser.tsx` 안 **두 군데**(`resultGames` useMemo, `renderGame`)가 각자 `group.clips[0].id` 를 무조건 읽어 결과표 이미지 URL을 골랐다. `renderGame` 쪽은 먼저 고쳤지만 `resultGames`(결과표 모아보기 갤러리용) 쪽을 놓쳐서, 클립 0개 코발트 게임이 하나라도 목록에 있으면 `useMemo` 안에서 예외가 나 컴포넌트 트리 전체가 죽었다.
- **수정**: 같은 실수가 세 번째로 나는 걸 막기 위해, "이 게임의 결과표 이미지를 어떤 API로 찾을지" 판단을 `grouping.ts::resultImageRef()` 한 곳으로 모았다(`record` → `clip` → `vodGame` 순 폴백, 반환 타입 `ResultImageRef` 판별 유니온). `ClipBrowser.tsx` 의 `resultGames`/`renderGame` 모두 이 함수만 호출하도록 바꿨고, `frontend/tests/grouping.test.ts` 에 `resultImageRef` 세 분기(레코드/클립/클립없음) 테스트를 추가했다.
- **검증**: 프론트 `npx tsc --noEmit`·`npm run test`(148개 전부 통과)·`npm run build`, 백엔드 `pytest`(1660개 전부 통과) 모두 통과. Playwright 로 `http://127.0.0.1:8000` 을 직접 띄워 영상 파일 탭에서 `코발트.mp4` 의 6개 게임 행이 전부 뜨고, 클립 0개인 게임을 펼치면 `/api/vods/{vid}/games/{index}/result-image` 로 실제 결과표 스크린샷(패배 화면)이 뜨는 것까지 확인 — 콘솔 에러는 무해한 `favicon.ico` 404 하나뿐이었다.
- **확인 필요**: 코발트 게임 행의 접힌 헤더가 아직 `#1`/`#2` (승패를 placement 1/2 로 매핑한 값)로 뜨고 `GameSection.tsx` 의 승리/패배 텍스트 표시로 안 바뀌어 있다 — `vod_analyze.py` 의 게임 요약에 `gameMode` 필드를 추가하기 *전에* 만들어진 기존 분석 캐시라서 그렇다. 사용자가 "다시 분석"을 한 번 더 돌리면 해결될 것으로 예상되나 아직 실측하지 않았다.

### 10-8. 코발트가 결과 화면은 다 읽으면서 클립이 0개인 이유 — 해결 (2026-09-27)

사용자 보고: "게임 결과 사진은 잘만 찍었으면서 클립이 0개야." §10-3 이 이미 "이 스트리머의 방송 오버레이가 미니맵을 가려 `spectating`이 계속 `None`" 이라고 원인을 짚어 뒀지만, "다음에 만나면 교차 검증하라"는 미해결 과제로 남아 있었다. 이번에 실제로 교차 검증하고 부분적으로 고쳤다.

**실측 1 — 코발트는 TK/K/A 칸이 배틀로얄과 다른 자리에 있다.** `코발트.mp4`(코발트)와 `하이용가리.mp4`(같은 스트리머의 배틀로얄, 같은 폴더)에서 같은 시각대의 프레임을 뽑아 프로필의 `k_value`/`a_value`/`tk_value` ROI 박스를 그려 겹쳐봤다:
- 배틀로얄(`하이용가리.mp4`, t=600s): 박스가 TK/K/A 숫자에 **픽셀 단위로 정확히** 맞는다.
- 코발트(`코발트.mp4`, t=1230s): 박스 자리엔 아무것도 없고(까맣게 빈 화면), 실제 TK/K/A 숫자는 그보다 **~80px 왼쪽**에 있었다.

같은 스트리머·같은 방송 설정에서 모드만 다른데 위치가 다르다는 건, §10-3 이 구분 못 했던 "코발트 자체의 차이"와 "이 방송 특유의 스케일 차이" 중 **전자**라는 뜻이다 — 스트리머 오버레이 문제가 아니라 코발트 프로토콜 자체가 이 HUD 를 다른 자리에 그린다.

**적용한 수정**: `profiles/builtin/1920x1080.json` 에 `cobalt_tk_value`/`cobalt_k_value`/`cobalt_a_value` ROI 를 실측 좌표로 추가하고(코발트는 기준 해상도 2560x1440 녹화가 없어 정규화 표엔 없다 — phase_digit/cobalt_outcome 과 같은 관례), `detect/match.py::analyze_frame` 이 배틀로얄 자리를 먼저 읽고 실패하면(그 자리에 숫자가 없으면) 코발트 자리를 다시 읽도록 고쳤다(`_crop_for_reference` 헬퍼로 기준 해상도 크기로 키워서 기존 본보기를 그대로 재사용). 프레임 하나만 봐서는 모드를 모르므로(`infer_game_mode` 는 전체 프레임을 모아야 판정) 위치 폴백으로 처리했다.

**실제 검증 결과 (재분석 재실행, 격리된 임시 폴더)**: `ANALYSIS_VERSION` 을 5 로 올려 캐시를 무효화하고 `코발트.mp4` 를 처음부터 다시 분석했다.
- 판독 성공률(전체 2414 프레임 중): `cobalt_phase` 1571(65%), `tk` 412(17%), `k` 145(6.0%), `a` 147(6.1%) — 수정 전엔 전부 0(100% `None`)이었다.
- 클립: 0개 → **1개**(게임 5). 게임별 `kFinal`/`aFinal` 도 여러 판이 `None` 대신 그럴듯한 값을 갖게 됐다.

**1차 시도의 한계(2026-09-27, 첫 번째 커밋)**: 위치만 고쳐서 재분석해보니 판독 성공률이 6~17%로 낮고 클립도 6게임 중 1개뿐이었다. 게임 1 시작 직후(t=168s, 육안으로 "TK 0 K 0 A 0"이 또렷한 프레임)를 직접 넣어보니 **0이 아니라 1로 오판**했다(confidence 0.60). 사용자가 "진짜 이게 그렇게 안 되나?"라고 재차 물어 다시 파고들었다.

**실측 2 — 위치뿐 아니라 세로 위치·크기도 배틀로얄과 다르다.** 커넥티드 컴포넌트로 두 모드의 "0" 글자 픽셀 경계를 직접 비교했다:
- 배틀로얄(`하이용가리.mp4`): 글자 높이 15px, 박스([y0,y1]=[20,38]) 안에서 거의 정중앙(중심 y≈29, 박스 중심과 거의 일치).
- 코발트(`코발트.mp4`): 글자 높이 13px인데 같은 박스를 그대로 썼더니 글자가 박스 **맨 위**에 붙어 있었다(중심 y≈26.5, 박스 중심보다 2.5px 위) — 아래쪽에만 여백이 몰려 있어 확대(`cv2.resize`)했을 때 본보기가 기대하는 글자 위치와 어긋났다.

**적용한 수정 2**: 코발트 ROI 3개의 세로 범위를 `[20,38]` → `[17,35]`로 3px 올려 글자를 박스 중앙에 오게 했다. 이 상태에서 실제 게임 시작 6곳(TK=K=A=0)과 중간 지점 2곳(K=5,7 등 실측 확인값)까지 8개 지점으로 격자 탐색(가로 ±4px·세로 14~20px)해 모든 지점에서 정답이 1등으로 나오는 좌표를 찾았고, 그 조합에서도 1·2등 점수차(margin)가 배틀로얄 경로 기본 문턱(0.05)보다 좁게는 0.014까지 내려가는 걸 확인해 코발트 폴백 전용 문턱 `COBALT_COUNTER_MIN_MARGIN=0.01`을 `detect/match.py`에 추가했다(배틀로얄 경로의 문턱은 그대로 둬 회귀 위험이 없다).

**실제 검증 결과 (재분석 재실행, 격리된 임시 폴더)**:
- 판독 성공률(전체 2414 프레임 중): `k` 1890(78%), `a` 1797(74%), `tk` 1821(75%) — `cobalt_phase`(65%)보다도 높다(배틀로얄 자리 폴백까지 두 경로 다 시도하므로).
- 값 분포가 여러 숫자에 고르게 퍼져 있다(예: `k`는 0~10 전 구간, `a`는 0~16 전 구간에 표본이 있음) — 1차 시도 때처럼 특정 숫자(1·9)에 쏠리지 않는다.
- **클립: 0개 → 1개 → 41개.** 6게임 전부 클립이 생겼다(게임당 5~8개). 게임별 `kFinal`/`aFinal`도 §10-4/§10-6에서 결과 화면 OCR로 이미 확인했던 값과 **정확히 일치**한다(예: 게임 2 `k=10,a=4`, 게임 6 `k=8,a=16` — 앱 UI에 표시됐던 "17/10/4"·"29/8/16"의 K/A 부분과 일치).
- 백엔드 전체 스위트 통과(기존 회귀 테스트 + `test_match.py`의 코발트 HUD 위치 테스트 4개).
- **결론**: 완전히 해결됐다. 1차 시도에서 "다음에 필요하다"고 적었던 코발트 전용 네이티브 본보기 재구축은 필요 없었다 — 진짜 원인은 본보기 자체가 아니라 세로 위치가 살짝 어긋나 있던 것과, 그 때문에 생기는 좁은 마진을 기본 문턱이 걸러내던 것이었다.

### 10-9. VOD 분석 진행률이 70% 로 순식간에 뛰었다가 밍기적거리는 문제 — 수정 (2026-09-27)

사용자 보고: "다시 분석 버튼 누르자마자 70%까지 한 번에 진행되는데 이후엔 진짜 밍기적거리면서 진행돼 기대하게 만들지 말라"는 요청, 그리고 "다른 프로그레스바 기능에도 똑같이 적용되는 원칙"이라는 지적. `plan-backfill.md` B8 이 과거 녹화 분석(backfill)에서 같은 증상을 이미 "설계만, 미구현"으로 남겨 뒀었다.

**VOD 분석(`pipeline/vod_analyze.py`)**: `DECODE_SHARE=0.70`(디코드 단계에 막대의 70%)가 원인이었다 — 그런데 키프레임만 읽는 디코드는 ~50배속으로 제일 빠른 단계고(plan-vod.md 실측), 실제로 오래 걸리는 클립 컷(ffmpeg 재인코딩+썸네일)은 나머지 20%(`1-DECODE_SHARE-GAMES_SHARE`)에 몰려 있었다 — 제일 빠른 단계에 제일 큰 몫을, 제일 느린 단계에 제일 작은 몫을 준 셈이다. `DECODE_SHARE` 를 0.70→0.15 로 낮춰 컷 단계가 막대의 대부분(75%)을 차지하게 했다. 추가로, 컷 단계 진행률이 게임 번호(`i/n`)로만 계산돼 클립이 여러 개인 게임 하나를 처리하는 동안 막대가 안 움직이던 문제도, 모든 게임의 클립 계획을 미리 세어(`plans_by_game`) 클립 번호(`clips_done/total_clips`) 기준으로 바꿔 고쳤다.

**과거 녹화 분석(`pipeline/backfill.py`, B8)**: 스캔 50%/게임 처리 50% 로 고정 반반이던 걸, 실측 상수(세션당 스캔 ~107초 = "28배속, 2세션 130분이 215초"; 게임당 처리 ~80초 = "60~100초 중간값")로 계산한 비율(`scan_share = scan_time_est/(scan_time_est+process_time_est)`)로 바꿨다. 스캔 진행 중엔 아직 최종 게임 수를 몰라 정확한 비율을 못 구하므로 잠정 상한 20%(`SCAN_SHARE_ESTIMATE`, 문서의 "스캔은 전체의 20% 안팎" 실측에 근거)로 표시하다가, 스캔이 끝나 게임 수를 알게 되면 실측 상수로 계산한 진짜 비율로 넘어간다 — 세션 1개·게임 6개처럼 게임이 많으면 이 비율이 20%보다 훨씬 낮아져(예: ~18%) 예전의 고정 50% 점프보다 훨씬 작은 폭으로 넘어간다. `process_window` 콜백 자체엔 진행률 훅이 없어 게임 하나 처리하는 동안 막대가 움직이게 하는 항목(B8 의 항목 3)은 여전히 미구현으로 남아 있다.

**검증**: 두 파이프라인 모두 기존 회귀 테스트 통과 + 새 테스트 추가 — VOD 는 클립 2개짜리 게임에서 컷 단계 진행률이 클립마다 다르게 나오는지(`test_cut_progress_advances_between_clips_in_the_same_game`), 백필은 세션 1개·게임 6개일 때 계산된 비율이 고정 50% 가 아니라 실측 상수 기반값인지(`test_process_phase_starts_from_the_estimated_time_share_not_a_flat_half`). 백엔드 전체 스위트(1666개) 통과.

### 10-13. TK/K/A 칸 위치 자동 보정 + 코발트 클립 범위를 "부활~사망"으로 재정의 (2026-09-28)

§10-12 정리 뒤 사용자가 두 가지를 더 결정했다.

**1) 카운터 칸 위치 자동 탐색(하드코딩 제거).** "이거 해상도에 따라 달라지는 값을 어떻게 학습시킬 방법 없을까?"라는 질문에서 출발했다 — §10-8/§10-12 에서 해상도별로 사람이 좌표를 실측해 하드코딩해 온 방식은 새 방송·새 영상마다 다시 반복해야 한다. 대신 `detect/counter.py::locate_digit()`(넓은 영역에서 숫자 본보기를 `cv2.matchTemplate` 로 슬라이딩 탐색)와 `detect/match.py::calibrate_counter_position()`을 추가해, `detect_source()` 가 영상 처음 몇 프레임(`CALIBRATION_SAMPLE_FRAMES=8`)에서 `k_value` 기본 자리가 안 맞으면(`CALIBRATION_MIN_HITS=3` 미만) 그 주변(±160px/±24px)을 뒤져 실제 위치를 찾고, `k_value`/`a_value`/`tk_value` 를 통째로 그 위치로 옮긴 프로필을 만들어 나머지 프레임에 쓴다. §10-8 에서 1920x1080 코발트용으로 하드코딩했던 `cobalt_tk_value`/`cobalt_k_value`/`cobalt_a_value` ROI·`COBALT_COUNTER_MIN_MARGIN` 은 이제 이 자동 탐색으로 대체 가능하지만(정리는 다음 기회로 미룸), 당장은 그대로 둬도 문제 없다 - 기본 자리가 맞으면 자동 탐색 자체가 아예 안 돈다.

**2) 코발트 클립 범위: "부활 직후~사망 직후"를 통째로 하나로.** 사용자 결정: "코발트는 그냥 죽었을 때만 클립 대상에서 제외하도록 하자. 어차피 야생동물도 없고 이동이랄 것도 거의 없거든? 계속 교전의 연속이야." 배틀로얄처럼 배지·킬 이벤트로 잘게 쪼개는 대신, 사망 감지(초상화 밝기·채도 하락, `detect/death.py` — 배틀로얄 1·2일차의 임시 사망과 같은 신호, 실측으로 코발트에도 그대로 작동함을 확인)를 경계로 살아있는 구간 전체를 클립 하나로 만든다.

- `finalize_match()`에 `game_mode` 분기를 추가했다(계산 시점을 함수 앞으로 당겼다 - 이전엔 맨 끝에서만 알았다). 코발트면 `death_ranges`(초상화 기반)와 `first_live` 이후의 관전 구간(스펙테이터 UI)을 합쳐 "죽은 시간"으로 보고, 그 여집합(`_invert_ranges`, 새 헬퍼)을 구간으로 쓴다. 사망으로 확정된 첫/마지막 샘플이 옆 구간에 안 섞이게 경계를 안쪽으로 한 칸(`step`)씩 당긴다. 배틀로얄 경로는 100% 그대로 남겨 회귀 위험이 없다.
- `died` 태그도 코발트 전용으로 보정했다 - 구간을 사망 프레임과 안 겹치게 당겨놨으므로 "겹치는지"가 아니라 "바로 다음(≤2×step)이 사망인지"로 판정한다.
- TK 는 여전히 안 쓴다(SPEC §2.8, 새 구간을 안 만드는 원칙은 그대로) - K/A 델타로 kill/assist 태그만 계속 매긴다.
- 클립 길이가 배틀로얄과 완전히 달라진다(한 목숨 전체 = 클립 하나, 실측 84~123초) - 사용자 확인: 이미 있는 "자르기" 기능으로 필요하면 직접 나눠 쓰면 된다는 전제.

**실제 검증(게임 10 원본으로 전체 파이프라인 재실행)**: `game_mode=cobalt`, 구간 6개(84~123초씩), 전부 `died=True`·`death` 태그, k_delta 합계 8·a_delta 합계 12 — §10-12 에서 확인한 결과 화면 값(K8·A12)과 다시 한 번 정확히 일치. 예전 배지·이벤트 기반 방식(11개 구간, 사이사이 빈틈)보다 훨씬 깔끔하다.

**검증**: `test_counter.py`(`locate_digit` 3개), `test_match.py`(`calibrate_counter_position` 3개 + `detect_source` 통합 + 코발트 alive-span 3개 + 기존 phase-최빈값 테스트를 사망 기반으로 갱신) 포함 백엔드 전체 스위트(1685개) 통과.

**부수 수정 — 클립창 배경 클릭 시 닫힘·자르기 작업 소실.** 사용자 보고: "클립 영상이나 버튼이 아니라 불투명한 바깥 부분 클릭하면 그대로 클립창이 꺼지거든? ... 자르기가 날라가." `PlayerModal.tsx`·`ResultCard.tsx`(`ResultViewer`) 둘 다 배경(backdrop) 자체에 `onClick={onClose}` 가 달려 있었다. 배경 클릭 시 닫기를 없애고 닫기 버튼·ESC 로만 닫히게 했다 - `ResultViewer` 에는 닫기 버튼이 아예 없어서(배경 클릭·ESC 뿐이었다) 새로 추가했다. 같은 패턴(`onClick={onClose}` 배경)이 `BackfillDialog`·`ExportDialog`·`SettingsModal`·`PrivacyDialog` 등 다른 대화상자에도 있지만, 이번 요청은 클립 보기 화면(상태 손실 위험이 있는 곳)에 한정해 그 두 곳만 고쳤다 - 나머지는 단순 확인/설정 창이라 배경 클릭으로 닫혀도 잃을 게 없다.

### 10-14. 실사용 사고 — 코발트 재분석하니 게임 전체가 클립 하나로 뭉침 (2026-09-28)

§10-13 배포 직후 사용자가 게임 10을 "다시 분석"했더니 "그냥 통짜로 하나만" 나왔다("중간중간 죽은 순간이 분명 있는데도 인식을 못 하고 있는건가?"). `detect_match()`/`finalize_match()` 를 직접 불러서 확인해보니 **검출 자체는 정상**이었다(구간 6개, §10-13 에서 실측한 것과 동일) — 문제는 그 뒤 클립 범위를 만드는 `resolve_clip_range`/`_plan_clips`(`pipeline/clip.py`·`orchestrator.py`)에 있었다.

- **원인**: §10-13 은 코발트 구간 자체(부활~사망)만 새로 만들고, 그 뒤 배틀로얄용 `preroll_sec`(5초)·`postroll_sec`(8초)·`mergeGapSec`(10초) 로직은 그대로 뒀다. 실측 사망~부활 간격(15~21초)에서 preroll+postroll(13초)을 빼면 남는 간격이 2~8초 — `mergeGapSec`(10초)보다 작아 **모든 구간이 옆 구간과 계속 합쳐져 게임 전체가 클립 하나로 뭉쳤다.**
- **수정**: `resolve_clip_range(interval, cfg, *, game_mode=...)`·`_plan_clips(intervals, cfg, *, game_mode=...)` 에 `game_mode` 매개변수를 추가해, 코발트면 preroll/postroll 을 아예 안 더하고 구간 경계를 그대로 클립 범위로 쓴다 - 그러면 사망 간격(15~21초)이 그대로 남아 `mergeGapSec` 보다 커서 안 합쳐진다. `orchestrator.py::process_match`·`vod_analyze.py::_make_clips` 두 호출부 모두 이미 알고 있는 `game_mode` 를 넘기도록 고쳤다.
- **검증**: `test_plan_clips_cobalt_mode_skips_preroll_postroll_so_short_death_gaps_stay_separate`(배틀로얄 모드로 부르면 옛날처럼 합쳐지고, 코발트 모드로 부르면 안 합쳐짐을 같은 테스트에서 대조), `test_resolve_clip_range_cobalt_mode_uses_the_interval_bounds_exactly` 추가. 게임 10 원본으로 `detect_match`→`apply_filter`→`_plan_clips` 전체 파이프라인을 다시 돌려 최종 클립 계획이 6개(구간과 정확히 1:1)임을 확인 — 클립 계획 단계까지 실측한 건 이번이 처음이다(§10-13 검증은 `finalize_match` 까지만 확인했었다). 백엔드 전체 스위트(1687개) 통과.

### 10-15. 코발트 클립 제목·타임라인 마무리 (2026-09-28)

사용자: "코발트 클립 추출 쪽은 이 정도로 마무리 하자. 다만 지금 Phase 3 낮 교전 같이 써있는데, 코발트에는 낮/밤 구분이 없어 ... 그냥 뒤에 넘버링을 붙여. Phase 1 교전 - 1 이렇게. 그리고 타임라인으로 봤을 때 Phase 1, 2, 3 이런 식으로 구분하고"

- **"Phase 3 낮 교전" 버그**: `day_night` 는 모드와 무관하게 매 프레임 읽으므로(§2.7) 코발트 화면에서 우연히 뭔가 읽혀 낮/밤이 섞여 들어갔다. `default_title`을 고쳐 `cobalt_phase` 가 있으면 `day_night` 값과 무관하게 절대 안 보여주도록 했다(`game_day` 분기에서만 낮/밤을 붙인다).
- **클립 번호 접미사**: §10-13 이후 코발트 한 게임에 목숨마다 클립이 생겨, 같은 Phase 에서 두 번 이상 죽으면 제목이 겹친다. `default_title`에 `clip_index` 매개변수를 추가해 코발트일 때만 뒤에 `" - N"`을 붙인다(예: `Phase 1 교전 - 1`, `Phase 1 교전 - 2`).
- **번호가 Phase 별로 리셋 안 되던 버그(같은 날 후속 보고, 스크린샷 첨부)**: 처음엔 `orchestrator.py::process_match`의 `enumerate(plans, start=1)`의 `i`, `vod_analyze.py::_make_clips`의 `len(game_clip_ids) + 1`을 그대로 `clip_index`로 넘겨서, "Phase 1 교전 - 1, 2" 다음 Phase 로 넘어가도 "Phase 2 교전 - 3"처럼 게임 전체 순번이 이어졌다. 사용자 지적: "페이즈별로 교전 넘버링 리셋 되어야 하는거 아니야? Phase 2 교전 - 1 이렇게 시작해야지". `orchestrator.py`에 `next_phase_clip_index(counts, cobalt_phase)` 헬퍼를 새로 만들어(Phase 값별로 별도 카운터를 갖는 `dict`) `process_match`·`_make_clips` 양쪽에서 공유하도록 고쳤다 - 두 곳에 로직을 복사해두면 다음에 또 따로 어긋날 수 있어서 하나로 뺐다.
- **타임라인 뷰(일자 타임라인)를 Phase 기준으로**: `frontend/src/timeline.ts`에 `buildCobaltPhaseColumns()`를 추가했다(`buildPhaseColumns`와 같은 `PhaseColumn<T>` 모양을 재사용하되 `cobaltPhase` 로 나누고 부활 구간(`zone`) 개념은 없다). `GameTimeline.tsx`가 `gameMode` prop 을 받아 `'cobalt'`면 이 함수를 쓴다. 프론트 `Clip` 타입에 `cobaltPhase` 필드가 빠져 있던 것도 추가했다(백엔드는 §10-11 에서 이미 클립 메타데이터에 쓰고 있었는데, 프론트 타입에는 안 반영돼 있었다 - API 는 메타데이터 JSON 을 그대로 넘기는 구조라 필드 자체는 이미 오고 있었다).
- **검증**: `test_default_title_never_shows_day_night_for_cobalt_even_if_it_was_read`·`test_default_title_appends_a_clip_index_for_cobalt_only`·`test_next_phase_clip_index_resets_when_the_phase_changes`(백엔드), `buildCobaltPhaseColumns` 테스트 2개(프론트) 추가. 백엔드 전체 스위트(1690개) 통과. 프론트는 이 수정이 백엔드 전용(제목 문자열 생성 로직)이라 재빌드 불필요.
