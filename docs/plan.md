# 교전 검출기 구현 계획 (SPEC 1단계)

> 대상: SPEC [§6 1단계](SPEC.md) — 녹화본에서 **내가 참여한 교전 구간**을 찾아내고, 각 구간에 태그를 다는 검출 레이어.
> 근거 수치는 [research.md](research.md)와 이 문서 §5.1의 실측에서 왔다. 확인되지 않은 것은 §8에 **확인 필요**로 표시했고, 추측으로 메우지 않았다.

## 0. 이전 판에 대한 정정

이 문서의 첫 판은 **킬 검출기** 계획이었다. 요청을 글자 그대로 받아 카운터 판독만 다뤘는데, 그건 이 프로젝트의 주 신호가 아니다.

SPEC은 이미 올바르게 적혀 있다.

> **§1** — "v1의 목표는 내가 참여한 **모든 교전**을 빠짐없이 추출하는 것이다. 이기든 지든, 킬을 냈든 못 냈든 전부 뽑는다."
>
> **§2.8** — "**교전 앵커는 배지가 잡고, `K`/`A` 는 그 교전에 태그를 다는 데 쓴다.** 예전 SPEC처럼 `K` 증가를 앵커로 삼지 않는다."

**SPEC은 고칠 필요가 없다.** 어긋난 건 계획서 쪽이었고, 이 판에서 교전 검출을 중심으로 다시 썼다. 카운터 판독은 §5.5로 내려가 제자리를 찾았다.

## 1. 무엇을 만드는가

```
매치 구간의 녹화 세그먼트
        ↓
   [교전 검출기]
        ↓
교전 구간 목록
  [ CombatInterval(start=412.0s, end=447.0s,
                   tags=["kill", "assist"],
                   k_delta=1, a_delta=1, died=False,
                   day=3, day_night="day"), ... ]
```

이게 SPEC §3 아키텍처의 `[프레임별 상태 판독]` ~ `[태그 부여]` 구간이다. 이 뒤의 컷·메타데이터·UI는 2단계다.

### 검출기 셋과 우선순위

SPEC §6이 정한 순서를 그대로 따른다.

| # | 검출기 | 역할 | 난이도 |
|---|---|---|---|
| **1** | **교전 배지** | **교전 구간을 정한다 — 주 신호** | 낮음 (색 픽셀 세기) |
| 2 | 사망 | 사망 구간 제외 + `death` 태그 | 낮음~중간 (램프 판정) |
| 3 | `K`/`A` 카운터 | `kill`/`assist` 태그, 자체 검증 | **높음** (글자 판독) |
| 4 | 일차·낮/밤 | 제목·필터용 | 낮음 (색 비교) |

**1번만 있어도 클립이 나온다.** 2·3·4는 태그와 품질을 더하는 것이다. 이 순서면 매 단계 끝에 돌아가는 물건이 남는다.

## 4. 공통 타입

```python
@dataclass(frozen=True)
class FrameState:
    t: float                    # 세션 시작 기준 오프셋(초)
    combat: bool | None         # None = 판독 불가
    dead: bool | None
    k: int | None
    a: int | None
    day: int | None
    day_night: str | None       # "day" | "night"
    confidence: float


@dataclass(frozen=True)
class CombatInterval:
    start: float
    end: float
    tags: frozenset[str]        # kill / assist / death / no_result
    k_delta: int
    a_delta: int
    died: bool
    day: int | None
    day_night: str | None
    confidence: float
```

**`None` 을 `False` 와 엄격히 구분한다.** SPEC §2.7이 반복해서 경고하는 지점이다 — "판독 불가를 교전 아님과 구분할 것". 어두운 프레임에서 배지 색 카운트는 전부 0이 되는데, 이걸 "교전 아님"으로 처리하면 교전이 끊겨 보인다.

## 5. 핵심 설계 결정과 트레이드오프

### 5.1 ★ 디코딩 전략 — 키프레임만 읽는다

**이게 이 계획에서 제일 큰 결정이다.** 검출 비용의 거의 전부가 HEVC 디코딩이다.

실측했다 (영상 60초 = 세그먼트 20개, 2560x1440 60fps HEVC, RX 6600 XT):

| 방식 | 60초 처리 시간 | 배속 | 20분 매치 환산 | 얻는 프레임 |
|---|---|---|---|---|
| 전체 디코딩 (소프트웨어) | 12.6초 | 4.8x | **4분 10초** | 원하는 만큼 |
| 전체 디코딩 + `-hwaccel d3d11va` | 9.4초 | 6.4x | 3분 8초 | 〃 |
| 전체 디코딩 + `-hwaccel dxva2` | 13.0초 | 4.6x | 4분 20초 | 〃 |
| **키프레임만 (`-skip_frame nokey`)** | **1.1초** | **55x** | **22초** | 세그먼트당 1장 |
| **키프레임만 + `-hwaccel d3d11va`** | **0.59초** | **102x** | **12초** | 〃 |

**16배 차이다.** 그런데 정밀도는 거의 잃지 않는다.

- 키프레임은 **세그먼트당 정확히 1개, 3.000초 간격**이다 (research §2.2).
- 그리고 SPEC §3의 컷은 **`-c copy` + 키프레임 스냅이라 어차피 3초 격자에만 붙는다**.
- 즉 **검출 정밀도와 컷 정밀도가 정확히 일치한다.** 3초보다 정밀하게 검출해봐야 컷 단계에서 버려진다.

```bash
ffmpeg -hwaccel d3d11va -skip_frame nokey -i <seg.mp4> -vsync 0 \
       -vf "crop=..." -f rawvideo -pix_fmt rgb24 -
```

#### 이 선택이 포기하는 것

| 잃는 것 | 영향 | 대응 |
|---|---|---|
| 3초보다 짧은 교전 | 샘플이 0개일 수 있어 통째로 놓친다 | SPEC §3의 **최소 길이 필터**가 어차피 버릴 대상이다 |
| 사망 램프의 형태 | 램프가 3.5~5초라 샘플이 1~2개뿐 (research §4.7) | 램프 "모양" 대신 **전후 값 차이**로 판정 (§5.4). ⚠ §8-3 |
| 카운터 증가 시각 정밀도 | ±1.5초 | 앵커가 배지라 카운터 시각은 태그용일 뿐. 영향 없음 |
| 배지 애니메이션의 저점 | 3초에 1장이라 저점을 밟을 수 있다 | 임계를 낮게(100) 두고 히스테리시스로 흡수. ⚠ §8-2 |

#### 폴백: 정밀 디코딩

필요하다고 판명되면 **2패스**로 간다.

```
1패스  키프레임만 전 구간 스캔 (12초)  → 교전 후보 구간
2패스  후보 구간 경계 ±6초만 전체 디코딩 → 경계 다듬기
```

교전이 매치당 5~10개면 2패스 대상은 매치 전체의 5~10%다. 전체 디코딩 4분이 20~25초로 줄어든다.

**단, 1패스만으로 목표 정확도가 나오면 2패스는 만들지 않는다.** 먼저 재고 결정한다 (§8-2, §8-3).

#### `hwaccel` 을 기본으로 켤 것인가

| | 켜기 | 끄기 |
|---|---|---|
| 속도 | 2배 빠름 (0.59 vs 1.1초) | — |
| 위험 | GPU 드라이버·기기에 따라 실패하거나 픽셀이 미세하게 달라질 수 있다 | 어디서나 동일 |

**기본은 켜되, 실패하면 조용히 소프트웨어로 떨어진다.** 22초도 충분히 빠르므로 hwaccel 은 있으면 좋은 정도지 필수가 아니다. 설정 키 `detect.hwaccel`(기본 `auto`).

> ⚠ **하드웨어 디코딩 결과가 소프트웨어와 픽셀 단위로 같은지는 확인하지 않았다** (§8-6). 색 임계를 쓰는 검출기라 미세한 차이가 판정을 뒤집을 수 있다. 라벨셋 평가를 두 경로로 각각 돌려 비교할 것.

### 5.2 ★ 교전 배지 검출기 — 주 신호

research §4.6이 이미 규칙을 확정해뒀다. 구현은 그대로 옮기면 된다.

```python
# detect/color.py — 배지·낮밤이 공용으로 쓴다
def count_colors(rgb: np.ndarray, v_min: int = 90, s_min: int = 60) -> ColorCounts:
    """ROI에서 '선명한' 픽셀만 골라 색 계열별로 센다."""
    a = rgb.astype(np.int16)
    r, g, b = a[..., 0], a[..., 1], a[..., 2]
    v = a.max(axis=2)
    s = v - a.min(axis=2)
    vivid = (v >= v_min) & (s >= s_min)

    warm = vivid & (r > b + 60)
    return ColorCounts(
        orange=int((warm & (r >= g) & (g < r * 0.80)).sum()),
        yellow=int((warm & (g >= r * 0.80)).sum()),
        blue=int((vivid & (b > r + 40)).sum()),
    )
```

```python
# detect/badge.py
ORANGE_MIN = 100      # 교전 판정. 실측 평상시 0~21 vs 교전 138~773
PRESENT_MIN = 250     # 배지가 화면에 있는가 (로비·암전 배제)

def read_badge(rgb: np.ndarray) -> bool | None:
    """교전 중이면 True, 평상시면 False, 판독 불가면 None."""
    c = count_colors(rgb)
    if c.orange + c.yellow + c.blue < PRESENT_MIN:
        return None                      # 배지가 안 보인다 — 로비/암전/관전
    return c.orange >= ORANGE_MIN
```

**왜 색 세기만으로 되는가**: 평상시 배지는 레벨 숫자(파랑 또는 노랑 원), 교전 중에는 주황 교차 칼이다. 주황 픽셀 수가 평상시 **0~21**, 교전 중 **138~773** 으로 6배 이상 벌어진다 (research §4.6). 템플릿 매칭이 필요 없다.

**주의 셋** (전부 research §4.6에서 실제로 부딪힌 것):

1. **평상시 배지 색이 매치마다 다르다** — 파랑인 판도, 노랑인 판도 있었다. 그래서 주황과 노랑을 **녹색 채널로 가른다**(`g < r * 0.80`). 노랑 배지 판에서도 교전 프레임은 주황 773으로 확실히 떴다.
2. **로비에서 주황 58이 잡힌 적이 있다** — 그래서 `PRESENT_MIN` 가드가 먼저 온다.
3. **완전히 어두운 프레임은 전부 0** — `None` 이지 `False` 가 아니다.

### 5.3 교전 구간 산출 — 상태 기계 + 히스테리시스

프레임 상태 시계열을 구간으로 바꾼다. 키프레임 샘플링이라 **한 샘플 = 3초**다.

```python
GAP_FILL_SAMPLES = 2      # 이 이하의 off 는 메운다 (= 6초)
MIN_COMBAT_SAMPLES = 2    # 이 미만의 on 은 버린다 (= 6초)

def to_intervals(states: list[FrameState]) -> list[tuple[float, float]]:
    """배지 on 구간을 교전 구간으로 만든다.

    규칙:
      1) None(판독 불가)은 직전 상태를 유지한다 — 교전 종료로 치지 않는다
      2) 짧은 off 는 메운다 (애니메이션 저점 / 순간 가림)
      3) 짧은 on 은 버린다 (야생동물 한 대 때린 것 등)
      4) 구간 경계는 샘플 시각 그대로 — 3초 격자에 이미 맞아 있다
    """
```

파라미터의 트레이드오프:

| | 크게 잡으면 | 작게 잡으면 |
|---|---|---|
| `GAP_FILL` | 별개 교전 둘이 하나로 붙는다 | 한 교전이 여러 조각으로 쪼개진다 |
| `MIN_COMBAT` | 짧지만 진짜인 교전을 놓친다 | 야생동물 사냥이 클립이 된다 |

**어느 쪽으로 틀릴지 미리 정해둔다.** SPEC §6은 *"오탐은 클립 하나 더 생기는 정도라 관대하게"* 라고 했다. 따라서 **놓치는 쪽보다 더 잡는 쪽으로 기울인다** — `GAP_FILL` 은 넉넉히, `MIN_COMBAT` 은 빠듯하게. 실제 값은 라벨셋으로 정한다 (§8-2).

> SPEC §3의 클립 구간은 `교전 시작 -5초 ~ 교전 종료 +8초` 이고 `-c copy` 가 3초 격자로 스냅한다. 즉 구간 경계의 오차 3초는 프리롤에 흡수된다.

### 5.4 사망 검출기

research §4.7이 두 신호를 줬다.

| 신호 | ROI | 정상 → 사망 |
|---|---|---|
| **초상화 얼굴** (1차) | `x 690..860, y 1250..1400` | 채도 25.9 → **13.3**, 밝기 111.4 → **33.9** |
| 화면 중앙 월드 (2차) | 가로 20~80%, 세로 15~72% | 채도 45 → 12.6, 밝기 131 → 54 |

초상화 쪽이 ROI가 작고 신호가 세다(채도 절반, 밝기 1/3). 1차로 쓴다.

**절대 임계를 쓰지 않는다.** research §4.7이 명시한 대로, 밤 맵·실내에서는 평상시 밝기도 40~80까지 떨어진다. 대신 **매치 내 기준선 대비 상대 하락**을 본다.

```python
def detect_death(states: list[FaceStat]) -> list[tuple[float, float]]:
    """얼굴 ROI의 채도·밝기가 '그 매치의 평소'보다 크게 떨어진 구간을 찾는다.

    기준선은 매치 전체의 중앙값으로 잡는다 — 사망 구간은 소수라 중앙값을 거의 안 흔든다.
    """
    base_v = np.median([s.value for s in states])
    base_s = np.median([s.sat for s in states])
    # 사망 = 밝기가 기준선의 REL_V 이하 AND 채도가 REL_S 이하
```

> ⚠ **키프레임 샘플링(3초)에서는 램프의 "모양"을 볼 수 없다.** research §4.7은 3.5~5초에 걸친 단조 하강을 신호로 쓰라고 했는데, 3초에 1장이면 램프 중 1~2장만 잡힌다. 그래서 **모양 대신 전후 값 차이**로 판정한다. 이게 충분한지는 재봐야 한다 (§8-3).

**사망 구간의 끝(부활)은 아직 정할 수 없다** — 샘플이 없다 (§8-4). 잠정적으로 "얼굴 지표가 기준선으로 복귀하는 시점"으로 두고, 그 잠정성을 코드 주석과 로그에 남긴다.

### 5.5 `K`/`A` 카운터 판독 — 태그용

**여기서만 글자를 읽어야 해서 셋 중 제일 어렵다.** 다만 **앵커가 아니라 태그용**이라, 실패해도 교전 구간 자체는 나온다. 우선순위를 3번에 둔 이유다.

#### 왜 단순 비교로 안 되는가

research §4.4의 결론이다. HUD 텍스트에 **불투명 배경판이 없어** 글자가 게임 화면 위에 직접 그려지고, 글자 테두리가 배경과 섞인다. **같은 숫자인데도 프레임마다 픽셀 배치가 달라서**(49프레임 → 49가지) 모양을 그대로 대조하는 방식은 못 쓴다.

#### 쓰려는 방법 — 쉬운 말로

이전 판에서 "흰 글자다움 맵 × 알파 템플릿 상관"이라고 적었는데, **그건 제가 만든 말이고 한국어로 읽히지 않는다.** 풀어 쓰면 이렇다.

> **1단계 — 화면에서 "글자일 만한 곳"에 점수를 매긴다.**
> 픽셀 하나하나에 대해 *밝은가* + *색기가 없는가(흰색인가)* 를 따져 **0에서 1 사이 점수**를 준다. 글자는 흰색이니 점수가 높고, 배경은 대개 색이 있거나 어두우니 낮다.
> 여기서 **"점수" 그대로 두고 이진(글자/배경)으로 자르지 않는 게 요점이다.** 값이 막 바뀐 직후에는 새 숫자가 흐리게 나타났다가 0.15초에 걸쳐 진해지는데(research §4.5), 잘라버리면 그 구간이 통째로 "글자 없음"이 된다.
>
> **2단계 — 숫자마다 "본보기"를 만들어 둔다.**
> 0부터 9까지 각각, **어느 위치에 글자가 얼마나 진하게 찍히는지**를 담은 기준 이미지다. 실제 게임 화면에서 같은 숫자를 여러 배경에서 모아 만든다.
>
> **3단계 — 화면 점수와 본보기를 겹쳐 모양이 얼마나 닮았는지 잰다.**
> 가장 닮은 숫자를 답으로 고른다. 1등과 2등의 점수 차이가 작으면 **답을 내지 않는다** — 억지로 고르면 틀린 값이 조용히 들어간다.

이름을 다음과 같이 정한다.

| 이전 표현 | 이 판에서 쓰는 이름 | 뜻 |
|---|---|---|
| 흰 글자다움 맵 | **글자 점수 맵** | 픽셀마다 "흰 글자일 가능성" 0~1 |
| 알파 템플릿 | **숫자 본보기** | 숫자별 기준 이미지. 값은 글자의 진하기(0~1) |
| 상관 | **모양 비교** | 두 이미지의 패턴이 얼마나 닮았는지 (평균 제거 정규화 상관) |

#### 글자 점수 맵

```python
# detect/glyph.py
def text_score(rgb: np.ndarray, v_lo: int = 120, s_hi: int = 70) -> np.ndarray:
    """픽셀마다 '흰 글자일 가능성'을 0~1로 매긴다.

    이진화하지 않는 것이 핵심이다. 값이 바뀐 직후 새 숫자가 흐리게 나타났다가
    0.15초에 걸쳐 진해지는데(research §4.5, 밝기 113→169→220→255),
    임계로 자르면 그 구간이 통째로 '글자 없음'이 된다.
    """
    a = rgb.astype(np.int16)
    v = a.max(axis=2)              # 밝기
    s = v - a.min(axis=2)          # 색기 (글자는 흰색이라 0에 가깝다)
    bright = np.clip((v - v_lo) / (255 - v_lo), 0.0, 1.0)
    achroma = np.clip(1.0 - s / s_hi, 0.0, 1.0)
    return (bright * achroma).astype(np.float32)
```

#### 숫자 본보기 만들기

글자는 흰색(≈255)이 배경 위에 겹쳐진 것이다. 픽셀별로

```
보이는 값 = 진하기 × 255 + (1 - 진하기) × 배경
```

배경만 프레임마다 바뀌고 진하기는 글꼴이 정한 고정값이다. 따라서 **같은 숫자를 여러 배경에서 모아 픽셀별 하위값을 취하면 진하기를 역산할 수 있다.** 어두운 배경 샘플이 섞여 있으면 `배경 ≈ 0` 이므로:

```python
def build_template(samples: np.ndarray) -> np.ndarray:
    """같은 숫자 크롭 N장 (N,H,W,3) → 숫자 본보기 (H,W) 0~1.

    최솟값 대신 하위 10 퍼센타일을 쓰는 것은, 압축 아티팩트 같은
    이상치 한 장이 진하기를 통째로 깎지 않게 하기 위해서다.
    """
    v = samples.astype(np.int16).max(axis=3)
    return np.clip(np.percentile(v, 10, axis=0) / 255.0, 0, 1).astype(np.float32)
```

#### 모양 비교

```python
def _similarity(a: np.ndarray, b: np.ndarray) -> float:
    """평균을 뺀 뒤 정규화해 비교한다.

    평균을 빼므로 '글자 모양 안쪽은 점수가 높고 바깥쪽은 낮다'를 동시에 요구하게 된다.
    이게 없으면 흰 덩어리가 아무 숫자에나 높은 점수를 받는다.
    """
    a = a - a.mean(); b = b - b.mean()
    d = float(np.sqrt((a * a).sum() * (b * b).sum()))
    return float((a * b).sum() / d) if d > 1e-6 else 0.0
```

**1등과 2등의 차이를 신뢰도로 쓴다.** 절대 점수보다 오판을 훨씬 잘 걸러낸다. 차이가 작으면 `None` 을 반환한다.

#### 자릿수

research §4.2: **자릿수가 늘면 필드 중심을 기준으로 좌우로 확장된다.** 우측 정렬이 아니고, 한 필드가 늘어도 다른 필드는 안 밀린다.

자릿수를 먼저 판정하지 않고 **ROI 전체에 훑어서 매칭한 뒤 피크를 묶는다.** 1자리·2자리를 한 코드로 처리할 수 있다. ROI가 36x24, 본보기가 12x17이라 후보 위치가 수십 개뿐이고, 키프레임 샘플링이면 20분 매치가 400프레임이라 **최적화할 이유가 없다.**

#### 본보기를 어디서 구하나 ⚠

`K`는 보통 한 자리다. **7·8·9는 좀처럼 안 나온다.**

| 방법 | 장점 | 단점 | 판정 |
|---|---|---|---|
| `TK`/`K`/`A` 세 필드에서 수집 | 같은 글꼴·크기가 확실 | 높은 숫자는 판을 많이 쌓아야 모인다 | **1차** |
| 매치 타이머(`00:25`)에서 수집 | 매 판 0~9가 전부 돌아 데이터 무한 | **⚠ 글자 크기가 같은지 미확인** (§8-5) | 확인 후 결정 |
| 게임 리소스에서 글꼴 추출 | 즉시 전부 확보 | Unity 에셋 파싱. 인게임 렌더와 일치 보장 없음 | 위가 다 막히면 |

없는 숫자는 본보기가 없으므로 **판독기가 `None` 을 반환한다.** 조용히 틀린 값을 내지 않는다.

## 6. 구멍 난 시계열을 견딜 것

링버퍼는 매치를 통째로 지우지 않고 **앞에서부터 깎는다**(SPEC §7.2.1). 백로그로 늦게 처리하는 매치는 앞부분 세그먼트가 이미 없을 수 있다.

- 구멍이 있으면 자체 검증(증가 횟수 == 최종값)이 당연히 안 맞는다. **검출기 실패로 집계하지 말 것.**


```
분할/병합 횟수  라벨 1개가 검출 N개로 쪼개짐 / 라벨 N개가 1개로 붙음
```


### 8-2. 키프레임 샘플링(3초)으로 교전 경계가 충분한가 (신규 · **제일 먼저 확인**)

§5.1의 디코딩 전략 전체가 여기 걸려 있다.

- **모르는 것**: ① 배지 애니메이션의 주황 픽셀 저점이 3초 간격 샘플에서 임계 100 아래로 내려가는가 ② 3초 격자로 잡은 교전 경계가 라벨과 얼마나 어긋나는가 ③ 3초 미만 교전이 실제로 얼마나 있는가
- **확인 방법**: 교전 한 구간을 **전체 디코딩**해 60fps 전 프레임의 주황 픽셀 수를 그린다. 그 위에 3초 간격 샘플을 겹쳐 본다. `scripts/probe/` 도구를 조금 고치면 된다.
- **막는가**: 아니다. 다만 결과에 따라 2패스 폴백(§5.1)을 만들지 말지가 갈린다. **작업 순서 2번에 둔 이유다.**

### 8-3. 3초 샘플링으로 사망 램프를 잡을 수 있는가 (신규)

- **모르는 것**: research §4.7은 3.5~5초 램프를 봤다. 3초에 1장이면 1~2장만 잡히는데, "전후 값 차이"만으로 밤 맵의 어두운 구간과 구분되는가.
- **현재 처리**: 매치 중앙값 기준 상대 하락으로 판정하되, 임계는 비워뒀다.
- **확인 방법**: §8-2와 같은 프레임 데이터로 동시에 잰다.
- **막는가**: 아니다. 사망 검출기는 2순위다.

### 8-4. 팀원 생존 상태의 사망·관전 화면 (research §7-1, §7-2)

**이 계획에서 가장 큰 미지수다.**

- **모르는 것**: 내가 죽고 팀원이 살아있을 때 화면이 어떻게 생겼는지. SPEC §3은 "관전 화면은 UI가 다르니 판독 불가로 처리"하라는데, **그 화면을 아직 아무도 못 봤다.** 부활 순간도 마찬가지.
- **영향**: §5.4의 사망 구간 끝 판정, §5.2 배지의 `PRESENT_MIN` 가드가 관전 화면에서 통하는지.
- **현재 처리**: 사망 구간 끝을 "얼굴 지표 복귀"로 **잠정** 정의하고, 잠정임을 코드와 로그에 남긴다.
- **확인 방법**: 팀원이 살아있는 상태로 죽은 매치가 필요하다. 조사한 3판은 전부 "사망 = 매치 종료"였다. **라벨셋 수집 때 이 조건을 의도적으로 만들 것.**
- **막는가**: 교전 검출은 막지 않는다. 사망 태그의 정확도를 보증할 수 없을 뿐이다.

### 8-5. 타이머·일차 숫자가 카운터와 같은 글꼴·크기인가 (신규)

- **영향**: §5.5의 본보기 조달, §5.6의 일차 판독.
- **현재 처리**: 같다고 가정하지 않는다. 확인 전까지 일차는 비워둔다.
- **확인 방법**: 같은 프레임에서 글리프 높이를 비교한다. 카운터는 **높이 17px, 폭 11~13px**로 이미 재뒀다(research §4.2). 30분이면 끝난다.
- **막는가**: 아니다. 같다면 라벨링 부담이 크게 준다.

### 8-6. 하드웨어 디코딩 결과가 소프트웨어와 같은 픽셀인가 (신규)

- **영향**: §5.1. 색 임계를 쓰는 검출기라 미세한 차이가 판정을 뒤집을 수 있다.
- **현재 처리**: 기본 `auto`, 실패 시 소프트웨어 폴백.
- **확인 방법**: 같은 세그먼트를 두 경로로 디코딩해 ROI 픽셀을 직접 비교. 라벨셋 평가도 양쪽으로 돌린다.
- **막는가**: 아니다. 소프트웨어만 써도 20분 매치가 22초다.

### 8-7. 다른 해상도에서 UI가 비례 스케일되는가 (research §7-4)

- **영향**: §5.7 전체.
- **현재 처리**: 추정하되 `measured=False` 로 표시하고 경고.
- **막는가**: 아니다. 2560x1440 하나로 개발·평가가 가능하다.

### 8-8. 색 임계값들 (신규)

`text_score()` 의 `v_lo=120 / s_hi=70`, `GAP_FILL=2`, `MIN_COMBAT=2`, 사망 상대 임계 — **전부 research 수치에서 역산한 출발점이지 검증된 값이 아니다.** 라벨셋을 만든 뒤 §7의 평가 하네스로 정한다.

## 9. 작업 순서

> **진행 방식**: §8의 "확인 필요" 항목은 별도 확인 단계로 멈추지 않는다. 구현하면서 실제 동작으로 검증한다. 완료한 항목은 아래 체크박스에 표시한다.

- [x] **1. 골격** — `profiles/`, `video/session.py`, `video/segments.py`, `video/frames.py`. 세션 폴더 + 매치 시각 → ROI 프레임 스트림. probe 스크립트 로직을 옮기는 것에 가깝다
- [x] **2. 배지 검출기** — `detect/color.py`, `detect/badge.py`, `detect/intervals.py`. ★ 여기까지만 해도 교전 구간이 나온다
- [x] **3. 사망 검출기** — `detect/death.py`. death 태그 + 사망 구간 제외
- [ ] **4. 카운터 판독** — `detect/glyph.py`, `detect/counter.py`, `tools/build_templates.py`. kill / assist 태그
- [ ] **5. 낮/밤·일차** — `detect/daynight.py`
- [ ] **6. 통합** — `cli/detect_match.py`. 매치 하나를 통째로 돌려 자체 검증 결과를 본다
- [ ] **7. 라벨링 도구** — `tools/collect_frames.py`, `tools/label_combat.py`, `tools/eval_detect.py`
- [ ] **8. 실측 라벨셋으로 튜닝** — 실제 녹화본 5판 이상 라벨링 후 §8-8 파라미터 확정 (도구는 갖춰짐, 라벨셋 축적은 실사용과 함께 진행)
