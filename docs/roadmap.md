## 4. 추가로 필요해 보이는 것 (기존 plan 에 없었거나 약했던 것)

1. ~~릴리스 전용 공개 저장소 안~~ → 검토했으나 채택하지 않음. 저장소를 공개하고 Release 로 배포하기로 결정([§6](#6-결정-사항과-남은-결정)). 그래서 D7(이력 정리)이 D13·D9 의 선결 조건이다.
2. **서버 API 토큰 — 결정(2026-09-25): 토큰은 "공개된 키" 수준으로 보고, 실질 방어는 서버의 요청 제한·이상 감지·알림으로 한다.**
   - 토큰은 서명·만료·사용자 구분이 없는 **고정 공용 문자열**이다(JWT 와 다르다). 공개 저장소의 설치기에 들어가므로 누구나 꺼낼 수 있고, 하는 일은 자동 스캔 봇이 아무 요청이나 던지는 것을 거르는 정도다. 사용자 구분은 `installId`, 버전 구분은 `appVersion`·`schemaVersion` 이 한다.
   - 계정 없이 서버와 통신하는 프로그램(Sentry DSN, 각종 크래시·사용 통계 수집)이 흔히 쓰는 방식과 같다: 클라이언트에 공개 키를 넣고 방어는 서버가 한다.
   - **옛 토큰으로 오는 요청을 받는 것 자체는 문제가 아니다.** 그래서 "옛 앱이 대부분 사라질 때까지 기다렸다가 토큰을 바꾸는" 절차는 의미가 작다. 서버가 여러 토큰을 동시에 허용하는 기능(`RECEIVER_API_TOKENS`)은 이미 만들어 뒀으니 필요할 때 쓰되, 토큰을 바꾸면 옛 토큰을 쓰는 앱(업데이트를 끈 사용자)은 전송만 실패하고 그 사람의 로그·라벨은 서버에 쌓이지 않는다는 점만 안다(앱 자체는 정상 동작, 로컬 라벨은 그대로).
   - **남용 대응은 토큰 교체가 아니라 요청 제한이다(구현 완료 — [P3](#p3--서버-운영-보강-i4-와-나란히-급하지-않음)).** 서버가 IP 별 요청 수와 거부되는 요청(401·404·405·413·422) 횟수를 세어 임계값을 넘으면 그 IP 를 1시간 차단(429)하고 Discord 웹훅으로 알린다. IP 는 서버 메모리에만 두며 디스크에 쓰지 않는다([privacy.md](privacy.md)).
   - **토큰을 git 에 커밋하지 않는다(공개 저장소 전제).** 빌드 때 주입한다(D13 의 GitHub Secrets → 설치기 빌드 → 앱 설정 기본값). Discord 웹훅 URL 도 비밀 값이라 서버 `.env`(`DISCORD_WEBHOOK_URL`)로만 둔다.
   - D10 에서 앱이 401 을 받으면 화면에 "서버 연결 정보가 바뀌었습니다. 업데이트해 주세요" 같은 안내를 띄워 조용히 안 보내지는 상태를 알리는 것을 권한다(아직 계획에 반영 안 함).
3. ✅ **관리자 대시보드(2026-09-26).** 개발 모드 앱의 "관리자" 탭이 서버 상태·진단 번들·오류 로그(묶음)·라벨을 보여 준다(배포 모드에는 없음, 5초 자동 새로고침). 서버 읽기 API 5개는 `server/receiver` 에 추가했고(서버 코드를 infra 저장소에서 이 저장소로 이관, plan-infra I6) **이미지 배포(push)만 남았다**. 설치판과 개발판 동시 실행은 `run-parallel.bat`(`LUMIA_PROFILE`, [DEVELOPMENT §0](DEVELOPMENT.md)).

## 7. 서버 연동 기능의 테스트 자동화

D9·D10·D14 는 네트워크·설치기·서버가 얽혀 손으로 확인하기 어렵고, 잘못되면 **조용히 안 보내지거나(데이터 유실) 개인정보가 새는** 종류다. 기능과 같은 커밋에서 자동 테스트를 함께 만든다(TDD). 진짜 외부 서비스(GitHub·운영 서버)는 기본 테스트에서 호출하지 않는다.

| 층 | 무엇을 | 방법 |
|---|---|---|
| **계약 테스트** | 앱이 보내는 페이로드가 서버 스키마와 맞는가(`labelNote` 추가·필드 허용 목록 대조 포함) | 계약을 한 곳(JSON Schema 또는 공용 픽스처)에 두고, 이 저장소는 그 픽스처로 페이로드를 만들어 검증, infra 저장소의 수신 API 테스트는 같은 픽스처로 수락·거부를 검증. 스키마가 어긋나면 어느 한쪽 CI 가 깨진다 |
| **클라이언트 단위** | 대기 큐, 하루 1회 묶음, 20MB 상한, 재시도·백오프, 실패해도 앱이 안 멈춤, 동의 꺼짐이면 네트워크 호출 0회, 개인정보 제거 | `httpx.MockTransport` 로 가짜 서버(200·401·413·500·타임아웃·연결 거부). 시계·sleep 주입(기존 `watcher` 방식). 개인정보 제거는 실제 로그 샘플 기반 회귀 테스트 |
| **업데이트 흐름** | 최신 버전 판별, 새 버전 알림, 다운로드 → SHA-256 검증 → 설치기 실행, 체크섬 불일치 거부, `update.check` 꺼짐이면 자동 확인 안 함·수동 확인은 동작 | GitHub Releases API 모양의 가짜 JSON 과 로컬 HTTP 서버로 설치기(더미 파일) 서빙. 설치기 실행은 함수 주입으로 대체 |
| **서버 통합** | 실제 수신 API 컨테이너에 앱 클라이언트로 보내 저장·삭제·접수 번호까지 | `server/receiver` 의 pytest 와 `docker compose` 로 띄운 서버에, 이 저장소의 전송 클라이언트를 같은 서버에 붙이는 통합 테스트를 로컬·CI 에서 선택 실행(`-m integration`) |
| **운영 스모크** | 배포된 서버가 살아 있는가 | 읽기 전용 확인만: 서버 주소(`.env` 의 `LUMIA_RECEIVER_URL`) 헬스체크·토큰 없음 401·`/docs` 404. 데이터를 쓰는 요청은 하지 않는다. 필요하면 정기 실행 |
| **릴리스 파이프라인** | 태그와 `__version__` 불일치 시 실패, `.sha256` 생성, 설치기 이름 규칙 | 순수 함수 테스트 + 워크플로에서 실제 실행(D13) |

원칙: ① 시간·네트워크·설치기 실행은 주입해 실시간 지연 없이 테스트한다(기존 `pipeline/watcher` 방식) ② 서버 장애 시나리오(타임아웃·500·오프라인)는 전부 자동 테스트로 고정한다 ③ 업그레이드 덮어쓰기 설치처럼 자동화가 어려운 것은 [deploy §10](plan-deploy.md) 수동 체크리스트에 남긴다.

## 8. 개인정보 처리 제안안 (→ 2026-09-25 [privacy.md](privacy.md) 로 확정, 아래는 당시 제안)

법률 자문이 아니라 최소 수집 원칙에 따른 제안이다. 확정하면 `docs/privacy.md` 로 만들어 첫 실행 화면·README 에서 링크한다.

- **서버가 실제로 보는 개인정보성 값은 IP 주소다.** 앱이 보내는 값은 무작위 `installId` 뿐이지만 caddy·receiver 접근 로그에 IP 가 남는다. → 접근 로그에서 IP 를 남기지 않거나 7~14일 후 자동 삭제.
- **보관 기간**: 오류 로그·진단 번들 90일 후 자동 삭제, 라벨은 연구 자료라 삭제 요청 전까지 보관(영상·닉네임이 없어 식별 불가). 기간은 안내문에 그대로 적는다.
- **삭제 요청**: 앱 옵션의 "보낸 데이터 삭제 요청"(전체 `installId` 기준, D10) + 연락 이메일 하나.
- **안내문에 넣을 것**: 수집 항목, 목적(검출기 개선), 보관 기간, 제3자 제공 없음, 서버 위치(OCI 리전이 국외면 국외 이전 고지), 삭제 방법, 연락처, 옵트인이며 꺼도 기능 제한 없음.
- 미성년 이용자가 있을 수 있으나 전부 옵트인·비식별이라 별도 절차는 두지 않는 안.

## 9. 전송 데이터 명세 보강안 (2026-09-25 점검)

서버 수신 스키마(`server/receiver/app/schemas.py`)를 실제 클립 메타데이터(`clips/*.json`, `.labels/*.json`)와 대조했다. **지금 스키마로는 데이터만 보고 분석·판단하기 어렵고, 일부는 앱이 보내는 값을 거부한다.** P1 6번(계약 확정)에서 아래를 반영한다. 원칙은 그대로다: 영상·이미지·닉네임·팀원 정보·경로 원문은 보내지 않는다.

**방침(2026-09-25 결정): 버그 리포트용 오류 로그와 라벨 데이터는 위 금지 항목을 뺀 범위에서 최대한 자세히 보낸다.** 개인정보가 섞이지 않는 한 필드를 아끼지 않는다. 대신 (1) 페이로드에 `schemaVersion` 을 넣고, (2) 서버가 허용 목록에 없어 버린 필드 이름을 집계해 앱·서버 스키마가 어긋나면 알아챌 수 있게 하며, (3) 자유 텍스트(로그 메시지·라벨 메모)는 개인정보 제거 규칙과 회귀 테스트를 통과한 것만 보낸다.

### 라벨

**바로 고칠 것 (버그성)**
- `userLabel` 허용값이 `pvp/hunt/none` 인데 앱은 `pvp/pve` 를 저장한다. **서버가 `pve` 라벨을 검증 실패로 거부한다.**
- **라벨 분류는 `교전` / `그 외` 두 가지로 확정한다(2026-09-25 결정).** 그 외에는 사냥뿐 아니라 이동·대치·대기 장면이 들어간다. 로컬 저장값은 기존 `pvp`/`pve` 를 유지해 이미 붙인 라벨·`.labels/` 보관소·`eval_pvp.py` 를 마이그레이션하지 않는다(과거의 `pve` 는 "사냥"이었지만 새 정의 "그 외"의 부분집합이라 그대로 쓸 수 있다). **전송할 때는 중립 값 `combat`/`other` 로 변환**하고 서버 스키마도 이 값으로 정의한다. 나중에 세분류(사냥·대치·이동 등)가 필요해지면 서버 필드를 추가한다(`labelSchemaVersion` 포함).

**분석에 필요한데 빠진 것**
- 재현 조건: `sourceWidth`·`sourceHeight`(해상도별 정확도 비교의 핵심), `gameMode`, `sourceIncomplete`(잘린 경기 표시), `prerollSource`
- 검증용 정답값: `matchKills`·`matchAssists`·`matchTeamKills`(결과 화면 최종 K/A — 검출값 `killDelta` 와 대조해 판독 오류를 찾는 근거)
- 교전 구간 길이·위치: `combatStartOffsetSec`·`combatEndOffsetSec`(길이만 있고 위치가 없다)
- 같은 경기 묶기·중복 방지: **익명 경기 키**(`sessionDir`+`matchStartUtc` 의 해시)와 **클립 키**(해시). 없으면 같은 경기의 클립을 묶을 수 없고, 라벨을 고쳐 다시 보낼 때 중복 저장된다(서버는 `installId`+클립 키로 덮어쓰기)
- 라벨링 맥락: `labelNote`(D12), 라벨을 붙인 시각, `labelConflict`(라벨과 검출 근거 충돌 표시), 라벨 출처(`labelSource` — 서버에는 있으나 앱 메타데이터에는 없으니 값 정의 필요)
- 모드: `mode`(`dev`/`release`) — 개발 PC 의 라벨이 운영 데이터에 섞이지 않게 서버가 분리 표시
- 캐릭터: **내 캐릭터(`myCharacter`)는 보낸다(2026-09-25 결정 — 닉네임이 아닌 게임 정보라 식별성이 낮고 캐릭터별 정확도 비교에 유용).** 팀원 캐릭터·닉네임은 "팀원 정보 전송 안 함" 원칙에 따라 계속 제외
- `pvpSignals` 는 **이름 목록뿐**이다. 신호별 수치(궁 델타, 팀 전투 비율 등)가 없어 가중치 튜닝의 재료로는 약하다 — 현재 메타데이터에 있는 `pvpScore`·`enemyRingMean`·`ultimateDelta` 외에 신호별 값을 넣을지 정한다

**보내지 않는 것 유지**: `title`(캐릭터·지역 포함 자동 생성이지만 수동 편집 가능해 개인정보가 섞일 수 있음), `sessionDir`·`thumbnailPath` 등 경로, `matchStartUtc` 원문(시청 시각 → 필요하면 상대 시각만)

### 오류 로그·환경

서버 `LogEntry` 는 `ts`·`level`·`message` 뿐이고 `Environment` 는 버전·OS·해상도·코덱·판독 실패 통계뿐이다. 친구 배포에서 실제로 물었던 항목([friend-guide](friend-guide.md))과 대조하면 부족하다.

- 로그: 로거 이름(모듈), 예외 종류·스택(경로 제거 후)을 분리 필드로. 같은 오류를 묶어 셀 수 있게 **오류 지문**(모듈+예외 종류+발생 위치의 해시)
- 환경 추가: `mode`, CPU 모델·코어 수, GPU 이름, 메모리, 디스플레이 배율, 화면 비율, 하드웨어 디코딩 사용 여부(`hwaccel`), HEVC 재생 가능 여부(프록시 전환 여부), ffmpeg 빌드·사용한 프록시 인코더(`h264_mf` 등), 스팀 버퍼 분(`buffer minutes`), 로캘/타임존
- 성능: 경기 분석 소요 시간과 경기 길이 비율(게임 중 부하 영향 판단 — deploy §7-14), 프록시 생성 시간
- 판독 건강도: `readFailStats` 를 키 목록으로 확정(배지 판독불가 비율, K/A·지역명·일차 본보기 유무, 결과 화면 OCR 성공 여부, 프로필이 측정값인지 축척 추정인지). **게임 패치로 HUD 가 바뀌었을 때의 조기 경보**가 되게 한다

### 서버(인프라 저장소) 쪽에 필요한 변경 메모 (**2026-09-25 서버에 모두 반영·배포 완료** — 아래는 당시 요구사항)

- 라벨 스키마에 `labelNote`(문자열, 앱이 이미 500자로 자름·앞뒤 공백 제거, 라벨이 없으면 없음)를 추가하고 허용 필드 목록에 넣는다. 서버도 500자 상한을 방어적으로 둔다.
- `userLabel` 허용값을 `combat`/`other` 로 바꾼다. 앱은 로컬에 `pvp`/`pve` 를 그대로 저장하므로 **전송 시 변환은 D10 클라이언트가 한다**(`pvp→combat`, `pve→other`).
- 자유 텍스트라 서버는 로그·집계에 `labelNote` 원문을 남기지 않는 편이 안전하다([privacy.md](privacy.md) 와 함께 확인).

### 한계 (의도적)

영상·화면 이미지를 보내지 않으므로 **"검출기가 왜 틀렸는가"를 프레임 단위로 재현하는 분석은 불가능**하다. 수치·라벨·판독 통계로 "어느 환경에서 얼마나 틀리는가"를 보는 것까지가 이 전송의 목적이다. 프레임 재현이 필요한 사례는 사용자가 직접 보내는 진단 zip(이미지 없음)이나 친구와 별도 협의로 다룬다.
