## 1. 목표

- 사람 확인은 **릴리스마다 고정 4개 + 그 릴리스에 해당할 때만 조건부 몇 개**. 한 번에 1시간 안쪽(게임 플레이 시간 빼고).
- 나머지는 `python tools/release_check.py` 한 번으로 돌고, 결과는 보고서 한 장(통과/실패 + 스크린샷 모음)으로 본다.
- 릴리스 태그 조건 = **HEAD 커밋에 대한 release_check 전부 통과 + 사람 항목 전부 체크**.

## 2. 사람이 직접 볼 것만 남기는 기준

아래 중 하나에 해당할 때만 사람 항목으로 둔다. 아니면 테스트로 쓴다.

1. **실제 게임·스팀이 돌아야만 재현된다** — 실시간 감시, 스팀 녹화 끊김, 게임 중 부하·체감 프레임.
2. **체감·주관이다** — 반응이 빠른가, 보기 좋은가, 문구가 이해되는가. (단, "뜨는가/안 뜨는가"는 테스트다.)
3. **실사용자 데이터·환경이다** — 이전 버전 실데이터로의 업그레이드, 깨끗한 윈도우·설치기·업데이트, 다른 PC·해상도.

"앱 재시작 후 확인", "새로고침해도 남는지", "확인 창 문구가 맞는지", "버튼이 흐리게 꺼지는지" 같은 것은 전부 테스트 대상이다.

## 3. 자동화 설계

### 3.1 검증 묶음 실행기 `tools/release_check.py`

한 명령으로 아래를 순서대로 돌리고, `build/release-report/` 에 `report.json`(커밋 해시·단계별 결과)과 `index.html`(결과 + 스크린샷 모음 + §3.7 비교표)을 남긴다.

1. `pytest` (기본 묶음, 문서 검사 포함)
2. 프론트 단위 테스트 `npm test`, `npm run lint`
3. **dist 최신 확인**: `npm run build` 뒤 `git diff --exit-code frontend/dist` — 지금 체크리스트의 "dist 최신 빌드인지" 항목을 대신한다
4. 화면 E2E (§3.3)
5. 파이프라인 E2E (§3.5)
6. 골든 셋 (§3.6) — 데이터 폴더가 없으면 "건너뜀"으로 표시하고 **보고서를 통과로 치지 않는다**(`--no-golden` 을 명시해야 통과)
7. 조건부 사람 항목 제안(§2.2)

단계별로 `--only e2e` 처럼 골라 돌릴 수 있게 한다. 개발 중에는 해당 시나리오만, 릴리스 전에는 전부.

### 3.2 시드 라이브러리 (`e2e/world.py` — 지금은 `default`·`vod` 세트)

지금 있는 것: 스팀 게임 4판(두 날짜, 랭크·코발트, 풀영상 없는 게임 1개)과 `add_vod`(영상 파일 N편 + 게임·색인, 원본 삭제 옵션)를 `game.json` 으로 직접 써서 만든다(`tests/test_api_games.py` 와 같은 방식). 클립은 앱 API(`/candidates/<id>/save`)로 저장해 만든다. 아래 표의 나머지 시나리오와, `game.json` 도 앱의 저장 함수로 만드는 것은 남았다.

화면 테스트가 쓸 앱 상태를 임시 폴더에 만든다. 영상은 ffmpeg `testsrc`(320x180, 몇 초~1분, 시각이 박힌 화면)로 작게 만든다. 실제 앱 형식 그대로(`full.mp4`·`game.json`·`clipUid` 태그 클립·library json·config.json)여야 한다 — 형식을 손으로 흉내 내지 말고 앱의 저장 함수를 불러 만든다(형식이 바뀌면 시드도 따라 바뀌게).

| 시나리오 | 내용 |
|---|---|
| `basic` | 스팀 게임 5판(날짜 3일, 오늘 포함), 클립·카테고리 2개·메모·고정 게임, 결과(순위·일반/랭크)·초상화 |
| `vod` | 영상 파일 2편(날짜 다름, 1편은 원본 삭제됨), 게임 풀영상 |
| `cobalt` | 코발트 게임(스쿼드 4인, 승/패, 폴더에 남은 초상화 파일) |
| `legacy` | 이전 버전 구조 — 옛 클립 폴더(mp4+json 섞임)·한글 폴더(`클립\스팀 녹화`)·풀영상 없는 게임·원본 남은 게임 |
| `edge` | 스팀 녹화 오류 게임(녹화 없음/일부만), 풀영상만 지운 게임, 편집 저장 대기 후보, 앱 밖 영상(OBS mp4) |
| `fresh` | 설정 없음(첫 실행 화면) |

### 3.3 화면 E2E

- 러너: 파이썬 `pytest-playwright`(`.venv`, 기존 pytest 와 한 도구). 위치 `e2e/`. 브라우저는 Playwright Chromium(시드 영상은 H.264 라 재생된다).
- 테스트마다 시드 + 서버 프로세스(`e2e/run_server.py`, 임시 `LOCALAPPDATA`·임시 config, 빈 포트) 기동. "앱 재시작 후"는 서버를 껐다 켜는 도우미로 쓴다.
- 영상 확인은 `video.videoWidth > 0`·`currentTime` 으로, 클립 범위 확인은 ffprobe 길이로 한다([plan.md](plan.md) §4 의 "Playwright 로 실제 클립 videoWidth>0" 도 여기서 끝난다).
- 스크린샷: spec 안에서 `shot("이름")` 으로 찍은 것만 보고서 모음에 넣는다(H4). 픽셀 비교는 하지 않는다 — 폰트·렌더링 차이로 깨지기만 하고 사람이 보는 게 더 낫다.

### 3.4 테스트 전용 가짜 환경 (R2)

실제 PC 상태에 달린 화면(디스크 부족 경고, 같은 물리 디스크 경고, 스팀 녹화 중 속도 제한, 폴더 선택 창)을 재현하려고 서버에 가짜 공급자를 꽂는다.

- `LUMIA_E2E_FAKES=<json 경로>` 일 때만 `cli.serve` 가 읽는다. **배포본(`sys.frozen`)에서는 무시**하고 테스트로 고정한다.
- 대상: 경로별 여유 공간, 경로 → 물리 디스크 번호, 스팀 녹화 중 여부, 폴더 선택 창 응답 대기열, 실패 주입(클립 추출 실패 사유·ffmpeg stderr), 트레이 알림 기록(띄우지 않고 목록에 쌓음).
- 기존 코드가 이미 함수 주입·monkeypatch 로 테스트하는 지점을 그대로 쓴다 — 가짜를 위해 제품 코드 경로를 새로 만들지 않는다.

### 3.5 파이프라인 E2E (R3)

`tests/conftest.py` 의 합성 스팀 세션(`build_synthetic_session`)에 **가짜 검출기**(정해진 게임 경계·후보·사망 마커·결과를 돌려줌)를 끼워 감시/과거 녹화 분석/다시 분석/풀영상 만들기를 실제 ffmpeg 로 끝까지 돌린다. `pytest -m e2e` 로 묶어 기본 `pytest` 에서는 빼고 실행기에서만 돈다(느리다).

확인하는 것: `full.mp4` 재생 가능·길이, `game.json` 내용, `clip.saveMode` 자동/직접, 디스크 부족 시 풀영상만 건너뛰고 확실한 후보만 클립, 다시 분석 때 보관 클립·고정·직접 추가 구간 유지, 실패 시 이전 풀영상 유지, 원본 삭제 조건, `.staging` 이 비는지, 진행률이 단조 증가하는지.

검출 정확도는 여기서 보지 않는다(§3.6).

### 3.6 실녹화 골든 셋 (R4)

- 미디어는 git 에 넣지 않는다. `LUMIA_GOLDEN_DIR`(예: `H:\lumia_golden`)에 실제 녹화 조각을 두고, 기대값만 `tests/golden/*.json` 으로 커밋한다. `pytest -m golden`, 폴더가 없으면 skip.
- 표본(지금 가진 것부터): 2560x1440 스팀 일반·랭크 판, 연습 모드 녹화, 흰 머리 팀원 판, 코발트.mp4(1080p), 하이용가리 영상 파일(1080p, 방송 오버레이), 스팀 녹화 오류로 끊긴 세션.
- 비교: 게임 시작·끝(±10초), 연습/닷지 제외, 일반/랭크, 순위, 초상화 수(코발트 0), 코발트 게임별 클립 수, 사망 시각(±3초), 1080p 초상화.
- 기대값은 한 번 사람이 확인해 정한다: `--update-expected` 로 새 값을 쓰고 diff 를 보고 커밋. 그 뒤로는 바뀌면 실패.
- 검출을 고칠 때 이 셋이 회귀를 잡으므로, `tools/eval_detect.py`(교전 재현율)와 합칠지는 R4 에서 정한다.

### 3.7 업그레이드 도우미 (H2 보조)

실데이터 업그레이드는 사람이 보되, 실행기가 백업 사본에 새 버전 이전을 돌려 **이전 전·후 게임 수·클립 수·제목/라벨/메모가 붙은 클립 수·용량**을 표로 내고, 차이가 있으면 빨갛게 표시한다. 사람은 표와 앱 화면을 훑기만 한다.

## 4. 체크리스트 개편과 규칙 전환 (R5)

release-checklist.md "다음 릴리스" 절을 이렇게 바꾼다.

```
### 새로 구현된 기능 / 고친 버그        (지금과 같음 — 패치노트 재료)
### 자동 검증                           (체크박스 없음 — 이번 릴리스에서 추가한 시나리오·골든 이름만 나열)
### 사람 확인                           (H1~H4 고정 + 해당 C 항목 + §2 기준을 통과한 이번 릴리스 고유 항목)
```

- CLAUDE.md "릴리스 체크리스트 관리": 기능·버그 커밋에서 **확인할 것을 먼저 테스트(E2E·파이프라인·골든)로 쓰고**, §2 기준에 걸리는 것만 "사람 확인"에 올린다. 사람 항목에는 왜 자동화가 안 되는지 한 마디를 붙인다.
- DEVELOPMENT §13 선행 조건: `report.json` 이 HEAD 커밋으로 전부 통과 + "사람 확인" 미체크 0개.
- `tools/check_docs.py`: "자동 검증" 절에 적은 spec/시나리오 이름이 실제로 있는지 검사.
- 강제 수단(태그 단계에서 `release_tools check-tag` 가 report.json 을 확인할지)은 §6 에서 정한다.
