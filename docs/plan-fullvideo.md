# 풀영상 중심 구조 전환 계획

> 현재 동작(클립 중심)은 [spec/pipeline.md](spec/pipeline.md)·[spec/ui.md](spec/ui.md). 옛 "풀 영상 탭(보조 뷰, 기본 꺼짐)" 계획을 **대체한다**.
> 결정 배경: 2026-09-29 대화. 이 게임은 야생동물 사냥에도 궁극기를 쓰는 등 변수가 많아 교전만 100% 골라내는 것은 원리상 어렵다고 판단했다. 그래서 목표를 "자동으로 완벽히 자르기"에서 **"게임 전체 영상 위에서 교전 후보를 빨리 찾고 쉽게 고쳐 저장하기"**로 바꾼다. 결정(§1·§6)은 확정됐고 구현은 아직이다.
> 단계를 끝내면 결론을 spec 에 옮기고 이 문서에서 지운다. 전부 끝나면 이 문서를 없앤다.

## 0. 진행 상태 (세션이 끊겨도 여기부터 이어간다)

- [ ] F1 — 백엔드: 게임마다 풀영상 저장 + 게임 기록(후보 구간·마커) JSON
- [ ] F2 — 디스크 공간: 첫 실행 화면 강조, 부족 예상 알림, 공간 부족 시 대체 동작
- [ ] F3 — 자동 정리: 대상을 클립에서 풀영상으로 변경
- [ ] F4 — 풀영상 플레이어 UI: 타임라인 후보 표시·범위 조정·이전/다음·저장·일괄 저장
- [ ] F5 — 기존 카드 뷰 제거 (피드백 확인 후, 단독 커밋)
- [ ] F6 — 영상 파일(다시보기) 탭: 게임 단위 풀영상으로 나눠 저장
- [ ] F7 — 클립 정리 탭 (날짜별·폴더별·캐릭터별) — **논의 필요, 설계 전**

## 1. 결정 사항 (사용자, 2026-09-29)

1. **풀영상 방식으로 통일한다.** 처리한 모든 스팀 녹화 게임의 전체 영상을 저장한다. 기존 계획의 `fullVideo.enabled`(기본 꺼짐) 스위치는 없앤다.
2. **보기 방식은 풀영상 하나로 통일한다.** 카드 뷰와 풀영상을 둘 다 두는 안은 화면이 난잡해져 버렸다. 다만 **UI 변경은 피드백에 따라 되돌릴 수 있게 커밋한다** (§5).
3. **풀영상 위에 클립 후보 목록을 보여 주고, 후보마다 저장, 그리고 일괄 저장을 제공한다.**
4. **분석이 끝났을 때 클립을 자동으로 저장할지(기존 방식), 사용자가 직접 저장할지를 옵션으로 고른다.**
5. **클립은 자동 정리 대상이 아니다.** 저장된 클립은 사용자가 따로 남기겠다고 고른 것이기 때문이다(자동 저장을 고른 경우도 사용자의 선택으로 본다). 자동 정리는 풀영상만 대상으로 한다.
6. **첫 실행 화면에서 50~100GB 여유 공간이 필요하다는 것을 읽지 않을 수 없게 강조한다.** 공간이 부족할 것 같으면 **미리 알림**을 띄운다.
7. **영상 파일(다시보기)도 게임 단위 풀영상으로 나눠 저장한다** — 범위는 캐릭터 선택 화면부터 결과 화면(로비로 나가기 직전)까지. 그래서 V7 "분석 후 원본 삭제"는 그대로 유효하다(§3.7).
8. **클립을 편하게 정리하는 탭을 따로 둔다**(날짜별·폴더별, 사용자는 캐릭터별로도 모은다). **세부는 추가 논의 후 정한다**(F7).

## 2. 용량 (실측 비트레이트 기준)

기존 클립 32개(34.9분, 6.65GB)로 잰 스팀 녹화 비트레이트는 **약 25.5Mbps, 분당 약 190MB** 다(2560x1440, 2026-09-29).

| 게임 | 길이(시작 전 대기·로딩 포함, 추정) | 풀영상 | 클립 자동 저장 시(+1.5~2GB, 사용자 경험치) |
|---|---|---|---|
| 1등 판 | 22~27분 | 4.2~5.2GB | 5.7~7.2GB |
| 중간 순위 | 15분 | 약 2.9GB | 4.4~4.9GB |
| 일찍 탈락 | 8~10분 | 1.5~1.9GB | 3~3.9GB |

- 참고로 스팀 백그라운드 녹화 2시간 버퍼(README 권장)가 이미 약 23GB 를 쓴다.
- 해상도·스팀 녹화 품질 설정에 따라 비트레이트가 다르다. 계산에는 **실제 풀영상 파일 크기의 이동 평균**을 쓰고, 기록이 없을 때만 190MB/분을 쓴다.

## 3. 설계

### 3.1 저장 구조

게임 하나 = 폴더 하나. 기존 `clips/` 와 나란히 `games/` 를 둔다(경로 설정 `paths.games`, 기본 `%USERPROFILE%\Videos\LumiaBriefingRoom\games`).

```
games/<경기키>/
  full.mp4            게임 전체 (-c copy, 원본 화질)
  game.json           결과·초상화·후보 구간·마커·사용자 수정
  thumb.jpg / result.jpg / portrait_*.jpg
clips/                저장된 클립 (기존 형식 유지, 자동 정리 대상 아님)
```

`game.json` 의 핵심 필드(초안):

| 필드 | 내용 |
|---|---|
| `candidates[]` | 교전 후보. `id`, `start`/`end`(풀영상 기준 초), `pvpScore`, `pvpSignals`, `tags`, 제목 재료(일차·낮밤·지역) — 지금 클립 메타데이터의 검출 필드를 그대로 옮긴다 |
| `candidates[].user` | 사용자 수정: `start`/`end`(조정한 범위), `dismissed`(무시), `savedClipId`(저장한 클립), `label`(교전/사냥) |
| `userCandidates[]` | 사용자가 직접 추가한 구간 |
| `markers[]` | 점 사건: 킬·어시스트·내 사망·팀원 사망(시각과 종류). 이미 판독하는 값이라 추가 비용이 거의 없다 |
| `fullVideo` | 파일 크기, 길이, 소스 세션 |

**사용자 수정 기록은 구간 경계 단위의 정답 데이터가 된다.** 지금 라벨은 "이미 만든 클립이 교전인가"뿐이라 놓친 교전을 셀 수 없었는데, 후보 조정·추가·무시 기록이 그 빈틈을 채운다.

### 3.2 파이프라인 (`process_match`)

1. 검출 (그대로)
2. **풀영상 컷**: 경기 전체 세그먼트를 `-c copy` 로 한 파일에 만든다. 링버퍼가 지우기 전에 끝나야 하므로 클립 컷보다 **먼저** 한다.
3. 결과 화면·초상화 (그대로, 저장 위치만 게임 폴더)
4. 후보 구간과 마커를 `game.json` 에 쓴다 (기존 `_plan_clips` 병합 규칙 재사용)
5. **`clip.saveMode = auto` 일 때만** 후보를 기존 방식대로 클립 파일로 자른다

- 풀영상 컷이 실패해도(디스크 부족 등) 후보 기록과 클립 저장은 계속한다(§3.4).
- 과거 녹화 분석(백필)도 같은 순서를 따른다.
- 클립 저장(수동)은 **풀영상에서 자른다**(원본 세그먼트가 이미 지워졌을 수 있다). 풀영상도 `-c copy` 결과라 키프레임 3초 격자가 그대로다.

### 3.3 클립 저장 옵션

| 키 | 값 | 기본값 |
|---|---|---|
| `clip.saveMode` | `auto`(분석 끝나면 후보 전부 저장, 기존 방식) / `manual`(직접 저장) | **`auto`** (§6-2) |
| `retention.preserveBeforeDelete` | 풀영상이 자동 정리로 지워지기 직전에 확실한 후보(킬·어시·사망) 중 아직 저장 안 된 것을 클립으로 남긴다 | **`false`** (§6-3) |

- 기본이 `auto` 라 자동 정리 대상이 아닌 클립이 게임마다 1.5~2GB 씩 쌓인다. 옵션 화면에 이 점을 적고, §3.4 부족 알림 문구에 "저장한 클립 정리"도 해결책으로 넣는다.

### 3.4 디스크 공간

**첫 실행 화면.** 여유 공간 안내는 별도 단계의 경고 상자로 둔다.

- 큰 글씨로 "게임 하나에 2~5GB 가 저장됩니다. **50~100GB 여유 공간을 확보하고 사용하세요.**"
- 저장 폴더가 있는 드라이브의 **현재 여유 공간을 그 자리에서 보여 준다**. 50GB 미만이면 빨간색으로 표시한다.
- **"확인했습니다" 체크박스를 켜야 `시작하기` 가 눌린다.**

**부족 예상 알림.**

- 게임 처리 전과 앱 시작 시에 여유 공간을 잰다.
- 경고 기준(초안): 여유 공간 < `예상 게임 용량 × 5`(약 25GB). 이 경우 트레이 알림과 화면 상단 배너를 띄운다. 기존 설정 키 `paths.minFreeGb`(기본 20, 지금은 쓰이지 않음)를 이 기준으로 되살린다.
- 문구는 원인과 해결책을 같이 준다: "여유 공간이 N GB 남았습니다. 풀영상 자동 정리 한도를 낮추거나 오래된 풀영상을 지워 주세요."

**공간이 모자랄 때.** 풀영상을 저장할 공간이 없으면 조용히 건너뛰지 않는다. **확실한 후보(킬·어시스트·사망)만 클립으로 저장**하고, 풀영상을 못 만들었다고 알린다. 교전을 영구히 잃지 않는다는 SPEC §1 의 원칙을 지키기 위해서다.

### 3.5 자동 정리 (`retention.*`)

- 대상을 **풀영상**으로 바꾼다. 클립은 대상이 아니다(결정 5).
- 기준은 용량 한도를 기본으로 한다. **기본 40GB**(§6-1).
- 풀영상이 지워져도 `game.json`(결과·후보·마커·수정 기록)과 저장된 클립은 남는다. 기존 "게임 기록 보관"(`retention.keepGameRecords`)과 같은 원리다.
- 삭제 예정 표시(빨간 배지), 고정(pin)은 풀영상에 그대로 적용한다. 고정한 풀영상은 지우지 않는다.
- **F3 설계 때 함께 정할 것**(2026-09-28 대화에서 나온 요구): 스팀 녹화·영상 파일 풀영상의 기준을 따로 켜고 끌지, 그리고 **현재 사용량 막대**(예: `10.8GB / 40GB`, 한도에 가까우면 빨강, 한도가 없으면 표시 안 함)를 어느 화면에 둘지.

### 3.6 UI

**게임 목록 → 풀영상 플레이어** 두 층으로 단순화한다.

- **게임 목록**: 지금 게임 행(순위·시각·초상화 3장·TK/K/A·결과표)을 유지하고, 클립 카드 격자 대신 **후보 수·저장한 클립 수·풀영상 용량**을 보여 준다.
- **풀영상 플레이어**:
  - 재생바에 후보 구간을 노랑으로 겹쳐 표시한다. **확실한 후보(킬·어시·사망)는 진하게, 나머지는 옅게** 칠한다.
  - 마커(킬·어시·사망 아이콘)를 정확한 시각에 찍는다.
  - 구간 양 끝을 끌어 범위를 조정한다. 참고로 첨부된 스팀 녹화 편집기 화면의 조작감(노란 선택 영역 + 양 끝 핸들)을 따른다.
  - 이전/다음 후보로 이동한다(진한 것만 / 전부).
  - 빈 곳을 드래그해 후보를 직접 추가한다.
  - **후보 목록**(플레이어 옆 또는 아래): 제목·길이·태그, 저장/무시 버튼, **일괄 저장**(전부 / 진한 것만 / 선택한 것).
- 태그 필터·라벨링은 후보 단위로 옮긴다.
- 저장된 클립은 F7 의 클립 정리 탭에서 본다. 그 전까지는 게임 목록에서 "저장한 클립" 으로 접근한다.

### 3.7 영상 파일(다시보기) 탭

- **스팀 녹화와 똑같이 게임 단위 풀영상을 만든다**(사용자 결정, 2026-09-29). 범위는 **캐릭터 선택 화면부터 결과 화면(로비로 나가기 직전)까지**다. 원본에서 `-c copy` 로 잘라 `games/` 아래에 저장한다.
- 그래서 원본 파일이 지워져도 게임별 풀영상은 남고, V7 "분석 후 원본 삭제"(`vod.deleteSourceAfter`)는 그대로 유효하다. 삭제 조건만 "클립 1개 이상"에서 **"게임 풀영상이 1개 이상 저장됨"**으로 바꾼다.
- 게임 경계는 이미 있는 다시보기 게임 나누기(`pipeline/vod_games.py`)를 쓰되, 앞끝을 캐릭터 선택 화면까지·뒤끝을 결과 화면까지로 넓히는지 확인한다(§7).
- 스팀 녹화의 풀영상 범위도 같은 기준(캐릭터 선택~결과 화면)에 맞춘다.

## 4. 단계별 작업

| 단계 | 내용 | 커밋 단위 |
|---|---|---|
| F1 | `games/` 저장 구조, `process_match` 풀영상 컷(클립보다 먼저), `game.json` 기록, `clip.saveMode`. 순수 로직(구간·후보·마커 직렬화, 저장 순서, 실패 시 대체)은 TDD | 백엔드만 |
| F2 | 여유 공간 계산·경고 기준(순수 로직 TDD), 첫 실행 화면 단계 추가, 트레이 알림·배너 | 백엔드 → 프론트 따로 |
| F3 | `retention` 대상 전환(풀영상), 기존 클립 제외, 삭제 예정 표시 연결 | 백엔드 → 프론트 따로 |
| F4 | 게임 API(`GET /api/games`, `/api/games/{key}`, 풀영상 스트리밍, 후보 수정·저장·일괄 저장), 플레이어 UI | API 와 UI 따로. UI 는 기능별로 잘게 |
| F5 | 카드 뷰 컴포넌트 제거 | **단독 커밋** |
| F6 | 다시보기 탭 | |
| F7 | 클립 정리 탭 | 논의 후 |

- 기존 클립은 그대로 "저장된 클립"이 된다. 자동 정리 대상에서 빠진다는 점을 업데이트 안내(패치노트)에 쓴다.
- 서버 전송(라벨, D10)은 지금 클립 단위다. 후보 단위 라벨로 바뀌면 전송 계약(`receiver.schema.json`)도 바뀌어야 한다. F4 이후 따로 다룬다.

## 5. UI 커밋 원칙 — 되돌릴 수 있게

- **백엔드 변경과 UI 변경을 한 커밋에 섞지 않는다.** API 는 새 경로로 추가하고, 기존 클립 API 는 F5 전까지 지우지 않는다.
- 새 화면은 **새 컴포넌트로 만든다**(기존 `ClipBrowser`·`GameSection`·`ClipCard` 를 고쳐 쓰지 않는다). 기본 화면을 새 것으로 바꾸는 것은 **작은 커밋 하나**로 한다. 그러면 그 커밋만 되돌려서 옛 화면으로 돌아갈 수 있다.
- 옛 화면 코드 삭제(F5)는 피드백을 받은 뒤 **단독 커밋**으로 한다.
- 커밋마다 `npm run build` 로 `frontend/dist` 를 갱신한다(CLAUDE.md).

## 6. 결정 사항 (F0)

모두 확정했다(2026-09-29, 사용자).

1. **풀영상 자동 정리 기본 한도: 용량 40GB**(1등 판 약 8개, 평균 10~13개). 첫 실행 권장 여유 공간 50~100GB 와 맞춘 값이다.
2. **`clip.saveMode` 기본값: `auto`**(기존 방식 유지). 자동 정리 대상이 아닌 클립이 쌓인다는 점은 옵션 화면·부족 알림에서 안내한다.
3. **삭제 직전 보존은 옵션**(`retention.preserveBeforeDelete`, 기본 꺼짐).
4. **다시보기도 게임 단위 풀영상으로 나눠 저장하므로 V7 은 그대로 유효하다**(§3.7).

## 7. 확인 필요 (구현 중 실측)

- 25분 경기 풀영상 `-c copy` 컷에 걸리는 시간과 디스크 쓰기 부하. 게임 중에 돌 수 있으므로 프레임 저하가 있는지 본다([plan.md §4](plan.md) 게임 중 분석 부하와 같이).
- 링버퍼 여유가 적을 때(§7.2.1 구출 정책) 풀영상 컷이 클립 컷보다 먼저여야 하는지, 둘 다 가능한지.
- 게임 경계: 캐릭터 선택 화면 시작과 결과 화면 끝(로비로 나가기 직전)을 스팀 녹화(`Player.log` 경계)와 다시보기(화면 판독 경계) 각각에서 어떻게 잡는지.
- 브라우저 플레이어에서 5GB HEVC 파일 탐색(seek) 반응 속도. 프록시(H.264) 폴백에서 풀영상 전체를 변환하는 비용.
- 과거 녹화 분석에서 이미 클립을 만든 옛 게임의 풀영상 소급: 원본 세그먼트가 링버퍼에 없으면 건너뛰고 알린다.
- 풀영상 폴더가 클립 폴더와 다른 드라이브일 때의 복사 시간.
