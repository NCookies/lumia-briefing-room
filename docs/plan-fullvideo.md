# 풀영상 중심 구조 전환 계획

> 현재 동작(클립 중심)은 [spec/pipeline.md](spec/pipeline.md)·[spec/ui.md](spec/ui.md). 옛 "풀 영상 탭(보조 뷰, 기본 꺼짐)" 계획을 **대체한다**.
> 결정 배경: 2026-09-29 대화. 이 게임은 야생동물 사냥에도 궁극기를 쓰는 등 변수가 많아 교전만 100% 골라내는 것은 원리상 어렵다고 판단했다. 그래서 목표를 "자동으로 완벽히 자르기"에서 **"게임 전체 영상 위에서 교전 후보를 빨리 찾고 쉽게 고쳐 저장하기"**로 바꾼다. 결정(§1·§6)은 확정됐고 구현은 아직이다.
> 단계를 끝내면 결론을 spec 에 옮기고 이 문서에서 지운다. 전부 끝나면 이 문서를 없앤다.

## 0. 진행 상태 (세션이 끊겨도 여기부터 이어간다)

- [ ] F3 — 자동 정리(프론트): 삭제 예정 배지·필터·사용량 막대를 새 게임 목록(F4)에 연결 (백엔드·옵션 문구는 끝)
- [ ] **F4-b — 플레이어 개정(§3.6-b, 2026-09-30 사용자 피드백)**: 스팀 녹화 편집기식 재생 막대 하나(노란 구간이 막대 위에, 재생 위치도 그 막대에서), 후보 목록은 오른쪽 패널, 별도 탭 대신 "스팀 녹화" 탭 안에서 게임 목록 → 풀영상. 기본 화면 전환은 작은 커밋 하나
- [ ] F4 — 나머지: 후보 라벨·태그 필터 UI. (게임 API·일괄 저장은 끝)
- [ ] F5 — 기존 카드 뷰 제거 (피드백 확인 후, 단독 커밋)
- [ ] F6 — 영상 파일(다시보기) 탭: 게임 단위 풀영상으로 나눠 저장
- [ ] F7 — 클립 정리 탭: 클립 폴더를 실제 폴더 그대로 보여 주는 탐색 화면 (§3.9)

## 1. 결정 사항 (사용자, 2026-09-29)

1. **풀영상 방식으로 통일한다.** 처리한 모든 스팀 녹화 게임의 전체 영상을 저장한다. 기존 계획의 `fullVideo.enabled`(기본 꺼짐) 스위치는 없앤다.
2. **보기 방식은 풀영상 하나로 통일한다.** 카드 뷰와 풀영상을 둘 다 두는 안은 화면이 난잡해져 버렸다. 다만 **UI 변경은 피드백에 따라 되돌릴 수 있게 커밋한다** (§5).
3. **풀영상 위에 클립 후보 목록을 보여 주고, 후보마다 저장, 그리고 일괄 저장을 제공한다.**
4. **분석이 끝났을 때 클립을 자동으로 저장할지(기존 방식), 사용자가 직접 저장할지를 옵션으로 고른다.**
5. **클립은 자동 정리 대상이 아니다.** 저장된 클립은 사용자가 따로 남기겠다고 고른 것이기 때문이다(자동 저장을 고른 경우도 사용자의 선택으로 본다). 자동 정리는 풀영상만 대상으로 한다.
6. **첫 실행 화면에서 50~100GB 여유 공간이 필요하다는 것을 읽지 않을 수 없게 강조한다.** 공간이 부족할 것 같으면 **미리 알림**을 띄운다.
7. **영상 파일(다시보기)도 게임 단위 풀영상으로 나눠 저장한다** — 범위는 캐릭터 선택 화면부터 결과 화면(로비로 나가기 직전)까지. 그래서 V7 "분석 후 원본 삭제"는 그대로 유효하다(§3.7).
8. **클립을 편하게 정리하는 탭을 따로 둔다**(2026-09-30 확정, §3.9). **실제 폴더**로 정리한다 — 앱에 종속시키지 않는다. **분류(캐릭터별 등)는 앱이 하지 않고** 사용자가 폴더를 만들어 한다. 앱은 폴더를 다루는 인터페이스만 준다.

## 2. 용량 (실측 비트레이트 기준)

기존 클립 32개(34.9분, 6.65GB)로 잰 스팀 녹화 비트레이트는 **약 25.5Mbps, 분당 약 190MB** 다(2560x1440, 2026-09-29).

| 게임 | 길이(시작 전 대기·로딩 포함, 추정) | 풀영상 | 클립 자동 저장 시(+1.5~2GB, 사용자 경험치) |
|---|---|---|---|
| 1등 판 | 22~27분 | 4.2~5.2GB | 5.7~7.2GB |
| 중간 순위 | 15분 | 약 2.9GB | 4.4~4.9GB |
| 일찍 탈락 | 8~10분 | 1.5~1.9GB | 3~3.9GB |

- 참고로 스팀 백그라운드 녹화 2시간 버퍼(README 권장)가 이미 약 23GB 를 쓴다.
- 해상도·스팀 녹화 품질 설정에 따라 비트레이트가 다르다. 계산에는 **실제 풀영상 파일 크기의 이동 평균**을 쓰고, 기록이 없을 때만 190MB/분을 쓴다.

## 3. 설계

### 3.1~3.3 저장 구조·파이프라인·클립 저장 옵션

구현됐다([spec/pipeline.md §11](spec/pipeline.md)). 남은 것:

- `game.json` 의 `userCandidates[]`·`candidates[].user`(범위 조정·무시·라벨)는 자리만 있고 쓰는 곳이 없다(F4).
- 클립 저장(수동)은 **풀영상에서 자른다**(원본 세그먼트가 지워졌을 수 있다) — 후보 범위 그대로 `-c copy`, 키프레임 3초 격자(F4).
- `retention.preserveBeforeDelete`(기본 꺼짐, 삭제 직전 확실한 후보를 클립으로 남김)는 F3.
- 과거 녹화 분석(백필)의 옛 게임 풀영상 소급은 §7.
- 결과 화면·초상화는 클립 쪽 폴더(`.thumbs`)에도 그대로 두고 게임 폴더에 사본을 둔다. 카드 뷰를 지우는 F5 때 사본만 남긴다.

### 3.4 디스크 공간

**첫 실행 화면.** 여유 공간 안내는 별도 단계의 경고 상자로 둔다.

- 큰 글씨로 "게임 하나에 2~5GB 가 저장됩니다. **50~100GB 여유 공간을 확보하고 사용하세요.**"
- 저장 폴더가 있는 드라이브의 **현재 여유 공간을 그 자리에서 보여 준다**. 50GB 미만이면 빨간색으로 표시한다.
- **"확인했습니다" 체크박스를 켜야 `시작하기` 가 눌린다.**

**부족 예상 알림·공간이 모자랄 때.** 구현됐다([spec/pipeline.md §12](spec/pipeline.md), [spec/ui.md](spec/ui.md)). 경고 기준은 초안(`max(예상 게임 용량 × 5, paths.minFreeGb)`)대로 두고 쓰면서 조정한다(§6-8).

### 3.5 자동 정리 (`retention.*`)

풀영상만 대상으로 바꾸는 백엔드는 구현됐다([spec/pipeline.md §9](spec/pipeline.md)). 남은 것:

- **스팀 녹화·영상 파일 풀영상은 기준 하나(합산 40GB)로 관리한다**(2026-09-30 확정, §6-5). 지금은 스팀 게임(`paths.games`)만 대상이고, 영상 파일 게임은 F6 에서 같은 폴더에 풀영상을 만들면 자동으로 합산된다.
- 게임 목록의 삭제 예정 배지·고정 버튼은 붙였다. **"삭제 예정" 필터**는 아직 없다.
- **현재 사용량 막대**(예: `10.8GB / 40GB`, 한도에 가까우면 빨강, 한도가 없으면 표시 안 함)는 **게임 목록 위 "게임 N개" 줄 옆**에 둔다(2026-09-30 확정, §6-6).
- 옛 클립 카드의 삭제 예정 배지·필터는 키가 안 맞아 비어 있다 — F5 에서 코드와 함께 지운다.

### 3.6 UI

**게임 목록 → 풀영상 플레이어** 두 층으로 단순화한다. 게임 목록은 지금 게임 행(순위·시각·초상화 3장·TK/K/A·결과표, 날짜 머리줄)을 유지하고 클립 카드 격자 대신 **후보 수·저장한 클립 수·풀영상 용량**을 보여 준다. 저장된 클립은 F7 클립 정리 탭에서 본다.

#### 3.6-b 플레이어 개정 (F4-b, 2026-09-30 사용자 피드백)

첫 구현(`GamePlayer.tsx`, 커밋 `24c3837`)을 써 본 피드백: **직관적이지 않고 불편하다, 영상이 작다.** 원인은 브라우저 재생기의 한계가 아니라 조작 설계였다.

- 기본 재생 막대(`<video controls>`)와 후보 막대가 따로 있어 **재생 막대가 두 개**다.
- 후보 막대 한 곳에서 이동과 편집을 같이 받는다. 노란 구간을 누르면 누른 자리가 아니라 구간 시작점으로 가거나(선택 전), 구간 통째 옮기기가 시작되고(선택 후), 빈 곳을 누르면 새 구간 만들기가 시작된다. 그래서 노란 구간 안으로는 재생 위치를 옮길 수 없다.
- 후보 목록이 영상 아래에 있어 영상이 `55vh` 로 작다.

사용자가 원한 모습은 **스팀 녹화 편집기의 타임라인**이다(스크린샷: 얇은 파란 재생 막대 위에 노란 구간이 얹히고, 구간 양 끝은 노란 점선 세로선, 재생 위치 표시(흰 핀)는 막대 어디서나 움직인다). 비슷한 앱(유튜브 챕터, Medal·Outplayed, 스팀 편집기, 영상 편집기)의 공통점은 **"누르면 이동"과 "편집"을 한 동작에 겹치지 않는 것**이다.

**위치.** 별도 "게임(풀영상)" 탭을 없애고 **"스팀 녹화" 탭 안에서** 게임 목록 → 게임을 누르면 풀영상 화면(← 게임 목록으로 돌아가기)으로 간다. 이 전환은 작은 커밋 하나로 한다(§5, 되돌릴 수 있게). 옛 카드 뷰 코드는 F5 까지 남긴다.

**배치.** 영상 + **오른쪽 후보 목록 패널**(고정 폭, 세로 스크롤). 영상 아래에는 재생 막대와 컨트롤만 둔다. 영상 높이는 화면 높이에서 헤더·컨트롤을 뺀 만큼 최대로 쓴다.

**재생 막대 — 하나만.**
- 기본 컨트롤을 끄고(`controls` 제거) 직접 만든다: 재생/일시정지, 10초 뒤로/앞으로, 이전/다음 후보, 현재 시각/전체 길이, 볼륨, 전체화면(영상과 막대를 담은 영역 전체를 전체화면으로 — 막대가 같이 보이게).
- 막대 모양은 스팀 편집기처럼: 얇은 파란 막대 + 눈금, 그 위에 후보 구간(확실한 후보는 진한 노랑, 나머지는 옅은 노랑) + 양 끝 노란 점선 세로선, 킬·어시·사망 마커는 막대 아래 작은 눈금, 재생 위치는 흰 핀 + 세로선.
- **막대 어디를 누르거나 끌어도 재생 위치만 움직인다 — 노란 구간 안도 같다.** 노란 구간을 누르면 그 자리로 가면서 그 후보가 선택된다(목록에서도 강조).
- 마우스를 올리면 그 위치 시각과 후보 제목을 띄운다.

**편집 — 손잡이와 버튼으로만.**
- 선택된 후보에만 양 끝 손잡이가 나온다. 잡기 쉽게 막대보다 크게(위로 튀어나오게) 둔다. 손잡이를 끌 때만 범위가 바뀐다.
- **구간 통째로 옮기기와 빈 곳 끌어서 만들기는 없앤다**(이동과 부딪힌다).
- 스팀 편집기 버튼처럼 **"시작점을 현재 위치로" / "끝점을 현재 위치로"**(단축키 `I`/`O`), **되돌리기**, **확대**(선택한 후보 앞뒤 30초만 막대 전체 폭으로 — 25분 영상은 막대 1px 이 약 1초라 세밀한 조정이 안 된다).
- 새 구간은 **"+ 여기서 구간 추가"**(현재 위치 앞뒤 10초로 만들고 손잡이·`I`/`O` 로 다듬는다).

**오른쪽 후보 목록.**
- 맨 위: 저장 대기 개수, 일괄 저장(전부 / 확실한 것만 / 선택한 것), 무시한 후보 보기.
- 행: 체크박스, 제목, 시각·길이, 확실·태그, 저장/무시(사용자 구간은 삭제). 누르면 그 후보 시작으로 이동·선택.
- 재생 위치가 들어가 있는 후보를 강조하고 목록이 따라 스크롤한다.

**단축키.** Space 재생/일시정지, ←/→ 5초(기존 클립 플레이어와 같게), `N`/`P` 다음/이전 후보, `S` 선택 후보 저장, `D` 무시, `I`/`O` 시작·끝점.

**TDD 대상(순수 로직).** 막대 좌표 ↔ 시각(확대 상태 포함), 누른 위치의 후보 찾기, 확대 범위 계산, `I`/`O` 적용 규칙(시작 > 끝이 되지 않게, 최소 길이), 현재 위치가 든 후보. 화면은 새 컴포넌트로 만들고 Playwright 로 "노란 구간 안을 눌러 그 자리로 이동", "손잡이로 범위 변경", "목록이 오른쪽에 있고 영상이 커졌다"를 확인한다.

### 3.7 영상 파일(다시보기) 탭

- **스팀 녹화와 똑같이 게임 단위 풀영상을 만든다**(사용자 결정, 2026-09-29). 범위는 **캐릭터 선택 화면부터 결과 화면(로비로 나가기 직전)까지**다. 원본에서 `-c copy` 로 잘라 `games/` 아래에 저장한다.
- 그래서 원본 파일이 지워져도 게임별 풀영상은 남고, V7 "분석 후 원본 삭제"(`vod.deleteSourceAfter`)는 그대로 유효하다. 삭제 조건만 "클립 1개 이상"에서 **"게임 풀영상이 1개 이상 저장됨"**으로 바꾼다.
- 게임 경계는 이미 있는 다시보기 게임 나누기(`pipeline/vod_games.py`)를 쓰되, 앞끝을 캐릭터 선택 화면까지·뒤끝을 결과 화면까지로 넓히는지 확인한다(§7).
- 스팀 녹화의 풀영상 범위도 같은 기준(캐릭터 선택~결과 화면)에 맞춘다.

### 3.8 게임 경계 — 불필요한 장면을 풀영상에 넣지 않는다

풀영상 범위는 **캐릭터 선택 화면 시작 ~ 결과 화면 끝(로비로 나가기 직전)** 이다. 매칭 대기 로비, 닷지로 끝난 캐릭터 선택, 연습 모드는 넣지 않는다.

로그가 있는 게임(감시)의 경계는 구현됐다([spec/game.md §3](spec/game.md)). 로그 흐름과 화면의 대응은 아래와 같다: 캐릭터 선택(`MatchingComplete`) → 루트 선택 → "잠시 후 실험이 시작됩니다" → 로딩(`[LOADING][GAME]`, 약 80초 뒤) → 본게임 → 결과 화면 → `나가기`(`[LOADING][LOBBY]`). **닷지 표본은 아직 없다** — 닷지는 캐릭터 선택 뒤 `[LOADING][GAME]` 없이 로비로 돌아가는 경우다.

**경계 규칙 (남은 구현: 화면).** 선택 화면 판독기와 시작 확장·닷지 제외(`split_games` 의 `select_start`)는 구현됐다([spec/game.md §7](spec/game.md)). 남은 것:

- 끝은 결과 화면의 마지막 프레임이다(`vod_result.scan_game_end`·`find_result_after` 가 이미 찾는 화면). 결과 화면을 못 찾으면 지금처럼 마지막 인게임 프레임에 여유를 붙인다.
- 코발트 프로토콜도 같은 흐름인지(캐릭터 선택 → 로딩)는 표본으로 확인한다(§7).

### 3.9 클립 정리 탭 (F7)

- **원칙: 앱에서 보든 탐색기에서 보든 클립이 똑같이 보여야 한다**(사용자, 2026-09-30). 그래서 클립 폴더에는 **영상 파일만** 두고, 클립 폴더 안의 영상 파일이면 정보 파일이 없어도 클립으로 본다. 써 봐야 체감할 수 있는 부분이라 아래 추천안으로 먼저 해 본다.
- **클립 저장 폴더(`paths.clips`)를 실제 폴더 구조 그대로 보여 준다.** 위치 표시(경로 조각), 하위 폴더 목록, 그 폴더의 클립.
- **앱은 분류하지 않는다.** 캐릭터별·날짜별 모음은 사용자가 폴더를 만들어 한다.
- **기본 동작은 다 넣는다**: 새 폴더, 이름 바꾸기(폴더·클립), 이동(폴더 고르기 창·끌어다 놓기), 삭제(폴더·클립, 기존 삭제 확인 창 — Windows 휴지통/영구 삭제), 여러 개 선택해 일괄 이동·삭제·내보내기, 탐색기에서 열기.
- **클립 저장은 Windows 저장 창으로 한다.** 기본 위치는 클립 폴더(또는 마지막으로 저장한 폴더)이고, 사용자는 그 창에서 새 폴더를 만들어 바로 분류할 수 있다. 클립 폴더 바깥에 저장하면 그냥 내보내기로 본다(정리 탭에 안 보인다).
- **자동 저장(`clip.saveMode = auto`)은 클립 폴더 맨 위에 저장한다.** 자동 분류(날짜별 하위 폴더 등)는 넣지 않고, 쓰다가 필요하면 다시 정한다(사용자 미정, 2026-09-30).
- **클립 인식 — 영상 파일이 기준이다.**
  - 지금은 `.json` 이 기준이라(`api/clips.py::scan_clips`, `glob("*.json")`, 비재귀) mp4 만 옮기면 클립이 사라진다. 이것을 **클립 폴더 아래(하위 폴더 포함) 영상 파일 전부**로 바꾼다.
  - **앱 전용 데이터는 클립 폴더 밖으로 옮긴다**: 클립 정보(json), 썸네일(`.thumbs`), 재생용 영상(`.proxy`), 라벨 보관(`.labels`), 게임 기록(`.games`), 작업 폴더(`.staging`) → 앱 데이터 폴더(`%LOCALAPPDATA%\LumiaBriefingRoom\`). 클립 폴더에는 영상만 남는다.
  - **영상 파일 안에 클립 ID 를 넣는다.** 클립을 자를 때 mp4 메타데이터 태그에 `clipUid` 를 쓴다(`-c copy` 그대로라 비용이 거의 없다). 탐색기에서 이름을 바꾸거나 다른 폴더로 옮겨도 태그로 같은 클립을 알아보고 정보(제목·태그·라벨·게임)를 다시 잇는다. 태그 읽기는 경로·크기·수정 시각으로 캐시한다.
  - **앱이 만들지 않은 영상**(태그 없음, OBS 녹화 등)도 보여 준다. 제목은 파일 이름, 길이는 영상에서 읽고, 썸네일은 처음 볼 때 만들어 캐시한다. 게임 정보·태그는 없다.
  - 파일을 복사해 같은 ID 가 둘이 되면 둘 다 보여 주고 정보는 같이 쓴다.
  - **기존 클립 이전**: json·썸네일은 앱 데이터 폴더로 옮기고, 기존 mp4 는 다시 쓰지 않는다(클립당 수 초의 디스크 쓰기라 부담). 처음 한 번만 파일 이름으로 이어 주고, ID 태그는 새 클립부터 넣는다.
  - 앱 데이터 폴더가 지워지면(재설치 등) 영상은 남고 정보만 사라진다 — 영상 안의 ID 가 남으므로 정보 백업이 있으면 되살릴 수 있다.
  - 다시보기(영상 파일) 탭 클립도 같은 방식으로 맞춘다.
- 사용자가 **탐색기에서 직접 옮기는 것도 정상 사용**이다. 탭을 열 때·새로고침할 때 다시 읽는다.
- 대안으로 검토했으나 채택하지 않은 것: 앱 전용 파일을 클립 폴더에 두고 Windows 숨김 속성만 거는 안. 구현은 작지만 mp4 만 옮기면 정보가 끊기는 문제가 그대로다.

## 5. UI 커밋 원칙 — 되돌릴 수 있게

- **백엔드 변경과 UI 변경을 한 커밋에 섞지 않는다.** API 는 새 경로로 추가하고, 기존 클립 API 는 F5 전까지 지우지 않는다.
- 새 화면은 **새 컴포넌트로 만든다**(기존 `ClipBrowser`·`GameSection`·`ClipCard` 를 고쳐 쓰지 않는다). 기본 화면을 새 것으로 바꾸는 것은 **작은 커밋 하나**로 한다. 그러면 그 커밋만 되돌려서 옛 화면으로 돌아갈 수 있다.
- 옛 화면 코드 삭제(F5)는 피드백을 받은 뒤 **단독 커밋**으로 한다.
- 커밋마다 `npm run build` 로 `frontend/dist` 를 갱신한다(CLAUDE.md).

## 6. 결정 사항 (F0)

모두 확정했다(2026-09-29, 사용자).

1. **풀영상 자동 정리 기본 한도: 용량 40GB**(1등 판 약 8개, 평균 10~13개). 첫 실행 권장 여유 공간 50~100GB 와 맞춘 값이다.
2. **`clip.saveMode` 기본값: `auto`**(기존 방식 유지). 자동 정리 대상이 아닌 클립이 쌓인다는 점은 옵션 화면·부족 알림에서 안내한다.
3. **삭제 직전 보존은 옵션**(`retention.preserveBeforeDelete`, 기본 꺼짐).
4. **다시보기도 게임 단위 풀영상으로 나눠 저장하므로 V7 은 그대로 유효하다**(§3.7).
5. **풀영상 자동 정리 기준은 스팀 녹화·영상 파일 합산 하나**(2026-09-30).
6. **용량 막대는 게임 목록 위 "게임 N개" 줄 옆**(2026-09-30).
7. **사용자 설정 게임은 풀영상·클립 대상에 넣는다. 연습 모드만 뺀다**(2026-09-30).
8. 공간 부족 경고 기준(§3.4 초안: 여유 공간 < 예상 게임 용량 × 5)은 초안대로 구현하고 쓰면서 조정한다.

## 7. 확인 필요 (구현 중 실측)

- 25분 경기 풀영상 `-c copy` 컷에 걸리는 시간과 디스크 쓰기 부하. 게임 중에 돌 수 있으므로 프레임 저하가 있는지 본다([plan.md §4](plan.md) 게임 중 분석 부하와 같이).
- 링버퍼 여유가 적을 때(§7.2.1 구출 정책) 풀영상 컷이 클립 컷보다 먼저여야 하는지, 둘 다 가능한지.
- 게임 경계(§3.8): **닷지 표본** — 로그 경계는 "닷지 = 캐릭터 선택 뒤 `[LOADING][GAME]` 없이 `StartMatching` 이 다시 찍힘"이라는 가정으로 구현했다(표본 없음). 닷지했을 때 `Player.log` 에 어떤 줄이 남는지(취소 알림 줄이 따로 있는지), 화면이 선택 화면에서 바로 로비로 가는지. 사용자 설정 게임의 로그 모양. 코발트 프로토콜의 선택 화면 흐름. 스트리머 다시보기에서 선택 화면이 방송 화면 전환으로 가려지는 경우.
- 브라우저 플레이어에서 5GB HEVC 파일 탐색(seek) 반응 속도. 프록시(H.264) 폴백에서 풀영상 전체를 변환하는 비용.
- 과거 녹화 분석에서 이미 클립을 만든 옛 게임의 풀영상 소급: 원본 세그먼트가 링버퍼에 없으면 건너뛰고 알린다.
- 풀영상 폴더가 클립 폴더와 다른 드라이브일 때의 복사 시간.
