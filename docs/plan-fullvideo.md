# 풀영상 중심 구조 전환 계획

> 현재 동작(클립 중심)은 [spec/pipeline.md](spec/pipeline.md)·[spec/ui.md](spec/ui.md). 옛 "풀 영상 탭(보조 뷰, 기본 꺼짐)" 계획을 **대체한다**.
> 결정 배경: 2026-09-29 대화. 이 게임은 야생동물 사냥에도 궁극기를 쓰는 등 변수가 많아 교전만 100% 골라내는 것은 원리상 어렵다고 판단했다. 그래서 목표를 "자동으로 완벽히 자르기"에서 **"게임 전체 영상 위에서 교전 후보를 빨리 찾고 쉽게 고쳐 저장하기"**로 바꾼다. 결정(§1·§6)은 확정됐다. F1·F2·F4(대부분)·F6 은 구현돼 [spec/](spec/) 에 옮겼고, 아래 §0 이 남은 것 전부다(2026-09-30 대조).
> 단계를 끝내면 결론을 spec 에 옮기고 이 문서에서 지운다. 전부 끝나면 이 문서를 없앤다.

## 0. 진행 상태 (세션이 끊겨도 여기부터 이어간다)

- [ ] F4 — 나머지: 후보 라벨(교전/사냥)·태그 필터 UI. 후보 단위 라벨이 생기면 서버 전송 계약(`receiver.schema.json`)도 바꿔야 한다 — 라벨링을 다시 시작할 때 한다
- [ ] F5 — 기존 카드 뷰 제거 (피드백 확인 후, 단독 커밋)
- [ ] F7 — 남은 것: 새 클립 탭(§3.9 — 보관한 클립만, 왼쪽 카테고리 목록·`자동 보관` 맨 아래 흐리게, 게임 정보 중심 카드, 체크박스는 "선택" 모드에서만). 폴더 이름 영어화·이전, 카테고리 API, 보관 위치 팝업, 저장/보관 문구는 구현됨([spec/](spec/))
- [ ] F9 — 안내 가이드: 풀영상·클립·자동 정리가 무엇인지 처음 쓰는 사람이 알 수 있게 (§3.11)
- [ ] F10 — 남은 것: 스팀 녹화 탭 게임 행 `⋯` 메뉴의 `다시 분석`(기존 `POST /api/games/reprocess` 는 옛 클립 기준이라 풀영상 구조에서의 의미를 정해야 한다 — 사용자에게 확인 필요) (§3.12)
- [ ] F11 — 클립 메모: 좋았던 점·아쉬웠던 점을 적는 개인 메모 (§3.13)

## 1. 결정 사항 (사용자, 2026-09-29)

1. **풀영상 방식으로 통일한다.** 처리한 모든 스팀 녹화 게임의 전체 영상을 저장한다. 기존 계획의 `fullVideo.enabled`(기본 꺼짐) 스위치는 없앤다.
2. **보기 방식은 풀영상 하나로 통일한다.** 카드 뷰와 풀영상을 둘 다 두는 안은 화면이 난잡해져 버렸다. 다만 **UI 변경은 피드백에 따라 되돌릴 수 있게 커밋한다** (§5).
3. **풀영상 위에 클립 후보 목록을 보여 주고, 후보마다 저장, 그리고 일괄 저장을 제공한다.**
4. **분석이 끝났을 때 클립을 자동으로 저장할지(기존 방식), 사용자가 직접 저장할지를 옵션으로 고른다.**
5. **클립은 자동 정리 대상이 아니다.** 저장된 클립은 사용자가 따로 남기겠다고 고른 것이기 때문이다(자동 저장을 고른 경우도 사용자의 선택으로 본다). 자동 정리는 풀영상만 대상으로 한다.
6. **첫 실행 화면에서 50~100GB 여유 공간이 필요하다는 것을 읽지 않을 수 없게 강조한다.** 공간이 부족할 것 같으면 **미리 알림**을 띄운다.
7. **영상 파일(다시보기)도 게임 단위 풀영상으로 나눠 저장한다**(구현됨, [spec/vod.md](spec/vod.md)) — 범위는 캐릭터 선택 화면부터 결과 화면까지.
8. **클립은 "보관"한 것을 카테고리별로 모아 보는 곳이다**(2026-09-30 재설계, §3.9). 카테고리는 **실제 폴더**다(A안 — 앱에서 보든 탐색기에서 보든 같게, 한 클립은 한 카테고리). 분류(캐릭터별 등)는 앱이 하지 않고 사용자가 카테고리를 만들어 한다. 처음 설계한 탐색기식 정리 탭은 너무 난잡하다는 피드백으로 바꿨다.
9. **자동 저장 옵션(`clip.saveMode`)은 남기고, 앱이 만든 클립도 자동 정리하지 않는다**(2026-09-30, §1-5 유지). 대신 정리는 게임 행 `⋯` 메뉴로 사용자가 쉽게 한다(§3.12).

## 2. 용량 (실측 비트레이트 기준)

기존 클립 32개(34.9분, 6.65GB)로 잰 스팀 녹화 비트레이트는 **약 25.5Mbps, 분당 약 190MB** 다(2560x1440, 2026-09-29).

| 게임 | 길이(시작 전 대기·로딩 포함, 추정) | 풀영상 | 클립 자동 저장 시(+1.5~2GB, 사용자 경험치) |
|---|---|---|---|
| 1등 판 | 22~27분 | 4.2~5.2GB | 5.7~7.2GB |
| 중간 순위 | 15분 | 약 2.9GB | 4.4~4.9GB |
| 일찍 탈락 | 8~10분 | 1.5~1.9GB | 3~3.9GB |

- 참고로 스팀 백그라운드 녹화 2시간 버퍼(README 권장)가 이미 약 23GB 를 쓴다.
- 해상도·스팀 녹화 품질 설정에 따라 비트레이트가 다르다. 계산에는 **실제 풀영상 파일 크기의 이동 평균**을 쓰고, 기록이 없을 때만 190MB/분을 쓴다.

## 3. 설계

### 3.1~3.3 저장 구조·파이프라인·클립 저장 옵션

구현됐다([spec/pipeline.md §11](spec/pipeline.md), 옵션 화면·삭제 직전 보존은 [spec/ui.md §6](spec/ui.md)·[spec/pipeline.md §9](spec/pipeline.md)). 남은 것:

- 과거 녹화 분석(백필)의 옛 게임 풀영상 소급은 §7.

### 3.4 디스크 공간

첫 실행 경고 상자·부족 예상 알림·공간 부족 시 대체 동작은 구현됐다([spec/pipeline.md §12](spec/pipeline.md), [spec/ui.md](spec/ui.md)). 경고 기준은 초안(`max(예상 게임 용량 × 5, paths.minFreeGb)`)대로 두고 쓰면서 조정한다(§6-8). F8 에서 저장 폴더가 하나로 바뀌면 경고 문구·기준 드라이브를 그에 맞춘다(§3.10).

### 3.5 자동 정리 (`retention.*`)

풀영상만 대상으로 바꾸는 백엔드·게임 목록의 삭제 예정 배지·필터·용량 막대는 구현됐다([spec/pipeline.md §9](spec/pipeline.md), [spec/ui.md](spec/ui.md)). 남은 것:

- **스팀 녹화·영상 파일 풀영상은 기준 하나(합산 40GB)로 관리한다**(2026-09-30 확정, §6-5).
- 옛 클립 카드의 삭제 예정 배지·필터는 키가 안 맞아 비어 있다 — F5 에서 코드와 함께 지운다.

### 3.6 UI

**"스팀 녹화" 탭: 게임 목록 → 풀영상 플레이어**(구현됨, [spec/ui.md](spec/ui.md)) 두 층으로 단순화했다. 게임 목록은 지금 게임 행(순위·시각·초상화 3장·TK/K/A·결과표, 날짜 머리줄)을 유지하고 클립 카드 격자 대신 **후보 수·저장한 클립 수·풀영상 용량**을 보여 준다. 저장된 클립은 F7 클립 정리 탭에서 본다.

### 3.8 게임 경계 — 불필요한 장면을 풀영상에 넣지 않는다

풀영상 범위는 **캐릭터 선택 화면 시작 ~ 결과 화면 끝(로비로 나가기 직전)** 이다. 매칭 대기 로비, 닷지로 끝난 캐릭터 선택, 연습 모드는 넣지 않는다.

로그가 있는 게임(감시)의 경계는 구현됐다([spec/game.md §3](spec/game.md)). 로그 흐름과 화면의 대응은 아래와 같다: 캐릭터 선택(`MatchingComplete`) → 루트 선택 → "잠시 후 실험이 시작됩니다" → 로딩(`[LOADING][GAME]`, 약 80초 뒤) → 본게임 → 결과 화면 → `나가기`(`[LOADING][LOBBY]`). **닷지 표본은 아직 없다** — 닷지는 캐릭터 선택 뒤 `[LOADING][GAME]` 없이 로비로 돌아가는 경우다.

**경계 규칙 (남은 구현: 화면).** 선택 화면 판독기와 시작 확장·닷지 제외(`split_games` 의 `select_start`)는 구현됐다([spec/game.md §7](spec/game.md)). 남은 것:

- 끝은 결과 화면의 마지막 프레임이다(`vod_result.scan_game_end`·`find_result_after` 가 이미 찾는 화면). 결과 화면을 못 찾으면 지금처럼 마지막 인게임 프레임에 여유를 붙인다.
- 코발트 프로토콜도 같은 흐름인지(캐릭터 선택 → 로딩)는 표본으로 확인한다(§7).

### 3.9 클립 = 보관 + 카테고리 (F7, 2026-09-30 재설계)

탐색기식 정리 탭(구현됨, [spec/ui.md](spec/ui.md) "클립 정리 탭")은 자동 저장 클립 수십 개가 한 폴더에 쌓이고, 비슷한 썸네일·반복되는 제목·파일 이름·체크박스로 난잡하다는 피드백을 받았다. 유튜브 "저장 위치"(재생목록) 방식으로 바꾼다. 클립 인식(영상 파일 기준·`clipUid` 태그·지문·모르는 영상)과 폴더 API 는 그대로 쓴다([spec/pipeline.md §8](spec/pipeline.md)).

- **용어 — "저장"과 "보관"은 다른 기능이다**(사용자, 2026-09-30). 화면 문구·버튼·배지·단축키 설명에서 섞지 않는다.
  - **보관** = 후보를 클립(영상 파일)으로 만들어 카테고리에 남기는 것. 북마크 아이콘, "보관됨", "보관 해제", 클립 탭.
  - **저장** = 풀영상 화면에서 **이미 보관한 클립의 범위를 고친 뒤 그 클립에 반영하는 것**(다시 자르기). 지금의 `다시 저장`·`전부 저장 (N)`·"N개 저장 대기"가 이것이다. 보관하지 않은 후보의 범위 수정은 지금처럼 바로 기억되므로 저장 버튼이 필요 없다.
  - 그래서 지금 보관 안 한 후보에 붙은 `저장`(= 클립 만들기)과 `저장됨` 배지, 단축키 `S`, 게임 행·날짜 머리줄의 "저장한 클립 N", 옵션 "클립 저장 방식"의 문구는 "보관"으로 바꾼다. 자동 모드 이름도 `자동 보관`.
- **카테고리 = `clips\` 아래 실제 폴더**(A안, 사용자 결정). 한 클립은 한 카테고리에만 있다 — 여러 곳에 넣으려면 파일 복사(클립 하나 100~500MB)라 하지 않는다. 탐색기에서 폴더를 만들거나 옮겨도 그대로 보인다. 스팀 녹화/영상 파일로 클립 폴더를 나누지 않는다(§3.10).
- **기본 칸 `보관함`**(유튜브 "나중에 볼 동영상"처럼, 사용자 결정). 카테고리를 안 골라도 여기에 보관된다.
- **자동 보관 클립**(`clip.saveMode = auto`)은 **`자동 보관` 카테고리**에 따로 두고 클립 탭 카테고리 목록 맨 아래에 흐리게 보인다(사용자 결정). 자동 정리하지 않는다(§1-9). 사용자가 다른 카테고리로 옮기면 그냥 그 카테고리의 클립이다.
- **풀영상 화면의 `보관`**(북마크 아이콘) → "보관 위치" 팝업: 카테고리 목록(첫 클립 썸네일·개수) + `+ 새 카테고리`. 누르면 그 카테고리에 보관. 보관한 후보는 채워진 북마크가 되고, 다시 누르면 카테고리 바꾸기(파일 이동)·보관 해제(§3.12). **Windows 저장 창 안은 버린다.**
- **클립 탭은 보관한 클립만 보여 준다**(사용자 결정): 왼쪽 카테고리 목록, 오른쪽 그 카테고리의 클립. 카드에는 파일 이름 대신 게임 정보(날짜·순위·초상화)와 메모 유무(§3.13). 체크박스는 "선택" 모드에서만. 이름 바꾸기·이동·삭제·내보내기·탐색기에서 열기는 이 화면에 맞게 줄여 둔다.

- **두 칸의 폴더 이름은 한글 그대로 `clips\보관함`·`clips\자동 보관`**(2026-09-30 확정). 카테고리는 사용자가 이름을 붙이는 콘텐츠라 앱과 탐색기에 같은 이름으로 보이게 한다. 영어 이름은 앱이 관리하는 틀(`clips`·`full_video`·`steam_replay`·`vod`, §3.10)에만 쓴다.

### 3.10 저장 폴더 구조 (F8, 2026-09-30 사용자 결정)

**원칙 (2026-09-30 사용자 확인): 사용자가 위치를 정하는 것은 영상 파일(클립·풀영상)뿐이다. 정보는 전부 앱 기본 경로(`%LOCALAPPDATA%\LumiaBriefingRoom\`)에 둔다** — 작아서(클립당 수십 KB) 어디 둬도 부담이 없고, 영상이 어디로 옮겨지든 앱이 한 곳에서 읽는다.

| 종류 | 위치 | 비고 |
|---|---|---|
| 클립·풀영상(영상 파일) | 사용자가 정한 곳(아래 구조) | 큼 |
| 클립 정보·클립 썸네일·라벨 보관·영상 색인 | 앱 기본 경로 | 작음 |
| 게임 기록(`game.json`)·결과표·초상화 | **풀영상과 한 묶음으로 풀영상 폴더의 게임 폴더에 둔다**(2026-09-30 사용자 결정 — 앱이 관리하는 폴더라 사용자가 옮기지 않는다). 단점은 §7 | 작음 |
| 재생용 변환 영상(`.proxy`, H.264 사본) | **예외 — 영상 드라이브의 `<저장 폴더>\.cache\proxy`(숨김)** (2026-09-30 사용자 결정). 원본 클립만큼 커서 앱 경로(C:)에 두면 영상을 다른 드라이브로 옮긴 사람도 C: 가 찬다 | 큼·다시 만들 수 있음 |
| 작업용 임시(`.staging`) | **영상 결과물(클립·풀영상)의 임시는 그 결과물이 놓일 폴더의 드라이브** — 클립은 `<저장 폴더>\.staging`, 풀영상은 `<풀영상 폴더>\.staging`(풀영상 위치를 따로 둔 경우 그 드라이브). 같은 드라이브라야 `os.replace` 로 한 번에 바꿔치기되고, 다르면 수 GB 를 C: 에 만들었다가 다시 복사하게 된다. **정보 파일(json 등)의 임시만** 앱 경로(`library_*\.staging`) | 일시적 |

- **정보와 영상을 잇는 열쇠**: 클립은 사용자가 탐색기에서 옮기고 이름을 바꾸므로 경로로 잇지 않고 **영상 안의 `clipUid` 태그**로 잇는다(§3.9). 풀영상은 앱이 관리하고 사용자가 옮기지 않으므로 게임 키로 잇는다.
- 앱 기본 경로가 지워지면(재설치 등) 영상은 남고 정보만 사라진다(§3.9).


종류(스팀 녹화/영상 파일 × 클립/풀영상)가 늘어 처음 쓰는 사람이 헷갈린다. 경로 4개를 따로 고르게 하지 않고 **폴더 하나만 고르게 한다.**

```
<저장 폴더>\                  사용자가 고르는 것은 이것 하나 (기본 %USERPROFILE%\Videos\LumiaBriefingRoom)
  clips\                      사용자 것. 아래 폴더 하나 = 카테고리 하나(§3.9). 자동 정리 안 함
    보관함\  자동 보관\  (사용자가 만든 카테고리들)
  full_video\                 앱이 관리. 자동 정리 대상(합산 40GB)
    steam_replay\  vod```

- **폴더 이름을 영어로 바꾼다**(사용자, 2026-09-30 — 지금 구현된 `클립\`·`풀영상\`·`스팀 녹화\`·`영상 파일\` 은 직관적이지 않고 애매하다): `clips`, `full_video`, `steam_replay`, `vod`. 코드는 `config.py` 의 `CLIPS_FOLDER`·`FULL_VIDEOS_FOLDER`·`STEAM_FOLDER`·`VOD_FOLDER` 와 `library_routes.py`·`storage_migrate.py` 의 폴더 이름 비교. 클립은 스팀 녹화/영상 파일로 나누지 않으므로 `steam_replay`·`vod` 는 `full_video\` 아래에만 있고 클립 탭에는 보이지 않는다.
- **이미 새 구조를 쓰는 사용자 이전**: 앱 시작 때 옛 한글 폴더를 새 이름으로 바꾸고, `클립\스팀 녹화`·`클립\영상 파일` 의 클립은 `자동 보관` 으로 옮긴다(수동으로 저장한 것도 구분하지 않는다 — 사용자가 옮기면 된다). 옛 경로 모드 사용자는 "새 구조로 옮기기" 때 바로 새 이름으로 옮긴다.
- **풀영상 위치만 옵션 "고급"에서 따로 바꿀 수 있다**(한 판에 수 GB 라 큰 HDD 로 빼고 싶은 사람). 기본은 `<저장 폴더>ull_video`. 여유 공간 경고(§3.4)는 풀영상 폴더가 있는 드라이브 기준, 따로 두면 두 드라이브 모두 본다.
- 스팀이 녹화를 쓰는 폴더(`gamerecordings`)는 스팀이 관리하므로 그 안에 만들지 않는다.
- 첫 실행 화면의 저장 공간 경고(50~100GB)는 이 저장 폴더 하나를 기준으로 설명한다.
- **기존 설정 이전**: 지금은 클립·영상 파일 클립·풀영상 경로가 따로 있다(`paths.clips`·`paths.vodClips`·풀영상 경로). 기존 사용자는 이미 쓰던 경로를 그대로 인정하고(파일을 강제로 옮기지 않는다), 옵션에서 "새 구조로 옮기기"를 고를 수 있게 한다. 옮기기는 기존 클립 폴더 이동(`POST /api/clips-dir/move`)과 같은 방식(진행률, 충돌 시 거부). F7 의 "앱 전용 데이터를 앱 데이터 폴더로 이전"과 한 번에 한다.

### 3.10a F7·F8 이전 설계 (0단계 조사, 2026-09-30 — **사용자 승인됨**, `.staging`·`.proxy` 위치만 §3.10 표대로 고침)

**핵심 단순화: 지금의 "클립 폴더" 를 둘로 쪼갠다.** 코드의 `clips_dir` 는 사실 (a) 영상(mp4)을 두는 곳과 (b) 정보·썸네일·라벨·게임 기록·작업 폴더를 두는 곳을 한 덩어리로 가리킨다. (b) 전체를 **구조 그대로** `%LOCALAPPDATA%\LumiaBriefingRoom\library\{steam,vod}\` 로 옮긴다(`<id>.json`, `.thumbs\`, `.labels\`, `.games\`, 정보 파일 임시 `.staging\`, vod 는 `.vods\`. **`.proxy` 와 영상 결과물 임시는 제외** — §3.10 표: 영상 드라이브에 둔다). 그러면 json 안의 상대 경로(`.thumbs/…`)·`clip_assets`·라벨 보관·게임 기록 코드는 **그대로** 동작하고, 바뀌는 곳은 "mp4 를 어디서 찾나" 뿐이다(`meta_path.with_suffix(".mp4")` 류 약 15곳).

**(1)~(6) 경로 해석·앱 전용 정보 이전·읽는 코드 전환·저장 폴더 화면과 새 구조로 옮기기·클립 ID 태그·이음·모르는 영상·정리 탭 API/화면은 구현됐다**([spec/config.md](spec/config.md) `paths.*`, [spec/pipeline.md §8·§9](spec/pipeline.md), [spec/ui.md](spec/ui.md)). 남은 것은 §3.9 재설계다.

### 3.11 안내 가이드 (F9, 2026-09-30 사용자 요청)

처음 쓰는 사람이 "풀영상이 뭔지, 클립이 뭔지, 무엇이 자동으로 지워지는지"를 파악하기 어렵다. 짧은 그림 설명을 준다.

- **담을 내용**(각 1~2문장 + 작은 그림):
  1. **풀영상** — 게임 하나 전체(캐릭터 선택~결과 화면). 앱이 자동으로 만들고, 용량 한도(기본 40GB)를 넘으면 오래된 것부터 **자동으로 지워진다**. 고정하면 안 지워진다.
  2. **교전 후보** — 풀영상 재생 막대의 노란 구간. 앱이 찾은 "교전일 것 같은 곳". 진한 노랑 = 킬·어시·사망이 있는 확실한 것.
  3. **클립** — 후보 중 보관한 것(직접 보관 또는 자동 보관). **자동으로 지워지지 않는다**. `clips\` 아래 카테고리 폴더에 영상 파일로 있고 탐색기에서 마음대로 정리해도 된다. "보관"과 "저장"(고친 범위 반영)의 차이도 적는다(§3.9).
  4. **폴더 구조** — §3.10 그림 그대로.
  5. **스팀 녹화 / 영상 파일** — 스팀 백그라운드 녹화는 자동, 다른 영상은 직접 넣는다.
- **보여 주는 곳**: ① 첫 실행 화면 마지막 단계(건너뛸 수 있음) ② 머리줄의 `?` 버튼 → 같은 내용 모달 ③ 헷갈리는 자리의 짧은 도움말 `(?)`(자동 정리 옵션, 클립 보관 방식 옵션, 풀영상 위치 옵션, 게임 목록의 "풀영상 없음" 배지) — 기존 `HelpTip` 재사용.
- 문구는 기존 UI 어조(합니다체)와 용어("게임"·"클립"·"풀영상"·"교전 후보")를 따른다. 그림은 코드로 그린다(미디어 파일을 git 에 넣지 않는다).
- 순서: F8 폴더 구조가 정해진 뒤 문구를 확정한다(폴더 그림이 들어가므로).

### 3.12 게임 행 `⋯` 메뉴와 보관 해제 (F10, 2026-09-30 사용자 요청)

지금은 원하는 풀영상을 지울 수단이 없다(스팀 녹화 탭은 없음, 영상 파일 탭은 영상 묶음 "전체 삭제"뿐). 앱이 만든 클립도 자동 정리하지 않기로 했으므로(§1-9) 사용자가 쉽게 정리할 수 있어야 한다.

- **게임 행에 `⋯`(점 세 개) 메뉴**(두 탭 공통, 사용자 결정): `풀영상만 삭제` / `클립만 전체 삭제` / `풀영상과 클립 전체 삭제`, 스팀 녹화 탭은 `다시 분석` 도 넣는다(지금 새 게임 목록에는 없고 옛 카드 화면 `GameSection` 에만 있다). 영상 파일 탭의 다시 분석은 지금처럼 영상 묶음 머리에 둔다. 게임 행 단위 동작은 이 메뉴로 모은다.
  - 삭제는 기존 삭제 확인 창(`DeleteConfirmDialog`, 휴지통/영구)을 쓰고 무엇이 지워지는지(풀영상 크기·클립 N개) 적는다.
  - 풀영상만 지우면 행은 "풀영상 삭제됨"으로 남고 결과표·보관한 클립은 그대로. 클립 삭제는 클립 탭 삭제와 같은 처리(`clipUid` 로 찾아 지움, 라벨 보관·게임 기록 유지). 게임 기록은 `retention.keepGameRecords` 대로.
  - **고정한 게임**을 지울 때는 막지 않고 경고 창을 띄운다(사용자 결정 — "고정한 게임입니다" 한 줄을 확인 창에 더한다. `다시 묻지 않기` 를 켰어도 고정한 게임은 묻는다).
- **풀영상 화면의 보관 해제**: 보관한 후보의 북마크(§3.9) → `보관 해제` 는 클립 영상을 `clipUid` 로 찾아 지우고 **그 후보는 무시 처리**한다(사용자 결정 — 무시한 후보 보기에서 되살려 다시 보관할 수 있다).

### 3.13 클립 메모 (F11, 2026-09-30 사용자 요청)

클립마다 "어떤 점이 좋았다·아쉬웠다"를 적는 개인 메모.

- 라벨 메모(`labelNote`, 라벨링용·서버 전송 대상)와 **별개 필드**로 두고 서버로 보내지 않는다(로컬 전용 — 전송 분류표에 `excluded` 로 적는다).
- 쓰는 곳: 풀영상 화면의 보관한 후보, 클립 탭의 재생 화면. 클립 탭 카드에는 메모가 있다는 표시만.
- 정보는 클립 정보 파일(앱 데이터 `library`)에 두므로 탐색기에서 옮기거나 이름을 바꿔도 `clipUid` 로 이어진다.
- 길이 제한은 넉넉하게(예: 5,000자, 사용자 결정). 성능에 문제가 없으면 클립 탭 검색 대상에 넣는다(클립 수백 개 × 수 KB 는 메모리에서 거르면 충분할 것으로 본다 — 구현 때 확인).

## 5. UI 커밋 원칙 — 되돌릴 수 있게

- **백엔드 변경과 UI 변경을 한 커밋에 섞지 않는다.** API 는 새 경로로 추가하고, 기존 클립 API 는 F5 전까지 지우지 않는다.
- 새 화면은 **새 컴포넌트로 만든다**(기존 `ClipBrowser`·`GameSection`·`ClipCard` 를 고쳐 쓰지 않는다). 기본 화면을 새 것으로 바꾸는 것은 **작은 커밋 하나**로 한다. 그러면 그 커밋만 되돌려서 옛 화면으로 돌아갈 수 있다.
- 옛 화면 코드 삭제(F5)는 피드백을 받은 뒤 **단독 커밋**으로 한다.
- 커밋마다 `npm run build` 로 `frontend/dist` 를 갱신한다(CLAUDE.md).

## 6. 결정 사항 (F0)

모두 확정했다(2026-09-29, 사용자).

1. **풀영상 자동 정리 기본 한도: 용량 40GB**(1등 판 약 8개, 평균 10~13개). 첫 실행 권장 여유 공간 50~100GB 와 맞춘 값이다.
2. **`clip.saveMode` 기본값: `auto`**(기존 방식 유지). 자동 정리 대상이 아닌 클립이 쌓인다는 점은 옵션 화면·부족 알림에서 안내한다.
3. **삭제 직전 보존은 옵션**(`retention.preserveBeforeDelete`, 기본 꺼짐).
4. **다시보기도 게임 단위 풀영상으로 나눠 저장한다. V7 원본 삭제는 풀영상 기준**([spec/vod.md](spec/vod.md)).
5. **풀영상 자동 정리 기준은 스팀 녹화·영상 파일 합산 하나**(2026-09-30).
6. **용량 막대는 게임 목록 위 "게임 N개" 줄 옆**(2026-09-30).
7. **사용자 설정 게임은 풀영상·클립 대상에 넣는다. 연습 모드만 뺀다**(2026-09-30).
8. 공간 부족 경고 기준(§3.4 초안: 여유 공간 < 예상 게임 용량 × 5)은 초안대로 구현하고 쓰면서 조정한다.

## 7. 확인 필요 (구현 중 실측)

- **풀영상 폴더를 외장 드라이브에 두고 뽑으면 게임 목록이 안 보인다**(게임 기록 `game.json`·결과표·초상화가 풀영상과 한 묶음이라서, 2026-09-30 알려진 단점). 뽑혔을 때 "풀영상 드라이브를 찾을 수 없습니다" 안내를 줄지, 게임 기록만 앱 경로에 캐시할지는 쓰면서 본다. 드라이브가 없는 것을 "게임이 지워졌다"로 읽어 자동 정리·기록 삭제가 돌면 안 된다.
- 25분 경기 풀영상 `-c copy` 컷에 걸리는 시간과 디스크 쓰기 부하. 게임 중에 돌 수 있으므로 프레임 저하가 있는지 본다([plan.md §4](plan.md) 게임 중 분석 부하와 같이).
- 링버퍼 여유가 적을 때(§7.2.1 구출 정책) 풀영상 컷이 클립 컷보다 먼저여야 하는지, 둘 다 가능한지.
