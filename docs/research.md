### 1.3 파일명 규칙 (확정)

- 세션 폴더: `bg_<appid>_<YYYYMMDD>_<HHMMSS>` — **시각은 UTC**
- 클립 폴더: `clip_<appid>_<YYYYMMDD>_<HHMMSS>` — UTC
- 조각: `chunk-stream<0|1>-<5자리 zero-pad 번호>.m4s`, 번호는 **세션마다 1부터** 증가
- 기록 중인 조각에는 `.tmp` 가 붙는다. 스캔 시 반드시 제외할 것
- `stream0` = 영상, `stream1` = 음성

UTC라는 근거는 §3.4의 로그 교차검증에서 초 단위로 확정했다.

### 1.5 메타데이터 파일 — 어떤 필드가 시간 정보를 담는가

#### `session.mpd` — 여기가 핵심이다

녹화 **중**인 세션 (`type="dynamic"`):

```xml
<MPD type="dynamic"
     minimumUpdatePeriod="PT500S"
     suggestedPresentationDelay="PT3.0S"
     availabilityStartTime="2026-09-19T13:07:47Z"     ← ★ 세션 시작 절대시각 (UTC)
     publishTime="2026-09-19T14:55:29Z"
     timeShiftBufferDepth="PT2H0M0.0S"                ← ★ 링버퍼 길이
     maxSegmentDuration="PT3.0S">
  <Period id="0" start="PT0.0S">
    <AdaptationSet contentType="video" maxWidth="2560" maxHeight="1440">
      <Representation codecs="hev1.2.4.L123.B0" bandwidth="22000000" width="2560" height="1440">
        <SegmentTemplate timescale="1000000" duration="3000000"     ← ★ 3.000초
                         initialization="init-stream$RepresentationID$.m4s"
                         media="chunk-stream$RepresentationID$-$Number%05d$.m4s"
                         startNumber="1"/>            ← ★ 남아있는 가장 오래된 번호
```

녹화가 **끝난** 세션은 `type="static"` 으로 바뀌고 필드 구성이 달라진다.

```xml
<MPD type="static" mediaPresentationDuration="PT12M47.43S" maxSegmentDuration="PT3.0S">
  <Period id="0" start="PT3H16M6.0S">                 ← ★ (startNumber-1) × 3초
    ... <SegmentTemplate ... startNumber="3923"/>
```

- `availabilityStartTime`이 **없다.** 대신 폴더명의 UTC 시각이 세션 시작이고, `Period@start` 가 남아있는 첫 조각의 오프셋이다.
- 실측: `startNumber=3923` → `(3923-1)×3 = 11766초 = 3h16m06s` = `Period@start`. **정확히 일치.**

#### ★ 시간 매핑 공식 (확정)

```
세그먼트 N의 시작 시각(UTC)
  = 세션 시작(UTC) + (N - 1) × 3.000초

세션 시작(UTC)
  = session.mpd 의 availabilityStartTime        (녹화 중)
  = 폴더명 bg_<appid>_<YYYYMMDD>_<HHMMSS>       (종료 후. 녹화 중에도 동일한 값이다)
```

포맷 레벨에서도 확인했다. 2100번 조각을 병합하니 ffprobe `start_time = 6297.002454` 가 나왔고 `(2100-1)×3 = 6297` 이다.

#### `timelines\timeline_<appid><YYYYMMDD>_<HHMMSS>.json`

```json
{ "daterecorded": "1789794055", "starttime": "0", "endtime": "12549787" }
```

| 필드 | 의미 | 확인 |
|---|---|---|
| `daterecorded` | 세션 시작 **epoch 초** | 1789794055 = 2026-09-19 14:00:55 KST = **05:00:55 UTC** → 파일명 `_050055` 와 일치 |
| `starttime` / `endtime` | 세션 내 오프셋 **밀리초** | 12549787 ms = 3h29m |
| `entries[]` | 마커 목록 | 있는 것은 **`"type": "screenshot"` 뿐** |

- **킬/전투 마커는 없다.** SPEC §2.2(ER은 `ISteamTimeline` 미지원)가 실물로 재확인됐다.
- 타임라인 파일명 시각과 video 폴더 시각이 **다르다** (`050055` vs `050108`, 13초 차이). 두 개를 이름으로 매칭하면 안 된다.

#### `gamerecording.pb` / `clip.pb`

스키마 없이 protobuf wire format으로 해독했다 (`decode_pb.py`).

`gamerecording.pb` — 세션 레코드의 반복:

```
f1 { f1 str "timeline_104959020260216_055509"
     f2 varint 1049590          ← appid
     f3 varint 1771221309       ← 시작 epoch 초 (UTC)
     f4 varint 6182472 }        ← 길이 ms
```

`clip.pb`:

```
f1 { f1 "timeline_104959020260917_123530", f2 1049590, f3 1789648530, f4 21872(ms 오프셋)
     f5 { f1 "bg_1049590_20260917_123545"  ← ★ 원본 세션 폴더명
          f3 21872, f4 4, f10 14747 } }
f3 1789655894   f4 1049590   f7 "이터널 리턴 - 2026-09-18 오전 9:02:28"
f12 1920   f13 1080          ← ★ export 해상도
```

→ **스팀 export는 1080p로 다운스케일한다.** 우리는 export를 거치지 않고 원본 m4s를 쓰므로 1440p 원본을 그대로 얻는다.

### 1.6 ★ 링버퍼가 실시간으로 지운다 (SPEC에 없던 사실)

조사 도중 옛 세션의 조각이 눈앞에서 사라졌다.

| 시각 | `bg_..._050108` 의 가장 오래된 조각 | 영상 조각 수 |
|---|---|---|
| 23:54 | `03923` | 256 |
| 23:59 | `03997` | 183 |
| 00:04 | `04102` | 77 |

- 5분(=100 세그먼트) 동안 oldest가 105 전진. 새 세션이 쓰는 만큼 옛 세션이 앞에서 깎인다.
- 00:04 시점 보존량: 옛 세션 77 + 새 세션 2,329 = **2,406 세그먼트 = 7,218초 = 2h00m18s**.
- `timeShiftBufferDepth="PT2H0M0.0S"` 와 일치. **링버퍼는 세션 단위가 아니라 게임 단위로 합산되어 2시간에서 잘린다.**

매치 길이가 9~19분이고 버퍼가 2시간이므로 추출 여유는 충분하다. 다만 "세션 폴더가 있으니 조각도 있다"는 가정은 틀린다. **번호로 접근하기 전에 항상 존재를 확인해야 한다.** 조사 중 실제로 이것 때문에 첫 병합 시도가 실패했다.

## 2. m4s 조각 병합 가능성

### 2.1 방법과 결과

원본을 작업 폴더로 복사한 뒤(`merge_m4s.sh`) 단순 바이트 결합했다.

```bash
cat init-stream0.m4s chunk-stream0-02100.m4s ... chunk-stream0-02109.m4s > merged.mp4
```

**성공.** 10세그먼트(30초)를 완전 디코딩했다.

```
frame= 1801  time=00:00:30.00  speed=5.22x       # 오류 0건
```

ffprobe:

| 항목 | 값 |
|---|---|
| 코덱 | **hevc (Main)**, `hev1`, level 156 |
| 해상도 | **2560x1440**, SAR 1:1, DAR 16:9 |
| 픽셀 포맷 | yuv420p, bt709 (range tv) |
| fps | **60.02** (`r_frame_rate=60/1`) |
| B프레임 | `has_b_frames=0` |
| 비트레이트 | 15,660 kb/s 실측 (mpd 선언값은 22,000 kb/s) |
| 길이 | 30.00초 (1,801 프레임) |

> ffprobe가 헤더에서 읽는 `Duration`은 `01:45:27` 로 **틀리게** 나온다. init의 `mvhd`가 세션 전체 길이를 들고 있기 때문이다. 실제 길이는 디코딩해서 재야 한다.

### 2.2 ★ 키프레임 간격 = 정확히 3.000초

측정한 키프레임 PTS:

```
6297.002454  6300.005885  6303.007641  6306.010278  6309.013354
6312.014694  6315.000315  6318.002402  6321.002390  6324.007594
```

**세그먼트당 키프레임 1개, 세그먼트 경계마다 1개.** 60fps이므로 180프레임 간격이다.

→ `-c copy` 컷은 3초 격자에만 붙는다. 클립 컷 정밀도의 상한이 이 값이다.

### 2.3 실패 케이스와 원인

**init 없이 chunk 단독** → 실패.

```
could not find corresponding trex (id 1)
could not find corresponding track id 0
trun track id unknown, no tfhd was found
error reading header
```

박스 구조를 뜯어보니 원인이 분명하다.

```
init-stream0.m4s          892 B   ->  ftyp(28) moov(864)
init-stream1.m4s          765 B   ->  ftyp(28) moov(737)
chunk-stream0-02100.m4s   8.8 MB  ->  moof(104) mdat(158135) moof(100) mdat(85703) ... (180쌍)
```

- `init`에만 `ftyp` + `moov`(트랙 정의, `trex` 기본값, HEVC 파라미터셋)가 있다.
- `chunk`는 `moof`+`mdat` 뿐이다. 참조할 `trex`/`tfhd` 기본값이 없어 헤더 파싱 단계에서 죽는다.
- **chunk 하나에 `moof`/`mdat` 쌍이 180개** = 프레임당 1프래그먼트.

### 2.4 ★ 단일 세그먼트도 독립 디코딩된다 (설계에 영향)

```bash
cat init-stream0.m4s chunk-stream0-01544.m4s > seg.mp4     # 정상 디코딩
```

세그먼트가 키프레임으로 시작하므로 **init + 조각 하나만으로 그 3초를 독립 디코딩할 수 있다.**
조사에서 2시간 세션 전체에 걸쳐 56개 세그먼트를 이 방식으로 샘플링했고, 모두 성공했다.

→ 검출용 프레임 샘플링에 "구간 전체 병합"이 필요 없다. 병합은 실제로 컷할 구간에만 하면 된다.

### 2.5 A/V 합치기

```bash
ffmpeg -i merged-stream0.mp4 -i merged-stream1.mp4 -c copy -map 0:v:0 -map 1:a:0 av.mp4
```

정상. `Duration: 00:00:30.02`, 타임스탬프가 0 기준으로 리베이스된다(원본은 6297초에서 시작).
음성은 `aac (LC) 48000 Hz stereo`.

### 2.6 녹화 중 읽기

녹화가 **진행 중인** 세션에서 완료된 조각을 읽는 데 문제가 없었다(파일 잠금 없음).
`.tmp` 확장자가 붙은 조각만 피하면 된다.

## 3. 클라이언트 로그

### 3.1 위치와 포맷

```
%USERPROFILE%\AppData\LocalLow\NimbleNeuron\Eternal Return\
├─ Player.log        (현재 세션, 1,483줄)
├─ Player-prev.log   (직전 세션, 1,896줄)
└─ sdk_log_YYMMDD.log  (163~652 B, 쓸 내용 없음)
```

라인 포맷:

```
[LEVEL][HOSTNAME][YYYY-MM-DD HH:mm:ss,SSS][thread][Class:Method:Line] message
```

예:

```
[INFO][DESKTOP-IFDC4S7][2026-09-19 22:16:45,957][1][ClientService:OnUpdateGamePlayPhase:3473] OnUpdateGamePlayPhase : PlayGame, 48.6 48.6
```

**시각은 로컬 타임존(KST)** 이다. 녹화 폴더/mpd의 UTC와 다르다.

### 3.2 ★ 킬 이벤트는 없다 (확정)

## 4. HUD 좌표

### ⚠ 스크린샷이 첨부되지 않았다

이번 세션 대화에 이미지가 오지 않았고, 프로젝트 폴더에도 `docs/SPEC.md` 하나뿐이었다.
**대신 실제 녹화본에서 프레임을 직접 추출해 조사했다.** 스팀 스크린샷(`userdata\...\760\remote\1049590\screenshots`)도 31장 있었지만, 해상도와 시점이 섞여 있어 쓰지 않았다.

녹화본 프레임을 쓴 게 오히려 낫다 — 검출기가 실제로 보게 될 바로 그 픽셀이다.

### 4.1 발견: 우상단 킬 카운터

```
TK 31   K 12   A 17
```

`TK`=팀 킬, **`K`=내 킬**, `A`=어시스트. SPEC이 기대한 "내 킬 카운터"가 실재한다.

### 4.2 정확한 픽셀 좌표 (2560x1440, UI 스케일 기본)

세로는 **모든 프레임에서 `y = 31..47` (높이 17px)** 로 고정.

| 요소 | 1자리 x | 2자리 x | 필드 중심 |
|---|---|---|---|
| `TK` 라벨 | 2357..2385 | — | — |
| TK 값 | 2400..2411 | 2394..2417 | 2405.5 |
| `K` 라벨 | 2437..2449 | — | — |
| **K 값 (내 킬)** | **2464..2475** | **2458..2481** | **2469.5** |
| `A` 라벨 | 2497..2511 | — | — |
| A 값 | 2525..2536 | 2519..2542 | 2530.5 |

- 글리프 폭 11~13px, 자간 advance 12px.
- **자릿수가 늘면 각 필드의 중심을 기준으로 좌우로 확장된다.** 우측 정렬이 아니고, 한 필드가 늘어도 다른 필드는 밀리지 않는다. `TK 31 / K 12 / A 17` 프레임에서 K·A 라벨 좌표가 1자리 프레임과 동일한 것으로 확인했다.
- → **각 필드를 독립 ROI로 고정할 수 있다.** 권장 K 값 ROI: **`x 2452..2488, y 27..51`** (2자리 + 여유).

### 4.3 판독 가능성

세션 전체(2시간)에서 40세그먼트 간격으로 56프레임을 뽑아 확인했다.

- HUD가 있는 **49프레임 전부 판독 가능**했다.
- 배경 무관: 어두운 실내, 초록 수풀, 붉은 피격 이펙트, 밝은 하늘 모두 정상.
- 흰 글자 + 어두운 드롭섀도가 들어가 있어 대비가 확보된다.

로비 화면도 같은 영역에 흰 아이콘(지구본/메일/톱니, `x 2391..2421 / 2441..2475 / 2497..2525`, `y 30..54`)을 그린다. 다만 흰 픽셀 수가 255~259로 숫자(56~96)와 크게 달라 쉽게 배제된다.

### 4.4 ★ 정확 비트마스크 매칭은 불가능하다

**HUD 텍스트에 불투명 배경판이 없다.** 게임 화면 위에 직접 그려진다.

| 마스크 조건 | 프레임 수 | 고유 마스크 종수 |
|---|---|---|
| 휘도 > 110 | 49 | **49** (전부 다름) |
| 휘도 ≥ 210 **그리고** 채도 ≤ 40 | 41 | 34 (최대 동일군 3장) |

- 단순 휘도 임계로는 배경이 그대로 섞여 들어온다.
- 고휘도+저채도로 좁히면 일부는 완전히 일치하지만, 안티에일리어싱 경계 픽셀이 배경과 블렌딩되어 여전히 대부분 다르다.

→ **해시/정확 매칭은 쓸 수 없다. `cv2.matchTemplate` 같은 상관 기반 매칭이 필요하다.**

### 4.5 ★ 카운터 증가 타이밍

`K 5 → 6` 전이를 60fps 프레임 단위로 잡았다(세그먼트 1544, 2026-09-19 23:24:56 KST 시작).

| 프레임 | 시각(세그먼트 내) | 글리프 |
|---|---|---|
| 175 | 2.899s | `5` (밝기 255) |
| **176** | **2.916s** | **`6` (밝기 113)** ← 자형이 한 프레임에 전환 |
| 178 | 2.949s | `6` (밝기 169) |
| 181 | 2.999s | `6` (밝기 220) |
| 다음 세그먼트 프레임 5 | +0.067s | `6` (밝기 255) — 정착 |

- **자형 전환은 한 프레임에 끝난다.** 크로스페이드 없음.
- 새 숫자는 **알파 페이드인**이 붙어 약 0.15초에 걸쳐 불투명해진다.

시사점 둘:

1. **킬 앵커의 시간 정밀도는 60fps 1프레임.** 2~4fps 샘플링이면 ±0.25~0.5초. SPEC의 -30s/+8s 구간에는 전혀 문제되지 않는다.
2. **높은 휘도 임계(예: V≥210)는 전환 직후 5~8프레임을 "HUD 없음"으로 오판한다.** 실제로 조사 중 이 오탐이 났다. 임계를 낮추거나 상관 매칭을 써야 한다.

### 4.6 ★ 좌하단 초상화 배지 = 교전 중 표시 (확정)

사용자 제보로 확인한 항목. 화면 좌하단 캐릭터 초상화의 **좌측 하단 배지**가 상태를 나타낸다.

- **평상시**: 원형 배지에 **레벨 숫자**
- **교전 중**: 같은 배지가 **주황색 + 교차된 칼 아이콘**으로 바뀐다 (애니메이션 있음)

2560x1440 기준 좌표:

| 요소 | ROI |
|---|---|
| 초상화 전체 | `x 640..870, y 1240..1440` |
| 초상화 얼굴(원형 중심부) | `x 690..860, y 1250..1400` |
| **좌하단 배지** | **`x 680..732, y 1395..1440`** |

#### 색으로 갈린다 — 템플릿 매칭이 필요 없다

배지 ROI에서 선명한 픽셀(`V≥90` 그리고 `S≥60`)만 골라 색상별로 센 결과다.

배틀로얄 한 매치(세그먼트 3600~3780, 6세그먼트 간격 31프레임):

| 상태 | 주황 px | 파랑 px |
|---|---|---|
| 평상시 (26프레임) | **0 ~ 21** | 398 ~ 546 |
| 교전 중 (5프레임) | **138 ~ 522** | 97 ~ 225 |

→ **주황 픽셀 수만으로 6배 이상의 마진으로 갈린다.**

#### 평상시 배지 색은 매치마다 다르다 (주의)

다른 매치 샘플에서는 평상시 배지가 **노란색**이었다. 레벨 티어에 따라 바뀌는 것으로 보이나 규칙은 확인하지 못했다.

주황과 노랑을 가르려면 녹색 채널을 봐야 한다.

```
주황 = V≥90 AND S≥60 AND R > B+60 AND R ≥ G AND G < R×0.80
노랑 = V≥90 AND S≥60 AND R > B+60 AND G ≥ R×0.80
파랑 = V≥90 AND S≥60 AND B > R+40
```

이 규칙으로 재측정:

| 샘플 | 주황 | 파랑 | 노랑 | 판정 |
|---|---|---|---|---|
| seg 180 / 260 / 340 | 0 | 473~520 | 0 | 평상 (파랑 배지) |
| seg 420 / 460 / 500 / 580 | 9~14 | 8~60 | **392~410** | 평상 (노랑 배지) |
| seg 220 / 300 / 540 | **481~773** | 8~122 | 101~258 | **교전** |

노랑 배지 매치에서도 교전 프레임(540)은 주황 773으로 확실히 뜬다.

#### 구현 시 가드

- **판정 전에 배지가 보이는지부터 확인할 것.** 로비(seg 620)에서는 주황 58 / 파랑 0 / 노랑 0 에 평균 RGB (128,84,83) 이 나와 오판 소지가 있다. `주황+파랑+노랑 ≥ 250` 정도를 "배지 있음"의 조건으로 둘 것.
- 완전히 어두운 프레임(seg 3720, 평균 RGB (5.5,10.5,4.4))에서는 전부 0이 나온다. **"판독 불가" 상태를 따로 둘 것.** 없는 것으로 처리하면 안 된다.
- 칼 아이콘에 애니메이션이 있어 주황 픽셀 수가 138~773으로 크게 변동한다. 임계는 **100 근처**로 낮게 잡을 것.

#### 왜 중요한가

**교전 구간을 직접 알 수 있다.** SPEC이 v2로 미뤄뒀던 "교전 시작 시점 정밀 검출(고정 프리롤 대신)"의 수단이 v1에서 확보된 것이다. 게다가 색 카운팅이라 `matchTemplate` 보다 훨씬 싸다.

### 4.7 ★ 사망 시 화면이 회색으로 덮인다 (확정)

사용자 제보를 받고 실제 녹화본에서 사망 순간을 찾아 60fps 프레임 단위로 측정했다.

#### 전체 화면 — 월드 레이어만 탈채도·암전된다

배틀로얄 한 매치의 사망 순간(세그먼트 3824~3827). 화면 **중앙 월드 영역**(가로 20~80%, 세로 15~72%) 기준:

| 사망 후 경과 | 중앙 채도 | 중앙 밝기 |
|---|---|---|
| 0.0s (정상) | 45.0 | 130.9 |
| 1.5s | 27.2 | 122.6 |
| 2.0s | 19.5 | 90.2 |
| 3.0s | 15.2 | 75.2 |
| 4.0s | 14.1 | 64.7 |
| 5.2s | 12.6 | 54.1 |
| 5.3s | 0.7 | 0.7 (암전) |

- 램프는 약 **3.5~5초에 걸쳐 단조 감소**한다. 계단식이 아니다.
- **HUD는 회색화되지 않는다.** 미니맵·킬피드·상단 카운터는 색을 유지한다.
- 그래서 **화면 전체 평균으로 재면 HUD에 희석돼 신호가 죽는다.** 실제로 전역 평균(채도 28→14)으로는 매치 내내 있는 밝기 변동과 구분이 안 됐다. 다른 매치(세그먼트 3187~3359)를 전역 지표로 훑었을 때도 사망 구간을 못 집어냈다.
- 스킬바가 회색으로 비활성화되고 `"일원이 사망하였습니다"` 텍스트가 뜬다.

**단일 절대 임계는 위험하다.** 밤 맵·실내에서는 평상시 중앙 밝기도 40~80까지 떨어진다. **수 초에 걸친 단조 하강(ramp)** 자체를 신호로 삼아야 한다.

#### 초상화 — 훨씬 선명한 신호

전체 화면과 별개로 **초상화 자체가 회색으로 변한다.** ROI가 작아 신호가 훨씬 세다.

사망 세그먼트 전후 실측 (초상화 얼굴 ROI `x 690..860, y 1250..1400`):

| 세그먼트 | 얼굴 채도 | 얼굴 밝기 |
|---|---|---|
| 3824 (정상) | 25.9 | 111.4 |
| **3825 (사망)** | **13.3** | **33.9** |
| 3826 (전환) | 11.7 | 15.4 |
| 3827 (결과 화면) | 18.5 | 97.7 |

채도 절반, 밝기 1/3. **작은 ROI라 전체 화면 평균보다 신호가 훨씬 선명하다.**

추가로 사용자 제보로 확인한 것:

- 사망 시 초상화 중앙에 **부활까지 남은 시간 카운트다운 숫자**가 뜬다.
- **2일차 밤까지 죽으면 시간만 지나면 무료 부활**한다. 3일차 낮부터는 크레딧(인게임 재화)을 써야 한다. 즉 **배틀로얄에서도 초반 사망은 영구 사망이 아니다.**

> 이건 설계에 직접 영향을 준다. "사망 = 매치 종료"가 아니므로, 사망 구간 제외 로직은 **배틀로얄에서도 "사망 → 부활까지"** 로 다뤄야 한다. 코발트 프로토콜만의 문제가 아니었다.

### 4.8 ★ 게임 구조 — `K`는 항상 내 값이다 (사용자 확인)

측정이 아니라 사용자가 알려준 사실이지만, **조사 결과의 해석을 바꾸므로 여기 적어둔다.**

- 이터널 리턴은 **3인 1팀 배틀로얄**이다.
- 나나 팀원이 죽어도 **조건을 만족하면 부활**한다. **2일차 밤까지는 무료**, 3일차 낮부터는 **크레딧** 소모.
- **3명이 전부 죽어야 게임이 끝난다.** 내가 죽어도 팀원이 살아있으면 매치는 계속된다.
- **본 게임 플레이 화면과 관전 화면은 UI 자체가 다르다.**

#### 이전 조사의 "가장 중요한 미확인"이 해소된다

§7에서 최우선으로 꼽았던 `"관전 중 K 값이 내 것인지 관전 대상 값인지"` 는 **질문 자체가 잘못됐다.**

**`K`는 항상 내 값이다.** 팀원 것으로 바뀌지 않는다. 그리고 여기서 말한 "관전"은 별도의 리플레이 관전이 아니라 **내가 죽고 팀원이 살아있는 상황**이었다.

→ SPEC이 걱정했던 "관전 화면의 킬을 내 것으로 오판" 문제는 **존재하지 않는다.** 내가 죽어있으면 내 `K`는 애초에 오르지 않는다.

→ 그래도 사망 구간을 따로 다뤄야 하는 이유는 남는다. 다만 **이유가 바뀐다**:
> 1. 관전 화면은 UI가 달라 좌표가 안 맞는다. 판독 결과를 믿으면 안 되므로 **"판독 불가"로 빼야 한다.**
> 2. 내가 죽어있는 동안 팀원이 싸우는 건 내 교전이 아니다.

### 4.9 ★ 클립 제목에 쓸 정보의 출처 (위치 확인)

목표 제목: **`3일차 낮 아르다, 얀, 히스이`** (앞이 내 캐릭터, 뒤가 팀원 둘)

#### 화면에서

2560x1440 기준, 프레임에서 직접 재서 확인한 좌표다.

| 정보 | ROI | 확인한 내용 |
|---|---|---|
| **일차** | `x 1120..1180, y 6..32` | `1일 차` ~ `4일 차` 판독 확인 |
| **낮/밤 아이콘** | `x 1145..1185, y 30..58` | 낮 = **노란 해**, 밤 = **보라 초승달** |
| **내 캐릭터 초상화** | `x 640..870, y 1240..1440` | §4.6 과 같은 영역 |
| **팀원 1 초상화** | `x 2097..2180, y 1165..1250` | 원형, 약 83x85 |
| **팀원 2 초상화** | `x 2097..2180, y 1302..1387` | 세로 간격 137px |

팀원 초상화가 정확히 2개다 — §4.8의 3인 1팀과 일치한다.

#### 낮/밤은 색으로 갈린다

아이콘 ROI에서 선명한 픽셀(`V≥90 AND S≥55`)만 색상별로 센 실측 (매치 하나, 26세그먼트 간격 16프레임):

```
노랑 = V≥90 AND S≥55 AND R > B+50 AND G > B+30      (해)
보라 = V≥90 AND S≥55 AND B > G+40 AND R > G+20      (달)
```

| 상태 | 노랑 px | 보라 px |
|---|---|---|
| 낮 | 305 ~ 1115 | 0 |
| 밤 | 0 | 198 ~ 204 |

깨끗하게 갈린다. 다만 **주의할 점이 있다.**

- **상단 바가 반투명이라 배경이 섞인다.** 배경이 밝은 주황(사막/석양)일 때 낮 프레임에서 보라 148~184가 잡혔다. 밤의 198~204와 마진이 얇다.
- → **단순 임계보다 "노랑 vs 보라 중 큰 쪽"으로 비교하는 게 안전하다.** 실제로 그 규칙으로는 16프레임 전부 정답이었다.
- 더 좁은 ROI나 색상(hue) 히스토그램으로 보완할 여지가 있다.

#### 일차 진행 속도

같은 매치에서 판독한 값:

| 세그먼트 | 화면 |
|---|---|
| 3456 | 1일 차 ☀ |
| 3508 | 1일 차 🌙 |
| 3586 | 2일 차 🌙 |
| 3612 | 3일 차 ☀ |
| 3638 | 3일 차 ☀ |
| 3690 | 4일 차 ☀ |

한 페이즈(낮 또는 밤)가 대략 **2.5~3분**이다. 20분 매치면 4~5일차까지 간다.

#### ⚠ 로그의 낮/밤은 믿을 수 없다

`Player.log` 에도 낮/밤 전이가 남는다.

```
[WARN][...][2026-09-19 22:16:45,959][1][WeatherDayNightMaterialColorControl:SetDayNight:139] Setting DayNightColorControl >>> Duplicate set input=Day.
[WARN][...][2026-09-19 22:23:36,476][1][...:139] Setting DayNightColorControl >>> Duplicate set input=Night.
[INFO][...][2026-09-19 22:27:49,557][1][...:134] Setting DayNightColorControl >>> Invalid input=None.
```

**화면과 대조해보니 로그가 틀렸다.**

| 로그가 말하는 것 | 실제 화면 |
|---|---|
| seg 3437 ~ 3574 `Day` | seg 3508 은 **밤**이었다 |
| seg 3574 ~ 3688 `Night` | seg 3612 · 3638 은 **낮**이었다 |

`Duplicate set` 경고가 났을 때만 기록되기 때문에, **정상 전이는 대부분 로그에 남지 않는다.** 로그상 한 매치에 전이가 3번뿐인데 실제로는 8~10번 일어난다.

→ **HUD 판독이 유일하게 믿을 수 있는 소스다. 로그는 교차검증에도 쓰지 말 것.**

(`input=None` 이 매치 로딩 시점에 찍히는 것은 사실이라, 매치 구분자로는 쓸 수 있다. 다만 §3.3의 `[LOADING][GAME]` 이 더 확실하다.)

#### 캐릭터 이름

초상화 **템플릿 매칭**이 필요하다. 캐릭터 수만큼 템플릿을 모아야 하는데, 게임 리소스에서 뽑거나 실사용하며 누적하는 두 방법이 있다. **이번 조사에서는 시도하지 않았다.**

### 4.10 ★ HEVC 재생 — 이 PC에는 코덱이 이미 있다

녹화본이 HEVC(H.265)라 웹 UI에서 재생될지가 걸렸다(§2.1의 코덱 참조). **설치된 코덱을 직접 확인했다.**

```
Get-AppxPackage -Name "*VideoExtension*"

Microsoft.HEVCVideoExtension        2.5.33.0   Status: Ok    ← 이것
Microsoft.AV1VideoExtension         2.0.35.0
Microsoft.VP9VideoExtensions        1.2.20.0
Microsoft.MPEG2VideoExtension       1.2.32.0
Microsoft.AVCEncoderVideoExtension  1.1.23.0
```

- **`Microsoft.HEVCVideoExtension`(단수)** 는 PC·GPU 제조사가 무료로 끼워 넣는 판이다. MS Store에서 개인이 따로 사는 **`Microsoft.HEVCVideoExtensions`(복수, 유료)** 와 다른 패키지다.
- 그래서 "설치한 기억이 없는데 스팀 녹화가 잘 재생된다"가 성립한다. 제조사가 넣어둔 것이다.
- GPU는 AMD RX 6600 XT 로 HEVC 하드웨어 디코딩을 지원한다.

**결론: 이 PC에서는 HEVC 재생에 문제가 없을 가능성이 높다.** WebView2(Chromium)는 OS의 HEVC 디코더를 쓰므로 그대로 재생될 것이다.

다만 **실제 재생 테스트는 아직 안 했다.** 그리고 코덱이 없는 PC도 있으므로, 배포를 고려한다면 H.264 프록시 생성을 **옵션**으로 남겨두는 게 맞다. 개인용 도구인 이상 기본값은 꺼둬도 된다.

## 5. BSER API

**조사하지 않았다. 쓰지 않기로 했기 때문이다.**

| `characterNum` | v1에서는 포기 | — |

`userNum=4958038` 은 로그에서 확보돼 있으니, 나중에 마음이 바뀌면 그때 쓰면 된다.

## 8. 이 발견이 SPEC.md의 어떤 부분을 수정하게 만드는가

### 8.1 아키텍처 — 매치 종료 감지를 API 폴링에서 로그 감시로

**SPEC §3 아키텍처 첫 박스 `[매치 종료 감지]`.**

클라이언트 로그에 킬은 없지만 **매치 경계는 정확히, 실시간으로** 남는다(§3.3). `[LOADING][LOBBY]` 한 줄이면 매치 종료를 알 수 있고, `userId`까지 로그에서 나온다. API 폴링보다 즉각적이고 정확하다.

→ 아키텍처의 `[ER API 조회]` 박스를 **통째로 걷어내고** `[Player.log 감시] → [매치 종료 검출] → [세그먼트 범위 산출]` 로 고쳐 쓸 것 (§5).

### 8.2 §2.3을 "가정"에서 "확정"으로

> "클라이언트 킬 로그는 없다고 가정 … 있으면 검출 난이도가 급감하므로 확인 자체는 반드시 할 것"

확인했다. **없다**(§3.2). 이 절을 확정 사실로 다시 쓰고, 대신 §3.3의 매치 경계 이벤트 표를 추가할 것.

### 8.3 §2.4에 실측값과 실패 조건 추가

> "init 세그먼트 + chunk들을 이어붙이면 ffmpeg로 바로 처리 가능하다"

맞다. 여기에 덧붙여야 할 것:

- **init 없이는 실패한다**(`trex` 없음). init은 `ftyp`+`moov` 뿐이고 chunk는 `moof`/`mdat` 뿐이다.
- **단일 chunk + init 만으로도 독립 디코딩된다.** 세그먼트가 키프레임으로 시작하기 때문.
- 파일명 규칙 확정: `chunk-stream{0=영상,1=음성}-{5자리}.m4s`, `.tmp`는 기록 중.
- 포맷 확정: HEVC Main / 2560x1440 / 60fps / yuv420p / B프레임 없음.

### 8.4 ★ §2에 "시간 매핑" 절을 새로 만들 것

SPEC에 지금 없는데, **로그·API·영상을 잇는 축이 이것이다.**

```
세그먼트 N 시작(UTC) = 세션시작(UTC) + (N-1) × 3.000초
세션시작(UTC) = session.mpd@availabilityStartTime  또는  폴더명 bg_<appid>_<YYYYMMDD>_<HHMMSS>
폴더명·mpd = UTC  /  Player.log = 로컬 타임존
```

타임존을 섞으면 9시간 어긋난다. 반드시 명문화할 것.

### 8.5 §3 "해당 구간 m4s 조각 복사 → 단일 fMP4로 병합" 단계를 쪼갤 것

단일 세그먼트가 독립 디코딩되므로(§2.4), 검출 단계에서 구간 전체를 병합할 이유가 없다.

```
[검출]  init + 세그먼트 1개씩 → 프레임 샘플링        (I/O 최소)
[컷]    실제로 자를 구간만 병합 → ffmpeg -c copy
```

### 8.6 §"클립 구간" — 키프레임 간격 3초를 명시할 것

> "컷은 `-c copy` + 키프레임 스냅"

**키프레임 간격은 정확히 3.000초다**(§2.2). 즉 `-c copy` 컷은 3초 격자에만 붙는다.

- "킬 시점 -30초"로 자르면 실제 시작은 **-30 ~ -33초**가 된다.
- 뒤쪽 +8초도 마찬가지로 최대 3초 길어진다.
- 복기 목적에는 앞이 길어지는 게 손해가 아니므로 **그대로 두고 "실제 프리롤 30~33초"라고 적으면 된다.** 정확한 경계가 필요하면 그때만 재인코딩할 것. 이 선택을 SPEC에 명시할 것.

### 8.7 §"킬 검출 방식" — 좌표표와 매칭 방식 제약

> "전제: 해상도와 UI 스케일 고정. 설정에 해상도 프로필을 두고 좌표를 분리한다."

유지하되 구체화할 것:

- §4.2 좌표표를 그대로 넣을 것. 2560x1440 프로필의 **K 값 ROI = `x 2452..2488, y 27..51`**.
- **필드별 중심 기준 확장**이라 각 필드를 독립 ROI로 잡아도 안전하다.
- **정확 매칭 불가.** HUD에 배경판이 없어 같은 숫자도 프레임마다 비트마스크가 다르다(§4.4). 상관 기반 매칭(`cv2.matchTemplate`)으로 가야 한다.
- 높은 휘도 임계는 값 전환 직후 5~8프레임을 놓친다(§4.5).
- **폴백(킬피드 + 캐릭터 초상화 매칭)은 당장 필요 없다.** 카운터가 49/49 프레임에서 판독됐다. 폴백 설계는 v2로 미뤄도 된다.

### 8.8 §7 운영 설정 — 숫자를 넣을 것

> "스팀 자동 녹화 최대 시간은 2~4시간으로 넉넉히 설정. 링버퍼 덮어쓰기 전에 추출을 끝내야 한다."

실측 근거를 붙일 것:

- **현재 설정은 2시간이고, 이미 꽉 차서 계속 삭제 중이다**(§1.6). 5분에 100 세그먼트씩 앞에서 깎인다.
- 1440p60에서 **약 8.5 GB/시간**. 4시간이면 34 GB.
- 매치 9~19분 / 버퍼 2시간이므로 여유는 충분하다. 하지만 **"폴더가 있으니 조각도 있다"는 가정은 틀린다.** 번호로 접근하기 전에 항상 존재 확인.

### 8.9 §3 클립 메타데이터 JSON에 필드 추가

지금 `videoOffsetSec` 만으로는 **어느 세션 폴더의 오프셋인지 복원되지 않는다.** 추가할 것:

```json
{
  "sessionDir": "bg_1049590_20260919_130747",
  "sessionStartUtc": "2026-09-19T13:07:47Z",
  "segmentStart": 1534,
  "segmentEnd": 1548,
  "videoOffsetSec": 4599.0
}
```

### 8.10 §4 기술 스택 / 배포 — ffmpeg 번들

> "ffmpeg 라이선스: LGPL 빌드를 번들하거나 첫 실행 시 다운로드"

이 PC에는 **PATH에 ffmpeg가 없다.** 시스템 곳곳에 다른 앱이 끼워둔 빌드가 있었지만(KMPlayer 2015년판, Ondisk 2014년판 등) 버전이 제각각이라 의존할 수 없다.
→ "번들 또는 첫 실행 다운로드"를 **선택이 아니라 필수**로 격상할 것.

### 8.11 원본 해상도가 1440p라는 이점을 명시할 것

스팀 UI로 export하면 **1080p로 다운스케일된다**(`clip.pb` f12/f13, §1.5).
우리는 export를 거치지 않고 원본 `.m4s`를 쓰므로 **1440p 원본을 그대로 얻는다.** 이건 이 접근법의 부수적 이점이라 SPEC에 적어둘 가치가 있다.

### 8.12 §5 개발 방식 — 라벨셋 구축 비용이 예상보다 낮다

> "샘플 프레임을 폴더에 모으고 킬 순간을 수동 라벨링한다(최소 30개)"

`init + 단일 세그먼트` 디코딩(§2.4) 덕분에 2시간 세션에서 임의 시점 프레임을 초 단위로 뽑을 수 있다.
조사에서 56프레임을 뽑는 데 수십 초밖에 안 걸렸다. **라벨셋 구축은 SPEC이 걱정한 것보다 훨씬 싸다.**

### 8.13 §2.2 재확인 (수정 불필요)

> "Steam 타임라인 마커는 쓸 수 없다"

`timelines\*.json`을 실제로 열어보니 `entries[]`에 있는 것은 `"type": "screenshot"` 뿐이었다(§1.5).
**SPEC이 맞다. 수정 불필요.**

### 8.14 ★ API 의존을 전부 걷어낼 것

SPEC §2.1, §3 아키텍처, §5 개발 방식이 전부 BSER API를 전제로 쓰여 있다. **API로 하려던 일이 전부 대체되므로(§5) 의존을 통째로 제거할 것.**

특히 §5의 "API를 자동 정답지로 쓴다"는 **"`K` 카운터가 자기 자신의 정답지다"** 로 바뀐다. 매치 마지막 인게임 프레임의 `K` 값이 그 매치의 총 킬 수이고, 검출기가 센 증가 횟수와 대조하면 외부 의존 없이 회귀 테스트가 된다. 네트워크도, 키 발급도, 레이트 리밋도 없어진다.

### 8.15 ★ §"교전의 판정 기준"을 `K` 단독에서 `K ∪ A` 로 넓힐 것

카운터 의미가 확정됐다 — `TK`=팀 전체 킬, `K`=내 킬, `A`=내가 관여한 팀 킬.

`A`는 `K`와 **같은 HUD 줄에 나란히** 있어 판독 비용이 같다. `A`를 버리면 "딜은 내가 다 넣었는데 막타를 팀원이 친" 교전이 통째로 빠진다. SPEC이 스스로 인정한 "킬 낸 교전만 보는 편향"도 일부 완화된다.

→ v1 앵커를 `K 증가 ∪ A 증가`로 잡고, 설정으로 `K만`을 고를 수 있게 할 것. `TK`는 앵커로 쓰지 말 것(내가 없는 곳의 팀원 킬까지 잡힌다).

### 8.16 ★ 교전 구간 검출을 v2에서 v1으로 당길 것

SPEC의 v2 후보 `교전 시작 시점 정밀 검출(고정 프리롤 대신)`.

초상화 배지(§4.6)가 **교전 중 주황색 교차 칼로 바뀐다.** 색 픽셀 카운팅만으로 6배 이상 마진으로 갈린다 — `matchTemplate` 보다도 싸다.

→ 고정 `-30초` 프리롤을 유지하되, **배지가 켜진 시점을 교전 시작으로 보고 그쪽을 우선하는 하이브리드**가 가능하다. 최소한 클립 메타데이터에 교전 구간을 같이 남겨둘 것.

### 8.17 ★ 사망 구간 제외를 "사망 이후 전부"가 아니라 "사망 → 부활까지"로

SPEC은 `[playTime 이후 구간 제외]` 로 "죽으면 끝"을 전제했다. **틀렸다.**

- 코발트 프로토콜은 부활이 있다(§4.6 모드 표 / SPEC §2.8).
- **배틀로얄도 2일차 밤까지는 무료 부활**이 있고, 3일차 낮부터는 크레딧을 쓰면 부활한다(§4.7).

→ 사망 구간은 **구간(interval)** 으로 다뤄야 한다. 시작은 회색 램프, 끝은 부활. 부활 검출은 미확인 항목이다(§7 #2).

### 8.18 사망 검출은 전체 화면이 아니라 ROI로

§4.7에서 전역 평균으로는 사망 구간을 못 집어냈다. **화면 중앙 월드 영역** 또는 **초상화 ROI**를 쓸 것. 초상화 쪽이 ROI가 작고 신호가 세다(채도 절반, 밝기 1/3).

절대 임계는 밤 맵·실내에서 오탐한다. **수 초에 걸친 단조 하강** 자체를 신호로 삼을 것.

### 8.19 두 게임 모드를 모두 추출 대상에 넣을 것

`TK`가 빠르게 오르는 구간은 **코발트 프로토콜(캐주얼 모드)** 이다. **HUD 좌표가 배틀로얄과 동일하므로 검출기는 그대로 쓴다.** 추출 범위에서 빼지 말 것.

차이는 부활 빈도뿐이고, 그건 §8.17의 사망 구간 처리로 흡수된다.

### 8.20 버퍼 길이를 자동 인식할 것

2시간 버퍼는 **스팀의 전역 설정**이다(게임별이 아니다). 사용자가 바꿀 수 있지만 보통은 그대로 쓴다.

→ `session.mpd`의 `timeShiftBufferDepth` → `localconfig.vdf` → 기본값 **120분** 순으로 폴백하고, 설정 UI에서 덮어쓸 수 있게 할 것.

### 8.21 ★ 낮/밤의 출처를 로그에서 HUD로 바꿀 것 (이전 판 정정)

**이 문서의 이전 판에서 "`Player.log` 의 낮/밤을 교차검증으로 쓰라"고 적었는데, 틀렸다.**

화면과 대조해보니 로그가 실제 상태와 어긋난다(§4.9). `Duplicate set` 경고가 났을 때만 기록돼 정상 전이가 대부분 누락된다 — 로그상 한 매치에 전이가 3번인데 실제로는 8~10번이다.

→ **HUD 아이콘 판독이 유일한 소스다.** 해=노랑, 달=보라로 색이 갈리며, 배경 간섭 때문에 단순 임계가 아니라 **"노랑과 보라 중 큰 쪽"** 으로 판정할 것. 로그의 `input=Day|Night` 는 교차검증에도 쓰지 말 것.

### 8.22 ★ 추출 대상을 "킬 낸 구간"에서 "모든 교전"으로 바꿀 것

SPEC §1 `교전의 판정 기준` = "내 캐릭터가 전투에 참여해 킬까지 낸 구간".

**교전 배지(§4.6)가 교전 자체를 직접 알려주므로 킬로 역추정할 이유가 없다.** 목표를 "내가 참여한 모든 교전"으로 바꾸고, `K`/`A` 증가와 사망 여부는 **각 교전에 붙는 태그**로 내릴 것.

- 태그: `kill` / `assist` / `death` / `no_result` (서로 배타적이지 않다 — 킬 내고 죽을 수 있다)
- 보관 정책을 옵션으로: `all`(기본) / `won` / `lost` / `custom`
- **검출은 항상 전부 하고 필터는 보관 단계에서만 건다.** 태그가 메타데이터에 남으므로 정책을 바꿔도 재추출이 필요 없다.

이러면 SPEC이 스스로 인정한 "킬 낸 교전만 보는 편향"이 v1에서 바로 해소된다. 진 교전은 `lost` 필터로 본다.

### 8.23 ★ 사망 구간을 다루는 *이유*를 고쳐 쓸 것

SPEC의 `[playTime 이후 구간 제외] ← 사망 후 팀원 관전 화면의 킬 걸러내기` 는 **전제가 틀렸다**(§4.8).

`K`는 항상 내 값이라 오판할 킬이 없다. 이유를 이렇게 바꿀 것:

1. 관전 화면은 **UI가 달라** 좌표가 안 맞는다 → 판독 결과를 믿지 말고 "판독 불가"로 뺀다
2. 내가 죽어있는 동안 팀원이 싸우는 건 내 교전이 아니다

그리고 **사망한 교전 자체는 버리지 않는다.** `death` 태그를 달아 남긴다 — 복기 가치가 제일 높다. 제외하는 건 *사망 이후 부활까지의 구간*이다.

### 8.24 UI 스택과 HEVC 재생

SPEC §4 `UI: FastAPI + 정적 페이지` 를 구체화할 것.

- **React + TypeScript + Vite + Tailwind**, 셸은 **pywebview(Edge WebView2)**. Electron은 추가 RAM 150~300MB에 배포 크기 +120MB라 쓰지 말 것. WebView2는 Windows 기본 탑재라 런타임을 안 싣고 40~80MB 선이다. 브라우저로 여는 폴백도 같이 둘 것.
- ⚠ **녹화본이 HEVC다.** 브라우저/WebView2의 HEVC 재생은 보장되지 않는다(Windows "HEVC 비디오 확장" 필요). **클립 생성 시 H.264 프록시를 같이 만드는 쪽을 기본으로 검토할 것.** 0.5단계에서 실측으로 확정.

### 8.25 열람 UI는 타임라인 중심으로

스팀 녹화 뷰어처럼 **가로 타임라인 위에 교전 구간이 블록으로 얹히고, 블록마다 썸네일 + 제목 + 태그 뱃지**가 붙는 형태를 목표로 한다.

클립이 수천 개가 되면 목록은 가상 스크롤 + 썸네일 lazy-load가 필요하다. 자동 생성 제목은 틀릴 수 있으니 **수동 편집 가능**하게 할 것.

### 8.26 자동 업데이트를 v2 목록에 넣을 것

GitHub Releases 기반. `--onedir` 이라 파일 교체 방식이 자연스럽다. 코드 서명이 없으니 **체크섬 검증**을 같이 둘 것.

### 8.27 ★ 설정을 상세하게 노출할 것

조사에서 나온 수치들이 **그대로 설정 항목이 된다.** SPEC §7을 다음 축으로 쪼갤 것.

| 축 | 조사에서 나온 근거 |
|---|---|
| **경로** (임시/클립/썸네일/프록시/휴지통/내보내기) | 병합이 수백 MB~GB I/O라 임시 폴더를 빠른 디스크로 옮길 수 있어야 한다(§2). 임시와 클립이 다른 드라이브면 최종 이동이 rename이 아니라 복사가 된다 |
| **생성 필터** | 태그 + 게임 시점(§4.9의 일차·낮/밤) + 부활 구간(§4.8) + 길이 + 모드(§4.6 모드 표) |
| **클립 구간** | 프리롤/포스트롤, 최대 길이, 병합 간격, 키프레임 스냅(§2.2의 3초 격자) |
| **인코딩** | H.264 프록시 on/off (§4.10 — 이 PC는 코덱이 있어 기본 꺼짐) |
| **보관·삭제·복구** | 휴지통 유예, 자동 정리 상한, 고정(pin), 내보내기 |

부활 규칙(§4.8)은 페이즈 순번으로 다루면 필터로 바로 쓸 수 있다.

```
phaseIndex = (일차 - 1) × 2 + (낮 0, 밤 1)
무료 부활 = phaseIndex ≤ 3        크레딧 = phaseIndex ≥ 4
```

**삭제는 되돌릴 수 있어야 한다.** 즉시 삭제가 아니라 휴지통 경유 + 유예 기간. 자동 정리는 고정한 클립과 `death` 태그를 기본 보호.

디스크 감각(§1.4에서 나온 비트레이트 기준): 교전 30~40초 클립이 **60~80 MB**, 매치당 5~10개면 **0.4~0.8 GB/매치**. 총량 상한을 걸어둘 근거가 된다.

### 8.28 ★ 검출은 키프레임만 디코딩할 것 (실측)

검출 비용의 거의 전부가 HEVC 디코딩이다. 영상 60초(세그먼트 20개)로 실측했다.

| 방식 | 60초 처리 | 배속 | 20분 매치 환산 |
|---|---|---|---|
| 전체 디코딩 (소프트웨어) | 12.6초 | 4.8x | 4분 10초 |
| 전체 디코딩 + `-hwaccel d3d11va` | 9.4초 | 6.4x | 3분 8초 |
| 전체 디코딩 + `-hwaccel dxva2` | 13.0초 | 4.6x | 4분 20초 |
| **키프레임만 (`-skip_frame nokey`)** | **1.1초** | **55x** | **22초** |
| **키프레임만 + `-hwaccel d3d11va`** | **0.59초** | **102x** | **12초** |

**16배 차이인데 정밀도 손실이 거의 없다.** §2.2에서 잰 대로 키프레임은 세그먼트당 1개, 3.000초 간격이고, `-c copy` 컷도 같은 3초 격자에만 붙기 때문이다(§8.6). **검출 정밀도와 컷 정밀도가 정확히 일치한다.**

```bash
ffmpeg -hwaccel d3d11va -skip_frame nokey -i <seg.mp4> -vsync 0 \
       -vf "crop=..." -f rawvideo -pix_fmt rgb24 -
```

- `dxva2` 는 소프트웨어보다 오히려 느렸다. `d3d11va` 를 쓸 것.
- hwaccel 은 있으면 좋은 정도지 필수가 아니다. 소프트웨어만 써도 20분 매치가 22초다.
- ⚠ **하드웨어 디코딩 결과가 소프트웨어와 픽셀 단위로 같은지는 확인하지 않았다.** 색 임계 기반 검출기라 미세한 차이가 판정을 뒤집을 수 있다.

### 8.29 해상도를 고정값으로 쓰지 말 것

2560x1440은 **이 PC의 환경에서 나온 값**이고, 모니터·게임 설정·스팀 녹화 설정에 따라 달라질 수 있다.

→ 런타임에 `session.mpd`의 `width`/`height`를 읽어 프로필을 고를 것. 좌표를 하드코딩하지 말 것. 모르는 해상도는 비례 스케일로 추정하되 **신뢰도를 낮추고 경고를 남길 것.**
