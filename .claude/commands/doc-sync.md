`docs/plan.md` 를 실제 코드와 대조해 문서를 동기화해라. 영역: `$ARGUMENTS`(비었으면 all).

규칙은 CLAUDE.md "spec 과 plan 의 역할을 섞지 않는다" 그대로다: spec = 확정·구현된 것만, plan = 남은 작업만.

## 절차

1. **기계 검사부터**: `python tools/check_docs.py`. 나온 문제(끊긴 링크, plan 의 완료 체크, spec 의 계획 표현, 설정 키 목록 차이)를 먼저 고친다.
2. **범위 정하기**: 영역이 주어지면 `docs/spec/<영역>.md` 와 plan 의 관련 절만 읽는다. SPEC.md 의 문서 지도를 보고 다른 spec 파일은 필요할 때만 연다.
3. **plan 항목 대조**: 각 항목이 코드에 이미 있는지 확인한다(함수·라우트·설정 키·테스트를 grep, `git log --oneline -- <경로>` 로 최근 변경).
   - 항목이 많거나 `all` 이면 영역별로 Explore 서브에이전트에 맡겨 **항목마다 판정만** 받는다: `완료 / 일부 / 안 됨 / 더 이상 의미 없음` + 근거 `파일:줄`. 서브에이전트 보고를 믿기 전에 애매한 것은 직접 확인한다.
4. **반대 방향 대조**: 마지막 문서 동기화 커밋 이후 `src/`·`frontend/src/` 에 들어온 기능 커밋(`git log`)을 훑어, spec 에 반영되지 않은 동작 변경을 찾는다.
5. **반영**
   - 완료: 결론(무엇을·왜)과 다시 밟지 말아야 할 함정만 해당 spec 파일에 짧게 쓰고, plan 에서 **지운다**. 실측 경위·사고 서술은 옮기지 않는다(커밋 메시지·git 이력에 있다).
   - 일부: plan 항목을 남은 부분만으로 고쳐 쓴다.
   - 더 이상 의미 없음(기한 지남 등): 이유를 커밋 메시지에 적고 지운다.
   - spec 과 코드가 다르면 코드를 기준으로 spec 을 고친다. 코드가 틀린 것 같으면 고치지 말고 plan 에 올린 뒤 사용자에게 알린다.
   - 우선순위가 바뀌면 plan §1 표도 고친다. 큰 작업 절이 다 끝나면 그 절을 지운다.
6. **검증·커밋**: `python -m pytest tests/test_check_docs.py -q` 통과 후, 영역 단위로 커밋한다(한국어, 무엇을 옮기고 지웠는지와 코드 대조로 발견한 것).

## 하지 않는 것

- 코드(`src/`, `frontend/`, `tests/`, `tools/`)는 고치지 않는다.
- 사용자가 편집 중인(커밋 안 된 변경이 있는) 문서는 건드리지 않고 알린다(`git status` 로 먼저 확인).
- 판단이 안 서는 항목은 임의로 지우지 말고 끝에 목록으로 묻는다.

## 마무리 보고

옮긴 항목(plan → spec 파일), 지운 항목과 이유, 코드와 어긋나 고친 spec, 사용자에게 물을 것.
